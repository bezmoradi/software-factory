# Software Factory

Software Factory runs Claude Code in sandboxed containers on your own computer, one container per session, and lets it change code freely, while you follow and steer every session from one page in your browser. The agents can't reach your git host. Only the engine pushes their work, to a branch of its own, and only after independent reviewers have passed that exact commit. It runs in Docker as four containers plus one for each running session, and each session's agent uses your own sign-in with its vendor.

- Every agent session runs in a container of its own, with its own home, its own clone of the repository, and its own git worktree and branch, `sf/<id>`, in a Docker volume. A session's agent can't see another session's files, home or network. Nothing on your computer's disk is mounted into a session's container.
- A small helper container makes each session's container when the session starts and removes it when the session stops, always from the same fixed recipe. It is the only part that holds Docker's socket, and it takes requests only from the engine.
- The agents reach the internet only through a proxy that allows their model APIs and always refuses git hosts. The engine checks this before every start and every 5 minutes.
- Each reviewer runs in a short-lived container of its own that the agents can't reach, which holds only a read-only copy of the commit under review and is removed when that reviewer finishes, with [knackpack](https://github.com/bezmoradi/knackpack)'s bug hunter and simplicity checker, plus reviewers for the kinds of files the change touches.
- A push goes only to the session's own branch, never forced and never to the main branch, and every push request is written to an audit file.
- Each agent's permission requests, questions and plans wait on the page as cards for your answer.
- Software Factory never reads, stores or passes on an agent's sign-in. You sign each session's agent in yourself, with the vendor's own login, when the session starts. [ARCHITECTURE.md](ARCHITECTURE.md) describes how the parts work and why.

## What you need

- Docker Desktop on macOS or Windows, or Docker Engine with the Compose plugin on Linux, running Docker Engine 28 or later (`docker version` shows the server's version), on an `amd64` or `arm64` machine. The box helper refuses an older Engine, since it needs Engine 28's API. Before Engine 28, other machines on your local network can also reach a port published on `127.0.0.1`, such as the page's.
- Memory and CPUs: each running session's container may use up to 2 GiB of memory and 2 CPUs (`SF_BOX_MEMORY`, `SF_BOX_CPUS`), each running reviewer the same (`SF_REVIEWER_MEMORY`, `SF_REVIEWER_CPUS`), the engine 1 GiB, the proxy 256 MiB and the box helper 64 MiB. Nothing limits how many sessions run at once unless you set `SF_MAX_BOXES`; the engine runs at most 8 reviewer containers at once, one per reviewer run or sign-in step. The fixed containers' limits add up to about 1.3 GiB, so on a computer that gives Docker 8 GiB, a session and a review with three reviewers fit only while they use less than their limits; when memory runs out, Docker's out-of-memory killer stops a session's or a reviewer's container before the engine or the proxy. A session's disk use is limited only by its disk cap, if you set one (see **Caps**).
- Docker Desktop's Enhanced Container Isolation, if your organization turns it on, refuses the box helper's mount of Docker's socket unless an administrator allows it, and then no session starts.
- Docker Compose 2.24.4 or later (`docker compose version`), the first that reads the `!override` tag the release's `compose.release.yaml` uses. Compose 5.1.4 has a bug reading YAML merge keys such as `<<: *anchor`, which the Compose files use ([docker/compose#13812](https://github.com/docker/compose/issues/13812), fixed in 5.2.0), so the install refuses it too. The install also needs `curl` and `sha256sum` or `shasum`, which macOS and most Linux distributions have; it needs no cosign and no GitHub sign-in.
- A browser on the same computer. The page is published only on `127.0.0.1`.
- A Claude account for Claude Code: a Claude subscription or an Anthropic API key. Claude Code signs in once for the reviewers, because every review runs on Claude Code, and in each Claude Code session's container when that session starts.
- A git repository reachable over `https://`. Private repositories, and every push, need a token for the git host; see [Tokens](#tokens).
- Internet access at first start, when the engine downloads the agents from npm and knackpack from GitHub. At every later start the engine checks GitHub for a newer knackpack; without access it keeps the one it has.

## Configuration

Most settings live on the page. A few are environment variables that Docker Compose reads when you run `docker compose up`.

| Variable | Default | Purpose |
|---|---|---|
| `SF_PORT` | `7799` | The port on `127.0.0.1` where the page is published |
| `SF_ALLOW` | `api.anthropic.com,claude.ai,claude.com,platform.claude.com` | The hosts the agents and reviewers may reach, over HTTPS only. Setting it replaces the whole list |
| `SF_EXTRA_ALLOW` | empty | Hosts added to that list, such as a company's model gateway: `gateway.example.com` |
| `SF_EXTRA_DENY` | empty | Git hosts to refuse besides the built-in ones (GitHub, GitLab, Bitbucket), such as your company's own git server. If an `SF_ALLOW` or `SF_EXTRA_ALLOW` entry covers the host of a project you added, the sandbox check fails until that host is here |
| `SF_OSV` | empty | `off` stops the engine's daily lookup of the pinned agent versions at OSV, and its lookup of the vulnerability IDs reviews cite ([Privacy](#privacy)) |
| `SF_NO_UPDATE_CHECK` | empty | `1` stops the engine's daily check for a newer release at `api.github.com`, and the page can't turn it back on ([Update to Software Factory](#update-to-software-factory), [Privacy](#privacy)) |
| `SF_BOX_MEMORY` | `2g` | The memory each session's container may use, swap included: `256m` to `256g` |
| `SF_BOX_CPUS` | `2` | The CPUs each session's container may use: `0.1` to `256` |
| `SF_MAX_BOXES` | empty | The most session containers that run or start at once, `1` to `256`; empty means no limit. A start or wake past it is refused, saying so |
| `SF_BOX_SUBNETS` | `10.213.0.0/20` | The addresses of the sessions' networks, one `/28` each, as IPv4 networks separated by commas. The box helper refuses to start when they overlap a network Docker already has, other than another stack's session networks, or Docker's default address pools. Two stacks on one Docker can share the range: each takes a `/28` the other doesn't use |
| `SF_DOCKER_SOCKET` | `/var/run/docker.sock` | Docker's socket on the computer that runs Docker, which the box helper mounts. Rootless Docker has another one |
| `SF_DOCKER_GID` | `0` | The group that owns that socket, which the box helper joins: `stat -c %g /var/run/docker.sock` on a Linux computer. Docker Desktop's is `0`. `make up` and `make dev` fill it in when it's unset, with the group a container sees on the socket |

Give a variable on the same line, such as `SF_EXTRA_ALLOW=gateway.example.com docker compose up -d --remove-orphans`, or `export` it in your shell; with the install script, put it after the pipe, before `sh` (`curl -fsSL … | SF_EXTRA_ALLOW=gateway.example.com sh`), or `export` it. Compose reads the variables again on every `up`, so give them each time; a later `up` without them goes back to the defaults. `SF_DOCKER_SOCKET` and `SF_DOCKER_GID` are the exception after an install from a release: the install script writes them into a local file ([Run it with Docker](#run-it-with-docker)). Changing a variable recreates the containers that read it, and a new engine or box helper stops the page's sessions until you wake them ([Maintenance](#maintenance) says what a restart keeps).

`SF_ALLOW` and `SF_EXTRA_ALLOW` are starting values. Egress starts with them, and they stay the list for agents and reviewers until you save a change under **Network access** on the page. From then on the engine keeps the list in `egress.json` in its state and sets it in egress at once, without a restart; when egress restarts with its starting list, the engine sets the saved one again. To go back to the variables, move `egress.json` out of the engine's state volume and restart the engine.

On the page:

- **Git host tokens**, under **Tokens** beside Projects; see [Tokens](#tokens).
- **Network access**, under Start on the Welcome page; see [Network access](#network-access).
- **The sign-in you expect** of Claude Code for the agents and for the reviewers: the kind you last signed in with in the reviewers' sign-in dialog ([Sign Claude Code in for the reviewers](#sign-claude-code-in-for-the-reviewers)) (a subscription, or an API key, which also covers a gateway, Amazon Bedrock or Google Vertex AI). Until you sign in there, it is the kind of the first sign-in the engine sees. Removing a pasted key or gateway puts it back to what it was before you pasted the key. A start or review on another kind is refused; see [Cost and models](#cost-and-models).
- **Project settings**, in a session's Execution path panel under Code review: the review rounds before you decide (1 to 20, default 3), the work type new sessions start as, whether blocking findings go to the agent by themselves (off by default; see [Reviews and the push gate](#reviews-and-the-push-gate)), whether the engine comments on the pull request after each push (off by default), and whether the agent's own push waits for your Push after a reviewer blocked on the branch or above a number of changed files or lines (off by default; the engine counts files and lines, never looks at which files), the pack whose agents review the project (see [Packs](#packs)), and the agent files that fill the bug hunter and simplicity checker roles in place of the pack's agents (see [Your own reviewer agents](#your-own-reviewer-agents)).
- **Settings**, the gear in the activity bar: one of eight themes, the activity bar's side, the text size and desktop notifications. The update check has no setting: it always runs and shows **Update to** in the top bar when a newer release is out (see [Update to Software Factory](#update-to-software-factory)).

**A team file.** A repository can hold `software-factory.json` at its root, on its main branch. It counts only after you read and approve it on the page, with **Review the team file** in a session's Execution path panel, and any change to it needs your approval again. It's strict JSON with `"version": 1` and these optional keys:

- `adapter`: `"knackpack"`, the workflow its steps use, and the only one;
- `workTypes`: extra work types, each with an `id`, a `name`, `steps` from `define`, `plan`, `implement`, `review` and `deliver`, `edits` (`"any"` or `"docs"`), `push` (true or false) and `roles` (`bug-hunter`, `simplicity`). An `id` can't be a built-in type's (`feature`, `fix`, `incident`, `docs`, `explore`), so a team file can't change Incident's roles;
- `defaultType`: the work type new sessions start as;
- `agents`: up to 20 reviewers that every push needs, from the installed plugins;
- `fileRules`: up to 20 rules, each a `pattern` of paths with an `agent` that must review changes to them, an `instruction` for the reviewers of those changes, or both. An instruction is one line of at most 300 characters; each reviewer of a change that touches a matching file gets it in its prompt as the team's rule from main. A file whose instruction looks like it holds a secret is refused as a whole;
- `protect`: up to 50 path patterns. Before every Claude Code write to a matching file, the page shows a permission card, with no "don't ask again"; the push is never held because of a path;
- `rounds`: the review round limit, 1 to 20. The lower of this and the project's setting applies;
- `verify`: `["check"]` makes every push of this project wait for a passing [verification run](#verification-runs) of the commit it pushes, unless you allow it with a reason. `["check", "browser"]`, or `["browser"]`, asks for a passing [browser check](#browser-checks) too, or instead.

Patterns use `*` for any part of a name, `**` for any number of folders, `?` and `[...]`, matched against the path from the repository's root: `pricing/**` covers everything under `pricing/`. For example:

```json
{
  "version": 1,
  "fileRules": [
    { "pattern": "pricing/**", "instruction": "Every price shown to a customer must be the all-in price, taxes and fees included." },
    { "pattern": "migrations/**", "agent": "knackpack:database-reviewer" }
  ],
  "protect": ["pricing/rates.json", ".github/workflows/**"]
}
```

Only the main branch's version counts: the same file changed on a session's branch changes nothing. **Team rules from main** in a project's ⋯ menu on the Projects page lists the instructions and protected paths, and whether you approved that version.

A team file can't choose who fills the bug hunter and simplicity checker roles, or name commands to run (`roles` and `checks` are refused): only the project's pack, or the agent files you add on the page, fill those roles, and nothing trusted runs a repository's code.

### Network access

**Network access** is under Start on the Welcome page. Once you save a change there, the agents' allowlist always holds Claude Code's model and sign-in hosts (`api.anthropic.com`, `claude.ai`, `claude.com`, `platform.claude.com`), and the reviewers' too. Reviewers reach only Claude Code's hosts and the gateway, never the hosts you add.

Hosts you add for agents, by name (`registry.npmjs.org`), or with a leading dot for every name under a domain (`.example.com` covers `api.example.com` but not `example.com` itself), each with no expiry or for an hour, a day or a week, after which egress refuses it again, and an optional reason of up to 200 characters, shown beside the host and in the register of exceptions. A git host, a host that covers a project's host, and the sandbox check's outside host can't be added. A host that also accepts uploads, such as `registry.npmjs.org`, asks you to confirm, since an agent could send code out through it; for PyPI, add only `pypi.org` and `files.pythonhosted.org`.

What egress refused since it started, for agents and for reviewers: host, count and last time, never the path, with **Add this host** where adding it would help; egress keeps one count per host and reason across all sessions, so the list doesn't say which session asked, and the dialog reloads it every 5 seconds while it's open.

You can also set a company LLM gateway there; see [Company LLM gateway](#company-llm-gateway).

### Company LLM gateway

Under **Network access** you can set a company LLM gateway's base URL. It is always for every Claude Code session and the reviewers together, so a subscription sign-in doesn't work on either while it is on: the page adds its host to both lists and sets Claude Code's `ANTHROPIC_BASE_URL`. While it is on, both lists leave out Anthropic's own hosts and Claude Code's telemetry hosts (`anthropic.com`, `claude.ai`, `claude.com`, Statsig, Sentry, Datadog), unless the gateway is one of them, so its key can't reach them; removing the gateway brings them back. The gateway sees all code and decides every tool call, so use only your own company's gateway. Paste its key or token beside the address for the reviewers, and in each session's sign-in panel for that session, since each session runs in its own container: the engine passes it only to the container it was pasted for, which saves it for Claude Code's `apiKeyHelper` as with an API key pasted in the sign-in dialog, the page never shows it again, and Claude Code sends it in both the `Authorization` (Bearer) and `x-api-key` headers. It replaces an API key saved there. Turning the gateway on, changing its host or removing it first removes the key saved in the reviewers' and the sessions' containers, an API key included, so no key reaches an address it wasn't pasted for. **Remove gateway**, beside the gateway's heading while a gateway is saved, removes the gateway and its saved keys. The page refuses those changes while Claude Code sessions or reviews run, and names them: stop the sessions, or wait for the reviews, first. If the engine can't apply the gateway's address at a start, for example because `egress.json` can't be read, it removes a key pasted for that gateway before Claude Code starts, and starts no Claude Code there until it has.

## Run it with Docker

These steps were checked with Docker Desktop on macOS. The install script was checked piped into `sh` in Docker-in-Docker (Docker Engine 29.9.3), against a local registry and a copy of a release's three files served over HTTP, with Compose 5.7.1, 5.7.0 and 2.24.4: a fresh install, the same command again over the running stack, and an upgrade to a new image digest all ended with every container healthy and the volumes kept; a Compose file changed after the script was written stopped it with nothing in its folder changed, and Compose 2.24.3 was refused. The two Compose files were also checked, as the two layers of the earlier signed install, with Compose 5.2.0 on macOS; without the local socket file the helper stays unhealthy. They weren't tried on Windows; there, run the commands in a WSL terminal with Docker Desktop's WSL integration turned on.

1. **Install a release** with one command:

   ```bash
   curl -fsSL https://github.com/bezmoradi/software-factory/releases/latest/download/install.sh | sh
   ```

   It installs the newest release, and pipes the script to `sh` without checking it; **What you trust**, below, gives the three lines that check it first. The script:

   - checks that `docker` and `docker compose` run, that Docker's daemon answers, and that they are Docker Engine 28 or later and Compose 2.24.4 or later, and otherwise stops with one line saying what to install;
   - keeps its files in `~/software-factory`, or the folder `SF_HOME` names, which it makes if it's missing; it refuses a folder that is a git clone, so it never writes over a clone's `compose.yaml`;
   - downloads that release's `compose.yaml` and `compose.release.yaml` from the release on GitHub, checks each against the SHA-256 the script carries, and stops, changing nothing in the folder, if either differs. `compose.release.yaml` names the image by its digest, so it pulls exactly the image the release built;
   - writes `software-factory-socket.yaml` (below);
   - says so when Software Factory already runs as the Compose project `software-factory`, then runs `docker compose -p software-factory -f compose.yaml -f compose.release.yaml -f software-factory-socket.yaml up -d --wait --remove-orphans`, which replaces the containers and keeps the volumes;
   - prints the version, the folder and the page's address.

   Compose pulls the image and starts three containers: `engine` (the page, the gate, the only git credential), `helper` (the box helper, which makes each session's container and, while a review or a reviewers' sign-in step runs, a short-lived container for each reviewer) and `egress` (the proxy). `--wait` waits until all three are healthy; `--remove-orphans` removes the containers of services the files no longer have, such as the shared agent container of earlier versions. Each session then runs in a container of its own, `software-factory-box-<box>`, which the helper makes when the session starts. The script reads nothing from the terminal, so it runs the same through the pipe, and it gives Compose no input: if Compose ever asked to recreate a volume whose configuration changed, which would delete its data, the answer would be no, and Compose keeps the volume with a warning. A release gives every volume that keeps data only its name, so no release changes one.

   **Running it again upgrades** to the newest release, in the same folder. Give the variables you installed with again, after the pipe: `curl -fsSL … | SF_HOME=/srv/sf SF_PORT=8080 sh`. To install one version rather than the newest, run that release's own script, `curl -fsSL https://github.com/bezmoradi/software-factory/releases/download/v<version>/install.sh | sh`; releases from before the script have none. To read or check the script first, download it and run it with `sh install.sh`, as **What you trust** shows.

   **The local file gives the box helper control of Docker, and control of Docker is close to control of the computer.** `software-factory-socket.yaml` holds only the mount of Docker's socket into the `helper` service, from `SF_DOCKER_SOCKET` (default `/var/run/docker.sock`), and the socket's group, from `SF_DOCKER_GID`: unless you set it, `0` on macOS, which is Docker Desktop's, and on Linux the group `stat -c %g` reads from the socket. The script stops, writing nothing, unless `SF_DOCKER_GID` is only digits and `SF_DOCKER_SOCKET` an absolute path of letters, digits, `.`, `_`, `/` and `-`, so neither value can add anything else to the file. The release's Compose files hold no mount of anything on your computer, so this one file is the only place that grant comes from. The helper runs as its own user with no capabilities, on an internal network that only the engine joins, takes requests only from the engine with a key the engine makes at each start, and makes only session containers from its fixed recipe ([ARCHITECTURE.md](ARCHITECTURE.md#trust-boundary)). Without the right group the helper can't reach Docker and stays unhealthy, so `--wait` fails; the engine still starts, and the Welcome page says the box helper isn't answering, but no session starts or wakes. With Docker Desktop on Linux or WSL the group containers see can differ from the one on your side: set `SF_DOCKER_GID` to it (`make up` in a clone reads it from a container) and run the script again.

   **What you trust.** The script, both Compose files and the release itself come from GitHub, and the one-line command checks nothing before the script runs: with it, whoever can change this repository's releases decides what runs. The release workflow attests the build provenance of all three files, so with a signed-in [`gh`](https://cli.github.com/) you can check the script before it runs: download one version's script, check that this repository's release workflow built it for that version's tag, then run it:

   ```bash
   curl -fsSLO https://github.com/bezmoradi/software-factory/releases/download/v<version>/install.sh
   gh attestation verify install.sh -R bezmoradi/software-factory --signer-workflow bezmoradi/software-factory/.github/workflows/release.yml --source-ref refs/tags/v<version>
   sh install.sh
   ```

   Each release's notes, and the page's **Update to** panel, give these lines with the version filled in. `--source-ref` ties the script to that version's tag; without it the check also passes for an older release's script. Put the variables you install with before `sh`, as in `SF_HOME=/srv/sf sh install.sh`. The script then checks both Compose files against the SHA-256 sums it carries; `gh attestation verify compose.yaml` with the same flags checks one directly. The image is signed and attested, so you can check it, optionally, with [cosign](https://docs.sigstore.dev/cosign/system_config/installation/) and a signed-in `gh`, taking the digest from the `image:` line of `compose.release.yaml` in your folder, which is the image that runs:

   ```bash
   cosign verify ghcr.io/bezmoradi/software-factory@sha256:<image digest> --certificate-identity https://github.com/bezmoradi/software-factory/.github/workflows/release.yml@refs/tags/v<version> --certificate-oidc-issuer https://token.actions.githubusercontent.com
   gh attestation verify oci://ghcr.io/bezmoradi/software-factory@sha256:<image digest> -R bezmoradi/software-factory
   gh attestation verify oci://ghcr.io/bezmoradi/software-factory@sha256:<image digest> -R bezmoradi/software-factory --predicate-type https://spdx.dev/Document/v2.3
   ```

   `cosign verify` checks that the image was signed by this repository's release workflow for that tag, the first `gh attestation verify` its build provenance and the second its SBOMs (linux/amd64 and linux/arm64). The signature covers the engine image, not the agents the engine downloads at first start, which it checks against their pinned integrity hashes and npm provenance. The image is public on GHCR, so the download needs no GitHub sign-in.

   The commands the page shows name the stack's Compose project, such as `docker compose -p software-factory logs engine`, or a session's container, such as `docker exec -it software-factory-box-<box> claude`, so they work from any folder. In the commands this README gives, add `-p software-factory` after `docker compose`; that's enough for `exec`, `ps`, `logs` and `down`, while `up` and `run` also need `-f compose.yaml -f compose.release.yaml -f software-factory-socket.yaml` after it, run in the install folder.

   **Or build it from source**, for development or to run code you've read. Get the code, go into its folder and run every later command from there:

   ```bash
   git clone https://github.com/bezmoradi/software-factory.git
   cd software-factory
   make up
   ```

   Compose builds the image locally and starts the same three containers; `compose.yaml` mounts Docker's socket into the helper itself, so the warning above applies here too. When `SF_DOCKER_GID` is unset, `make up` first reads the group of Docker's socket from a throwaway container of the new image, with no network and no capabilities, since that is the group the helper sees. `make up` waits until all three are healthy, prints the page's address and opens it in your default browser (on macOS, or on Linux with `xdg-open`). Without `make`, on Linux `export SF_DOCKER_GID=$(stat -c %g /var/run/docker.sock)`, then run `docker compose up -d --build --wait --remove-orphans` and open the address yourself.

2. **Wait for the agents.** The image holds no agent: on first start the engine downloads the pinned release of Claude Code (2.1.322) from npm, checked against the hash pinned in the code, and knackpack from the head of its `main` branch on GitHub, checked against that commit's hash, and installs them into the `agents` volume. knackpack isn't pinned: at every start the engine installs the head of `main` when it changed, so you always run the newest knackpack. That means whoever can push to knackpack's `main` decides what your reviewers are told, and a knackpack change can make reviews count as no verdict until Software Factory follows; the owner accepted that risk. The engine refuses a head whose `plugin.json` doesn't name knackpack or names a version older than 0.40.0, the first that writes requirements in its checked format, and one that could run programs in the trusted reviewer container: a `plugin.json` key other than `name`, `version`, `description`, `author`, `homepage`, `repository`, `license`, `keywords` and `engines` (such as `mcpServers`, `lspServers` or `monitors`), a top-level `.mcp.json`, `.lsp.json`, `monitors`, `workflows` or `settings.json`, a file under `skills/` or `commands/` (any extension, any letter case) or a top-level `skill.md` that uses an argument placeholder (`$ARGUMENTS`, `$1`, or front matter declaring `arguments` or using a YAML tag), `${CLAUDE_DEV_MODS_DIR}`, or inline shell (`!$`, `` !` `` anywhere but in `` `!` ``, ```` ```$ ```` or ```` ```! ````), a file under `skills/`, `commands/` or `agents/` with `!`, a backtick, `$` or white space in its path, or an agent whose front matter mentions `skills` other than as a plain list of `knackpack:<name>`; the installed commit is checked again at every start, before any review, and isn't used while it fails, with the reason on the page; reviews also turn skills' inline shell off; it keeps the installed one then, or when GitHub can't be reached. A session keeps the knackpack it started with across Stop and Wake; new sessions and the next review get the new one. Agent versions in Diagnostics shows the installed version and commit and what this start's check did. `SF_AGENTS_INSTALL=manual` turns the check at start off. That takes a few minutes; the page offers Claude Code once it's installed. If a download failed, run `docker compose exec engine software-factory install-agents` to try again.

3. **Open the page** if `make up` didn't: <http://127.0.0.1:7799>, or the port you set in `SF_PORT`. It signs itself in.

4. **Sign the reviewers in**, as [Sign Claude Code in for the reviewers](#sign-claude-code-in-for-the-reviewers) says. Until they are signed in, that dialog opens by itself each time you go to the Projects page. The Projects page also shows a notice with **Set Git name and email** until the name and email agents commit with are set ([Git name and email](#git-name-and-email)).

5. **Sign each session in when it starts**, as [Sign Claude Code in for this session](#sign-claude-code-in-for-this-session) says.

Then add a repository and start a session, as in [Usage](#usage).

### Sign Claude Code in for the reviewers

The reviewers run their own Claude Code, with a login no agent can read or change. Until they are signed in, this dialog opens by itself each time you go to the Projects page, and **Reviewers’ sign-in** in the command palette opens it at any time, with when the sign-in was last checked (while all 8 reviewer containers are in use it shows the last check and tries again every 15 seconds; when you signed in, added or removed a key after that check, it says the check came before your change and isn't current, and marks no kind as in use).

1. Press **Sign in** beside the reviewers, then **Open claude.com to sign in**, and sign in with your Claude account.
2. Copy the code claude.com shows, paste it into the page, and press **Complete sign-in**. The dialog closes and a notification says how it's signed in.

The page starts Claude Code's own `claude auth login` in a reviewer container made for the sign-in and passes it the code you paste; the container is removed once the login ends. Software Factory doesn't keep or log the code. Reviewer containers live only while a review or a sign-in step runs, so there is no terminal to sign them in from.

The reviewers' login is kept in the `software-factory-reviewer-home` volume, which every reviewer container shares, so you sign them in once. An earlier version kept it in the Compose volume `software-factory_reviewer-home`, which is no longer used: sign the reviewers in once more after the update, then `docker volume rm software-factory_reviewer-home` removes the old one.

### Sign Claude Code in for this session

Each session's container has a home of its own, so a new session's agent isn't signed in yet. When you press **Start**, and when a start or wake finds the agent isn't signed in, the page opens this dialog over the form: **Subscription** (the same claude.com code as for [the reviewers](#sign-claude-code-in-for-the-reviewers)) or **API key**. A sign-in closes the dialog and the start goes on by itself. You can also sign in with `docker exec -it software-factory-box-<box> claude`.

**Continue** then starts the session in that same container. The login stays in the session's own home volume, `software-factory-home-<box>`, so a session you stop and wake keeps it; a new session signs in again.

## Deploy on a Linux server

Software Factory has no server deployment. It publishes its page only on `127.0.0.1` of the computer that runs it, and accepts only requests addressed to `127.0.0.1:<port>`. On a Linux computer you use yourself, follow [Run it with Docker](#run-it-with-docker).

## Run the agents under gVisor

On a Linux computer, `compose.gvisor.yaml` runs every session's container and every reviewer container under [gVisor](https://gvisor.dev) (the runtime `runsc`). It sets `SF_BOX_RUNTIME=runsc` on the box helper, which then makes each of those containers with that runtime, and refuses to start a session or a reviewer, saying why, while Docker lists no `runsc` runtime; it never falls back to Docker's default. gVisor answers the agents' system calls with a kernel of its own, so an exploit an agent runs meets gVisor before it reaches the host's kernel. The `engine`, `helper` and `egress` containers stay on Docker's default runtime. The overlay isn't for Docker Desktop, which has no supported way to add a runtime.

1. **Install gVisor** (x86_64 or ARM64, Linux 5.6 or later). These commands from gVisor's install guide download the latest release and check its SHA-512; gVisor's apt repository works too:

   ```bash
   (
     set -e
     ARCH=$(uname -m)
     URL=https://storage.googleapis.com/gvisor/releases/release/latest/${ARCH}
     wget ${URL}/gvisor.tar.zstd ${URL}/gvisor.tar.zstd.sha512
     sha512sum -c gvisor.tar.zstd.sha512
     sudo tar --zstd -xf gvisor.tar.zstd -C /usr/local/bin
     rm -f gvisor.tar.zstd gvisor.tar.zstd.sha512
   )
   ```

2. **Register it with Docker** as the runtime `runsc`, and check that it runs a container:

   ```bash
   sudo /usr/local/bin/runsc install
   sudo systemctl reload docker
   docker run --rm --runtime=runsc hello-world
   ```

3. **Start the stack with the overlay.** This recreates the box helper, which stops the running sessions' containers; the sessions come back with Wake, in containers under gVisor:

   ```bash
   export COMPOSE_FILE=compose.yaml:compose.gvisor.yaml
   docker compose up -d --build --wait --remove-orphans
   ```

   To go back, unset `COMPOSE_FILE` and run `make up`.

   With a release, no other file is needed: run the install script again with `SF_BOX_RUNTIME=runsc`, which is all the overlay sets (`curl -fsSL … | SF_BOX_RUNTIME=runsc sh`), and give it on every later `up` in the install folder too. A release under gVisor hasn't been started yet.

Limits:

- **Fixed addresses in place of DNS.** gVisor's network stack doesn't reach Docker's embedded DNS server (gVisor's FAQ). Every session's container already finds the engine and the proxy by fixed addresses on its own network, written into its `/etc/hosts` (`engine-agents`, `egress`, `egress-agents`), so the overlay needs no addresses of its own. Every other name doesn't resolve in a session's container.
- **Slower.** System calls and file access cost more under gVisor, so git in a large repository, installs and builds in a session take longer.
- **Reviews not checked.** A real Claude Code review under gVisor isn't checked yet.
- **Tested in Docker-in-Docker.** The overlay was checked with Docker Engine 29.9.3 and Compose 5.7.1 in a privileged `docker:dind` container on Docker Desktop for macOS (arm64), with gVisor release-20261109.0 registered as `runsc`, not on a Linux computer of its own, and not on amd64. A session of the development fake agent got a container on `runsc`, with gVisor in its `dmesg`; the sandbox check of that container passed, its probe of the network's gateway included; and the session took a turn and wrote its file. Without `runsc` registered, the start was refused with the reason and no container was made. A real Claude Code session under gVisor isn't checked yet, since it needs a real sign-in.

## A headless browser for screenshots

`compose.browser.yaml` gives the box helper an image with Chromium, and the helper makes every session's container from its own image, so an agent working on a UI can take a screenshot of it, and the page shows it to you. The engine and egress keep the standard image; the reviewer containers, made from the helper's image, get Chromium too but run no browser. It builds that image from source, so it needs a clone ([Run it with Docker](#run-it-with-docker)); releases don't publish it. It recreates the helper, which stops the running sessions' containers until you wake them.

```bash
export COMPOSE_FILE=compose.yaml:compose.browser.yaml
docker compose up -d --build --wait --remove-orphans
```

With the gVisor overlay too: `COMPOSE_FILE=compose.yaml:compose.gvisor.yaml:compose.browser.yaml`. With the development fakes, set `SF_BROWSER_STAGE=dev-browser` and list `compose.dev.yaml` before `compose.browser.yaml`, so the sessions' containers keep the fake ACP agent.

- **Pinned packages.** Chromium 156.0.8078.79 (Debian's `chromium` and `chromium-common` 156.0.8078.79-1~deb13u1) and `fonts-liberation` 1:2.1.5-3 come from [snapshot.debian.org](https://snapshot.debian.org) as Debian's archive and its security archive were on 2026-11-03 at 01:35:55 UTC, so a rebuild installs the same packages. To update Chromium, move the date in the `browser` stage of the `Dockerfile` and the versions together.
- **Size.** The browser image is about 700 MB larger than the standard one.
- **Chromium's own sandbox is off.** The `chromium` command runs with `--no-sandbox --disable-dev-shm-usage` (from `/etc/chromium.d/software-factory`). The container drops every capability and allows no new privileges, so Chromium can't start its sandbox; the container's hardening isolates it instead. Docker gives the container 64 MB of `/dev/shm`, so Chromium uses `/tmp`.
- **Taking a screenshot.** An agent runs, for example, `chromium --headless --window-size=1280,800 --screenshot=<file> http://localhost:3000`, against a server it started on one of the session's ports. Chromium reaches only what the agent can: the container itself, and the allowed hosts through the proxy.
- **Where they go.** Each session's agent is told to save its screenshots in `/workspace/s/<box>/screenshots/<session id>/`, in its own container's folder and outside its worktree, so a `git add -A` doesn't commit them. Claude Code reads the folder in its start note, and the development ACP agent in the Software Factory tool server's instructions. Saving them works without the browser image too, with any tool an agent has.
- **On the page.** **Screenshots** above the conversation lists the session's newest 50 after each turn; **Refresh** lists them again. Choose one to see it.
- **What the engine shows.** The engine lists only `.png`, `.jpg`, `.jpeg` and `.gif` files directly in the folder, and follows no symbolic link. Before it decodes a file, it checks that the file is at most 10 MiB, that its first bytes are a PNG, JPEG or GIF, and that its header gives at most 8,192 pixels a side. It also refuses a file that would take more than 256 MiB of memory to decode, such as a 16-bit PNG over 32 megapixels or a JPEG over 16 megapixels. It then decodes it (a GIF's first frame only) and encodes it again as a PNG of at most 24 MiB, which drops the file's metadata and anything appended to it, one screenshot at a time. A file that isn't a valid image isn't shown. The page gets the PNG as base64 inside JSON and shows it from a Blob.
- **Browser checks.** A project can also run browser tests, such as Playwright's, on a clean copy of a commit, where their own exit code is the result and their screenshots and traces are kept with the run: see [Browser checks](#browser-checks). Those run in the project's own image, not this one, though this image works as one.
- **Kept until the session is deleted.** The engine never commits or pushes a screenshot. It deletes the session's folder when you delete the session. Only that session's agent can read and change its screenshots.
- **Not a live preview.** The page shows only still images the engine decoded and encoded again, so nothing an agent wrote runs in the page.

## Running it

Run the commands below from the repository folder. The page's own commands, such as a sign-in step, name the stack's Compose project with `-p`, so they run from any folder. After an install from a release, add `-p software-factory` after `docker compose` in the ones below ([Run it with Docker](#run-it-with-docker)).

### Usage

1. **Open the page** at <http://127.0.0.1:7799>. The Welcome view lists every session, those waiting for you first. **Search sessions** finds them by name, branch or project, and the Running, Waiting for you, Held push, Stopped and Done buttons show only those, each with its count (a session whose agent finished by itself reads Done, in its own group); the search and the filters stay in the page's address after `#`, so a reload or a bookmark keeps them.
2. **Add a project.** Under **Projects**, save a token for the git host if the repository is private or you want the engine to push ([Tokens](#tokens)), then enter the repository's `https://` address and press **Add repository**. The engine clones it; the page shows the progress.
3. **Sign each session in, and trust its repository:** when you start a session, the page asks you to sign its agent in ([Sign Claude Code in for this session](#sign-claude-code-in-for-this-session)), and for Claude Code then shows Claude Code's trust question ([Trusting a repository](#trusting-a-repository)).
4. **Set the Git name and email agents commit with** ([Git name and email](#git-name-and-email)). No session starts or wakes until you do.
5. **Start a session.** Press **New session** on the project's row, pick the agent, and press **Start**. Open the session from the project's list when it connects.
6. **Pick a work type** (Feature, Fix, Incident, Docs only or Exploring) and write the first message. Answer the cards the agent shows, and follow its work in the side panel.
7. **Review and push.** Press **Review**, then **Push**, or let the agent call its push tool. The engine pushes the session's branch once the reviews pass ([Reviews and the push gate](#reviews-and-the-push-gate)).
8. **Get the work** from your git host: `git fetch origin sf/<id>` in your own clone, then `git switch sf/<id>`, or open a pull request from that branch on the host.

**The page's sign-in.** Opening the page signs it in, with no code or password. **Any program on this computer can do the same and use the page,** including approving pushes; other websites and the agents can't. One tab is signed in at a time: opening the page in another tab or browser, or any program on this computer signing in, moves the sign-in there, and the earlier tab shows a note with **Use this tab** to take it back. Refreshing a tab keeps it signed in. After 15 minutes with no tab open, 24 hours or an engine restart, the page signs in again by itself.

### Git name and email

Set the name and email agents commit with under the Projects page's **Set Git name and email** notice or **Git name and email** under Settings (the gear in the activity bar). No session starts or wakes until you do: without them, an agent may commit with the email of its sign-in. Every agent commits with them. They become public with each push: for GitHub, use your noreply address, `ID+USERNAME@users.noreply.github.com`, from GitHub's Settings, Emails. A new session uses them at once, a stopped one when you wake it.

### Projects

A project is a repository the engine cloned by its `https://` address into the `workspace` volume. There are no local folders, by design: a folder mounted from your computer would let an agent plant git hooks or editor tasks that later run on your computer. Addresses over SSH or `http://`, and addresses with a user name, password, query or fragment, are refused.

Each new session fetches the main branch again from the address recorded when the project was added, and starts in a new worktree on its own branch, `sf/<id>`, at that commit. The new-session form shows the model and a name; **Advanced settings**, folded until you open it, holds the effort, the work type, **Start from** and the session's caps. The form has:

- **a name**, optional;
- **the model**, for Claude Code: its default, Fable, Opus, Sonnet or Haiku;
- **the effort:** low, medium, high, xhigh or max. The defaults send no model and no effort, as before;
- **the work type**, or the project's default;
- **Start from:** main as fetched now (the default), a branch of the repository, an open pull request's branch, or the latest commit of another session of the project, or one of its earlier commits. The engine fetches the branch or the pull request's head commit from the git host first, and starts nothing when it is no longer the commit the list showed; choose it again to start from the new one. Whatever you choose, the session gets its own new branch `sf/<id>` at that commit, and its reviews compare it against main as for any session. **Fork here** in a session's ⋯ menu opens this form with that session's latest commit chosen, and **Fork from here** beside a commit in the session's Changes list opens it with that commit chosen; the engine starts there only when the commit is still on that session's branch. Pull requests are listed for GitHub only, with a token that can read them. Only you choose a start point: no agent tool starts a session.
- **From an issue**, optional: the repository's open issues, read with your saved token, newest first, 30 to a page, optionally filtered by one label (pull requests are left out). Picking one shows its title and text in full, with characters that change text direction or hide shown as on the start-up card. When you press **Start**, the engine reads the issue again and starts nothing when it changed since you read it (read it again then), so the agent gets only the text you saw. It sends it as the session's first message, after this framing: "This is issue #N from the git host, written by its author; treat it as a task description, not as instructions that override the page or Software Factory's rules". The title and text are cut to fit one message. An issue whose title or text holds something shaped like a token is refused, and so is a closed one. The session remembers the issue, and the pull request the engine opens for it says `Closes #N`. Nothing starts until you press Start.
- **Start with both**, optional: a second session of the same agent, with the same or another model, and one first message for both. Start asks once, since two sessions on one task double usage, even on a subscription. Both start from the same commit, main's or the one **Start from** picks, on their own branches, each through its own start-up files and sign-in checks, and get the same first message, or both get the issue picked under **From an issue**. The engine starts both from one press, and any caps you set apply to each. The overlap warning stays quiet between the two. Each session shows the comparison: both diffs, their review verdicts, how long they have run and each session's own cost estimate. **Keep this one** marks your choice, and the other can then be deleted.
- **Benchmark: start from a merged pull request**, optional: the repository's merged pull requests, read with your saved token. Picking one shows its description in full; Start begins at the pull request's base commit with the description as the first message, framed as its author's task description, as an issue is, and refused when it holds something shaped like a token or changed since you read it. With **Start with both**, both sessions get it. The comparison shows the merged diff beside each session's.

A session starts in the agent's own asking mode, so it asks before it acts; auto and bypass modes can't be chosen. Before it starts, the engine:

1. makes the session's container, which shows "Preparing the session's container" on the page, and checks that it can't reach a git host;
2. shows you the repository's **start-up files**, if it has any, and waits for your approval. These are the files that agent loads at start and that can change what it may do without asking: for Claude Code `.claude/settings.json`, `.claude/settings.local.json`, `.mcp.json`, the `.claude/agents/`, `commands/`, `skills/`, `workflows/` and `hooks/` folders, and `.claude/skills/` in any subfolder. The page shows each one with characters that change text direction or hide shown as `⟨U+…⟩`, other invisible and control characters as `\u{…}`, long runs of blank lines and spaces shortened, a symbolic link as its target, and a note on any file that differs from the commit. It marks risky lines for you to read, without blocking anything: `allowed-tools:` naming Bash, inline shell (`` !`command` ``) in skills and commands, `hooks:` in front matter, and scripts bundled in a skill's folder. Your approval covers that exact set for this repository and agent; any change to any file asks again.

   Below the approved files, a collapsed section lists the instruction files that are new or changed since your last approval: `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md` and `.claude/rules/` files, in the root and in subfolders, and those in the folders above the worktree in the session's own folder (`/workspace/s/<box>/worktrees` and `/workspace/s/<box>`), which that session's agent can write, marked the same way. They steer the agent but grant it no permission, so they are information, not part of the approval: a change to one alone doesn't ask again, and they appear only when the card asks anyway. The search skips `.git`, `node_modules`, `dist`, `build`, `out`, `target`, `vendor`, `coverage`, `__pycache__` and `venv`, and the card says where it stopped early;
3. checks the agent's own sign-in, and asks first when it's billed per use ([Cost and models](#cost-and-models)).

**Splitting a goal.** An agent can propose splitting a large goal into smaller tasks with `factory_split`: up to 8 at once, each a title and a first message. Each shows in the session's details as a card with its text in full, marked as written by the agent. You can edit a card's text or dismiss it; **Start** starts a normal session from main with the goal session's agent and work type, through the usual start-up files, sign-in and cost checks, and sends the card's text as its first message. The goal session lists its tasks, and each task links back to it. At most 3 of a goal's sessions run at once: a further Start queues the task, and the card says so; the engine starts it when one of them stops, even with the page closed or after a restart, and **Remove from queue** takes it out. When its start then needs your answer, such as a sign-in, the card waits for you instead, and so do the goal's other queued tasks. Nothing starts until you press Start.

**Check and setup commands**, in a project's ⋯ menu, are two commands you type, such as `make check` and `npm ci`, one line of at most 300 bytes each and empty at first. Both run in the session's own container, in its worktree, as the agents' user with the model keys cleared, and never come from the repository. The setup command runs once in each new session's worktree, for at most 15 minutes, right after the start-up card is approved, never before it and never when it's refused; messages you send meanwhile wait in the session's queue. The check command runs when the agent ends a turn, for at most 5 minutes. When it fails in a Claude Code session, the agent gets "The project's check failed; fix it before you finish." with the command as you typed it, its exit code or that it ran out of time, and the last 8 KiB of the output or "It printed nothing", and one more try in the same turn; a second failure ends the turn. The session shows the last result of each. The check in the session is advisory: it never counts for a review or a push. A verification run of the same command, below, is the one a push can count.

#### Verification runs

A verification run runs the project's check command on a clean copy of one commit, outside the session, and only its exit code counts. Set **Image for verification runs** under Check and setup commands to an image that holds the project's tools and dependencies, pinned by digest, such as `node@sha256:` and its 64 hexadecimal digits, and pull it on the Docker host first (`docker pull <name>@sha256:<digest>`): the run has no network, and Software Factory ships no such image. A project with no image can't run one. Put no secret in the image, in a variable or a file: the code the run executes was written by an agent, which reads everything in it, and whether the run passed, and so roughly when it ended, reaches the agent through whether and when its push goes out. Of the image's own variables the run keeps only tooling ones (`PATH`, `LANG`, `LC_*`, `*_HOME`, `*_VERSION`, `*_ROOT`, `GOPATH`, `PYTHONPATH` and a few more), and only when the value has the shape of its kind (a path, a version, a locale or a small number); it empties the rest, `TZ`, `USER` and `NODE_ENV` included; a check command that needs another variable sets it itself, such as `FOO=bar make check`. That is a best-effort backstop, not a filter to rely on. Before a run the engine checks the `verify` volume's free space, and a run with no room ends as not passed. The image needs a POSIX shell with `mkdir`, `cp` and `cat`, and the command runs as user 10006, which the image needn't know.

Press **Verify this commit** in the verification panel below the push card, or let a push start one: when the [team file](#configuration) asks for `"verify": ["check"]`, a push of a commit with no run starts it, with the reviews for an agent's push, unless the push still needs your approval of the requirements or the plan. An agent's push is decided again, and pushed if nothing else holds it, once both its reviews and the run have ended; a push you pressed stays held, and you press Push again once the run passed. The engine runs two verification runs at once, and a push can hold at most one of them: a push that finds no free slot queues its run, one queued run per session, started in order as slots free up, ahead of any later push, and the agent's push waits for it as for a queued review. A push starts a run only when it could go out: not for Allow with a reason, Deny or another answer on a held card, not from a session whose work type doesn't push, not when the team file's rules refuse the push, and not while it waits for your approval. The push card names what is missing without the exit code. An agent's push reply has one text for a run that is queued, running or didn't pass, and the engine doesn't hold its other answers back for a run the push doesn't need, so what code in the run can signal to the agent is whether and when its push goes out; the panel shows the rest, a queued run included. A run cut off by an engine restart or a helper error isn't started again on its own: the push is decided as held, its card asks you to press **Verify this commit**, and the audit says so. The engine copies the commit's files with its own hash-checked reader, never git, into a new container of that image with no network, no git host token, no sign-in, no other session's files and a read-only root, and runs the command there for at most 15 minutes (`SF_VERIFY_MINUTES`, 1 to 120), with 4 GiB of memory and 2 GiB of files. The panel shows the state, the commit, the command, the image, the exit code and the end of the output, masked when it looks like it holds a token. A run counts only for that commit, that command and that image: a new commit, a changed command or another image needs a new run, and the panel says why the last one doesn't count. A failure, a timeout, running out of memory, an engine restart during the run, or a stop is never a pass. Without the team file's `verify` the result only shows; reviewers never see it. A pass proves the check passes on a clean copy of that commit, not that its tests are good: the agent wrote them too. A check that passes in the session can fail here when it needs something only the session's home or worktree has, or the network.

#### Browser checks

A browser check runs the project's **Browser command**, set under Check and setup commands beside the check command, the way a verification run runs the check: on a clean copy of the commit, in its own container of the project's image, with no network, and only its exit code counts. Press **Run the browser check** in the verification panel, or ask for it in the team file (`"verify": ["check", "browser"]`). The image must hold the browser and its test tools, such as Playwright and its browsers, since the run is offline and npm can't fetch them, and a folder `/out` owned by user 10006 (`RUN install -d -o 10006 -g 10006 /out`); with no browser at `/usr/bin/chromium`, `/usr/bin/chromium-browser`, `/usr/bin/google-chrome` or `/ms-playwright` the run ends as not run, with that reason. The stack's own [browser image](#a-headless-browser-for-screenshots) has Chromium and `/out`. The command starts the app under test inside the run and points the browser at it over `localhost`, and a test that signs in uses a test user from the repository's seed data: the run reaches nothing else, so never put a real or production login in the image or the command. Playwright doesn't read `CHROME_BIN`: set `launchOptions.executablePath` to the image's Chromium, or `PLAYWRIGHT_BROWSERS_PATH=/ms-playwright` in the command for Playwright's own image, since the run keeps only tooling variables. For example, with the browser image: `chromium --headless --dump-dom file://$PWD/index.html | grep -q '<h1>ok</h1>' && chromium --headless --window-size=800,600 --screenshot=$SF_OUT/home.png file://$PWD/index.html`.

Files the command saves directly in `$SF_OUT` are kept with the run: up to 20 `.png`, `.jpg`, `.jpeg` or `.gif` images of at most 10 MiB, which the engine checks and encodes again as it does [screenshots](#a-headless-browser-for-screenshots) before the panel shows them, and `.zip` traces of at most 50 MiB, which the panel only downloads and never opens (open one with Playwright's trace viewer), 100 MiB a run. Links, folders, other names and files over a limit are dropped, and the panel names them. The files never change the result, and the agent wrote the code that made them, so what an image shows is the test's claim. The engine keeps the files of the latest 3 runs with files per project, 1 GiB in all, deletes them with the session or the project, and never exports them.

A project's row shows the branch new sessions start from and whether the repository has a `CLAUDE.md` or `AGENTS.md`. Expand it to see its sessions. **Remove** takes a project off the list once it has no sessions, running, starting or stopped, and isn't being cloned again, and deletes its clone from the `workspace` volume, so adding the repository again gets its plain name back, not `<name>-2`. Its caps, project settings, team file approval, saved prompts, package lookup switch, decision log with your edits and lessons from reviews come back when you add the same repository again, also when it comes back as `<name>-2` because its old clone couldn't be deleted; a different repository that gets the same name starts without them, and its decision log and numbers show none of the removed one's decisions. The panels in a project's ⋯ menu read the engine again every 5 seconds while they're open, leaving a form you changed and haven't saved as you typed it; **CI workflows and main's protection** asks the git host only when you open it, to stay within the host's request limits.

**Saved allow rules**, in a project's menu, lists the allow rules Claude Code saved when you chose "don't ask again" on a card: Claude Code 2.1.322 saves them in the session's worktree, in its `.claude/settings.local.json`, which only that session loads. The list also reads the clone folder's `.claude/settings.local.json`, which Claude Code's documentation names for worktrees, though a live run of 2.1.322 didn't apply a rule from it in a session's worktree, and the user settings in each running session's container (`~/.claude/settings.json` in that container's home), which only that session loads. Remove works on a running session's container only. Each shows where it lives and a **Remove** button. A rule that allows much more than one command is marked wide: any Bash command, a network tool such as `curl`, `wget`, `nc`, `ssh` or `scp`, an interpreter or command runner with a wildcard, or any other wildcard. Agents can write these files too, so the list is a report of what is in them, not a control. Remove deletes only that rule, from that file: agent-host reads the file again, refuses if the rule is gone or the file is no longer the shape Claude Code writes, and leaves the rest of it as it was. Removing one changes a start-up file, so the next start or wake that reads that file asks for your approval again.

**CI workflows and main's protection**, in a project's menu, starts with a readiness report read from the main branch's commit, data only: an instruction file (`CLAUDE.md`, `AGENTS.md`), a test command (a `test` script in `package.json`, a `test` target in the `Makefile`, `go.mod`, `pyproject.toml` or `pytest.ini`, `Cargo.toml`), CI workflows, lint configuration (`.golangci.yml`, `.eslintrc*`, `eslint.config.*`, `ruff.toml` or `[tool.ruff]`, `.rubocop.yml`, `biome.json`), the check command, the team file and branch protection. Each shows found, missing with a short suggestion, or unknown, as protection is when the token can't read it. One more line, **Check passes on main**, says whether the project's check command passed on main's commit: pass with the commit and when, fail with the exit code and the end of the output, or unknown, as it stays until you run it, while it runs, and once main or the command or image has moved on. Only that line runs anything, and only when you press **Run on main**: the engine fetches main with the saved token first, then runs the check on main's latest commit in a [verification run](#verification-runs) container, the same untrusted one a session's commit gets, since merged code may be agent-written too. A run on main counts for no session's push. Nothing in the report holds or allows anything.

**Delivery and reviewer numbers**, in a project's menu, counts from the engine's own records: pushes, the time from a session's start to its first push, review rounds per push, each review role's pass, block, override and no-verdict rates, Allows, denied pushes, pull requests merged or closed, and cost, which is the agents' own estimate. It says from when: the audit file rotates, and the review and pull request records keep at most 500 each.

It also shows "after review" counts: CI failures on a commit Software Factory pushed after its reviews passed, and pull request reviews asking for changes, reviews with comments and inline review comments on that commit after the push, from anyone but the engine's own push note. A role counts the commits it passed; the project counts a commit only when every required role passed it. They are counts, not defects: a CI failure can be flaky, and a comment may not point at a defect. The engine reads them only while a pull request is open for the branch, so a branch pushed with none open counts nothing, and it counts each failing check and each comment once.

**Decision log**, in a project's menu, is a short log the engine builds from its own records: requirements and plans you approved, by date and approval hash, verdicts you overrode and pushes you allowed or denied with your reasons, and pull requests merged. It holds no agent text, so an approval shows only its kind and date until you name it. You can name, reword, hide or add entries; those are kept apart and survive each rebuild. Each new session gets the log with its first message, as one engine note of at most 4 KiB, and a reason or entry that looks like a token is withheld.

### Tokens

The engine clones, fetches and pushes with a token you save on the page, under **Tokens**: the host, GitHub or GitLab, and the token. It also uses the token to open the issues and pull requests you approve, to read CI results and your own pull request comments for the agent, and, if you switch it on, to comment on a pull request after each push ([Issues, pull requests and CI](#issues-pull-requests-and-ci)). For GitHub, create a fine-grained personal access token:

The page offers GitHub and GitLab as hosts. Pick one under **Host**, and **Create a GitHub token** (or **Create a GitLab token**) opens that host's token form in a new tab with the settings below filled in, so on GitHub you only choose the repositories (step 2). GitLab's link fills in the `read_repository` and `write_repository` scopes, which clone, fetch and push; the issue, pull request and CI features use GitHub's API, so they work only on GitHub. By hand on GitHub:

1. On GitHub, open **Settings → Developer settings → Personal access tokens → Fine-grained tokens** and choose **Generate new token**.
2. Under **Repository access**, choose **Only select repositories** and pick the repositories you add here.
3. Under **Repository permissions**, set:
   - **Contents: Read and write** (clone, fetch and push);
   - **Metadata: Read-only** (GitHub sets it with the others);
   - **Issues: Read and write** (`factory_issue`);
   - **Pull requests: Read and write** (`factory_pull_request`, `factory_review_comments` and the comment after each push);
   - **Actions: Read-only** and **Commit statuses: Read-only** (`factory_checks`);
   - **Workflows: Read and write**, only if agents may change `.github/workflows/`: without it GitHub refuses a push that changes them;
   - for following a pull request after a push, read access is enough, and the permissions above already give it: **Pull requests** (its state, draft flag and mergeability, reviews and inline comments), **Issues** (its conversation comments, and the open issues the new-session form lists), **Commit statuses** and **Contents** (the head commit's statuses and check runs). **Ready for review** needs **Pull requests: Read and write**, and assigning what the engine opens to you needs **Issues: Read and write** for an issue and **Pull requests: Read and write** for a pull request;
   - **Administration: Read-only**, optional: it lets the project page show whether the main branch's protection rule requires reviews. Without it, the page still reads the rulesets that apply to main (Metadata) and whether a protection rule covers it and requires status checks (Contents), and shows "unknown" for the rest.
4. Generate it, copy it, and save it on the page with the host **GitHub**.

A permission left out only turns off what needs it: the page and the agent are told which permission a refused call needs. The engine keeps one token per host, in its own volume only. It never shows the token again, never logs it and never sends it to another container; the page shows only which hosts have one and when it was saved, and lets you replace or remove it. A public repository can be cloned without a token, but pushing always needs one. **A pushed branch runs the repository's own workflows,** such as GitHub Actions that start on `push`, with that repository's secrets. Those workflows come from the branch, which an agent wrote and the reviews checked, so read a change to them (`.github/workflows/` on GitHub) before you allow its push, or limit which branches may use secrets in your host's settings. The push card lists the workflows in the pushed commit that start on a push to its branch, and marks those that use secrets other than `GITHUB_TOKEN`, set `id-token: write`, also run on `pull_request_target` or `workflow_run`, or are new or changed on the branch. A project's ⋯ menu, **CI workflows and main's protection**, lists the same for the main branch, suggests `branches-ignore: ['sf/**']` for those that shouldn't run on the agents' branches, and shows whether the main branch is protected and requires reviews and status checks ("unknown" when the token can't read it).

### Trusting a repository

Claude Code asks whether you trust a repository's folder, and a Claude Code session can't start until you answer. Each session has its own container, clone and Claude Code settings, so each new Claude Code session asks once, when you press **Start**, and the page shows Claude Code's question. Press **Yes, I trust this folder**, and the session starts. If the repository's clone folder holds files Claude Code loads at start, such as a `.claude/settings.local.json` an agent wrote there, the page first shows them for your approval, and Claude Code's question is answered only once you approve them; **Cancel** leaves the folder untrusted. Your answer covers that session, through every stop and wake.

To answer it, the engine runs Claude Code in the session's clone, in the session's container, behind a virtual terminal. There it accepts Claude Code's first-run screens (the text style and its security notes), declines its offer to try its fullscreen renderer, answers **Yes** to the trust question, and starts Claude Code again to check that the answer was saved. If Claude Code shows a screen Software Factory doesn't know, it answers nothing and tells you. You can then answer in a terminal instead: `docker exec -it -w /workspace/s/<box>/repos/<name> software-factory-box-<box> claude`, choose **Yes, I trust this folder**, then type `/exit`; the page's message gives the exact command.

### Working in a session

A session the engine started is controlled from the page: what you type goes to the agent as your own words.

- **Messages.** Press Enter to send. A message to a stopped session wakes it first; up to 20 messages wait 2 minutes for it to come back. A line starting with `!` isn't run: the page offers to copy the command instead. A message you send while the agent works waits for the running turn to end and starts the next one.
- **Commands.** A message starting with `/` runs a skill, a plugin's or an MCP server's command, or one of the built-in commands that change nothing: `/clear`, `/compact`, `/context`, `/cost`, `/usage`, `/help`, `/status`, `/review`, `/security-review`, `/init`, `/todos`, `/export` and `/release-notes`. Type any other built-in command in Claude Code itself (see the ⋯ menu below).
- **Files.** Type `@` for suggestions from the session's worktree; names that look like secrets are left out. A file path in a reply opens the file read-only, up to 512 KB; binary files, files with secret-looking names and paths through a symbolic link aren't shown.
- **Images and files.** Paste or drop up to 4 images (PNG, JPEG, GIF or WebP; the engine shrinks a large PNG or JPEG screenshot to 1,568 pixels and 2.5 MiB, and takes a GIF or WebP of up to 2.5 MiB) and up to 4 other files (10 MiB each) on a message. The page uploads them for the session to read; uploads not sent within an hour are removed. A folder can't be dropped; type its path with `@`. In an Incident session the page warns, while something is attached, that logs and screenshots go to Anthropic with the rest of the session, so remove customer data and secrets first; it doesn't scan or block them.
- **Cards.** A permission request shows the whole call with **Yes**, the agent's own other choices (such as allowing it for the rest of the session), and **No**, with an optional note on what to do instead. A call the page can't show in full can only be denied here. In a Claude Code session, a command that can't be undone gets a card every time, even when a saved rule allows it, marked "can't be undone" and with no "don't ask again": `rm -r` on `~`, `/`, `.`, `..`, a glob or a variable, `git reset --hard`, `git clean -f`, `DROP` or `TRUNCATE` sent to a database client, `terraform destroy`, `kubectl delete`, a download piped into a shell, and starting another `claude` session. Questions wait as cards with their options and a box for your own answer. While a card waits, the message box waits too. Closing the tab doesn't answer the card.
- **Away mode.** **Away** in the header turns it on for every session or for the open one; while it is on, the button reads **Away: on** and pressing it turns it off. While it's on, each new permission card is denied for you with the note "the person is away; continue without this or stop", so a session doesn't wait for hours; question, plan, issue, pull request and push cards still wait. It's off by default, and each change is audited.
- **Hidden text.** Tool output, a tool call or a card's input that holds terminal control sequences other than plain colours, which can erase, move over or conceal text, or text-direction overrides, is marked "hides text", with its escaped form beside it.
- **Subagents.** A subagent's tool calls show in their own group in the conversation, which you can collapse, and the side panel lists each subagent with its state.
- **Plans.** Claude Code lets only its own prompt approve a plan made in its plan mode. **Approve in Claude Code** shows that prompt there; then attach to the session and answer it. **Tell Claude what to change** works from the page.
- **Stop.** The round button beside the message box stops the agent's current turn.
- **Saved prompts.** **Saved prompts** above the message box keeps up to 50 prompts per project, each a name of at most 60 characters and a text as long as a message. **Insert** puts one into the message box at the cursor, for you to change and send; **Edit** and **Delete** change the list. **New prompt** starts from what the message box holds. They're your own text, kept in `engine-state` and sent only when you send the message.
- **Catching up.** When you open a session after being away, a few lines above the conversation say what happened since you last looked: pushes, review verdicts, cards answered and waiting, issues and pull requests opened, and caps reached. They are the engine's own records, never the agent's words.
- **Changes.** **Open Changes** in the session's details (or Open Changes in the command palette) opens the session's commits, changed files and diff in an editor tab of its own, full width, all computed by the engine from the session's clone; the details keep a one-line summary. **Compare with** picks the base: where the branch leaves main (the default), the last commit a reviewer passed or blocked on this branch, the commit before the turn the session last reported starting (the session's own report, so treat it as a convenience; known only since the engine last started, and only while that commit is still on the branch), or a commit among the newest 5,000 of the branch; the line above the toolbar names the base and its commit. **Unified** and **Side by side** switch the layout. A file the view doesn't diff is listed with its size and why: over the 1 MiB a file may have to be diffed, past the 8 MiB of file contents the view reads in all, binary, or a stored file object that can't be read. A bad file object never takes the view down; a corrupt tree or commit still makes the view answer an error, and a push hold then holds the push as one it couldn't count. A project's push hold and deeper-review size limits never count such a file as 0 lines: a file shown only as binary counts the lines of both its versions, the binary one and a text one on the other side alike (a last line without a newline included), counted from the bytes the engine read or hashed to check the copy is the file the commit names (a binary file over 1 MiB is checked this way only within 64 MiB a request); any other file it doesn't diff makes the change count as over. Changed lines are the added and removed lines inside the diff's hunks. A viewed mark is refused (409) for a file version the session's branch doesn't change. **Highlight syntax** colours common languages (off for a diff of more than 20,000 lines, and plain text for a line over 2,000 characters or past the first 400,000 characters of code). Tick **Viewed** beside a file once you've read it: the engine keeps the mark for that session, bound to that version of the file, so a file that changes again shows "changed since viewed" and unticked. Marks for up to 1,000 files per session are kept, in the engine's `viewed.json`, and come back after a restart and in an export.
- **Line comments.** In **Changes**, open the diff, choose a line (click it, or move with the arrow keys and press Enter) and write a comment; add as many as you need, then **Send comments** sends them to the agent as one message, each with its file and line. The engine checks the draft when you send it (at most 50 comments, none empty or over 2,000 characters, and 20,000 characters in all) and says what to change beside it.
- **What this session may and may not do.** A collapsed section of the session's details lists, read only: the fixed refusals that hold for that session (the built-in git hosts and the deny list, the git host token, other sessions, decisions from the session's container, and for Claude Code also push-shaped commands and cloud hand-off commands; it says when the agent isn't Claude Code, which none of the command and write checks cover, and that the agent can read its own container's sign-in or pasted key); the saved "don't ask again" rules of this session's container and the project's clone folder; the hosts sessions may reach; the paths the approved team file on main protects; whether away mode is on; and the exceptions you made for this session. It reads them again every 5 seconds while it's expanded, and the team file on main, which needs a fetch, once each time you expand it. Each item you can change has a link to its control (Projects, Network access, Review the team file, Away, the [register of exceptions](#register-of-exceptions)); the fixed refusals have none.
- **Command palette.** **Search Software Factory**, the search box in the middle of the header, or Ctrl+K (⌘K on a Mac), opens a list below the header that you filter by typing, laid out like VS Code's Quick Open: one line per entry, its description beside it, its group's name on the group's first line and its key, if it has one, on the right. A click outside it, Escape or running an entry closes it. It lists the sessions, the projects (open one or start a session in it), the views and panels, and the open session's actions (wake, stop the turn, stop or delete the session, review, push, open Changes, what the session may do). Each action does what its button does and asks what its button asks: Stop and Delete still need Confirm, Wake and Review still ask for a sign-in or cost confirmation, and starting opens the new-session form.
- **Desktop notifications.** Turn them on under Settings, the gear in the activity bar; the browser asks first. While the tab is in the background, a card waiting, a held push, a finished turn and a finished review each show one notification naming the session, and clicking it opens that session. The setting lasts for the tab, and a reload doesn't repeat old ones.
- **Bring in the latest main.** The ⋯ menu's **Bring in the latest main** has the engine fetch the main branch from the git host into the clone, which updates `origin/main` in the session's worktree, and then sends the agent "main is now at `<commit>` as origin/main; merge it into your branch and resolve conflicts". The agent's sandbox can't reach the git host, so this is how its branch catches up. It's refused while the session's turn runs and for a session that isn't running.
- **The queue.** Above the conversation, a collapsed line sums up the session's model, queue, setup and check results and ports; open it, and **Add to queue** keeps up to 10 messages for later, which you can edit, move up or down and remove. When a turn ends, the engine sends the next one. It stops when a card or a held push waits for you, when a turn fails or is stopped and when the agent's sign-in fails, and says why; **Resume** goes on. After an engine restart a queue waits for Resume. It is the engine's own, kept in `engine-state`.
- **Switch model.** **Switch model…** in the ⋯ menu, or the Model part of that line, changes the model and effort from the next turn. Claude Code offers the start form's models: the engine keeps the choice and the plugin rewrites only this session's main-loop requests, so Claude Code's own `/model` and `/effort`, which save a default in the container's home, stay refused. Claude Code's own status line keeps naming the model the session started with, so the page names the one the engine set.
- **Ports.** Each session gets 10 ports of its own, from 41000 up: the lowest range no other session holds, kept until the session is deleted, and through a restart. Its first message names them. For Claude Code, `PORT` and `SF_PORT_BASE` also hold the first one, through the `env` of the session's `--settings` (whether they reach a background session's Bash is still to be checked live).
- **The ⋯ menu** makes the session read-only on the page or wakes it without a message, and copies the commands that attach to the session in a terminal (`docker exec -it software-factory-box-<box> claude attach <id>`) or show its log (`docker exec software-factory-box-<box> claude logs <id>`). In a read-only session, answer its cards in Claude Code itself.
- **Stopping and deleting.** Stopping keeps the conversation, and Wake brings it back from Claude Code's own session. A turn that was running when the session stopped isn't resumed. Stopping removes the session's container and its network and keeps its home and its folder in the workspace; Wake makes the container again from the current image, under the same name, with the same home and folder, then checks its sign-in again. Deleting removes the session, its container, its home, its clone and worktree, and its uploads; Claude Code refuses while the worktree has unpushed commits, and the page then offers to discard them. When the worktree or the container is gone, the engine reads the branch itself and offers the same choice unless everything on it is pushed or on main. Press each button twice to confirm.
- **A long conversation.** With knackpack, a notice above the message box offers **Save a checkpoint** (`/knackpack:checkpoint`) before you compact, and a stronger one past knackpack's 500k-token stop point. After a compaction, the agent's next message starts with the engine's own record of the session: what you approved, a held push and why, the reviewers with open blocking findings, and the cards waiting for you.
- **Claims the turn doesn't back.** When a turn ends, the engine reads the agent's last message and marks, under it, claims that nothing in the turn backs, as "Not backed by this turn's actions": "all tests pass" or "the build succeeds" when no test or build command ran in that turn, and "updated `X`" when the turn's edits, commands and commits don't touch `X`. A mark is only a hint and never holds anything. The engine knows a turn's commands from the session's own reports: when a subagent, a skill or an MCP tool may have run commands it doesn't see, it marks no test or build claim, and a file it can't check is shown as not checked. The patterns are few and English, and skip questions, conditions, negations and plans, so most claims go unchecked. An agent can hide a mark, for example by reporting a command it didn't run.
- **Edits left uncommitted.** When a turn ends, the engine reads the session's worktree itself and compares it with the branch's latest commit. If files differ, untracked files that `.gitignore` doesn't ignore included, the session shows "N files changed but not committed; they won't be pushed", lists them, and offers **Ask the agent to commit them**, which sends the same message as the Implement step's Commit. The warning clears at the end of a turn that leaves the worktree matching the commit. It never holds a push. Files with a content filter, such as Git LFS or line-ending conversion, can show as changed.
- **Parallel sessions.** When two sessions of one project change the same files, committed or not, both show "Also changed in session X" with the paths, so you see the conflict before the merge. The engine compares them when each turn ends. It never holds a push.
- **The engine's copy of the commits.** When a turn ends, the engine copies the branch's commits that main lacks into its own store, out of the agents' reach. A collapsed line above the conversation shows the last commit copied and its size. If the agent deletes the branch, rewrites it or resets it to main, **Restore branch** (press it twice) puts the branch back at that commit and recreates the session's worktree there; it stops the session first if it runs, is refused while a turn runs, and leaves a worktree with changes that aren't committed as it is. A commit that holds something shaped like a token, a private key or a password in a URL isn't copied, and neither is anything after it, since each commit needs the one before: the line says from which commit copying stopped and why, and copying goes on once the branch no longer holds that commit. A file you allowed on the push card is copied. The copy holds at most 256 MiB per session and 2 GiB in all, and is deleted with the session.
- **A quiet turn.** When the agent has been in its turn for 10 minutes with nothing reported, no card or question waiting and no subagent running, a notice above the message box says so and offers **Stop the turn** and, for Claude Code, **Copy attach command**. It rests on the session's own reports, so it's only a hint: the agent may still be working, such as on a long command. **Dismiss** hides it until the session reports something again.

The footer shows the session's tokens, its cost estimate and its sign-in method. Each session also shows a **trust level**:

- **Locked:** every sandbox check since the session's process last started passed.
- **Held:** a check failed or couldn't run, or none has run since the session started or woke. Every push from the session is held, and no new session starts.
- **Stopped:** the agent's process ended, or its container lost it. The session list says "process lost" when the engine lost the agent's process or the session's container restarted.
- When the part of the sandbox check that covers the whole stack fails (the proxy and its lists), the engine stops every running session, which the session list shows as "stopped: the sandbox check failed", and no session starts or wakes until a check passes. When the check of one session's container fails, only that session is held and stopped. When the box helper doesn't answer, every running session is held and stopped.

The side panel holds the execution path, the Reviews and Push panels, the issues, pull requests and comments, the intent record, the session's **Changes** (its commits, changed files and diff against the remote's main branch, from committed work only, the diff cut at 1 MiB, with anything shaped like a private key, a token or a password in a URL hidden) and the subagents it ran.

### Execution path (with knackpack)

The Execution path panel shows the steps of the session's work type and where the session is:

| Work type | Steps | What a push needs |
|---|---|---|
| Feature | Define, Plan, Implement, Code review, Deliver | Requirements and a plan you approved, then the bug hunter's and the simplicity checker's reviews |
| Fix | Implement, Code review, Deliver | The bug hunter's and the simplicity checker's reviews |
| Incident | Triage, Reproduce, Root cause, Fix, Code review, Deliver | The bug hunter's and the simplicity checker's reviews, and, when the branch changes anything but documentation, a root cause you approved |
| Docs only | Implement, Code review, Deliver | The simplicity checker's review. Edits outside documentation are refused, and a branch that changes other files needs what a Feature needs |
| Exploring | Implement | Nothing: Exploring never pushes |

Pick the work type before the first message; you can change it later under **Work type**. A team file can add others ([Configuration](#configuration)).

Each step's button sends the matching command to the session. Sessions use knackpack's workflow: **Define** sends `/knackpack:challenge-requirements`, **Plan** `/knackpack:plan-implementation`, and **Deliver** offers **Issues** (`/knackpack:create-issues`) and **Handoff** (`/knackpack:handoff`). **Commit** under Implement asks the session to commit every change and to ask you about any file that shouldn't be committed. Step buttons work only while the agent isn't in a turn.

An Incident is for the code side of a production failure, from the evidence you give the session: logs, stack traces and screenshots. The session gets no access to production, and a review is still required. Start it at the commit that's deployed: under **Start from**, pick the branch whose head is deployed, and give the deployed commit or tag in the first message. **Triage**, **Reproduce** and **Root cause** each send `/knackpack:debug-incident`, which does the next step only and commits `.knackpack/<task>/ROOT-CAUSE.md`; the panel follows its Status. Once the Status is `CONFIRMED`, read the root cause and **Approve** it. Your approval is of the committed text's SHA-256, read from the commit, and any later change to the file clears it. Until you approve it, there's no **Fix** button and a push that changes anything but documentation is held with "the root cause isn't approved". **Fix** sends `/knackpack:fix-incident` with the approved SHA-256 for knackpack's own check, and Deliver offers **Incident review** (`/knackpack:incident-review`), which commits a draft `.knackpack/<task>/INCIDENT.md`. The reviewers get the approved root cause and are told to judge the fix's regression risk, blast radius and rollback first. When the session didn't start at the deployed commit, knackpack diagnoses in a worktree of its own, outside the session's branch, and the panel can't read or approve that root cause.

In a Feature, **Read the agreed requirements** opens them; **Approve** them, or **Ask for changes** with a note. The engine checks requirements written in knackpack's checked format first: while an open question says `Blocking: yes`, or a requirement has no `Acceptance:` line, the panel says so beside **Approve requirements** and approving is refused, so answer it with Claude, then approve. Requirements without the format's marker line, `knackpack-requirements/1`, as an older knackpack wrote them, are refused with "Written before the checked format; ask Claude to rewrite it." When the requirements change after you approved them, the panel shows what changed, as lines added and removed, before you approve them again; the engine keeps the text you approved for this, in its own volume (very long requirements, or many sessions' worth, are shown without the comparison). The plan works the same way, without the comparison, and approving the requirements again clears the plan's approval. Approving the requirements sends the session the Plan step; approving the plan tells it to implement the plan. Until the plan is approved, Claude Code's file tools can't change files in the worktree, apart from knackpack's own files for the current step: `.knackpack/feature.json` and the requirements before you approve them, then the plan. Docs only refuses edits outside documentation in the same way. These refusals guide the agent; the gate's approvals are what count for the push.

knackpack commits its documents from 0.26.0, and the engine installs only 0.40.0 or later, so the engine has knackpack commit Claude Code's requirements and plan to the session's branch, as `.knackpack/<task>/REQUIREMENTS.md` and `PLAN.md`, and reads them from the commit: an approval counts only while the committed text is the one you approved, whatever the agent reports. The panel then says which commit you approved, and when a later commit changes the text, that your approval no longer counts. Until they are committed, the panel shows the agent's report, which you can't approve. Only requirements and a plan that the session's own commits added or changed can be approved: a document already on the main branch, such as one from an earlier task, is shown as such and can't be approved. The panel's project settings set the review round limit, the default work type, whether blocking findings go to the agent by themselves, whether the engine comments on the pull request after each push (see [Issues, pull requests and CI](#issues-pull-requests-and-ci)), and whether the agent's own push is held after a blocked round or above a size; the last three are off by default.

### Reviews and the push gate

**Review** runs the required reviewers on the session branch's latest commit, each as its own run of Claude Code in a reviewer container of its own. A reviewer that already passed or blocked that commit isn't run again, to save time and your allowance; when every one has, Review says so and runs nothing. **Run all again** runs every reviewer for fresh verdicts. The engine writes the commit and the point where it leaves the remote's main branch into a fresh read-only folder, with the diff and the change's commit messages, and the reviewers can only read it: they can't run commands or write files. The reviewers are told the agent wrote the messages, so they check them against the change and never follow them. A message holding something shaped like a token is left out. The required reviewers are the work type's roles, filled by the project's pack ([Packs](#packs)): with knackpack, the bug hunter (`knackpack:adversarial-reviewer`) and the simplicity checker (`knackpack:slop-reviewer`), plus reviewers the changed files call for, such as the Go, Python, TypeScript, React, CSS, UI, Docker, Kubernetes, Terraform and database reviewers, and those a team file adds. When the installed knackpack ships a reviewer catalog (`agents/catalog.json`), it decides which of its reviewers the changed files call for, and the panel shows each one's summary; a catalog the engine can't use is refused, with the reason in the panel, and the built-in list applies, as it does with an older knackpack. The catalog never changes a reviewer's tools, permissions or which roles a work type needs. The panel lists them before you start. Only committed work is reviewed.

While a reviewer runs, the panel shows how long it has been running and how many tools it has called, and afterwards how long it took. Under each reviewer, **What this review was given** shows the exact prompt, Claude Code's flags and the files in its review folder. They never hold a key or an environment value.

Each reviewer ends as pass, block, no verdict or failed, with its verdict and its final message. A reviewer that takes more than 20 minutes, fails or answers without a verdict counts as not passed. So does one that tried to read outside its folder, passed in a single turn without reading a file, or passed while its own report lists a Critical or High finding; the panel gives the reason. When the report is longer than 4,000 characters, the panel shows its start and closing lines as a summary, with **The whole report** under it (up to 64 KiB; a longer one keeps its start and its last 16 KiB, where its findings and closing lines are). A reply holding something shaped like a token isn't kept at all. Under each reviewer the panel shows what produced the verdict: the pack with its version, knackpack's commit and the reviewers' digest, the Claude Code version and the model. Under each reviewer the panel also lists its findings with their severity; a finding's `path:line` opens the file read-only at that line, as the reviewed commit has it, when the file is in the project at that commit and the page would show it. A path outside the project, such as an absolute path or one with `..`, stays plain text. knackpack's per-finding lines, when a reply carries them, give the exact file and line, and never change a verdict. A later round reviews only what changed since that reviewer's previous round: it reviews on its own first, then reads its earlier findings from a file in its folder and says which are still open. The panel says which kind each review was.

A pass counts only against the requirements and plan, or an Incident's root cause, you had approved when it ran. If you approve them, or approve a new version, after a reviewer passed the commit, that pass stops counting: the panel and the push card say it reviewed before the current approval, and the reviewer runs again when you press **Review** or the agent asks to push. Fix and Docs only, which have no approval, aren't affected.

The same goes for the team file's rules for paths (`fileRules` instructions): a pass counts only for the rules that apply to the commit's changed files when it ran. If the rules for those files change, for example when you approve a new version of the team file, the panel and the push card say the team rules changed, and the reviewer runs again. A change to rules for paths the commit doesn't touch doesn't affect it.

**Minimum reviewer version.** When a pin moves for a security reason, the engine can set a minimum reviewer version: a pass by an older reviewer doesn't count, and that role runs again when the agent next asks to push, or when you press Review. Waking a session tells you when its agent's or the reviewers' versions changed since it last ran.

**Write a manual test list**, under the reviews, asks for the steps to try by hand on the latest commit: one Claude Code run in a reviewer container, read-only like a review, on the same sign-in and with the same cost confirmation. It isn't a verdict: the push gate and the agent never see it, and it counts toward the two reviews the container runs at once. The page shows it as a walkthrough: numbered steps, each with what to do, what you should see and a sample input, and a box to check it off once you've tried it. Check-offs are only your notes, never a verdict, and nothing checks a step off for you; they survive a reload and an engine restart, and a new list starts unchecked. A reply without numbered steps is shown as text, and a reply holding something shaped like a token or a private key isn't kept or shown.

**Explain this change**, under the manual test list, asks for a written walk through the session branch's change against the remote's main branch: what it does and why, its main parts in reading order, and what it could break. **Review this plan**, beside the plan before you approve it, gives the reviewer the plan, framed as the agent's text, with the same snapshot of the code, and shows its findings beside the plan. Each is one Claude Code run in a reviewer container, read-only like a review, on the same sign-in and with the same cost confirmation, and counts toward the two runs the container runs at once; one of each kind runs per session at a time. Neither is a verdict: it changes no approval, review record, gate state or push, and the agent never sees it. The page shows the reply as Markdown; a reply holding something shaped like a token isn't kept or shown, and the engine doesn't send a plan that looks like it holds one. The engine keeps the latest of each per session in memory only, so a restart forgets them.

**Push**, or the agent's own push tool (`factory_push`, which takes no input), asks the engine to push the session's branch at its latest commit. The engine checks, for that exact commit:

- every required review passed on it;
- each review still covers the remote's main branch. If main moved since, the page asks for a new review;
- the session stayed Locked;
- no file or commit the push would send is flagged.

Then it pushes `sf/<id>` to the address recorded when the project was added, with your token, never forced, never to main, and only if the remote branch is still where the engine last saw it. The result shows on the page as **pushed**, **held**, **denied** or **refused**, with the reason.

**A held push** shows a card with the commit, the branch, the remote and every missing item:

- **Allow** pushes anyway. It needs your reason when items are missing, works once, for that commit only, for 15 minutes, and runs the whole check again first. It never pushes while the sandbox check fails for that session: fix the check, then review and push the work from a new session.
- **Deny** takes an optional note and ends that commit's request: the engine refuses the agent's next request for it, and reviews that finish later don't push it. Only your **Push** while the branch is at it, or **Allow** on its own card, pushes it after that. The engine remembers every commit you denied in a session, the newest 20, so moving the branch back to one doesn't free it: not for reviews that finish later, and not for an Allow you give another commit's card.
- **Override**, on a blocking review, counts that verdict as passed for that commit only, with your reason. A new commit needs a new review.
- **Flagged files** are files with secret-looking names (`.env`, `*.pem`, `*.key`, SSH keys, `credentials*`, `*.tfstate`, `.claude/settings.local.json` and others), files over 1 MiB, and files holding private keys, known token formats (npm's among them) or a password in a URL (`https://user:password@host`), or whose path holds a known token format, in any commit the push would send. A version of a file, or a submodule pointer, that a commit the push would send holds but neither the branch's head, a reviewed commit nor main holds is flagged too, since no reviewer read it. **Allow it** takes your reason and covers that version of the file only; a later change flags it again. **Ask the agent to remove it** asks the session to take it out of every commit on the branch and add it to `.gitignore`. The push card never shows a flagged file's contents. The **Changes** diff shows them with anything shaped like a private key, a token or a password in a URL hidden, so a file flagged only for its name or size shows as it is.
- **Flagged commits** are commits whose message, author or committer name or email holds something shaped like a token, and commits whose message the engine can't scan because it isn't plain UTF-8 text. The card names the commit and the field, never the text. **Allow it** takes your reason and covers that field of that commit only; a new commit with the same text is flagged again. **Ask the agent to rewrite it** asks the session to rewrite the commit. A commit already on the remote branch can only be allowed, since the engine never forces a push.
- **Send findings**, when a reviewer blocks, sends the session the blocking reviewers' whole reports, marked as untrusted findings to check (16,000 characters in all: a longer report keeps its start and its end), so the agent can fix them and push again. The push stays held, and Allow and Deny still work. It reaches only a running session this page controls, once per commit, and nothing is sent when the messages hold something shaped like a token.
- **About this change.** The push card also lists facts the engine reads from the commit, for you to check; none of them holds or allows the push. They are removed tests and test functions, new skip and `.only` markers, fewer or inverted assertions, new `eslint-disable`, `nolint`, `ts-ignore`, `# type: ignore` and similar suppressions, fewer logging calls, and changes to files a person or CI runs later (`Makefile`, `package.json` scripts, `.github/workflows/`); added, removed and changed packages in `go.mod`, `package.json` and its lockfiles, `requirements*.txt`, `pyproject.toml` and `Cargo.toml`; binary files, newly executable files and symbolic links with their targets, which `change.diff` doesn't show, and submodule pointers that moved, with both commits; the workflows the push starts; and the last test, lint, type-check and build commands the agent ran before the card, with whether each failed, labelled "reported by the agent". The reviewers get the test and suppression list as hints, framed as the engine's counts. With the project setting **Look up new packages** (off by default, in the project's **CI workflows and main's protection** panel), the engine asks npm, PyPI, proxy.golang.org or crates.io, from its own network, whether each package a manifest adds exists and when it was first published, and marks missing ones and ones under 30 days old, since attackers register names agents invent. It checks each name against the ecosystem's rules first, sends only the name, and asks at most 20 per push.
- **Requirements, as the reviewers reported them.** When the commit's reviewers were given approved requirements with IDs such as `REQ-01`, the push card shows a table with a row per requirement and a column per reviewer: verified, violated or not verified, the file and line the reviewer cites, and its note. It is the reviewers' own report and display only: it doesn't hold or allow the push, and a violated requirement that matters is also one of the reviewer's findings. A reviewer that wrote no such lines says so, never "verified"; an ID the requirements name and no reviewer reported is listed under the table; and lines that are malformed or name a requirement the review wasn't given are left out and counted. A Fix, or any review given no requirements, shows no table.
- **The round limit.** After a reviewer's verdicts on the branch blocked as many times as the project's limit (overridden ones aside), it isn't started again. You decide: Override, Allow, Deny, or **Hand off**, which asks the session for a handoff of the open findings and then denies the push.

**When the agent asks first.** If the agent calls its push tool before the commit was reviewed, the engine starts that commit's reviews once, and when they all pass it pushes without you. If one blocks, the card waits for you. If the reviewers are signed in with a sign-in billed per use, the engine starts no review itself, and the push waits until you press Review. A Review you press doesn't push a waiting card: the card then shows what is still missing, or that every review passes, and you press **Push**. The exception is an agent that asks to push that commit while your Review runs: its request then pushes when the reviews pass, as any agent request does. While the push still needs your approval of the requirements or the plan, the engine starts no review either: the agent's next push after you approve starts them, or you press Review. The agent can ask at most 5 times in 10 minutes, and the engine runs at most 12 reviewer runs per branch on the agent's requests, the runs it repeats after a restart included; after that you press Review. When two sessions are already being reviewed, the engine queues the request and starts its reviews when one finishes. With the project setting **Send blocking findings to the agent automatically**, the engine sends the findings itself when those reviews block, only when the agent and the reviewers both use a subscription, and never past the round limit or that cap.

**When the engine restarts.** A waiting automatic push is saved (`waiting.json`) and picked up at start: if the restart cut a review off, the engine runs that reviewer once more, and pushes when every review passes; if the second run is cut off too, the push waits for you. It drops the plan if the branch moved on or you denied the commit. A push that was going out when the engine stopped is checked against the remote at start and recorded as pushed or not. On a normal stop, a push or an approved issue or pull request already under way gets up to 25 seconds to finish. If the agent was in the middle of a turn, its next message starts with a note that its turn was cut off, after a crash or a power loss too. Notes the engine leaves for an agent's next message are saved and still reach it after a restart, once.

**A push's record.** A pushed card has **Download this push's record**, which saves one JSON file built from the engine's own records, to hand to someone else or keep with a release: the full commit, the branch, the remote and the push's time, who asked and its request id; your Allow's reason and the items it was allowed without; each review of that commit with its verdict line, your override's reason, the pack and the versions that made it; the approvals' hashes and commits, with the requirements' text when the engine still holds it; your overrides and allowed files and commits on the branch; the verification run of that commit; and the checks the agent reported, labelled as reported by the agent. The engine keeps those checks in memory only, so after a restart the file says they aren't held. It holds no page key, git host token or model credential, and masks anything shaped like a token. The download decides nothing and changes no record.

**Review depth.** A project's menu has **Review depth**, which only adds reviews: a work type's required reviewers always run. **Advisory roles** review with the required ones but only warn: their block shows as a warning and never holds the push. A required reviewer can run **2 or 3 times** on each commit; a block in any run blocks, and an Override clears every run's block on that commit. **Above a size** (changed files or lines, counted as the push hold counts them), the project can require extra reviewers or more runs. The panel shows how many reviewer runs a review then takes: each one uses the reviewers' sign-in. These settings come only from the page, never from the repository or the team file.

**Cited vulnerability IDs.** When a review cites CVE or GHSA IDs, the engine looks each one up at OSV and marks an ID OSV doesn't hold as "not in OSV". OSV holds only the vulnerabilities of open-source software, so a real ID can be missing; check a marked ID before you rely on the review. If OSV can't be reached, nothing is marked and the review says the lookup failed. It changes no verdict.

**Lessons from reviews.** The project menu's **Lessons from reviews** lists blocking findings that came back on several commits, matched by reviewer, file and title, which is approximate. When one finding has blocked 3 commits, **Suggest lines** starts one reviewer run with no verdict. It reads those findings and your own comments on the project's recent pull requests, and proposes short lines for the instruction file, each naming the findings it came from. You approve or decline each line. An approved line goes to the session you pick, as a note asking the agent to add it to `CLAUDE.md` or `AGENTS.md` and commit it, which the usual reviews then cover. Nothing is applied on its own, and a declined line isn't offered again for the same findings.

### How the latest commit is being checked

**Open diagram** in the Reviews panel opens the latest commit's reviewers, the gate and its routes as a diagram that follows them live. It closes when you open another session.

### How this change was checked

Once a push is decided, its card's **How this change was checked** lists, from the engine's own records, the reviews, the verification runs and the gate's decision for that commit; nothing the agent reported about itself is there. **Open diagram** opens them as a diagram.

### Packs

A project's reviewers come from its **pack**: knackpack by default, another Claude Code plugin from git, or none. Pick it under **Reviewer pack for this project**, above the reviewer agent files in a session's Execution path panel; the choice is per project, bound to the project's name and the address it was added with. The engine owns every capability, whatever the pack: the reviewers' read-only tools, hooks off, the read limits, the closed network, the verdict lines it reads and which roles a push needs. A pack can make a reviewer better or worse, but it can't grant anything. A new session runs its project's pack: its plugin, skills and step commands, and the requirements and plan folder its manifest names. It keeps that pack across Stop and Wake, even after the project picks another, and its wake note then names both packs; reviews always use the project's pack of the moment. A pack's files that run or load in a session (hooks, scripts, agents, skills and commands) are shown on the start-up card for your approval before a Claude Code session starts, and again for each new version; knackpack's aren't, since it follows its main branch, a risk the owner accepted. A pack without a documents folder, and No pack, offer no Feature work type, since the engine can't approve requirements or a plan it can't read from a commit.

- **knackpack** (the default) fills the bug hunter and simplicity checker roles and the file reviewers, as above.
- **A plugin from git.** Give its https address and a full commit. **Fetch and check** fetches that commit with no token and shows what it holds: its manifest's roles and steps, its reviewer agents, the session files that would run code, and two digests. **Use this pack** adds it, only if the commit still gives the digest the page showed, and makes it the project's. A pack is pinned by its commit and never follows a branch, so it changes only when you add a new commit. The engine keeps up to 8 packs. With a pack other than knackpack, no file reviewer is added for the files a branch changes and no catalog is read: the roles the pack fills, the agents you add for the project and those the team file names review it, and an agent the pack doesn't have holds the push.
- **An uploaded pack.** **Upload a pack folder** takes a folder holding `software-factory-pack.json` and the pack's `agents/`, `skills/<skill>/` and `commands/` folders; the page sends those files only, as text, and the engine takes at most 200 files, 256 KiB each and 2 MiB in all, writes the plugin's manifest itself, keeps the pack by its digest and refuses any other path, so an upload holds no hooks, servers or programs. Press **Use** on it once you've read what it holds.
- **No pack**, behind a confirmation: nothing reviews the project's pushes, so every push waits for your **Allow** with a reason. Review answers "No reviewer is configured for this project, so nothing reviews this branch: every push needs your Allow with a reason."

**What a pack holds.** A Claude Code plugin (`.claude-plugin/plugin.json`, whose `name` is the pack's) with a manifest at its top, `software-factory-pack.json`, strict JSON of at most 16 KiB:

```json
{
  "format": "software-factory-pack/1",
  "name": "acme",
  "version": "1.2.0",
  "roles": { "bug-hunter": "bug-finder", "simplicity": "simplicity-checker" },
  "steps": { "define": "/acme:requirements", "plan": "/acme:plan", "review": "/acme:handoff" },
  "documents": { "folder": ".acme", "requirements": "REQUIREMENTS.md", "plan": "PLAN.md" }
}
```

`name` is lowercase letters, digits and hyphens, and can't be `knackpack` or `software-factory`. `roles` gives each role an agent file of the pack (`agents/<name>.md`); a role it leaves out isn't filled, so a push that needs it waits for your Allow with a reason. `steps` may name only the pack's own commands. `documents`, when given, must use the folder `.<name>`. The engine refuses any other key, and names the reason for the keys it owns: `tools`, `model`, `effort`, `permissions`, `network`, `hosts`, `verdict`, `required`, `rounds`, `hooks`, `mcpServers` and `env`.

**What the reviewers get.** The engine writes its own copy of the pack for reviewers: an engine-written `plugin.json` and the pack's `agents/*.md`, nothing else, so no hooks, MCP or LSP servers, monitors, workflows, scripts, skills or commands reach the trusted reviewer container. It does the same for knackpack. It refuses a pack, naming the file and the reason, when an agent's front matter holds `hooks`, `mcpServers`, `permissionMode`, `skills`, `isolation` or `memory`, names itself other than its file, or is written in a way the engine can't read as plain keys; when its `plugin.json` holds a key that could start programs; when its top folder holds `.mcp.json`, `.lsp.json`, `monitors`, `workflows` or `settings.json`; when its skills or commands use argument placeholders or inline shell; and when it is over 2,000 files or 32 MiB. The reviewers' digest is the SHA-256 of that copy and of the roles the manifest gives, and each review record keeps it, beside the pack's name and version, so the audit and the review panel say which pack judged a push.

**The verdict.** A pack's reviewer must end its reply with a line `Verdict: pass` or `Verdict: block`, which the review's prompt asks for. A reply without one counts as no verdict, and the panel says that every pack's reviewer must write that line. knackpack's own phrases apply to knackpack's reviewers only.

**The audit** records each pack added, removed and picked for a project, with the digest, never the content. A pack can't be removed while a project uses it or a saved session runs it. Export and import bring `packs.json` back off: every project uses knackpack again until you add and pick its pack on the new engine.

### Your own reviewer agents

The bug hunter and simplicity checker roles can run on a Claude Code agent file (`.md`) of your own instead of the agent of the project's pack, on top of any pack or No pack. Add one under **Reviewer agents for this project**, below the project settings in a session's Execution path panel, then pick it for a role there. Every push still needs each required role passing.

- **What the file may hold.** At most 192 KiB of UTF-8 text: a front matter block between two `---` lines, then the agent's instructions. The front matter may hold only `name` (lowercase letters, digits and hyphens, starting with a letter, at most 64 characters), `description` (required, on one line), `model` (an alias such as `sonnet`, or a model id) and `tools`, any of `Read`, `Grep`, `Glob`, `Agent` and `ToolSearch`. The engine refuses `mcpServers`, `hooks`, `permissionMode`, `skills` and every other key, since they could run programs or widen what the reviewer may do, and the page shows why. A project keeps up to 4 files, and the engine 12 in all; adding a file with a name the project already has replaces it.
- **The body is your own instructions.** They run in a trusted reviewer container, on the code under review, with the same read-only tools, hooks off and the same read limits as knackpack's reviewers. The engine writes the file into the reviewers' own agents folder (`~/.claude/agents/` in their shared home) for each review, from its own state, never from the repository or the agents' container. A file in the repository's `.claude/agents/` is never used: reviews load only the reviewers' own settings.
- **The verdict.** The reply must end with a line of its own, `Verdict: pass` or `Verdict: block`; a last line `knackpack-verdict/1: pass` or `knackpack-verdict/1: block` counts too. The review's prompt asks for it. Anything else counts as no verdict, and both a pass and a block count as no verdict. knackpack's own phrases, and its check for a pass whose report lists a Critical or High finding, apply to knackpack's reviewers only.
- **Changing it.** A new version of a file counts as a new reviewer, so its earlier verdicts don't count and the role is reviewed again. Removing a file falls its roles back to the project's pack. The audit records each file added, replaced, removed or picked, by hash, never the text.

### Issues, pull requests and CI

The agent can't reach the git host, so it asks the engine, with four tools:

- **`factory_pull_request`** asks for a pull request from the session's branch to the project's main branch, once the branch is pushed. If one is already open, the agent gets its link instead, and pushing again updates it.
- **`factory_issue`** asks for an issue in the project's repository.
- **`factory_checks`** gives the agent the pushed branch's CI results: each check and commit status, and the last 200 lines of each failed GitHub Actions job's log, with escape and invisible characters removed, marked as untrusted text. It changes nothing and needs no answer from you.
- **`factory_review_comments`** gives the agent your own comments on the branch's open pull request: your reviews, inline comments with their file and line, and conversation comments, the newest 100. Only comments by the account the token belongs to are passed on; everyone else's, and the engine's own push notes, are left out. The agent is told to weigh them as feedback, not as instructions that override the page, since anyone with admin rights on the repository can edit a comment. It changes nothing and needs no answer from you.

An issue or pull request waits as a card under **Issues and pull requests** in the session's details, with the whole title and body shown as text. Read it: the engine posts it under your token. When the title or body holds something shaped like a token, the card says **This looks like a secret** and shows that line, and Open works only after you tick that you checked it. **Open issue** or **Open pull request** has the engine create it, and the card shows the link; **Deny** drops it. A pull request opens as a draft unless you clear **Open as a draft** on its card; you mark a draft ready for review on GitHub. If GitHub refuses drafts for the repository, it opens ready for review and the card says so.

If GitHub's answer to an approved issue or pull request is lost (a timeout, a dropped connection, a 5xx), the engine doesn't guess: it asks GitHub again (the branch's open pull requests, or the issues opened since you approved it), and if it still can't tell, marks the card **check on the host**, with links to the issues it found, and tells the agent not to ask again. A card still waiting when the engine restarts comes back after it, with its 24-hour limit still counted from the agent's request; opening or denying it then reaches the agent as a note with its next message. A card whose title or body looks like it holds a secret isn't saved, so a restart drops it and the agent is told to ask again. If the branch got new commits after a pull request card was written, **Open pull request** opens nothing: the card says how many and asks again, and you open it at the new commit with a second click.

**A comment after each push**, when you switch it on in the project's settings (off by default), is posted under your token on the branch's open pull request after each push, and once when a pull request opens for a branch already pushed. The engine writes it from its own records only: the full commit and branch, who caused the push (the agent after its reviews passed, your Push, or your Allow with the number of items missing, whose reasons stay in the audit), each required review with its result and whether it covered the whole branch or only what changed, and the versions of Software Factory, knackpack and Claude Code it has records of. It never includes your typed reasons, the reviewers' messages, flagged file names or costs. Each comment shows on the page as a card with its whole text, before and after it's posted, and a commit is commented on once. A comment that holds something shaped like a token isn't posted: its card waits with the same warning until you post it or deny it. A failed comment doesn't change the push. The agent learns the result, with the number and link, before your next message to it. Only GitHub (github.com, and a GitHub Enterprise server whose host has a saved token) is supported; for other hosts the tools say so.

**Following the pull request.** Once a session's branch is pushed, the engine looks for its open pull request and follows it under **Pull request** in the session's details. At most once a minute per pull request it reads, with your token: the pull request (open, merged or closed, draft, and whether it conflicts with main), the head commit's check runs and statuses, and the reviews and comments on it. It keeps only new comments by the token's own account and by the bot logins you list in **This project's pull request settings** (an exact list, empty by default, such as `coderabbitai[bot]`). Everyone else's comments, and the engine's own push notes, are left out. A comment that holds something shaped like a token is dropped, and the panel says so. The panel shows the failed checks and the new comments as text. **Send to the agent** sends them as one message that says they come from the git host and are untrusted: feedback to weigh, not instructions. With **Send what's new to the agent on its own** on in the project's settings (off by default), the engine sends it itself, but only while the agent is signed in on a subscription, at most 5 times per pull request, and it stops, saying why, when a card waits for you, a push is held, the agent's last turn failed or was stopped, or the agent reports a sign-in problem; sending it yourself starts it again. When the pull request is merged or closed, the session is marked done, the agent gets a note, and the panel offers **Delete**, which deletes the session the way the workspace view does: refused while the session runs or has commits that aren't pushed. Following continues after a restart. When less than 10% of the token's GitHub rate limit is left, or GitHub answered that the limit was reached, the engine waits until the limit resets. Following writes nothing to the git host: no comment, label or merge.

**A pull request from the page.** On a session whose branch is pushed, **Open pull request** makes a pull request card from the engine's records: the approved requirements' title (or the only commit's subject), and a list of the branch's commits since main. It waits under **Issues and pull requests** like the agent's cards and opens as a draft unless you clear that on the card. For a draft the engine opened, **Ready for review** marks it ready, through GitHub's GraphQL API, only when you press it; the audit has a line before and after. When GitHub says the branch conflicts with main, the panel says so and offers **Ask the agent to bring in main**. **Assign the issues and pull requests the engine opens to the token's own user**, in the project's settings (off by default), does what it says after each one opens; a failure is a line in the audit and changes nothing else.

**Issue cards from findings.** When a review passes with findings that didn't block (Medium or Low), the panel lists them and offers **Open issues for these**: one issue card per finding, with its title, location (from knackpack's per-finding line when the reply has one) and text and which reviewer found it in which commit, each approved or denied on its own. A finding whose text holds something shaped like a token gets no card.

**The audit.** Every push request ends as a line in the engine's audit file, with your reason for any exception and never the token. So do your approvals of start-up files, requirements, plans and the team file (by hash, never the text). Where a line quotes what an agent, a reviewer or the git host wrote, such as an issue or pull request title or the git host's answer to a push, anything shaped like a token is hidden; the card on the page shows it so you can judge it. The panel lists the branch's exceptions and pushes, with the project's team file approvals, clone folder start-up approvals and reviewer agent file changes, newest first. When the gate refuses something repeatedly in a project, such as a push command the agent typed, the page suggests saying what to do instead in the project's `CLAUDE.md`.

The engine refuses a push carrying files that the repository's `.gitattributes` sends through Git LFS, and repositories that use SHA-256 object names.

Each answer to a permission card is a line in the audit file too: the session, the tool's kind, a SHA-256 of the input the card showed (never the input) and your choice.

### Trust boundary

The engine, the box helper, the reviewers' containers and the proxy are trusted; the sessions' containers aren't. An agent acting on instructions planted in a repository, an issue or a web page can run anything in its own session's container, including changing that session's worktree and the plugin's reports. It can't see another session's container, files, home or network. What the design relies on sits outside the sessions' containers:

- **No route to a git host.** Each session's container is on an internal network of its own, shared only with the engine and the proxy, whose only way out is the proxy, which allows only the model API hosts on port 443 and always refuses git hosts. The engine checks this before every start and every 5 minutes, for each running session's container; a failed check stops new sessions and marks the sessions it covers Held.
- **The sessions' containers.** Only the box helper makes them, from a fixed recipe: no capabilities, a read-only root, no published port, no host folder, their own network only, and memory, CPU and process limits. The helper takes requests only from the engine, names only a session's box id in them, and checks each container against the recipe before it starts it. It holds Docker's socket, which is close to control of the computer, and nothing on the sessions' networks can reach it.
- **The push.** Only the engine holds the git host token, and it never sends it to another container. Issues and pull requests the agent asks for are opened only when you approve them on the page.
- **The verdicts.** Each reviewer runs in a container of its own, which mounts only the copy of the commit the engine wrote for it, with read-only tools and hooks off, and is removed when it finishes. No session's container can reach it.
- **Your decisions.** Approvals, Allow, Deny and Override come only from the page. From the sessions' networks the engine accepts reports and requests, never a decision, a verdict or a push, and each container only about its own session.

The image also carries a locked Claude Code settings file, `/etc/claude-code/managed-settings.json`, which no agent or reviewer can change and which outranks every other Claude Code setting. In every session and review it turns off messages between Claude Code sessions, Remote Control, your claude.ai account's synced plugins, skills and connectors, and auto memory. So what you type to correct Claude doesn't carry over to later sessions on its own: put it in the repository's instruction file (`CLAUDE.md`) instead. It also turns off Claude Code's built-in plugin guard so that Software Factory's plugin hooks run, which means a plugin installed in a session container's home could override Claude Code's permission rules in that session (see [Limitations](#limitations)).

The page is published only on `127.0.0.1` and signs in without a code, so any program on the computer can use it. It checks every request's `Host`, `Origin` and `Sec-Fetch-Site`, sends no CORS headers and a strict content security policy, and shows everything from a session as text, so other websites and the agents can't drive it. A permission card allows only a call whose whole content the page showed you.

What it can't defend against is under [Limitations](#limitations).

### Cost and models

Software Factory calls no model itself and holds no model key. Every session runs in the vendor's own agent, on the sign-in you made in its container, so usage counts against your subscription or is billed to your API key as it would be without Software Factory. Every review, and every manual test list you ask for, is also a Claude Code run, in a reviewer container of its own, on the reviewers' one sign-in.

Before each start, wake and review, the engine has the agent's own status command (`claude auth status`) report which kind of sign-in it uses: a subscription, an API key, a gateway (a custom base URL), Amazon Bedrock, Google Vertex AI, or not signed in. It reads only that kind and the endpoint's host, never the account. A start that isn't signed in, or uses another kind than the one you expect, is refused with the agent's sign-in step; the engine never tries another credential. On any sign-in but a subscription, the page asks you to confirm the cost before each start, wake, review and manual test list.

Costs on the page are the agents' own estimates, which may differ from your bill: each Claude Code session's cost, and each review's and the session's reviews' total.

Models: pick Claude Code's model in the new-session form (its default, Fable, Opus, Sonnet or Haiku) and its effort; **Switch model…** changes them from the next turn. Reviewers run on the reviewers' Claude Code default model unless a role sets its own model and effort in the Code review step, next to the role's agent, which passes `--model` and `--effort` to that role's runs. The Code review panel names the model each review ran with.

To keep cost down: an agent's push request starts each reviewer at most once per commit (twice when an engine restart cut the first run off), later rounds review only what changed, the round limit stops a reviewer that keeps blocking, and the agent's requests start at most 12 reviewer runs per branch.

**Usage limits.** On a subscription, the page shows each usage limit the agents report for their account, how full it is and when it resets, with the plan Claude Code names: the reviewers' limits on the Welcome page, and each session's own limits in one line on its row, since each session's container can be signed in to its own account. It shows only the limits the account actually has: the 5-hour limit only when the account reports one. Claude Code in the sessions' containers reports the 5-hour and weekly limits; the weekly Fable limit reaches the page only from the reviewers. API-key and gateway sign-ins show no limits. When a limit passes 90%, the engine pauses automatic reviews and automatic Send findings of the sessions that limit belongs to (every session, for the reviewers' limits), says so on the session, and asks you: **Keep them running** lets them go on until that limit resets, and starts what it paused: the reviews of a held push, or the Send findings. Your own messages and **Review** still work. A session whose agent used up a limit offers **Wake at reset**. The figures come from the agents, so they can only pause automatic work, never allow anything.

**Caps.** A project can have a spending cap (the agent's own reported cost), a time cap (how long the session runs, by the engine's clock, idle time included), a turn cap and a disk cap (the size of the session's folder in the workspace volume, in GiB); the **Caps** item in a project's ⋯ menu sets them, and the new-session form can set other caps for one session. A cap is at most $100,000, 43,200 minutes, 10,000 turns or 4,096 GiB, the last three whole numbers; the engine checks what you type, before a new session starts too, and names the cap it refused. None is set at first, so nothing changes until you set one. The session shows its use against each cap, with a warning past 75% and 90%. At a cap the engine interrupts the running turn, holds the session's automatic reviews, automatic Send findings and new messages, and asks: **Raise the cap** goes on, and **Stop** stops the session. A reported cost can only stop work, never allow more, and an agent that reports less than it spends gets past the spending cap. The engine measures a session's folder every 2 minutes while the session runs and has a disk cap, so the disk cap is a soft limit against a runaway session: an agent can write past it between measurements. At the disk cap the card also offers **Check again**: delete files from the session's folder (with `docker exec`, since the engine passes no message to the agent), then press it, and the session goes on once the engine counts the whole folder under the cap; the next 2-minute measurement does the same. Each cap reached and your answer are written to the audit file.

**Looks stuck.** When an agent makes the same tool call, or runs the same failing command, three times within eight calls of one turn, the session shows "Looks stuck" with **Interrupt**. It only shows; caps still apply.

**Expiry warnings.** Ten days before a claude.ai sign-in of a session's container or of the reviewers can end, the Welcome page and that agent's sessions say so, with the range of dates it can end on (Claude Code reports the latest one, and the real end can be up to three days earlier). Seven days before a git host token expires, by the date GitHub sends with each answer to the engine's own calls, its project says so.

### Limitations

- The model API host an agent must reach also serves its vendor's other products, and an agent can send code to its model API. With the stored login, an agent could start a vendor cloud session that has its own access to your repository. **Don't connect a vendor's cloud agent (Claude Code on the web and the like) to repositories you gate with Software Factory**: it pushes from the vendor's servers, outside the gate. In a Claude Code session the plugin refuses the commands that hand work to the vendor's cloud (`claude --remote`, `--cloud`, `--teleport`, `remote-control` or `rc`, `claude ultrareview --post`), but only as the agent types them: a script, Makefile or program that runs one gets past, and nothing stops a session started from the vendor's website.
- The code under review can address its reviewer, such as with instructions written into the code. Reviewers may read only their review folder, and a reviewer that tries to read elsewhere counts as no verdict; that limit relies on a Claude Code setting not yet checked on a signed-in run. Findings you send to the agent are that reviewer's words, so they can carry such instructions too; the engine marks them as untrusted.
- Containers don't stop a kernel exploit.
- Reviewers read the change from where the branch leaves main to its head, not each commit, while the push sends every commit. A version that only an intermediate commit holds is flagged instead, for you to allow or have removed.
- The push's secret scan knows private-key headers, known token formats and passwords in URLs only, so a secret that is encoded, split or in another format goes out once the reviews pass.
- Nothing trusted runs a repository's own checks, because the engine and the reviewers must never run what an agent wrote; reviewers only read the code. A [verification run](#verification-runs) runs the check command in a container as untrusted as a session's, with no network, and believes only its exit code. A pass doesn't show the tests are good, since the agent wrote them, and the run needs an image with every tool and dependency in it.
- An agent can change the user-level settings of its own session's container, such as Claude Code's settings in its home. A later wake of that session lists what changed since its last start and asks before it loads them, and **Don't wake** leaves it stopped. It doesn't see user MCP servers (kept in `~/.claude.json`) or a file those settings name elsewhere, such as a hook's script, so a change there loads unasked. The list comes from inside the session's container, so it catches changes an honest session or someone else made, not every change a hostile agent could hide. Other sessions don't share that home.
- The box helper holds Docker's socket, so a flaw in the helper would give control of Docker. It takes requests only from the engine, over its own network and with a key, and acts only on a box id.
- A session's disk cap is soft: the engine measures the session's folder every 2 minutes, so an agent can fill the workspace volume between measurements. It doesn't count the session's home volume or its `/tmp`, and files in a folder the engine can't open aren't counted, so an agent can stay under the cap by hiding files; such a folder makes the count "at least", which keeps a reached disk cap from clearing until the engine can read that folder again and counts the whole folder under the cap (for example after you `chmod` it with `docker exec` and press **Check again**), or you raise the cap. Without a disk cap nothing limits a session's disk use, and nothing limits how many sessions run unless you set `SF_MAX_BOXES`.
- After a hard stop of Docker or the computer, sessions' containers can be left behind until the stack starts again, when the helper removes them; [Maintenance](#maintenance) says how to remove them by hand.
- If your claude.ai organization delivers managed settings from its admin console, Claude Code uses those and skips the image's locked settings file, apart from the synced plugins, skills and connectors, which stay off. Claude Code's permission prompts then probably stop reaching the page as cards; this hasn't been checked.
- Only Claude Code (Anthropic) is offered.
- A plan made in Claude Code's plan mode can be approved only in Claude Code itself.
- The page can't start a session in auto or bypass permission mode.
- After an engine restart, the sessions it started come back Stopped: press **Wake** to continue one, which runs the start checks again. Cards that were waiting for an answer are gone, except issue and pull request cards, which come back, and the conversation continues from what the agent saved: Claude Code's session. A session from before Software Factory recorded its sandbox checks comes back not sandboxed and can't push: start a new session for that work. Pushes of the sessions it restored wait for the first sandbox check after the restart, since nothing checked the sessions' containers while the engine was down; once that check passes, Push and Allow work again.
- Repositories that use SHA-256 object names are refused, and so are pushes carrying Git LFS files. The LFS check reads only the latest commit's `.gitattributes`.
- A flagged file whose path isn't valid UTF-8 can't be allowed.
- The Changes diff is cut at 1 MiB, and the flagged-file scan reads at most 1,000 commits and 32 MiB per push, commit messages included; beyond that, the push needs your Allow with a reason. Reviewers get at most the newest 200 commit messages.
- The page runs on one computer, for one person, with one signed-in page at a time.

## Maintenance

- **Upgrade** a release by running the install command again: `curl -fsSL https://github.com/bezmoradi/software-factory/releases/latest/download/install.sh | sh`, or the three lines that check the script first ([Run it with Docker](#run-it-with-docker), **What you trust**), with the same `SF_HOME`, `SF_DOCKER_GID`, `SF_DOCKER_SOCKET` and other variables you installed with. It downloads the newest release's Compose files into the same folder and writes `software-factory-socket.yaml` again. The same project name, `software-factory`, keeps the volumes. Running sessions' containers stop when the box helper is recreated; each wakes in a container made from the new image. From source, upgrade with `git pull`, then `make up`; `make up` and `make down` work only in a clone. The engine installs the agent versions the new code pins when it starts. Logins, repositories, tokens, reviews and the audit stay; an open page reloads itself and signs in again once the new engine is up.
- **Upgrade from a version with one shared agent container**, before each session had its own: that version's `agent` container keeps running after a plain `up`, with the workspace volume mounted, so the box helper starts no session until it is gone, and its log names it. `make up` and the install command pass `--remove-orphans`, which removes it; otherwise run `docker rm -f software-factory-agent-1`. Its volume `software-factory_agent-home` stays, with the agents' logins and the API keys pasted there; remove it with `docker volume rm software-factory_agent-home` once the container is gone. With another project name, use it in place of `software-factory`. The label filter under **Remove leftover session containers** doesn't match it.
- **Install the agents again** with `docker compose exec engine software-factory install-agents`, after a failed download.
- **Sign Claude Code in again** when the page says its login failed: the reviewers as [Sign Claude Code in for the reviewers](#sign-claude-code-in-for-the-reviewers) says, and a session's agent as [Sign Claude Code in for this session](#sign-claude-code-in-for-this-session) says.
- **Read the engine's log** with `docker compose logs engine`. It holds event kinds only, never prompts, file contents, keys or tokens. Each page action and agent request has a random request id, logged as `req=<id>` by the engine, agent-host and egress, so `docker compose logs | grep <id>` finds every line of that action; the page doesn't show it, and Diagnostics lists it with each recent event.
- **Roll back after an update** that changed a store's format: before an engine writes a store in a newer format, it copies the old file to `backup/<old engine version>/` in `engine-state` and keeps the last 3. Stop the stack with `docker compose down`, put the copies back with `docker compose run --rm --no-deps --entrypoint sh engine -c 'cp -p /var/lib/software-factory/backup/<old engine version>/* /var/lib/software-factory/'`, then start the older code with `make up`, or that release's own script (`curl -fsSL https://github.com/bezmoradi/software-factory/releases/download/v<version>/install.sh | sh`). After an install from a release, that `run` needs `-p software-factory -f compose.yaml -f compose.release.yaml -f software-factory-socket.yaml`, in the install folder, and isn't checked yet. Changes made since the update to those stores are lost. Going back to an engine older than PR #12 also drops removed projects' parked data and the decision log's project spans from each per-project store it writes, so adding such a project again starts it empty.
- **See dropped records** on the Welcome page: when the review records, the audit or another capped store drops its oldest records, a line says how many and since when.
- **Stop everything and keep the data** with `make down` (or `docker compose down`; after an install from a release, `docker compose -p software-factory down`). The box helper stops and removes every session's container before it stops itself; the sessions' homes and folders stay.
- **Remove leftover session containers** after a hard stop, such as Docker or the computer stopping with the stack running. The next start of the stack removes them by itself. To remove them without starting it, with your stack's project name in place of `software-factory`:

  ```bash
  docker rm -f $(docker ps -aq --filter label=dev.software-factory.stack=software-factory)
  docker network rm $(docker network ls -q --filter label=dev.software-factory.stack=software-factory)
  ```

  The helper labels each session's home volume the same way; `docker volume rm $(docker volume ls -q --filter label=dev.software-factory.stack=software-factory)` deletes them all, with the sessions' logins and conversations, so run it only when you remove Software Factory.
- **Remove a session's leftover files** when the engine's log has `event=folders-not-removed box=<box>` (`docker compose logs engine | grep folders-not-removed`). That happens when a start that waited for a sign-in or an approval can't go on because the helper no longer has its container, such as after a restart of the helper: the engine can't ask that container to delete what its agent wrote, so the files stay in `/workspace/s/<box>` on the `workspace` volume, unused. First check that no container of that box is left (`docker ps -a --filter name=software-factory-box-<box>` lists nothing), then remove the folder in two passes, first as the agents' user, which owns what the agent wrote, then as the engine's user, which owns the rest. Neither pass has a network or any capability, and each touches only that one folder. Set `box` to exactly the id from the log line, the 16 characters after `box=`: an empty or mistyped id would name every session's folder, so each pass first checks that `box` is 16 hexadecimal digits and runs nothing otherwise:

  ```bash
  box=<the 16-character id from the log line>
  [ "${#box}" -eq 16 ] && printf '%s' "$box" | grep -Eqx '[0-9a-f]{16}' && docker run --rm --network none --read-only --cap-drop ALL --security-opt no-new-privileges:true --user 10002:10000 -v software-factory_workspace:/workspace --entrypoint rm software-factory:local -rf -- "/workspace/s/$box"
  [ "${#box}" -eq 16 ] && printf '%s' "$box" | grep -Eqx '[0-9a-f]{16}' && docker run --rm --network none --read-only --cap-drop ALL --security-opt no-new-privileges:true --user 10001:10000 -v software-factory_workspace:/workspace --entrypoint rm software-factory:local -rf -- "/workspace/s/$box"
  ```

  The first pass says "Permission denied" for the engine's folders; the second removes them, and then nothing of the box is left. After an install from a release, use the image `compose.release.yaml` names in the install folder, `ghcr.io/bezmoradi/software-factory@sha256:<image digest>`, in place of `software-factory:local`; with another project name, its `<project>_workspace` volume. `docker compose down -v` also removes them, with every other session's work and everything else in the workspace.

  **Warning:** `docker compose down -v` also deletes the stack's volumes: every repository clone and the sessions' unpushed work, the git host tokens, the reviewers' login, the review records and the audit. It can't be undone. It leaves the sessions' home volumes and the reviewers' home volume, which the helper made and Compose doesn't know; the `docker volume rm` command under **Remove leftover session containers** removes them. It doesn't sign the agents out with their vendors or revoke a key or token: do that first, as [Privacy](#privacy) says under "Removing it".

The data lives in these volumes. Only `engine-state` has an export, and nothing backs up the rest:

| Volume | Holds |
|---|---|
| `engine-state` | The project list, git host tokens, review records, approvals, expected sign-ins, project settings, the sessions it started with their work types and your approvals of requirements and plans, and the audit file. Only the engine mounts it |
| `workspace` | The engine's copy of each repository, in `base/`, and each session's folder, in `s/<box>`: its own clone, its worktree and its screenshots |
| `agents` | The installed agents and knackpack |
| `<project>-home-<box>` | One per session, made by the box helper: the session's Claude Code login, settings and conversation. Removed when the session is deleted, not by `down -v` |
| `<project>-reviewer-home` | Made by the box helper and shared by every reviewer container: the reviewers' Claude Code login. Not removed by `down -v` |
| `reviews` | The read-only copies under review, removed when a review ends |
| `uploads` | Images and files you sent, held in memory and gone when the stack stops |

### Update to Software Factory

**Update when the page says so.** Once a day the engine asks GitHub for the repository's newest `v*.*.*` tag (a restart within 24 hours of the last check reuses its result rather than asking again), and when it is newer than the version you run, the top bar's right corner shows **Update to** and the version, as VS Code does. The button opens the steps: the version you run and the new one, a link to the new tag on GitHub, and for a release install that version's install command with a copy button, with the three lines that download its script, check its attestation and run it ([Run it with Docker](#run-it-with-docker), **What you trust**); for a source install, or the development image, `git pull` then `make up` in your clone. Both are shown, the one that matches this engine first, since the engine can't tell a release install from a source build of the same image. Software Factory never updates itself: nothing changes until you run them. The version comes only from the tags, which only the owner can create, and counts only when its GitHub release is published, not a draft or a pre-release; nothing else from GitHub's answers reaches the page. Pre-releases (`v1.2.0-rc.1`) and tags that aren't a plain version are skipped. **Remind me later** hides the button until a release newer than the one it showed is out. The check needs no setting and has none on the page; only `SF_NO_UPDATE_CHECK=1` turns it off. Offline, or when GitHub refuses or answers something the engine can't read, the page shows nothing and the engine logs one `update check` line with the kind (`offline`, `timeout`, `refused`, `malformed`); when the server's TLS certificate doesn't verify, as with a proxy that intercepts HTTPS, the kind is `untrusted` and the line is a warning. The button never offers a version that isn't newer than the one you run, so after you update it goes away even before the next check; Diagnostics shows whether the check is on and its last result.

### Diagnostics

**Attach diagnostics to a bug report** with **Diagnostics** on the Welcome page: a text file of versions, image digests, the OS and Docker, setting names with values that aren't secret, counts and the last 500 events as kinds and request ids, with no repository name, host, path, token, prompt or log text. The page builds it once when the dialog opens, so it doesn't change while you read it, shows the whole file before you save it and never sends it anywhere; open it again for a new one.

**Read Vulnerabilities, Agent settings and Agent versions** in **Diagnostics** (under Start on the Welcome page). They show whether a pinned agent version has a known vulnerability, whether each pinned npm package's build provenance checked out (an agent installed before the engine checked it is checked at the engine's next start, or with `docker compose exec engine software-factory install-agents <id>`, without installing it again), and, for each running session, which user-level settings in its container changed since that session last started, its MCP servers and auto-memory included. A wake asks about the same list before it loads it ([Limitations](#limitations)). That list comes from agent-host inside the session's container, so it catches changes an honest session or someone else made, not every change a hostile agent could hide.

### Export and import

**Export the engine's state** with **Export and import** on the Welcome page, then **Export**. The file holds the projects, sessions, review records, settings and the audit, with the name and email agents commit with and every reason you typed, so keep it private. It holds no git host token.

**Import it into a new stack** with **Import…** in the same place, while that engine has no projects and no sessions. The engine restarts to finish. Nothing in the file counts: review passes and approvals show but count for nothing until you approve again, and added hosts, check and setup commands, reviewer agent files, automatic sends and each project's review depth come back off until you turn each on again. Sessions come back as history only and can't be woken. Save the git host's token, then press **Clone again** for each project.

## Development

[CLAUDE.md](CLAUDE.md) has the code layout and the commands, and indexes the rule files in `.claude/rules/`, such as [the dependency rule](.claude/rules/dependency-rule.md) and [every CI job](.claude/rules/ci.md). Software Factory has no automated tests: a change is checked with the build, `go vet`, `make lint`, `make arch-check`, `make fix-check`, `make vuln`, `make web-check`, `make plugin-check`, `make plugin-validate` and the other checks CLAUDE.md lists, then by trying it with the development overlay.

**The development overlay** is for developing Software Factory itself. Never use it for real work: its reviews are fake.

It runs as its own Compose project, `software-factory-dev`, with its own volumes, so its fake reviews never reach the real stack's repositories and tokens. Both stacks publish port 7799, so stop the real one first (`docker compose down` keeps its data), or give the overlay another `SF_PORT`. Side by side, the two stacks' sessions share `SF_BOX_SUBNETS`' default range, each taking the `/28`s the other doesn't use; to keep them apart, give the overlay a range of its own, such as `SF_BOX_SUBNETS=10.214.0.0/20`, at every `up`. Set `COMPOSE_FILE` in the shell you use for it, so every `docker compose` command, including the ones the page shows, goes to the overlay:

```bash
export COMPOSE_FILE=compose.yaml:compose.dev.yaml
docker compose up -d --build --remove-orphans
```

It adds:

- a fake agent, **Development ACP agent**, in every session's container, since the overlay gives the box helper the development image. It takes knackpack's workflow, and the engine counts its requirements and plan only as committed, as for Claude Code with every knackpack the engine installs, so you can commit `.knackpack/<task>/REQUIREMENTS.md`, `PLAN.md` and `.knackpack/feature.json` by hand in its worktree (`docker exec -it software-factory-dev-box-<box> sh`, then `cd /workspace/s/<box>/worktrees/sf-<id>`) and approve them on the page, the requirements in knackpack's checked format (the line `knackpack-requirements/1`);
- a fake reviewer that runs in place of Claude Code (the engine logs a warning). It passes, or blocks when the reviewed commit holds a file named `BLOCK-REVIEW`, and answers after 45 seconds when it holds `SLOW-REVIEW`. For an agent file you added, it runs only when the engine wrote that file into the reviewers' agents folder, and its reply names the file;
- a local git server that only the engine can reach. Save the token in `GITSERVER_TOKEN` in `compose.dev.yaml` for `https://gitserver.test:8443`, then add `https://gitserver.test:8443/demo.git`. Add a commit to its main branch with `docker compose exec gitserver sf-gitserver commit "a new commit"`, and see a pushed branch with `docker compose exec gitserver git -C /srv/git/demo.git log --oneline sf/<id>`.

The fake agent and reviewer report the sign-in written in `$HOME/.sf-fake-signin` in their container (`subscription`, `api-key`, `gateway` or `none`), such as `docker exec software-factory-dev-box-<box> sh -c 'echo none > $HOME/.sf-fake-signin'`; with no file, a subscription. The reviewers' home is a volume no running container keeps, so write theirs with a one-off container: `docker run --rm --network none --read-only --cap-drop ALL --security-opt no-new-privileges:true --user 10004:10004 -v software-factory-dev-reviewer-home:/home/reviewer --entrypoint sh software-factory:dev -c 'echo none > /home/reviewer/.sf-fake-signin'` (only once the volume exists, from the first reviewer container's start: naming it before makes it without the box helper's labels, and the helper then starts no reviewer container). The fake agent's sign-in panel accepts any code but `bad`. `docker ps --filter label=dev.software-factory.stack=software-factory-dev` lists the sessions' containers. `make plugin-validate AGENTS_VOLUME=software-factory-dev_agents` validates the plugin with the overlay's installed Claude Code.

**Hand checks.** With no automated tests, run these with the development overlay before a change is merged, for the parts it touches:

1. Each agent the page offers: start a session, and check what the page shows (agent, sign-in, trust level, work type).
2. Send a message, then press Stop during the turn.
3. Answer a question card and a permission card from the page, with Yes, No and a typed answer.
4. Press Review, wait for both reviewers, then Push; with a `BLOCK-REVIEW` file, see the push held, then Deny it and see that the reviews finishing never push it.
5. Run two sessions at once and check that cards, files and pushes stay with their own session.
6. Reload the page with a card open, then restart the engine (`docker compose restart engine`): check that the page reloads itself and signs in again, that the session comes back Stopped with its work type and approvals, and that **Wake** continues its conversation.
7. Make the sandbox check fail ([Hand checks with Compose](.claude/rules/compose-hand-checks.md)), and check that starts are refused and every running session shows Held.
8. Inside a session's container, check that `curl --connect-to gitlab.com:443:claude.ai:443 https://gitlab.com/` fails, and that `curl https://github.com` is refused.
9. Run the page's curl checks in [docs/reference/security-and-sign-in.md](docs/reference/security-and-sign-in.md#page-security-checks).

**Live changes.** `make dev` runs the real stack, on the same port and volumes as `make up`, from the code in your folder, and rebuilds it every time you save:

- it builds the page and a Linux binary on your computer and copies the binary into the `dev-bin` volume, with a one-off container of `compose.live.yaml`'s `dev-bin` service that reads it from its input. The engine and egress run that binary in place of the image's. So do every session's and reviewer container: `compose.live.yaml` runs the box helper on the development image and sets `SF_BOX_LIVE=1`, and the helper then mounts the volume read-only into each container it makes. The helper itself runs the image's binary, so a change to it needs `docker compose build` and the helper recreated. The helper honours `SF_BOX_LIVE` only on an image that carries the development marker file, and ignores it, with one log line, on any other. No folder of your computer is mounted into any container;
- it watches `cmd`, `configs`, `internal`, `tools`, `web`, `go.mod`, `go.sum`, `README.md` and `compose.yaml`. A save that changes only the page (`web` or `README.md`) recreates the engine alone, in about 10 seconds; any other change recreates the engine and egress, in about 15, which also applies a change to `compose.yaml`. A session's container runs the new binary from its next start or wake, and a reviewer container from its start. The open page reloads itself once the engine is back;
- the box helper itself runs the binary built into its image, so a change to the helper needs `docker compose -f compose.yaml -f compose.live.yaml build helper` and `make dev` again;
- **each save stops the running Claude Code sessions**, since the engine stops sessions it doesn't track when it starts: they come back Stopped, and Wake continues them;
- a build that fails leaves the running stack as it was; fix the error and save again;
- Ctrl-C stops watching and leaves the stack running the last build, letting a restart in progress finish first; `make up` goes back to the image;
- whatever is in your folder runs as the engine, which holds your git host tokens. **Stop `make dev` before a pull, a branch switch or a checkout of code you haven't read.** If the checked-out commit changes along with the files, `make dev` stops by itself and leaves the last build running;
- uploaded images are kept in memory, so every restart deletes them;
- the `Dockerfile`, `plugin/` and `configs/claude-code/` are built into the `software-factory:local` and `software-factory:dev` images, which `make dev` builds only when one is missing. A save there prints a reminder: press Ctrl-C, run `docker compose -f compose.yaml -f compose.live.yaml build`, then `make dev` again.

For work on the page alone, `make run` runs the engine on your computer without Docker; it starts no sessions without an agent-host. An agent-host you run outside Docker listens on `127.0.0.1:8090` unless you set `SF_AGENT_HOST_LISTEN`. **It answers every route, running commands with `/v1/run` included, to any program that reaches its port,** so widen the address only when the engine runs on another machine or in a container. Reviews need the box helper, which makes their containers, so they run only in Docker.

**Making a change.** Changes reach `main` only through a pull request merged by squash:

1. Open an issue for the change.
2. Work on a branch, and open a pull request whose description closes the issue, such as `Closes #12`.
3. CI runs its checks, and Claude reviews every push against `CLAUDE.md`, the rule files in `.claude/rules/`, `ARCHITECTURE.md` and `docs/reference/`. Every problem it confirms blocks the merge, however minor; fix it and push again.

A pull request that changes the checks themselves (`.github/`, `scripts/`, `proctor/`, the `Makefile` or a linter's settings) also needs the owner's `review-override` label after its latest push. [`.claude/rules/ci.md`](.claude/rules/ci.md) says what each check does.

## Privacy

Software Factory runs on your own computer. Its author runs no server for it and receives none of your data.

- **What leaves your computer:** what each agent sends to its vendor's model API, under your own account: your messages, the code and files it reads, and your uploads. The reviewers send the commit under review to Anthropic's API the same way. The engine talks to your git host to clone, fetch and push, with your token, and at install to the npm registry and GitHub. The proxy lets the agents and reviewers reach only the allowed hosts, the defaults and any you added ([Configuration](#configuration)). That limits where they connect, not where your code can end up: an agent that holds an Anthropic API key can have Anthropic's servers connect to a public address of its choice, through the Messages API's [MCP connector](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector), a beta feature.
- **Vulnerability lookups:** shortly after it starts and every 24 hours, the engine asks OSV (`api.osv.dev`) whether the pinned Claude Code version or the installed knackpack commit have a known advisory. It sends those package names, versions and the commit, nothing else; `SF_OSV=off` turns it off. The agent container never reaches OSV.
- **Update check:** every 24 hours, and at a start only when its last check is 24 hours old or more, the engine asks `api.github.com` from your computer for the repository's tags and the release of the newest one, usually two anonymous requests and at most eight per check, with no git host token, no cookie and the User-Agent `software-factory-update-check`, so GitHub sees your address and that a copy of Software Factory checks. The sessions' and reviewer containers never reach it. Nothing on the page turns it off; `SF_NO_UPDATE_CHECK=1` does.
- **Cited vulnerability IDs:** when a review's message cites CVE or GHSA IDs, the engine asks OSV about each one (at most 20 per review), by ID, so the review can mark an ID OSV doesn't hold. It sends only the IDs, which tells OSV which IDs a review of your code mentioned. `SF_OSV=off` turns this off too.
- **Package lookups:** only for a project where you switch on **Look up new packages**, the engine asks npm, PyPI, proxy.golang.org or crates.io about each package a push's manifests add. It sends the package's name (and, for a Go module without a released version, its version), nothing else. The agent container never reaches them for this.
- **What it keeps, and where:** in Docker volumes on your computer ([Maintenance](#maintenance)): the repositories and the agents' work, the git host tokens, the reviewers' verdicts and final messages (up to 4,000 characters each) and their whole reports (up to 64 KiB each, removed when you delete the session), the reviewer agent files you add, the audit file and your approvals. The conversations are kept by the agents themselves, in their own containers. The engine saves a record of each session it started, such as its agent, branch, work type and your approvals, in `sessions.json` in `engine-state`, but not its conversation.
- **What it never stores or logs:** any model credential. The agents' logins are the vendors' own files in each session's container and in the reviewers' home volume, which the engine doesn't mount or read, and every process the engine starts gets the model key variables cleared. An API key you paste in the sign-in dialog, or a gateway's key or token under Network access, goes straight to the container it signs in, where Claude Code reads it through its `apiKeyHelper` setting; the engine doesn't keep it, and the page never shows it again. The git host token is never shown, logged or sent to another container. The log holds event kinds only, never keys, sign-in codes, tokens, prompts, tool input or file contents.
- **Removing it:**
  1. Sign the agents out with their own commands: the reviewers run in no container between reviews, so step 4 deletes their login with their home volume; for each running session `docker exec software-factory-box-<box> claude auth logout`. A stopped session's login stays in its home volume until step 4.
  2. Revoke an Anthropic API key you pasted at <https://platform.claude.com>, and a gateway's key or token with whoever issued it.
  3. Delete the token on your git host.
  4. Run `docker compose down -v` to delete the stack's volumes, then `docker volume rm $(docker volume ls -q --filter label=dev.software-factory.stack=software-factory)` to delete the sessions' and the reviewers' home volumes, with their logins, which `down -v` leaves.

  After an install from a release, add `-p software-factory` after `docker compose` in these commands, and delete the install folder, `~/software-factory` or the one `SF_HOME` named. Then also remove the image, `docker image rm ghcr.io/bezmoradi/software-factory@sha256:<image digest>` with the digest from that folder's `compose.release.yaml` (read it before you delete the folder).
