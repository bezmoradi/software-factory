# Reference: runs and operations

This is part of the Reference section of [ARCHITECTURE.md](../../ARCHITECTURE.md#reference), which describes how Software Factory works and why.

## Check and setup commands, the queue, models and ports

Code: core `session/checkcmd.go`, `setupcmd.go`, `queue.go`, `models.go`, `ports.go`, `portsenv.go`, `sessionwork.go`, `reviewargv.go`; adapters `agenthost/projectcmd.go`, `git/state/sessionwork.go`, page `sessionwork.go`; `plugin/hooks/register.ts` (`classic.Stop`, `turn.start`, `turn.step`); `web/components/session-work.ts`, `project-commands.ts`, `review-models.ts`.

- **The command route.** Agent-mode agent-host answers `POST /v1/project-command` (`{cwd, kind, command}`, `kind` `check` or `setup`); review mode doesn't offer it. It runs `/bin/sh -c <command>` in that folder, which must be inside the workspace, as the `agent` user, in its own process group, with the environment every agent process gets: `PATH`, `HOME`, `LANG`, `TERM` and the proxy variables, every key variable cleared. It kills the group at 5 minutes for the check and 15 for setup, runs at most 4 at a time, and answers the exit code and the last 8 KiB of stdout and stderr together. The command comes only from the engine, which reads it from `project-commands.json`; the page sets it, and nothing from the plugin, the agent or the repository can. The engine checks the tail with the flagged-file token detector before it keeps or shows any of it, and the page renders it as text.
- **What runs where.** Both commands are repository code in effect (`make check`, `npm ci` with its install scripts), so they run only in the session's container, where the agents already run anything. No trusted part runs them, and the registry hosts `npm ci` reaches are the ones Network access already allows.
- **Setup.** After a new session's start-up card is approved and its agent started, the engine runs the project's setup command in that worktree, once; a refused card removes the worktree before anything runs, and Wake doesn't run it again. While it runs, a message from the page waits in the session's queue (one with images or files is refused with the reason), and the queue sends it when setup ends. The result is shown on the session and written to the audit file (`setup-command`, its state only).
- **The check, Claude Code.** At each stop of the main loop, the plugin's `classic.Stop` handler posts `/turn-check` with `again` set to `stop_hook_active`. With no command set the engine answers `none` and the plugin lets the stop through. Otherwise the engine runs the command through the route and counts failures per turn (a turn is the span between two of the plugin's `busy` reports): it answers `block` only for the first failure of a turn and never when `again` is true. The block text is "The project's check failed; fix it before you finish.", then the command from `project-commands.json` as the person typed it, on one line after `CheckProjectCommand`, then the exit code (or that it was stopped at 5 minutes, or that it has none), then the tail or "It printed nothing." The engine runs the token detector on the whole text: a token-shaped command isn't shown, and if the whole text still matches, the command and the tail are both left out with the reason. The plugin returns `{ block }` only then, so Claude Code re-prompts once; the stop after it runs the check again, for the page, and ends the turn whatever it says. Whether `$.http.fetch` gives up before a 5-minute check ends isn't known; if it does, the stop goes through and the page still shows the result.
- **The check, the development ACP agent.** When a turn ends normally the engine runs the command, and on a failure sets a note (source `check`) with the same text and as much of the tail as a note's 1,200 bytes hold, which goes with the next message; a pass removes it. The queue waits for the check, so its next message carries the note.
- **Advisory.** No check or setup result from the session's container counts for the gate, a review or a push. A verification run of the same check command, in a container of its own (below, "Verification runs"), is a separate thing, and is the one the team file can make a push wait for. Changing either command writes a `project-command` audit line naming the project and whether it was set or cleared, never the command.
- **The queue.** Each session has an engine-held queue of at most 10 messages. When a turn ends (the agent's `idle` report), the engine sends the first one through the same path as a typed message, so caps and control apply. It stops instead, and keeps the reason, when that turn failed or was stopped, a card or a waiting issue or pull request card is open, a push is held, the agent's sign-in failed, the session isn't running, or the send is refused; a card shown during a turn stops it at once. Resume clears the reason and sends if the session is free. Commands and token-shaped text aren't queued. After a restart each queue waits for Resume. It works above the ACP bridge's own wait list, which holds messages sent during a turn, since the engine sends only when the session is free.
- **Models and effort.** The start form sends `effort` with `model`. Claude Code gets `--model=` and `--effort=` on `claude --bg`, from the form's models and `low`, `medium`, `high`, `xhigh` or `max`.
- **A switch mid-session.** For Claude Code the engine keeps a per-session override in `models.json`. The plugin reads it from `/session-model` at each main-loop `turn.start` and, in `turn.step`, sends main-loop requests (`agentId` absent) with `next({ ...e, model, effort })`; subagents keep theirs. `/model` and `/effort` stay refused, because Claude Code 2.1.322 saves them as defaults in the container's home. Claude Code's own `$.session.model()` and its context accounting keep following the start model.
- **Review roles.** The Code review step sets a model and an effort per role, next to the role's agent, kept in `models.json` by project name and address. `ReviewArgvWith` adds `--model=` and `--effort=` only when set, and the review record keeps the model and effort the run was started with (`runModel`, `runEffort`; none for the defaults). The review shows the model from the result's `modelUsage`.
- **Ports.** Each session gets 10 ports from 41000: at start the engine reserves the lowest range that no session it holds has, binds it to the session's id once the agent started, keeps it in `ports.json` until the session is deleted, and drops saved ranges of sessions it no longer has at its start. A note (source `ports`) names the range with the first message. For Claude Code, `PORT` and `SF_PORT_BASE` go in the `env` of the session's one `--settings=` JSON, merged with `KNACKPACK_DOCS` when that's on. That env part is `claudePortEnv` in `portsenv.go`: making it return nil takes it out, note sentence included, if a live check shows the variables don't reach a `--bg` session's Bash.
- **Page routes.** `/api/session-work` (`op` `read`, `model`, `queue-add`, `queue-edit`, `queue-move`, `queue-remove`, `queue-resume`), `/api/project-commands` (`read`, `set`), and `/api/review-models` (`read`, `set`) take the page's usual checks; `/api/project-commands`'s `set` also takes `image`, the verification runs' image (unchanged when absent), and its answers carry it; a change broadcasts a `session-work` frame with the session id only, and the page reads the route again.

## Verification runs

Code: core `session/verify.go` (with `CheckVerifyImage` and the push items), `session/pushes.go` (`verifyWait`, `stillRunning`), `workflow/team.go` (`verify`); adapters `sandbox/boxes/verifiers.go`, `verifyserver.go`, `verifyclient.go`, `git/files/verify.go`, `git/state/verify.go`, page `verify.go`; `cmd/server/verify.go`; `web/components/verify.ts`, `project-commands.ts`.

A verification run runs the project's check command, the one set under Check and setup commands, on a clean copy of one commit, in a throwaway container of the project's own image. The container is as untrusted as a session's, since an agent wrote what it runs; the engine believes only Docker's record of its exit (REQ-04).

- **The image.** Each project names its own, pinned by digest (`name@sha256:` and 64 hexadecimal digits, at most 300 bytes, `CheckVerifyImage`), kept in `project-commands.json` as `image` and set on the page beside the commands, never from the repository or the agent network. It holds the project's tools and dependencies, since the run is offline (REQ-42). Software Factory ships no such image, and a project with none set can't run a verification. The helper pulls nothing: the person pulls the image on the Docker host. The engine sends the helper only the digest's hex digits; the helper finds the one local image whose ID or one of whose repository digests is that digest, and refuses none, more than one, a non-Linux image, an image carrying a `dev.software-factory.*` label (which would make its container look like one of the helper's other objects), and one declaring a volume it can't cover (more than 8, or at `/`, `/in`, `/work`, `/tmp`, `/proc`, `/sys`, `/dev` or `/etc`).
- **The files.** The engine writes `/verify/<run>/files/` with the hash-checked reader `files.Reader.WriteTree` from the session's clone, as reviews do, so the files are the commit's whatever else the clone holds: it refuses `.git` entries, unsafe names, case clashes and symbolic links that leave the tree, caps 500,000 entries and 8 GiB, or less: before writing, the engine reads the `verify` volume's free space, refuses with "not enough space on the verify volume" (an `error`, never a pass) when less than 1 GiB and 64 MiB is free, and otherwise caps the tree at half of what is free beyond 1 GiB, so the two runs at once can't fill it, counting each file rounded up to the volume's own block size (from `statfs`) and each folder and link as a block, and at most 200,000 entries and, on a filesystem with an inode table, half of the free inodes beyond a reserve (a tenth of them, at least 65,536), refusing too when fewer inodes are free; a filesystem that reports no inode table (zero total inodes, such as btrfs) gets only the space floor, and writes a submodule as an empty folder and an LFS file as its pointer. Beside them it writes `/verify/<run>/command`, the command as stored. The command reaches the container only as that file, so the recipe doesn't change per project, and the engine never runs git. A tree the reader refuses records `error` with its reason.
- **The recipe.** Fixed by the helper, from its settings and the image:

  | Field | Value |
  |---|---|
  | Image | the image ID the digest picked |
  | User | `10006:10006` |
  | Entrypoint and command | `/bin/sh -c` with `mkdir -p /work/src /work/home && cp -RP /in/files/. /work/src/ && cd /work/src && exec /bin/sh -c "$(cat /in/command)"`, so the image needs a POSIX shell, `mkdir`, `cp` and `cat` |
  | Environment | `HOME=/work/home`, `LANG=C.UTF-8`, `TERM=dumb` and `CI=1`, and of the image's own variables only those with a tooling name (`PATH`, `HOME`, `LANG`, `LANGUAGE`, `LC_*`, `TZ`, `TERM`, `SHELL`, `USER`, `*_HOME`, `*_VERSION`, `*_ROOT`, `GOPATH`, `GOROOT`, `GOTOOLCHAIN`, `NODE_ENV`, `PYTHONPATH`, `PYTHONUNBUFFERED`, `PYTHONDONTWRITEBYTECODE`, `VIRTUAL_ENV`) whose value has exactly the shape its name allows: an absolute path of ordinary path characters (letters, digits, `.`, `_`, `+`, `/` and `-`) for `HOME`, `SHELL`, `*_HOME`, `*_ROOT`, `GOROOT` and `VIRTUAL_ENV`; a colon-separated list of such paths for `PATH`, `GOPATH` and `PYTHONPATH` (a list with an empty part, which means the working folder, is emptied); for `*_VERSION` at most 32 characters of dot-separated digit groups of at most 6 digits each, after an optional leading word of up to 4 lowercase letters such as `v` or `go` and before an optional suffix such as `-rc1` or `+auto`; for `GOTOOLCHAIN` `local`, `auto`, `path` or `go<version>` with an optional `+auto` or `+path`; a locale for `LANG`, `LANGUAGE` and `LC_*`; one to three digits for `PYTHONUNBUFFERED` and `PYTHONDONTWRITEBYTECODE`; and the token checks must not match. `TZ`, `USER`, `NODE_ENV` and every other image variable are emptied, and `TERM` is the recipe's `dumb`; every other image variable, and every value of another shape, is emptied. A check command that needs another variable sets it itself (`FOO=bar make check`). This is a best-effort backstop: agent-written code still reads everything else in the image, its files included, and whether the run passed, and roughly when it ended, reaches the agent through whether and when its push goes out, so the image must hold no secret |
  | Network | `none`: loopback only, no network made, no engine or egress attached, no `ExtraHosts` |
  | Mounts | the `verify` volume's `<run>` folder at `/in`, read-only, `NoCopy`; nothing else (no `workspace`, `agents`, `reviews`, `uploads`, `engine-state`, home or socket) |
  | Tmpfs | `/work` (`SF_VERIFY_DISK`, mode 0700, owned by 10006, `exec`), `/tmp` (512 MiB, `exec`), and one of 256 MiB at each volume the image declares, so Docker makes no anonymous volume |
  | Hardening | `Init`, read-only root, `CapDrop: [ALL]`, `no-new-privileges`, private cgroup and IPC namespaces, 64 MiB of `/dev/shm`, 2,048 processes, `OomScoreAdj` 800, no restart, `json-file` logs of 10 MiB × 3, no health check, `SF_BOX_RUNTIME` (gVisor applies) |
  | Limits | `SF_VERIFY_MEMORY` (memory and memory with swap, default 4 GiB, which the tmpfs pages count against), `SF_VERIFY_CPUS` (default 2), `SF_VERIFY_MINUTES` (default 15, 1 to 120) |
  | Labels and name | `dev.software-factory.stack`, `dev.software-factory.verifier=<run>`, `dev.software-factory.verify-image=<digest>`, `dev.software-factory.recipe=<hash>`, the image's Compose labels blanked; `<project>-verify-<run>` |

  The helper compares the created container with the recipe before and after it starts it, removing it and refusing on any difference, and refuses a second mount. It doesn't wait for a health check: the container may have exited by the second inspect.
- **The run.** `Verifier.Start` refuses another kind than `check` (400 `kind`), an engine without the helper or `SF_VERIFY` (409 `no-helper`), a session it didn't start, an unread branch, a project with no check command (409 `no-check`) or no image (409 `no-image`), a second run of the same session (409 `running`), and a third run on the engine (429 `verify-busy`). A run a push starts, when the two slots are taken, another push's run holds one (a push holds at most one), or another session's run is already queued, is queued instead: one queued run per session, which keeps its place when the session pushes a newer commit, started in order when a run ends (the first whose session has no run going; an item whose session has a run going doesn't hold back the others, at the start of a run either), only after the push conditions are checked again (the branch still at the queued commit, not denied by the person, the work type can push, no team-file refusal, no missing approval, the team file still requiring `verify`, no current run of that commit, passed or not) and on exactly the queued commit, a dropped item being decided again instead; Verify this commit pressed for a commit whose run is queued takes it out of the queue; while the queue hands a run to a free slot it stays counted as pending, a concurrent start of the same commit waits for it, and a start of a commit whose run with the same command and image already runs returns that run, and counted as running for the push that waits on it. The panel shows a queued run. It reads the branch's head itself; the page names no commit, command or image. It records the run as `running`, then writes the files, asks the helper to start the container, polls Docker's record every 2 seconds until it ends or the limit and 30 seconds pass, reads the log, removes the container and the files, and records the end. The person's Stop and the session's Delete stop a run at once, each recording `stopped`; a stop during the file writing is seen before the container is made, so none starts.
- **The pass rule** (`verdictOf`), in one place: a pass only when Docker's state is `exited` with exit code 0, not out of memory, no error, a start and an end time within the limit, the container's image ID and digest label are those the start answered, and the engine started that run in this process (a live set kept in memory only). Anything else is not a pass: a non-zero exit is `failed` with its code (`kill -9 $$` is 137), past the limit `timed-out`, an out-of-memory kill (the tmpfs counts too) `oom`, a helper or Docker error, a container that went away or one that doesn't match `error`, an engine restart `interrupted`. A container a list or a sweep finds is never read for a result.
- **The output.** The last 64 KiB the helper reads from Docker's log (demultiplexed, at most 64 MiB read), cut by the engine to its last 8 KiB, with terminal escapes removed; the whole kept tail is withheld when the flagged-file token detector matches it. The page shows it as text.
- **What counts.** A run is recorded against the full commit, the SHA-256 of the command and the image's digest, and counts only while all three are the current ones: a new commit, a changed check command or another image makes the page say why the last run doesn't count. A run of the same commit in another session of the project counts too.
- **The gate.** With `"verify": ["check"]` in the approved team file on main, every push of a commit, from the page or an agent, misses an item until that commit has a current pass: "a check command for this project, which the approved team file requires a verification run of", "an image for this project's verification runs, which the approved team file requires", "the verification run (check) of commit X to finish", or "a passing verification run (check) of commit X: none ran; press Verify this commit in the session's verification panel", "…: the last one didn't pass; the session's verification panel on the page shows why" (for a failure, a timeout or running out of memory alike; the panel shows the code), "… was cut off by an engine restart". An agent's push, and a decision after its reviews, gets one text for a run that is queued, running, failed, timed out or out of memory ("…, which the engine doesn't have yet; the session's verification panel on the page shows the run's state, …"), and the reply carries no other clause that depends on the run; a newer commit's run, asked for while the session's run of an older one runs, is queued rather than refused; and the push waits on a run only when the team file requires it and no required review blocks, so the reviews' findings go out at the reviews' own time. A decision after the reviews in a project that requires `verify` sends the agent no held note either, so the end of a run that didn't pass reaches it nowhere; a run asked for while the session's run goes, for a changed command or image too, is queued. What code in the run can signal to the agent is whether and when its push goes out, and nothing more is claimed. A push that needs a run and has none starts one itself, with the reviews for an agent's push, but only for a decision that could push: not for Allow with a reason, Deny or another answer on a held card, not for the refresh of a held card, not from a session whose work type doesn't push, not when the team file's rules refuse the push, and not while the push is held for a missing approval of the requirements or the plan, when reviews don't start either; a failed run isn't started again on its own, and nor is one cut off by an engine restart or a helper error (assumption ASM-17): the waiting push is decided as held, its card asks the person to press Verify this commit, and a `verify` `not-restarted` audit line records it once per run. A page push held for a run isn't pushed when the run ends: the card says so, and the person presses Push again. Allow with a reason overrides the item, recorded as an exception, as for every other item. An agent's waiting push follows one rule: it is decided again whenever any of its commit's pending work settles, and decided only when none is pending (`Pushes.ReviewDone`, guarded by `stillRunning`). Pending work is a verification run of the commit that is queued or running, reviews queued for a free reviewer slot or being resumed (the resume worker's marker is cleared under its lock with the decision to queue the item again), a review start that holds the session's reviewer slot for that commit (`Reviews.Busy`), and a review record still running. Every path that settles work calls it: a run's end (`Verifier.OnDone`, which then starts the next queued run), a review's end (`Reviews.OnDone`), a review start that refuses after holding the slot (`Reviews.OnRefused`, through `Pushes.Settled`), the resume worker, and a decision that itself starts or queues a run (`verifyWait`). A resumed review that finds another review of the session holding the slot (`reviewing`) stays queued. A run of a commit counts as pending for every session of the project at that commit, so a push waits on another session's live run of it too; a run's end decides again every waiting push and refreshes every held card on that commit, of any session, and a queued run is kept, not dropped, while another session's run of that commit is still going. A waiting push whose branch has moved to another commit by the time it would be decided is dropped (`push event=wait-dropped why=head-moved`), not decided for the new commit, which only the agent's or the person's own push decides. Without the team rule the result is shown only and holds nothing. Reviewers don't see it.
- **Restarts and leftovers.** At start every `running` record becomes `interrupted`. The engine sweeps every 5 minutes, first at start, removing each verification container it isn't running and each `/verify/<run>` folder of no live run; the helper removes every verification container at its own start and stop.
- **Page route and audit.** `/api/verify` (`op` `read`, `start` with `kind`, `stop` with `id`, each with `sid`, or `read` and `start` with `repo` for a run on main, "Readiness, project numbers and the decision log"; any other field 400 `fields`) takes the page's usual checks and answers the view: the head, the masked command, the image, whether the team file requires a run, the current run and the session's latest 5. A change broadcasts a `verify` frame with the session id only. Each start and end writes a `verify` audit line with the project, session, commit, kind, state and exit code, never the command or the output.
- **What a pass proves.** That the project's check passes on a clean copy of that exact commit in that image, which removes "the agent said tests pass" and stale results. Not that the tests are good: the agent wrote both the code and the tests. Expect "passes in the session, fails here" when the check needs what only the agent's home or worktree held, or the network.
- **Browser checks (REQ-13).** Code: core `session/verifyfiles.go`; adapter `git/state/verifyfiles.go`; `web/lib/files.ts`. A second kind, `browser`, runs the project's browser command (`Browser` in `ProjectCommands`, `browser` in `project-commands.json`, set on the page with `{op: "set", name, check, setup, image, browser}`, where a missing `browser` keeps the stored one, checked with `CheckProjectCommand`, never from the repository) the same way as `check`: its own run and container, the same tree, image and pass rule, its command file holding the browser command, so each kind has its own Docker exit code. Everything above holds per kind: a run counts for its commit, its kind's command hash and the image digest; a session runs at most one run of each kind at once; the queue keeps one item per session and kind; `"verify": ["check", "browser"]` in the team file needs a pass of each. The browser comes from the project's image, as every tool does (REQ-42), not from the stack's browser stage: the image needs a browser and a folder `/out` owned by `10006:10006` (the stack's `browser` stage has both, so its image works as a project's image). The run has no network, so the app under test starts inside the run and Chromium reaches it over loopback; a test that signs in uses a test user from the repository's seed data, and the engine holds no test account. Playwright doesn't read `CHROME_BIN`, and the recipe keeps no such variable: a project points `launchOptions.executablePath` at its image's Chromium, or sets `PLAYWRIGHT_BROWSERS_PATH` in the command for Playwright's own image.
  - *Recipe.* As above, plus `SF_OUT=/out` and a second mount: the per-run volume `<project>-verify-out-<run>` (labels `dev.software-factory.stack`, `dev.software-factory.verifier=<run>` and `dev.software-factory.verify-image=<digest>`, driver `local`, no options), which the helper makes before the container, at `/out`, read-write, without `NoCopy`, so Docker copies the image's `/out` and its owner into the new volume; with no `/out` in the image the volume belongs to root and the test can't write to it. The recipe comparison counts both mounts. An image volume at `/out` is refused, for every kind. Before it starts the container, the helper looks for a browser in it with Docker's archive route (`HEAD /containers/{id}/archive`) at `/usr/bin/chromium`, `/usr/bin/chromium-browser`, `/usr/bin/google-chrome`, `/usr/bin/google-chrome-stable` and `/ms-playwright`; with none it removes the container, never started, and refuses `no-browser` ("the image … has no browser at …"), which the run records as `error` with that reason, as it does a missing image. `/out` is outside `/work`, so the tmpfs doesn't cap it, and the volume has no quota (the same known limit as `workspace`).
  - *Files.* After the container exits, and before it is removed, the engine asks the helper for `GET /v1/verifiers/<run>/out`, which streams Docker's `GET /containers/{id}/archive?path=/out` of the stopped container (`application/x-tar`), only for an exited container with that volume at `/out`, cut at 128 MiB. The engine reads the tar as untrusted input, one entry at a time and never all of it in memory: only regular files directly in `out/`, named `^[A-Za-z0-9][A-Za-z0-9._-]{0,119}\.(png|jpe?g|gif|zip)$`, at most 20; an image at most 10 MiB, decoded and encoded again as a PNG with the screenshots' `reencoded` (one at a time), a `.zip` (a Playwright trace) at most 50 MiB that starts as a zip file does, kept as bytes and never opened; 100 MiB a run. Links, folders and what is in them, devices, other names, a 21st file, a file over its limit, a non-image named `.png` and what follows a cut are dropped and named in the run's `fileNote` (names the engine doesn't show plainly are counted only, and the note is withheld when it looks like a token). Video (`.webm`) isn't taken. The kept files go through `os.Root` into `engine-state/verify-files/<run>/` (0600 files in 0700 folders), and the run records each one's name, kind (`image` or `trace`), bytes, SHA-256 and, for an image, its size. Files never change a run's state: the pass or fail is the test's exit code, whatever the files show.
  - *Retention.* The files of the latest 3 runs with files per project are kept, 1 GiB in all, the oldest dropped first; a dropped run's record says so. They are deleted with the session (`Verifier.Forget`), with the project (`Verifier.ForgetProject`, on the repository's removal), and by the 5-minute sweep when no record keeps them. `verify-files` is never exported. The helper removes the run's volume with its container (DELETE, the sweeps, and its start and stop), and its list of verification runs includes a run with only a volume left, so the engine's sweep removes that too.
  - *Page.* `/api/verify` answers `browser: {command, hasCommand, required, queued, current, why}` beside the check's fields, and each run its `kind`, `files` and `fileNote`. `{op: "attachment", sid, id, name}` answers an image as `{name, type: "image/png", width, height, data}`, like the screenshots route, and a trace as `application/octet-stream` with `Content-Disposition: attachment` and `nosniff`; the page saves a trace through a Blob and never renders or unzips it, and labels every file as written by the test code, since a screenshot is agent-controlled pixels.

## Readiness, project numbers and the decision log

Code: core `session/readiness.go`, `session/verifymain.go`, `session/protection.go`, `session/metrics.go`, `session/decisionlog.go`; adapters `git/files/tree.go`, `git/state/decisionlog.go`, page `readiness.go`, `facts.go`, `metrics.go`, `decisionlog.go`; `web/components/project-facts.ts`, `metrics.ts`, `decision-log.ts`.

- **Readiness.** `/api/project-facts` also answers `readiness`, one line per kind (`instructions`, `tests`, `ci`, `lint`, `check`, `team`, `protection`), each `found` with what was found, `missing` with a suggestion, or `unknown` with why. The engine lists the root of main's commit with `files.Reader.ListTree` (at most 5,000 entries) and reads `package.json`, the `Makefile` and `pyproject.toml` with the hash-checked reader, up to 1 MiB each, as data. `package.json` counts with a `scripts.test` that isn't npm's placeholder, a `Makefile` with a `test:` target, and `go.mod`, `pyproject.toml`, `pytest.ini` and `Cargo.toml` by their presence. CI is the workflow files `Workflows` read; the check command is the one in `project-commands.json`; protection is the protection lookup, "unknown" when the token can't read it. Nothing is run for these lines. The `verified` line (after `check`, `Verifier.MainLine` in `session/verifymain.go`) is the one exception, below.
- **Check passes on main** (REQ-14). The `verified` line carries `commit`, `at`, `result` (`passed`, `failed`, `running` or none), `code` and `tail` besides the usual fields. It is `found` ("passed on <12 hex>") only for a run on main whose commit is the report's main and whose command hash and image digest are the current ones (the pass rule of "Verification runs"); `missing` for such a run that failed, timed out, ran out of memory, couldn't run, was stopped or was cut off by a restart, with what happened, the exit code and the masked tail; and `unknown` otherwise: no check command or image ("Set a check command first"), never run ("Not run on main's commit <12 hex>; press Run on main"), running, a last run on another commit ("The last run was on X, and main is at Y now"), or one with another command or image. **Run on main** sends `/api/verify` `{op: "start", repo, kind: "check"}`, with `repo` instead of `sid` (both or neither is 400 `fields`). `Verifier.StartMain` refuses as `Start` does (`kind`, `no-helper`, `no-check`, `no-image`, `verify-busy`) and a second run on main of the same project (409 `running`), checks the commands before it fetches, then fetches main with `Repos.Fresh` (the saved token; a failed fetch answers the fetch's error, records nothing and runs nothing), and runs F-01's loop on the fetched commit with the files from the base clone (`/workspace/base/<name>`, `session.RepoFolder`) through the same hash-checked reader and the same container. It answers 202 with the run's `id` and `commit`. `{op: "read", repo}` answers the same view as a session's read, for the project's main: the recorded main as `head`, the latest 5 runs on main, the current one and why the last one doesn't count. A run on main has no session (`sid` empty in `verify-runs.json`), its frame is `verify` with `repo` only, after which the page reads `/api/project-facts` again, and its audit lines carry no session. It never counts for a push: every lookup a session's view, gate item, queue and pending check makes skips runs with no session, and its end decides no waiting push and refreshes no held card. It has no Stop on the page; the time limit ends it. Removing the project drops its runs on main (`Repos.OnRemoved`), so a project added again starts unknown.
- **Numbers.** `/api/metrics` takes `{op: "read", repo}` and answers counts computed on each read from the last 50,000 lines of the audit file (`ReadAll`), `reviews.json`, `sessions.json`, `caps.json` and `prfollow.json`. Pushes are `pushed` lines; Allows are `allowed` lines with the person's reason, as the register of exceptions counts them; review rounds are the distinct commits reviewed on a branch between its pushes; role rates come from `review` and `override` lines; the "after review" counts (`afterCi`, `afterComments`, and the same two for each role) come from `after-review` lines (`ci-failure`, `review-comment`), each key counted once: a role counts the lines that list it as passed, and the project only the lines whose every required role passed. They are read only while a pull request is open for the branch, so a branch pushed with none open counts nothing, and the page calls them counts, not defects; the time to a push needs the session's start in `sessions.json`. Cost is `costUsd` from `caps.json` and the reviews' cost estimates, which the agents report. After an import the reviewer cost also counts `imported/reviews.json`, the display-only copy, and the answer says how much of it was imported (`importedReviewRuns`, `importedReviewCostUsd`); the numbers are only shown, so this reading decides nothing. The answer carries the oldest audit line read, the oldest review and the oldest followed push, so the page says from when.
- **Decision log.** `/api/decision-log` takes `{op: "read", repo}`, `{op: "set", repo, id, name, text, hidden}`, `{op: "add", repo, text}` or `{op: "remove", repo, id}`. The log is rebuilt on each read, from the project's own lines, matched by their URL or, for older lines and merged pull requests, by the project's spans ("Per-project stores"), from the audit file's `approve-requirements` and `approve-plan` lines (kind, date and approval hash), `override` lines, `allowed` push lines with a reason, `denied` push lines, and merged pull requests in `prfollow.json`. Its lines are the engine's fixed text with the reviewer's name, an `sf/<id>` branch and short hashes checked against patterns, and the person's reasons; no agent text, so requirements and plans carry a name only when the person gives one. The person's names, wording, hidden flags and own entries live in `decisionlog.json` by entry id (a hash of the audit line's kind, time, session, commit, hash and reviewer), so they survive every rebuild; a name or text that `flagText` matches is refused, and reasons, names and texts are checked again before they go into the note. Each change writes a `decision-log` audit line with what changed, never the text. When a session starts, the dispatcher sets a note (source `decisions`, at most 4 KiB) with the log's unhidden entries, oldest first, the oldest left out until it fits, which goes with the session's first message like any other engine note.

## The engine's copy of each session's commits

Code: core `session/keep.go`; adapter `git/keep`; page `keep.go`; `web/components/keep.ts`.

- **What is copied.** When a session's turn ends (the agent's `idle` report), the engine reads the branch head and the recorded main with its hash-checked reader and takes the objects the head has that main and the heads copied before lack: the push's own walk (`ObjectsToSend`, at most 128 MiB and 250,000 objects at once). It encodes them as one pack with go-git's encoder, writes it into `engine-state/keep/<sid>/` and adds the head to that folder's `heads` list. A head that is main or the last copied one, or that adds no object, changes nothing, so a branch reset to main keeps its copy. One copy runs at a time.
- **The scan.** Before anything is written, every object goes through the push scan's detectors, at any size: a blob holding token-shaped text or a password in a URL, a tree holding a token-shaped file or folder name, and a commit whose message or identity holds token-shaped text each stop the copy. A blob the person allowed on the push card, by its hash, is copied. Large files and names that only look like secrets don't stop it.
- **Where it stops.** Each commit names its parent, so nothing after a flagged commit is copied. The engine searches the branch's first-parent line for the first commit whose objects hold a flag (a binary search, each step the same walk and scan), copies up to the commit before it and records the flagged commit and the reason, which the page shows. At each later turn's end it checks with the hash-checked reader whether the branch still holds that commit, and copies again only once it doesn't. A head whose new objects are more than the walk reads at once isn't copied either: the copy stays where it was, with that reason, until the branch no longer holds that head.
- **Caps.** 256 MiB of packs or 500 packs per session, after which the engine copies nothing more for that session, and 2 GiB in all, past which a session's copy waits for room at a later turn's end. The page says which cap stopped it.
- **Restore branch** (`{op: "restore", sid}`, or `{op: "restore", sid, commit}` for one kept head). With no `commit` it restores the last copied commit; a `commit` must be one of the heads the copy lists, or it is refused with 409 `not kept` and nothing touched. Refused while the session's turn runs, when nothing is copied, when the branch holds the last copied commit (with no `commit`, or that one) or is at the chosen earlier one already, and, for an earlier head, when the branch holds commits past the last copied one (409 `not copied`), which the copy lacks and the restore would drop. The engine first writes every pack of the copy into the clone's `objects/pack` (all of them, so an earlier head's objects in earlier packs are there, and a later pack adds only objects nothing points at), each with an index it builds from the pack, through an `os.Root` on the clone's `.git`, and reads the commit back with the hash-checked reader. Then it stops the session if it runs and has agent-host remove the worktree (`git worktree remove`, never forced: a worktree with changes that aren't committed is left as it is, and so is the branch). It writes `refs/heads/sf/<id>` through the same `os.Root`, after checking that `refs`, `refs/heads` and `refs/heads/sf` are plain folders and that the ref path is neither a symbolic link nor a folder, and has agent-host add the worktree again on that branch (`existing: true`). Each attempt that got past removing the worktree is an audit line of kind `restore-branch` naming the restored commit, and for an earlier head the last copied one in its reason. A session the restore stopped stays stopped until Wake.
- **Kept heads and their recorded reviews.** The read answer lists the copy's heads, newest first, each with its time, whether the branch is at it, whether it can be restored now and why not. For a head with a review record on the session's branch it lists each required role (the roles `Work.Reviewers` gives for that commit against its merge base with the recorded main, advisory roles left out) with the verdict recorded for that commit: `pass` when every run passed, `block` when a run blocked with no override, `overridden` when the rest passed and the others are overridden, and `none` otherwise, such as a run missing, failed or with no verdict; and whether every role is `pass` or `overridden`. The panel gives each head but the one the branch is at a Restore this button with the usual confirmation, and names the newest head whose recorded reviews all passed. The list is display only and decides nothing: it doesn't recompute the gate, which also checks approvals, team rules, the reviews' trust and whether main still holds the review base, and the panel says so. The kept heads' roles, and whether the branch holds the last copied commit, are read within 5 seconds per read (`keepRolesFor`); past that a head shows as reviewed with its roles unknown (`rolesRead: false`). After a restore the answer's read gets its own 5 seconds, not what is left of the restore's time.
- **Deleted with the session.** `/api/remove-session` deletes the session's folder, and at its start the engine deletes the folders of sessions it no longer has. No push, review or gate reads the copy.
- **Page route.** `/api/keep` (`op` `read` or `restore`, with `sid`, and with `restore` an optional `commit` of 40 or 64 hex digits; another field, or a `commit` otherwise, is 400 `fields`) takes the page's usual checks; a copy at a turn's end and a restore broadcast a `keep` frame with the session id only, and the page reads the route again.

## Export, import and store formats

Code: core `session/backup.go` (the import rules, Clone again in `session/repos.go`, the history-only refusals); adapters `git/state/export.go` (the table of stores), `import.go`, `backup.go`, `drops.go`, page `export.go`; `web/components/backup.ts`; `cmd/server/backup.go`.

- **Format versions.** Every JSON store starts with `"version"`. A field an older engine can ignore keeps the version. A change an older engine would misread bumps it: a renamed, removed or re-meant field, or a new key shape. The engine that bumps it reads the old version and converts it. The version a store reads and writes is its row in the table in `git/state/export.go`, keyed by file name; a store that bumps its version changes its row and writes `writesVersion(<file>)`.
- **The table.** Each file in `engine-state` has one row: kept, kept for display only, kept but off, dropped, or never exported (`tokens.json`, the lock socket `engine.sock`, `engine-version.json`, `import-report.json`, and the folders `keep/`, `backup/`, `review-replies/` and `.import/`). A file or folder the table doesn't know is left out of an export and named in its manifest as left out, so a store added later is never exported by accident; add its row when it is added.
- **Export.** `/api/export` (`{}`) answers a gzip tar stream with its own 5-minute write deadline: `manifest.json` first (the archive format, the engine version, each store's format version and class, what was left out and why, and what the file holds), then each store as it is on disk, the audit files whole, and `imported/reviews.json` when there is one. Nothing is held whole in memory. The page reads the answer with fetch, since the page key travels only in a header, and saves it through a Blob. The page says the file holds the commit email and the person's reasons. Each export writes an `export` audit line with counts only.
- **Import.** `/api/import` takes `application/gzip` with no parameters, at most 256 MiB, with a 10-minute read deadline, and only while the engine has no projects and no sessions. It streams the archive to `.import/` with a cap per file (4 MiB, 40 MiB for each audit file, 4 KiB for `prefs.json`) and 512 MiB in all, so nothing is held whole in memory. It refuses an archive format or a store format newer than this engine reads, any entry that isn't a plain file with a plain name, and any store its own reader refuses. It also refuses, with 400 `archive` and nothing staged, a record the engine's own Add or start would never write, naming the store and the field but not the value: in `repos.json`, a project whose `name` isn't a folder name the engine gives a project (`^[A-Za-z0-9][A-Za-z0-9._-]{0,99}$`), whose `url` isn't what `NormalizeURL` makes of it (a plain `https://` address), whose `branch` isn't a valid branch name, or whose `commit` isn't 40 lowercase hex characters; in `sessions.json`, a session whose `repo` isn't a project in the same archive or whose `repoPath` isn't `<workspace>/repos/<repo>` in this engine's workspace, the folder its start gives a session (`session.RepoFolder`). So an export from an engine with another workspace path, with sessions, is refused. The loaders the engine reads its own files with don't add these checks, so a file an older engine wrote can't stop a start; the clone, fetch and commit copy check the name again before they touch the workspace. A store this engine doesn't know is left out and listed. Everything in the file is outside data, so nothing in it grants an action:
  - **dropped:** `waiting.json`, `forge-cards.json`, `queues.json`, `notes.json`, `agent-settings.json`, `splits.json` (the task cards agents proposed), `verify-runs.json` (so no imported result counts), and the in-memory push approvals and Allows, which an export never holds;
  - **kept for display only**, in `imported/`, where nothing that decides reads them: review records and overrides, `approvals.json`, and `work.json` as exported; the active `work.json` loses its team approvals, the sessions' requirement, plan and flagged-file approvals and their locked tests. A push of a commit an imported review passed needs its review again. `imported/reviews.json` keeps each record's run, and reads a format 1 export as every record's first run. `pairs.json` and `lessons.json` stay in place for display: each pair is marked `historyOnly`, so Start it and Keep this one are refused for it, and suggested instruction lines not yet approved are dropped, also from `lessons.json`'s `removed` entries;
  - **kept but off:** `egress.json` comes back with no added host and no gateway, `keyroutes.json`, `project-commands.json`, `reviewer-agents.json`, `packs.json` (every project uses knackpack until its pack is added and picked again), `prfollow.json`, `package-lookups.json` and `signin.json` come back only as display copies, and `work.json` turns off sending findings on its own, the comment after a push and each project's review depth (advisory roles, repeated runs and deeper review for larger changes), which raises reviewer spending, also in its `removed` entries. The report lists each one, and the person turns it on again on the page as usual;
  - **kept:** caps, denials, away mode (`halt.json`), identity, ports, models, saved prompts, manual test lists, recap marks, viewed marks (`viewed.json`), the update check's last result and the release put off (`update.json`), the person's decision log edits (`decisionlog.json`), drop counts, the page's preferences and the audit. The audit's lines go into `audit.1.jsonl` before this engine's own, keeping the newest 32 MiB;
  - **projects** come back as recorded. One whose clone the workspace doesn't hold needs a clone: **Clone again** (`/api/clone-again`, `{name}`) clones it from its recorded URL as Add does, into the same name, with the host's saved token;
  - **sessions** come back stopped, not sandboxed, with no turn in progress, and marked history only in `sessions.json` (`historyOnly`). Their records, reviews and audit show; the latest imported reviews of their branch show on the session with a note that they count for nothing. Wake, Review, Retry, Override, Explain, plan review, the manual test list, bringing in main, starting from its commit, Restore branch, Start on its split cards (and `factory_split`) and sending it a suggested instruction line are refused, since their worktrees and agent homes stayed on the old stack, and it gets no decision log note; Delete forgets the record without asking agent-host.
  - **settings the engine already has** are kept, not overwritten: identity, away mode, the page's preferences, the update check's setting, drop counts and `egress.json`; the report lists them.

  The import is checked and prepared in `.import/`, audited (`import`, `staged` or `refused`), and the engine restarts itself, as Compose's restart policy brings it back. At its next start, before any store is read, the engine checks again that it has no projects and no sessions and puts the files in place, writes `import-report.json` and an `import` line (`applied` or `refused`), and removes `.import/`.
- **Per-project stores.** `caps.json`, `work.json`'s project settings and team-file approvals (`teams`), `savedprompts.json`, `decisionlog.json`, `lessons.json` and `package-lookups.json` keep each project's entry under its name, and that entry belongs to the project now listed under that name with its URL. Remove moves the entry into the file's `removed` list (`removedTeams` for approvals, `removedSpans` for the decision log's spans) with the project's name and URL (`session.ProjectData.ParkProject`; at most 50 entries with a URL per list, the oldest of them dropped first). A finished Add moves any entry still under the new project's name into `removed` with no URL, then moves back the `removed` entry with the same name whose URL `sameRepository` matches or, when no entry has that name, the newest one whose URL matches, since a repository whose old folder couldn't be deleted comes back as `<name>-2` (`RestoreProject`). So adding the same repository again gets its data back and a different repository with the same name starts empty. Remove marks the name and URL as settling from the moment it saves `repos.json` until its folder is deleted and every store has parked the entry, and a finished clone does the same from its record until every store has restored; meanwhile Add of that URL answers `409 removing`, a clone doesn't take that name, and Remove of a project still being restored answers `409 cloning`. Without that, an Add in the gap could set the old entry aside with no URL before Remove parked it. At every start, once `repos.json` is read, an entry under a name no project has moves into `removed` with no URL (`KeepProjects`, logged per store), the owner's decision of 2026-11-17: nothing says which repository it belonged to, so it stays on disk and is never restored, since an entry with no URL matches no project, one with an empty URL included. Entries with no URL don't count toward the 50. The move empties the name's entry, so a later start finds nothing to move and adds no copy. Each audit line the engine writes now carries `repositoryUrl`: the audit file's writer looks up the line's project name in `repos.json` as it writes, and keeps the URL only when `NormalizeURL` gives it back unchanged, so a URL holding a user name or password is never written (Add refuses those anyway). The decision log, its note to new sessions and the project numbers' audit counts match a line that has `repositoryUrl` to the project whose URL `sameRepository` matches, whatever the name and clock say. Older lines, written before this field, and merged pull requests name only the project, so `decisionlog.json` also keeps each project's spans: the name it had and when it held it, from its record's `addedAt` to its removal, at most 20. Those take only the lines whose name and time fall in one of the project's spans; a restore brings the earlier spans back with their names, so the same repository sees its history again, as `<name>-2` too, and a different repository with the same name has only its own span, from when it was added. A listed project whose stored span doesn't start at its record's `addedAt` gets one that does, the old one set aside with no URL. The numbers' other sources follow the spans too: a session in `sessions.json` counts when its start time falls in one (one with no start time by its name, since Remove refuses a project that still has sessions), a caps session in `caps.json` only when its session is one of those, and a followed pull request in `prfollow.json` when its push time does, or its end time when it has no push time. Data in a `removed` list doesn't count toward the limits the page shows and enforces: the 1 MiB of saved prompts counts listed projects only, and a restore that would take them over 1 MiB isn't made, the entry staying in `removed` (`not-restored`). When a file would pass the 4 MiB the engine reads back, whole `removed` entries are dropped, those with a URL first, then those with no URL, oldest first in each, before any listed project's data is touched (`lessons.json` halves listed projects' findings only after that); this is the one case in which an entry set aside with no URL is deleted, and the dropped records are counted in `drops.json` and logged (`removed-trimmed-to-fit`). When `repos.json` can't be read, nothing moves and `project-data-not-checked` is logged with the error; a store that can't read or write its file logs `project-data-not-saved` with the project's name and the error. `caps.json`, `work.json`, `decisionlog.json` and `package-lookups.json` then remember that Remove's park or Add's restore in memory, at most 100, and apply them in order, with the same rules, at the store's next successful read, before anything else changes the file, so a project added under that name later doesn't inherit the entry; `caps.json`, otherwise read only at start, is read again at the next Remove or Add, and once it reads, its caps are in effect again without a restart. A remembered step lives only in memory: when the engine restarts before the store reads, it is lost and the entry stays under the name, where the next project of that name finds it. `savedprompts.json` and `lessons.json` keep no remembered steps yet, so with them the entry stays under the name. An older engine reads these files as before: it ignores `removed`, `removedTeams`, `spans`, `removedSpans` and the `url` in their entries, so no format version changed, but it drops them when it writes the file; it ignores audit lines' `repositoryUrl` too and matches them by name, as it did.
- **A store the engine can't read.** The engine doesn't write over it and holds what it would have allowed: while `denied.json` can't be read, the agent's push requests are held and the person pushes from the page; while `sessions.json` can't be read at start, no new session starts, with the reason on the page, the file isn't written, and nothing keyed on it is pruned at start (the copies of sessions' commits in `keep/`, port reservations and waiting notes); an unread `work.json` is a missing item on every push ("project settings the engine can read"), so a push hold can't turn off unseen; an unread `caps.json` counts every cap as reached, so messages are refused with the reason and automatic reviews don't start, and the page says it couldn't read them. `halt.json` leaves away mode off (Away mode). A store in a newer format than this engine writes is left as it is: the engine reads the file's format before every write, so also when the file changes while it runs, and then the write fails and the file isn't changed.
- **A copy before a format change.** Before an engine writes a store in a newer format than the file on disk holds, it copies the file to `backup/<version of the engine that last ran>/` (`earlier` when none is recorded), 0700, and keeps the newest 3 folders. If the copy fails, the store isn't written. After a rollback, the older engine reads the copy once it is put back (README, Maintenance). `SF_DEV_STATE_VERSION=2` (development only) makes `savedprompts.json` write and read format 2, so a saved prompt leaves a copy that an engine without it reads after the rollback step.
- **Dropped records.** When `reviews.json` drops records (500 records, whole oldest branches, then 4 MiB), the audit rotation overwrites `audit.1.jsonl`, or `walkthroughs.json`, `notes.json`, `recap-seen.json`, `prfollow.json`, `pairs.json`, `splits.json`, `lessons.json` or `decisionlog.json` drop entries past their caps, the store's save adds the count to `drops.json`. Where the engine trims a list before saving it (the 200 pairs, the 100 split cards, a project's lessons and lines, decision log edits of entries no longer in the log), it hands the store the count with `Dropped`. The Welcome page shows one line per store with how many and since when, and so does Export and import. `SF_DEV_AUDIT_ROTATE=<bytes>` (development only, 1024 or more) rotates the audit at that size, so a drop shows quickly.
- **Page routes.** `/api/export` and `/api/backup` (`{}`: drop counts, copies, the last import's report, projects that need a clone, and whether an import may run) and `/api/clone-again` take the page's usual checks; `/api/import` takes the key, `Host`, `Origin` and `Sec-Fetch-Site` checks of every route, its own content type and cap, and no `X-SF-*` header.

## Request ids, the session audit and diagnostics

Code: core `shared/request.go`, `session/lifecycle.go`, `session/diagnostics.go`; adapters `http/page` `middleware.go` and `diagnostics.go`, `agenthost/server.go`, `egress/status.go` and `refusals.go`, `sandbox/docker/probe.go`, `git/state/person.go` and `owners.go`, `loggers/slog`; `web/api.ts`, `web/components/diagnostics.ts`; `cmd/server/diagnostics.go`.

- **Request ids.** The page server's request logging makes a random id (16 hex digits, `shared.NewRequest`, from `crypto/rand`, never from content) for each page request and each agent listener request, puts it in the request's context, and logs it as `req=<id>` on the `request` line. The core passes that context on, so the log lines of the action's flow carry `req=<id>` (`shared.For`), and so do the audit lines it writes (`req` in `audit.jsonl`, beside the push decision's own `request` id). A review keeps its id for the whole run, which goes on after the page's answer (`ReviewTarget.Req`, `ReviewView.Req`). Work a request sets off for later keeps that request's id: an agent's push request that waits on reviews keeps it with the wait (`Pushes.waitAs`), so the reviews it starts, a queued retry, the push after the reviews and its `allowed` and `pushed` lines, the automatic Send findings and the comment on the pull request carry it; the person's Push, Allow, Send findings, an issue or pull request card's answer and Continue at a usage limit carry the person's request; a held card keeps the id of the request that held it for its later refresh. A wake at the usage reset gets an id of its own. What the engine does on its own with no request behind it (a push resumed after a restart, a card that expires, the sandbox check rounds, sweeps and watches) logs no id. The engine sends the id as `X-SF-Request` on its own calls to agent-host (in a session's container and in each reviewer container, `/v1/key` included; the role-less reviewer runs, the manual test list, Explain this change, Review this plan and Suggest lines carry the id of the page action that started them), to the box helper, which logs its box and reviewer lines with it as `req=`, and to egress's control listener; agent-host logs `agent-host request path=<route> status=<code> req=<id>` and its run and review-run lines with it, and egress logs `egress control route=<route> status=<code> req=<id>`. Both log only a header that is exactly one valid id, and log nothing extra for a call without one. The sandbox probe gets the id as `-request` and sends it as `Software-Factory-Request` beside its marker on each `CONNECT`, so egress logs it beside the tunnels the engine asked the probe to try: as `req=<id>` on the reviewers' side, whose container is trusted, and as `claimed_req=<id>` on the agents' side, since an agent can change what its container sends. Nothing from the agent network sets an id the engine logs as its own: the agent listener makes a new id for every request and ignores any `X-SF-Request` it gets, and only the page side answers with the header. The page shows no id: an error's text is only its reason, and the id stays in the logs and in Diagnostics, where `grep` finds every line of an action.
- **The session audit.** `session-start`, `session-wake`, `session-stop`, `session-fork` and `session-delete` lines record each session's life: the session, its branch, its container (`box`), its agent, who did it (`by`: `page`; `engine` for a stop by a failed sandbox check; `engine, at reset` for a wake at the usage reset the person asked for, which gets a request id of its own), the result and a reason where there is one (the engine's reason for a stop or Restore branch, the Delete choice the person made, a message that woke the session). A start and a fork also carry the start point: `from` (`main`, `branch`, `pull-request`, `fork` or `pinned` for a pair's or benchmark's commit), `fromRef` (the branch or the pull request's number), `source` (the session forked from) and `commit`. A start from a session's commit writes `session-fork` and then `session-start`. The lines hold ids and reasons only, never conversation content. The session's history on the page shows them; `session-fork` and `session-delete` also show in every other session's history of that project, since a deleted session has no history of its own.
- **The local person and owners.** At start the engine reads `person.json` in `engine-state` (`{version, id, made}`), or makes it once with a random 128-bit id: never a name or an email. Every audit line carries it as `person`, and a line written before it existed reads as that person. Every saved record the person creates or decides carries it as `owner`: projects (`repos.json`), start-up approvals (`approvals.json`), team approvals, project settings and each session's approvals and allowed files (`work.json`), overridden review records (`reviews.json`), reviewer agent files and roles, added hosts and the gateway (`egress.json`), caps, check and setup commands, review roles' models, saved prompts, decision log edits, pull request follow settings, key routes, public-registry lookups, the expected sign-ins, away mode, the commit identity, sessions, denied commits and pairs. Saved permission rules are Claude Code's own settings files in the session's container, which the engine doesn't store; their answers are audit lines (`permission-answer`, `remove-allow-rule`). At each start, after an import is placed, the engine writes `owner` into every record of those stores that lacks it (`state.StampOwners`), only in a store its own reader accepts and in a format it reads, and adds nothing else. An older engine ignores both fields, so no store's format version changed. `person.json` is exported, and an import puts it in place (`state.adoptPerson` also updates the id the running engine stamps with), so the imported records and audit lines and this engine's later ones carry one id; an import only goes into an engine with no projects and no sessions, so nothing of its own is lost. The stores this engine keeps as its own (the commit identity, away mode, added hosts and the gateway) have their `owner` changed from the former id to the adopted one, and nothing else in them. The audit is append-only, so the lines this engine wrote before the import keep the former id; the `import` line with `applied` names it as `formerPerson`. An archive without one leaves the engine's own, and the stamping at start gives imported records without an owner that id.
- **Diagnostics.** Diagnostics on the Welcome page (`/api/diagnostics`, `{}`) builds a text file, `software-factory-diagnostics/1`, from fixed fields only: the product version, Go, the engine's OS and kernel, the pinned agents, knackpack's installed version and commit, the branch it follows and its last check, and from the box helper's list answer (`about`) Docker's version, OS, architecture and kernel, the image's ID and the box runtime; the names of the engine's settings, each with its value only when it is one the engine accepts for that setting (a port or the development audit size within its range, a umask the engine takes, the switch words `on`, `off`, `repo`, `1` or `2`) and otherwise `set` or `unset`, and only `set` or `unset` for any that can name a host, path or address; whether the update check is on and its last result kind ("The update check"), never a URL; counts of projects (and of those sending findings on their own, commenting on pull requests or holding the agent's push), sessions and reviews by outcome; and the last 500 events the engine logged, each as time, level, part (the line's component, such as `review` or `push`), event kind, error kind and request id, kept in memory by the logger (`shared.Recent`; a `request` line under 400 isn't kept). Every value must match a fixed pattern of its field or reads `[left out]` or `other` (an event or error kind is lowercase letters, digits, `-` and `_` only), and a line the token detector or the URL check matches is replaced by `[left out]`, so the file holds no repository name, host, path, URL, token, prompt or log text. The page shows the whole file before **Save as a file** saves it with a Blob; nothing sends it anywhere.

## The update check

Code: core `session/updates.go`; adapters `install/releases`, `git/state/update.go`, page `update.go`; `web/components/update.ts`; `cmd/server/updates.go`; the development fake in `dev/gitserver/release.go`.

- **Where it runs.** In the engine only, every 24 hours (`session.UpdateEvery`), in a goroutine of its own. At start it asks GitHub only when the last check stored in `update.json` is 24 hours old or more (or missing, dropped as malformed, or dated in the future); a younger one is reused as it was, with the release it found, so a restart within the day shows the same button, logs `update check` `event=reused` and checks again once those 24 hours are up. It runs in that goroutine so a slow or failing check never holds up a start, a page request or a push. It reaches `api.github.com` over the `outside` network, as the engine's git host traffic does. No session's or reviewer container takes part, and the page only reads the result (`/api/update`), so nothing on the agent network can name a release, and the page never contacts GitHub itself.
- **What it asks.** `GET /repos/bezmoradi/software-factory/tags` (100 a page, at most 5 pages) and then, for the tags newer than the running `Version`, newest first and at most 3, `GET /repos/bezmoradi/software-factory/releases/tags/<tag>`, stopping at the first that counts. Every request is anonymous: an `http.Client` of its own with no cookie jar, never the git host token (the GitHub adapter that holds tokens isn't used), `User-Agent: software-factory-update-check`, 15 seconds a request and one minute for the whole check, an answer over 1 MiB or not `application/json` counted as malformed, and redirects only to the same scheme and host, with `Authorization` and `Cookie` dropped.
- **What it trusts, and why.** The version only from a tag name that is exactly `v<major>.<minor>.<patch>` (no leading zeros, at most nine digits each), since only the owner can create tags (README, "Run it with Docker"); a pre-release tag such as `v1.2.0-rc.1`, `latest`, `v1.2` or anything else is skipped, and versions compare as numbers, part by part. A tag counts only when its GitHub release exists, isn't a draft or a pre-release, and names that tag; otherwise the next newer tag is tried. Nothing else from GitHub's answers is kept or reaches the page: not the release's notes, which anyone with write access to the repository can edit, nor a digest or a command. The panel shows the one install command, `curl -fsSL https://github.com/bezmoradi/software-factory/releases/latest/download/install.sh | sh`, fixed in the page's code, which installs the newest release rather than the version found.
- **What it never does.** It downloads, verifies and installs nothing, and starts no process: Software Factory never updates itself, and the person runs the steps the panel shows.
- **Results.** `newer`; `current` (no tag newer than the running version); `no-release` (no plain version tag, or no published release for the newer ones); `offline`, `timeout`, `refused` (any status but 200, and 404 on the tags), `malformed`; `untrusted` (the server's TLS certificate didn't verify: `tls.CertificateVerificationError`, or an unknown authority, a wrong host name or an invalid certificate from `crypto/x509`), kept apart from `offline` so an intercepted or misconfigured connection shows as such; `own-version-unparsable`; and, when it doesn't run, `off-by-variable` or `settings-unreadable`. Each check logs one line, `update check` with `event=<kind>`, at info level, or at warn level for `untrusted`, and saves its time and kind in `update.json` (`event=not-saved` when that write fails; the result still shows until the engine stops). The page shows nothing unless the last check found a release newer than the running `Version`, so a failed check, `untrusted` included, also hides an earlier find. A found version that isn't newer than the running one is never shown, and a running `Version` that doesn't parse shows nothing; at start, a stored find that isn't newer than the running version (after an update within the day, say) is dropped with the rest of the stored check, so the engine asks again. Diagnostics shows `update check` (on, or why it is off) and `update check result`, never a URL.
- **Settings.** The check always runs: nothing on the page turns it off (the owner's decision of 2026-11-20), and only `SF_NO_UPDATE_CHECK` or an unreadable `update.json` stops it. `update.json` (`{version: 1, later, last, owner}`) holds the version **Remind me later** put off, and `last`, the last check's time (`at`), result kind (`kind`) and, for `newer`, the release found (`release`). `last` is an optional field an older reader ignores, so the format stays version 1. A `last` whose kind or version doesn't match its pattern is dropped, and the engine checks at start; the `digest` and `problem` an earlier engine wrote there are ignored, and an earlier engine drops a `newer` without them and checks again. The `check` an earlier engine wrote there, the **Check for updates** setting it had, is ignored, so a file holding `"check": false` no longer stops the check, and the engine doesn't write it; an earlier engine reading a file without it counts the check as off. **Remind me later** keeps the button hidden until a newer version than that one is found. A file the engine can't read turns the check off, and the engine doesn't write over it. `SF_NO_UPDATE_CHECK` (documented as `1`; any value counts) turns the check off before any request, and the page can't turn it on.
- **Development.** `SF_DEV_UPDATE_API`, an `https` base URL with no user, query or fragment, takes the place of `https://api.github.com`, trusted through `SF_DEV_GIT_CA`. The engine honours it only when its own image has the development marker file (`/usr/share/software-factory/dev-image`), since it would let any server name a release; elsewhere it logs `dev-api-ignored` and asks GitHub. `compose.dev.yaml` runs the engine on the `dev` image for that, and passes the variable from your shell. With it honoured, a stored check is reused at start for one minute instead of 24 hours, so a restart a minute after a change to the fake asks it again. With the marker, the answer carries `development: true` and the panel lists the source steps first.
