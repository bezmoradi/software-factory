# Reference: reviews and pushes

This is part of the Reference section of [ARCHITECTURE.md](../../ARCHITECTURE.md#reference), which describes how Software Factory works and why.

## Reviews

Code: core `session.Reviews`, `review.go`; adapters `git/files` `Reviews` for snapshots, `git/state` `Reviews` for `reviews.json`.

The page's Review button (`/api/review`, `{sid}`, with `all: true` for Run all again) works for a session this engine started. The engine reads `refs/heads/<session branch>` from the clone with the hash-checked reader, fetches the main branch from the recorded URL  and takes the merge base of the two with the hash-checked reader (`files.Reader.MergeBase`, newest-first parent walk, at most 200,000 commits); that is the review's base, recorded in each review record, and an empty base (no shared history) means an empty `base/`. It refuses when the head is the base (nothing the main branch lacks). It compares egress's lists with its own (the global part of the sandbox check); a failure means no review starts, and the page shows why. Each role's run then gets its own reviewer container, whose probe runs through that container's agent-host, asking `egress-review:3128`, before the run; a failure there fails that role with the reason. Then it writes `<id>/base`, `<id>/head`, `<id>/change.diff` (the unified diff of head against base, written by the engine with go-git's diff encoder from the diff of the two trees, so it holds only paths whose blob or mode changed, and a submodule pointer shows as `Subproject commit <sha>` on each side) and `<id>/commits.txt` (the messages of the commits from base to head, oldest first, read with the engine's own reader: the newest 200, each clipped to 4 KiB and stripped of control and escape characters, each of its lines indented and starting with a bar (`|`) so it can't pass for one of the engine's notes, 256 KiB in all; a message that holds a token-shaped string, as written or once stripped, is left out with a note), `<id>/rules/`, `<id>/approved/` and `<id>/claims.md` ("Review, then push"; `session/reviewrules.go` and the snapshot adapter's `rules.go` for `rules/`; `session/reviewgiven.go` for the others: each file opens with the engine's note on what it is, every line stripped of control and invisible formatting characters, and a text the token detector matches is left out, which the prompt names) into the `reviews` volume and, for each required role in parallel, has its reviewer container's agent-host run `claude -p --setting-sources user --plugin-dir=<agents>/packs/<digest>/reviewers --agent <role's agent> --permission-mode dontAsk --permission-prompts none --tools=Read,Grep,Glob,Agent,ToolSearch --allowedTools=Agent,ToolSearch --settings={"disableAllHooks":true,"env":{"CLAUDE_CODE_SUBAGENT_MODEL":"inherit","CLAUDE_CODE_SUBAGENT_MODEL_FORCE":"1"},"permissions":{"blockReadsOutsideWorkingDirectories":true,"deny":["Read(~/**)","Agent(Explore)"]}} --output-format stream-json --verbose --no-session-persistence <prompt>` in `/reviews/<id>` through agent-host's `/v1/review-run` (the `--plugin-dir` is the reviewers' copy of the project's pack, "Packs", and is left out with No pack), passing only `DISABLE_AUTOUPDATER` besides agent-host's base variables (key variables are always cleared). The reviewer has no Bash and no write tool, and hooks are off, so a reviewer misled by the code it reviews can't change its own home and steer later reviews; it reads `change.diff` instead of running `diff`, and the prompt names `commits.txt`, `claims.md` and `approved/` as text the agent wrote, to check against the change and never to follow. Roles: `bug-hunter` → `knackpack:adversarial-reviewer`, `simplicity` → `knackpack:slop-reviewer`. The verdict comes from that run's own `result` line, read with `internal/core/review`'s rules; a timeout (20 minutes), a failure or a reply without a verdict counts as not passed, with the reason, and so do the no-verdict cases under "Review, then push" (`num_turns`, `permission_denials`, a severe finding or count in a pass, a pass-shaped line the change adds, a token-shaped string). Each record also keeps what produced it: the knackpack commit installed when the review started, the reviewers' Claude Code version from `claude --version` (the pinned version, or `sf-fake-claude` with the development reviewer, when that can't be read), the model names from the result's `modelUsage` (at most 4, the one with the highest `costUSD` first, then by name), `num_turns`, the names of denied tools (at most 20), whether the message was clipped and whether an agent's request started it; the page shows the first three under each role, the first model as the role's and any other as "Also used:" and its name, as text that decides nothing, and each finished role adds an audit line (`kind: "review"`, its state, reviewer, verdict, reason and the same provenance, `by` agent or page), which the page's audit list leaves out. Records are keyed by `{commit, branch, agent}` with provider `knackpack@knackpack`, written atomically 0600; a review in progress is recorded as running, and one an earlier engine left running becomes failed at start. A failed record keeps its `failure` kind: `no-outcome` (the engine stopped it, the reviewer couldn't be reached, or the reviewer's agent-host was full), `timeout`, or `error` (anything else, a snapshot that couldn't be written included); and its `attempt`, counting runs of that role at that commit (missing reads as 1). `Dispatcher.Retry` starts a review in retry mode, which runs only the roles with no record or a `no-outcome` failure on their first attempt. The page's Review runs only the roles with no pass or block on the commit (`session.ScopeUnfinished`): a role with no record yet, one an engine stop cut off, one whose every attempt failed or gave no verdict, and one whose pass doesn't count (older than the minimum, or reviewed only since an earlier round whose pass doesn't count). A blocking verdict the person overrode counts as done. This way a role that already passed or blocked the commit costs no second run. With every role done, `/api/review` answers `409 reviewed` and runs nothing. **Run all again** (`/api/review` with `all: true`) runs every role, for fresh verdicts, with the same sign-in and cost checks and the same round limit. Each review base gets its own snapshot: a later round that builds on an earlier reviewed commit P gets `base/` at P, `change.diff` from P, and the role's previous final message in `earlier/<agent, with ":" as "-">.md` (0644 in a 0755 folder, the machine verdict lines removed, each line stripped of control and escape characters, left out when it holds a token-shaped string); the prompt names that file and asks for the reviewer's own findings first; its record stores `since` (P) and `covers` (P's coverage), and a blocking P whose whole reply was clipped (or, with no whole reply kept, whose message was), or whose record has `shaped` (a pass-shaped line in the change, or a change too large to check for one), starts a full review instead. Rounds are counted from the records per branch and agent (reviewing the same commit again isn't a new round); a role at the project's limit whose last verdict blocks and wasn't overridden is skipped, and `/api/review` answers `409 capped` when no role is left. `/api/override` (`{sid, agent, commit, reason}`) sets `Record.Override` on a blocking record of the branch's current commit; a record that replaces it for the same commit, branch and agent keeps it. The snapshot folder is removed once every verdict is recorded; the record keeps the reviewer's final message, clipped to 4,000 characters: a longer one keeps its start, a line saying the middle is left out, and its closing `knackpack-findings/` and `knackpack-verdict/` lines. The whole reply, clipped at 64 KiB to its start and its last 16 KiB from a line's start (more, up to 32 KiB, when its finding and closing lines need it), with the middle marked as left out (`keptWhole`), goes to `review-replies/` (`state.Replies`), written through a temporary file and renamed, only after the token detector passed the reply as a whole; it is read back only for the same session, key and start time, a file whose record is gone is removed when the records are next saved, and Delete removes the session's files. Send findings, the issue cards, the lessons, a later round's `earlier/` file and the review panel read the whole reply; a record without one (saved before it existed, or after the file was lost) falls back to its 4,000 characters. The panel shows the 4,000 characters as the reply's summary and, when the reply is longer, **The whole report** under it, collapsed: the sessions list carries only `hasFull`, and opening the box reads the reply with `/api/review-reply` (`{sid, agent, commit, run}`; `Dispatcher.WholeReply` looks up the record on the session's branch and answers its whole reply, at most 64 KiB, or 404), which the page keeps per role and shows as text. An export leaves the folder out. The session's last review reaches the page with the sessions list (`review` on each session). That view is kept in memory (`Reviews.views`). So that it can be rebuilt, each run also keeps, when it starts (once its snapshot is written and its prompt made, before the reviewer runs), what the panel shows under "What this review was given" and why the role was required: `Reviews.keepGiven` writes `<session hash>-<key hash>-given.json` in `review-replies/` (`state.Replies.PutGiven`), 0600 through a temporary file and renamed, with the session, the key and the start time, the reason (at most 1,000 bytes), and the prompt (clipped like a whole reply, to 64 KiB with its start and its last 16 KiB), the flags (at most 32, 2 KiB each) and the file names (at most 41, 512 bytes each); a part the token detector matches is left out, and a file larger than its bound isn't written or read. It is read back only for the same session, key and start time, so a later run of the same key replaces it and an older one is never shown with a newer run; it goes with its record when the records are next saved and with the session at Delete, an export leaves it out with the folder, and nothing but the rebuilt panel reads it. It is a new file kind with its own format version, so the reply files' format is unchanged and no copy before a format change applies (the folder isn't one of the stores that rule copies). When the engine starts, `Dispatcher.Restore` rebuilds the view from `reviews.json` for each restored session that holds its branch (`Reviews.ShowKept`, `session/reviewkept.go`), so the panel doesn't go back to "No review of this session yet" after a restart. It takes the record on the session's branch that started last, and shows every record of that commit on the branch, as the gate counts them (`Reviews.Entries`): each role's state, verdict, reason, override, final message, findings, cited IDs, provenance and cost, "The whole report" when the session's own whole reply is kept, why it was required and what it was given when its `-given.json` file is kept (a run from before that file existed shows neither), the round from the records and the project's current round limit, and "run n of m" with m the highest run recorded for that agent. The review's cost is the sum over the records of its last start, the session's cost the sum over the branch, and its base the base of a full review of that commit, or the coverage of an incremental one when the commit has no full review. A review the engine stopped shows as failed with the stop as its reason, so the page offers Review again; a stored manual test list, plan review or explanation joins it as before. A pass that counts could have been set aside since by a change to the approved texts or team rules, which only the approval recheck (`ApprovalMoved`) knows, and the engine doesn't run that recheck at start: it reads the whole workflow, and the documents a session reports aren't back until it reports them again. So until the first recheck for that session after the restart (a report of new documents, an approval, a change of work type or team file, or a new review), each such pass is marked (`unchecked` on the role): the panel says once, at its top, how many passes haven't been rechecked against the current approved texts and team rules since the restart, and each of those passes carries a "not rechecked" tag next to its state; the recheck removes both and sets aside what it should. What the live view held and no record keeps is left out rather than guessed: the progress line (run time and tool calls), the sign-in checked at its start (the panel shows the reviewers' current one), its request id, the panel note (a round limit or a missing plugin; the gate rows still name both), and a review that didn't start at all, which writes no record. A history-only session (its imported reviews, if any, are shown instead), a session the engine no longer knows, and records of any other branch get no rebuilt view. The rebuilt view is shown on the page and, as a live view is, read by the note the engine sends a session's agent after a compaction (`CompactNote`, which reviewers' blocking findings are open, on which commit) and by the offer of issue cards from passing reviews' non-blocking findings (`findingsAt`, which takes the view's commit); before this change both found no view after a restart. The gate, the push, overrides, rounds and Retry read the records, as before. Nothing on the agent listener reaches the reviews. In `change.diff`, files over 1 MiB are listed as changed without their content, and the diff stops at 32 MiB with a note. The snapshot writer refuses a tree with a name that isn't valid UTF-8 or holds a backslash, a control character, U+2028 or U+2029 ("the tree has a name the snapshot can't hold"), so no file name can put a line of its own in `change.diff`; that review fails and the push waits for the person. The snapshot reader's errors show a path's control and invisible characters as `⟨U+000A⟩` and the like, so a name can't put a line break into a review's reason, the push view or the audit.

**Reviewer agent files** (`session/agentfile.go`, `session/revieweragents.go`, the page's `/api/reviewer-agents`, agent-host's `/v1/agents`, `git/state` `ReviewerAgents` for `reviewer-agents.json`). The person adds a Claude Code agent file on the page for one project, bound to the project's name and the URL recorded at clone time, so a later project with the same name and another URL gets none of it. The engine refuses a file over 192 KiB, one that isn't UTF-8 or holds control characters, and one whose front matter (between two `---` lines, one `key: value` per line, values plain or quoted on one line, `tools` also as a list) holds any key but `name`, `description`, `model` and `tools`, naming the reason: `mcpServers` would start programs and `hooks` run commands in the trusted reviewer container, `permissionMode` changes what the reviewer may do without asking, and `skills` loads instructions and scripts reviews don't allow. `name` is lowercase letters, digits and hyphens (at most 64), `description` is required, `model` is an alias or a model id, and `tools` lists only tools reviews allow (`ReviewTools`). A project keeps up to 4 files and the engine 12. The person picks a file for the bug hunter or simplicity checker role in the same panel; `Work` takes the pick in place of the agent of the project's pack when it works out the required reviewers, so the gate needs that agent's pass, and removing the file drops the pick, so the role falls back to the pack's agent, or to none with No pack. Each add, replacement, removal and pick is an audit line (`reviewer-agent`) with the file's SHA-256, never its text.

The agent a role runs is `<name>-<the first 12 hex digits of the file's SHA-256>`, so a new version is a new reviewer whose verdicts start afresh, and a file name or agent name can only be one the engine made: agent-host accepts only `sf-<name>-<12 hex>.md`, through an `os.Root` on the folder. Before each review the engine sends a reviewer container's agent-host (`/v1/agents`, keyed like every review route, 1 MiB; a container with no snapshot, started for this) the files that review's roles use and the names of every file it still keeps. agent-host checks each file again with the engine's parser and that its `name` is its file name, writes it 0600 in Claude Code's user agents folder (`$CLAUDE_CONFIG_DIR/agents`, else `~/.claude/agents`) and removes every other `sf-*.md` there, so a removed file goes at the next review. The engine writes the front matter again from what it accepted (the name it made, the description quoted, model and tools) and keeps the body as written. A role whose file can't be written fails with the reason; the others run. The review's prompt asks such an agent to end with `Verdict: pass` or `Verdict: block`. The role's record names the provider `page-upload`, and the gate accepts it as an agent from the reviewer's own user settings.

A file in the repository's `.claude/agents/` with the same name is never used, for two reasons in the command line: `--setting-sources user` leaves out the project source, which is what loads `.claude/agents/` (Claude Code's documentation of setting sources), and the run's working folder is the snapshot's folder, whose `head/` and `base/` hold the repository, so no `.claude/agents/` lies between it and the filesystem's root. The repository can't write the reviewer's home: the reviews volume is read-only there and reviewers can't write files. Files of other projects stay in the same folder until they are removed, so a reviewer's `Agent` tool could start one as a subagent; it runs with the same read-only tools and limits. The body is the person's own instructions, run in a trusted reviewer container on the code under review: the engine checks only its front matter.

**The manual test list** (`/api/test-list`, `{sid, costOk}`; `session/testlist.go`) is a reviewer run without a role: the same snapshot of the head against the merge base, the same sign-in and cost check, the same sandbox check, in a reviewer container of its own, and the same command line as a review (`TestListArgv` is `ReviewArgv` without `--agent`, so a later change to the reviewers' flags applies to it too), with a prompt asking for the steps to try by hand. It counts toward `MaxReviewerRuns` (the running set holds `test-list:<sid>` next to the sessions being reviewed), one per session at a time. The reply, clipped to 16,000 characters, is kept per session with its commit and reaches the page in the session's review view (`testList`); a reply the token detector (`flagText` in `session/flag.go`) matches isn't kept or shown, only that it was withheld. It records no verdict, writes nothing to `reviews.json`, and never reaches the gate or the agent.

The prompt asks for the list as a walkthrough: numbered steps, at most 30, each with what to do, `Expected:` and `Input:`, a sample value from the change or none. `session/walkthrough.go` reads those steps from the reply, each field stripped of control and invisible formatting characters and clipped to 400 characters, and the page shows them as a numbered list with a check-off box each. A reply with no numbered step is shown as text. `/api/walkthrough-check` (`{sid, commit, step, done}`: the walkthrough's 40-hex commit, the step's number from 1 and a boolean) checks a step off or clears it. It refuses a step of a walkthrough a newer one replaced, and only the person changes a step: a new list starts with every step unchecked, and nothing marks one done by itself. A check-off records only that the person tried the step, never a verdict. Each session's latest list and its check-offs are saved in `walkthroughs.json` in `engine-state` (`git/state` `Walkthroughs`), 0600, the newest 200 sessions, within the 4 MiB a state file may hold, so they survive a reload and an engine restart; a list an earlier engine left running comes back failed.

**Progress while a review runs.** `/v1/review-run` takes the same request as `/v1/run` and answers `application/x-ndjson`: a `progress` line (`elapsedMs`, `toolCalls`) each second the tool-call count changes and at least every 5 seconds, then one `end` line with the exit code, the elapsed time, the tool calls, a 64 KiB stderr, the run's last `result` line and its last `rate_limit_event` line. agent-host reads Claude Code's output line by line without a limit on the total, so a review that reads more than 16 MiB still records its verdict: it skips each line whose type isn't `result`, `assistant` or `rate_limit_event`, counts the `tool_use` blocks of assistant lines up to 4 MiB, and keeps only the last `result` line up to 16 MiB and the last `rate_limit_event` line up to 64 KiB. The engine's client (`agenthost/reviewrun.go`) refuses a line over its cap, an unknown field or frame type, a count out of range, more than 20,000 frames and anything after the `end` line. The page shows a running role's elapsed time, ticking each second, and its tool calls; the engine passes them on when the count changes or every 5 seconds. A finished role shows how long it ran and its tool calls. Each role run this engine started also shows what it was given: the exact prompt, Claude Code's flags in order and the review folder's file list (`base/` and `head/` with their commits, `change.diff`, `commits.txt` and the engine's files beside them). Those are kept with the session's review view in memory, not in `reviews.json`; no environment value or credential is in them, since the command line holds none. The engine parses the last `rate_limit_event` strictly (`session.RateWindowsOf`: a line up to 64 KiB, `rate_limit_info.unifiedWindows` with `five_hour`, `seven_day` and `seven_day_overage_included`, each a utilization from 0 to 10, a reset in whole Unix seconds and a status of `allowed`, `allowed_warning` or `rejected` when it has one; any other window or value is dropped) and hands the windows to the handlers registered with `Reviews.OnRateWindows`, side `reviewers`. They are Claude Code's own report, read as data: they can't allow a push or pass a review.

The prompt is one argument of that command line. The previous message is a file now, so nothing is cut from it, but the team rules are in the prompt, so a long team file makes it longer. The engine sets no limit of its own: agent-host takes arguments up to 32 KiB each (`agenthost.MaxArg`; environment values stay at 4 KiB), below Linux's 128 KiB per argument, while its 64 KiB request body bounds the whole command line. A longer prompt is refused, and the role fails as `host-refused:argv`. When the helper can't start the role's reviewer container, or its agent-host refuses or can't be reached, the role fails with a plain reason, and the page shows it once beside the Review button with what to do next: press Review again, or allow the push with a reason.

## Logs of refusals and failures

These lines name a kind, never content (no prompt, reply, path or URL). A line logged for a page action or an agent request also carries that request's `req=<id>` ("Request ids, the session audit and diagnostics"):

- `review event=finished state=failed why=<kind>` (WARN): `host-refused:<agent-host's code>`, `host-unreachable`, `timeout`, `engine-stopped`, `not-claude-json` or `claude-error` (the record's `failure` is `no-outcome` for `engine-stopped`, `host-unreachable` and `host-refused:full`, `timeout` for `timeout`, `error` for the rest); a reply without a readable verdict logs `state=unknown` with `no-verdict` or `two-verdicts`, and the other no-verdict cases with `denied-read`, `verdict-shaped`, `shallow`, `severe-pass` or `token-in-reply`; a pass whose result has no `num_turns` logs `state=pass why=turns-unknown`.
- `reviewer container event=started|removed run=<id>` (INFO), and `event=not-started|key-refused|sandbox-failed|not-removed run=<id>` (WARN) when the helper didn't start one, its agent-host refused the engine's key, its probe failed or the helper didn't remove it (the engine's sweep then does, `event=leftover-removed`); the helper logs `reviewer action=start|remove|sweep|make_home run=<id> outcome=ok|refused reason=<reason>`, and `egress event=dropped side=reviewers` counts connections to the reviewers' proxy from outside a reviewer container's /28.
- `review event=agent-files-not-written uploaded=<n>` (WARN) when agent-host refused or missed the agent files; with `uploaded` above 0 the roles using them fail.
- `review event=refused why=auto-capped` (INFO) when an agent's request would pass the automatic-review cap; `push event=findings-sent|findings-not-sent|findings-withheld` and `push event=findings-not-automatic why=reviewer-sign-in|session-sign-in|auto-capped|not-sent`.
- `push event=card-refreshed missing=<n>` (INFO) when a review that finished refreshed a held card, and `push event=card-kept why=target|branch|head-unread|head-moved|card|outcome` when it left the card as it was: the session has no target, its branch changed, its head couldn't be read or moved off the card's commit, the card expired or was answered, or the evaluation ended other than held (`was=<result>` names it).
- `request refused side=agent route=<route> why=<kind> box=<id>` (WARN) when the engine's agent listener refuses a request from a session container: a browser's headers, a connection or push secret that isn't that container's, a registration another container's session holds or one that isn't valid, an unknown connection, events while a batch is still read, or a 401, 409 or 5xx from what it asked; `box` is the 16-hex container id the engine took from the connection's source address, never from the request, and is left out when the address isn't a session container's. A limited registration logs `registration limited side=agent box=<id>`.
- `agent-host request refused path=<route> status=<code> why=<code>` (WARN) for every refused request; a path that isn't one of its routes is logged as `other`. Asking to stop a process that already ended isn't logged.
- `plugin relay event=client-gone` (INFO) when Claude Code's plugin drops its request, as it does when Claude Code exits; `event=engine-unreachable why=dial|timeout|other` (WARN) only when the engine's agent listener didn't answer.
- `egress event=refused reason=<reason> host=<name> side=agents|reviewers` (WARN): which listener refused it, and the `CONNECT` host, and on `sni_mismatch` the ClientHello's name as `sni=`, so the person can tell what a session was refused. Only a valid host name or IP address is logged (an agent chooses it, so anything else is logged as `(not a host name)`); a `CONNECT` request carries no path. A name an agent chooses can still carry data it puts in it, in the person's own log.
- egress also counts each refusal by listener, host and reason, at most 200 per listener, the least recent dropped first, for the page's Network access (`GET /refused`): the `CONNECT` host, the TLS name on `sni_mismatch`, and the host of a plain-HTTP request on `method`, never a path. The counts start again when egress restarts. Each session's container reaches egress from its own /28 network, which egress admits only while the engine has set it, and egress keeps the sandbox probe's marked refusals and its log rate limit per network; these counts and the `refused` log line, though, are kept per listener and host, not per network, so Network access doesn't say which session a refusal came from. `egress event=closed reason=revoked` when a tunnel's host was removed or expired.
- `egress allowlist event=set|not-set|restored|expired|unreadable` (INFO or WARN), with only the number of hosts on each side; the page logs `egress allowlist op=<op> ok=<bool>` for each change.

## Pushes

Code: core `session.Pushes`, `pushes.go`; adapters `git/push` for the transport, `git/files` for heads, ancestry and changes, `git/state` `Audit` for `audit.jsonl`.

The agent's `factory_push` (`/push-request` on the agent listener, authenticated by the session's push token, no input) and the page's Push button (`/api/push`, `{sid}`) take the same path, for a session this engine started: the commit is `refs/heads/sf/<id>` read with the hash-checked reader, the remote is the URL in `repos.json` with the token saved for its host. The engine asks the remote for its refs (`Pusher.Remote`); when the remote's `sf/<id>` already points at the head, the request ends `up-to-date` with no card (the agent hears it as pushed, and a held card for that commit is dropped), so a commit already on the remote never offers Allow or Deny. Otherwise it fetches the main branch (refused when the two disagree, or when the session branch is the remote's main branch), and decides with `gate.Push`: the session's work type (`fix` when the engine holds no work facts for it) with its roles filled by the engine's reviewers (offered as `knackpack@knackpack`), the review records, the session's level from the engine's own sandbox checks, and an item for every review whose recorded base isn't an ancestor of (or equal to) both the remote's main and the head ("review again, the remote's main moved"). Workflow items the plugin reports come from the session's container and never reach the gate (guidance only). Allowed: go-git pushes from an in-memory pack to `refs/heads/sf/<id>`, never forced, with the remote branch's commit the engine saw as the expected old value, so a branch that moved in between fails with the reason. Held: the session's push view carries a card (random id, commit, branch, remote, missing items, expiry 15 minutes); the page answers it with `/api/push-answer` (`{sid, card, commit, allow, reason}`): the card and commit must match, Allow needs a reason when items are missing and re-runs the whole decision with a `gate.Answer` bound to that commit, branch and remote (single use); Deny ends it: the engine remembers every denied commit per session in `denied.json` (the newest 20), so neither a later `factory_push` nor reviews that finish afterwards push it, also when the branch moves away and back (Hand off does the same); the person's Push frees only the head it reads when pressed and Allow only the card's commit, and a decision whose head turned out to be another denied commit pushes nothing. A held request from the agent of the same commit keeps the card. When the agent's request is held and misses the person's approval of the requirements or the plan (`gate.Decision.NeedsApproval`, set from the workflow items that ask for an approval, `workflow.Items`, never from the items' wording), the engine starts no review: the agent hears that reviews start when it pushes after the person approves on the page, and that the person can press Review any time. The reason: such a commit can't be pushed before the approval, so reviews started then (for example on the commit of the requirements alone) spend the reviewers' sign-in on a push that can't go out. Otherwise, when the agent's request is held and no review of its commit has a record yet, the engine starts the reviews (`StartReview`, `Dispatcher.AgentReview`) and remembers the commit; when they finish (`Reviews.OnDone` → `Pushes.ReviewDone`) it decides that request again (audited `by: "agent, after reviews"`), so a background session's work is pushed without the person when every review passes, and otherwise waits on the card. Reviews of a held card's commit that finish later, when the engine isn't waiting on that commit (the ones the person starts with Review included), never push it: the person presses Push. When the agent asked to push that commit while those reviews ran, the engine waits on it, and its request is decided and pushed as above. They only refresh the card (`Pushes.heldReviewed`, a decision that evaluates the gate and stops before any push), while the card hasn't expired and the branch is still at its commit. The card then shows the current reason and missing items; when every review now passes, it says so and asks the person to press Push. The refresh replaces the card only while the same card (commit, branch and remote) is still held and, by the clock at that moment, hasn't expired; it keeps the card's id, expiry and sent findings, and takes Hand off and Send findings from the current outcome. Nothing is written to the audit, the agent hears nothing, and no findings are sent. When that evaluation ends any other way (the remote can't be reached, the branch moved, the commit is already on the remote, the record of denied commits can't be read), or the card expired or was answered meanwhile, the card stays as it was and the page isn't updated. A review that finishes while another decision of the session runs refreshes the card once that one ends. Finished reviews of a commit aren't started again by the agent; the branch moving on drops the old request. The agent's calls are capped at 5 per 10 minutes per session (refused past it, one audit line per window). Before deciding, the engine reads what the push carries (`git/files` `pushed.go`: every commit from the remote's main to the head, each against its parents, at most 1,000 commits and 32 MiB of content) for flagged files and Git LFS paths; an LFS path refuses the push, and each flagged file is a missing item until `/api/allow-file` (`{sid, path, digest, reason}`, refused as `stale` when the flag's digest isn't the one the page sent, bound to the path and the flagged blob hashes, kept with the session) or until a new commit removes it; `/api/flag-remove` sends the session a message asking the agent to remove the file and add it to `.gitignore`, or, for a file under `proctor/` or the root Makefile in a project that uses Proctor, whatever its flag's kind, to take the branch's change to it out of every commit and leave `.gitignore` alone. `/api/send-findings` (`{sid, card, commit}`, checked like `/api/handoff`) sends the session the blocking reviewers' messages for the card's commit ("Send findings" under "Review, then push"); it refuses an expired or other card, a push being decided, the round limit, a commit with no blocking message, a second send and a token match, and answers 409 with the reason when the session isn't running and controlled from the page. The push view carries `findings` (the card offers it) and `findingsSent`. Each attempt is an audit line with `kind: "findings"`, `result` `sent`, `withheld` or `not-sent`, and the reviewers' names, never the text. A role capped by the round limit is a missing item ("the developer's decision on …") and the card offers Hand off (`/api/handoff`), which sends the handoff message first and denies only once it was delivered. After a push that went out (never up-to-date), `Pushes.OnPushed` hands the engine's facts about it (`PushedFacts`: commit, branch, who caused it, how many items an Allow covered, each required role's result and scope from the review records) to `Forges.AfterPush`, which may comment on the pull request (Issues, pull requests and CI results). Every request ends as pushed, up-to-date, held, denied, refused or unclear, appended to `audit.jsonl` (time, session, repository, branch, commit, remote URL, by, result, reason, missing items, the person's reason, and for exceptions their kind, reviewer, verdict, path and blobs; rotated to `audit.1.jsonl` past 32 MiB; an entry's `reason` is cut at 16 KiB and its `missing` at 100 items and 64 KiB, the last saying how many more the page's gate panel lists, and the push card carries the same bounded list, so no decision makes a line large enough to rotate the audit away); reasons are cleaned of the token, and every audit line is masked as it is written, approvals and allowed files and commits included: each match of the token detector in the reason, the person's reason, the path and the missing items, and a token cut short where a reason was clipped, is replaced by `[hidden: looks like a secret]`, so the git host's answer to a push, a failed call's reason, an issue or pull request title and a review's reason don't carry a token into the file or the page. `/api/audit` returns the newest 50 lines for the session's repository and branch, together with that repository's project-level lines (no branch) of kind `reviewer-agent`, `approve-team`, `forget-team` and `approve-startup`, and the counts of refusals `/check` made in that repository (push-shaped commands, held remote tools, protected writes, cloud hand-off commands), kept in memory, so the page can suggest a CLAUDE.md line. The push view reaches the page with the sessions list (`push` on each session). `/api/changes` (`{sid, from?, commit?}`) returns the session's commits (at most 100), changed files and unified diff (go-git's encoder, in memory, 1 MiB at most) against a base the engine picks for `from` ("Changes view" in "Recap, workspace, register and notifications"), by default the merge base with the main branch as last fetched (no network). Before reading a file the engine probes its blob: the size from a whole object's loose or pack header, or a delta's declared result size from the start of its data, and, for a whole object over 1 MiB, its first 8,000 bytes. A file over 1 MiB is decided from that size before the 8 MiB is charged: it is a candidate for `binary` only when the probed copy is a whole blob of at most 100 MiB whose first 8,000 bytes hold a NUL, and only within 64 MiB of such candidates a request; otherwise it is listed `large`. A candidate is listed `binary` only when the same copy is proven to be the named blob and is binary in the same read: the engine streams it through the reader's hash (`blob <size>`, a NUL and exactly that many inflated bytes, then reads to the end of the stream and requires nothing more), checking the request every 1 MiB and holding only the first 8,000, runs the NUL test on those first 8,000 bytes of the hashed stream, counts the stream's newlines, and compares the hash with the blob's name. The probe's own bytes only choose whether to try, so a copy swapped between the two reads can't decide it. A copy that isn't a whole blob or doesn't match is listed `large`, and no other copy is tried for the binary verdict. The declared size is checked against the reader's 4 GiB work limit, without overflow, and charged to it. A file at most 1 MiB that would take the request past 8 MiB of file contents is listed `budget`. A probe or read that fails on the file's own object (a corrupt object, or a size header that doesn't match its content, which an agent can plant) lists the file `unreadable` and the rest of the view goes on; only a context that ended fails the request. Each listed file carries `notDiffed` and its `size` (as its probed copy declares it), shows in the diff only as changed, and the view names it and why. Reading a file under those limits is bounded separately: while it is read, the file's own object may be at most 1 MiB, every delta base and delta stream at most 4 MiB, and everything inflated for file contents in the request, bases and intermediate results included, at most 256 MiB; each limit is checked from the header before the object is inflated, before the reader's 100 MiB cap. A read that hits one of these lists the file `large` or `budget`, and it stops at the first object past a limit rather than looking for another copy, so a corrupt object can't hand the read on to a larger one. A `large`, `budget` or `unreadable` file marks the change `Uncounted`, which the push hold and the review-depth rule treat as over. A `binary` file never counts as 0 lines: the change carries `UndiffedLines`, the lines of both sides of every file listed `binary`, whichever side is binary (a text version on the other side included, since the diff then shows the file only as binary), counted as newlines plus one for a non-empty side whose last byte isn't a newline (a submodule side counts as the one `Subproject commit` line its diff would show), while hashing for a binary side over 1 MiB and from the bytes read for a smaller side; a diffed file adds nothing there. The push hold and the review-depth rule add it to the diff's changed lines, which count only the `+` and `-` lines inside hunks (after a line starting with `@@` and a space, until the next line starting with `diff --git` and a space), so content that starts like a file header still counts. When the two sides disagree, the label ranks `unreadable` over `large` over `budget` over `binary`. The probe reads a whole object's first 8,000 bytes only when it is over 1 MiB, the only case that uses them. Trees and commits keep the reader's own limits. Secrets are masked in commit messages, file paths and the diff ("Flagged files" in "Review, then push"). Nothing on the agent listener can allow, deny or start a page push. The push uses the same HTTP client as clones and fetches (no proxy, TLS 1.2 or later, plus the development CA when `SF_DEV_GIT_CA` is set), so it trusts exactly the hosts a fetch does. An agent's push request is answered within 55 seconds (`session.AgentReplyFor`), below the MCP server's 60, so the agent hears the engine's answer rather than a timeout: change both together. The decision isn't cut off then: it runs on, bounded by `PushFor` (two minutes), and a request still running at 55 seconds is answered held, with the result shown on the page. Every decision gets a random `request` id that its `allowed` line and its outcome line share. When go-git's `ReceivePack` fails after the pack was sent (no report came back), the outcome is unclear: the engine asks the remote again (20 seconds), records pushed when the branch is at the commit, refused when it's still where the gate saw it, and otherwise `unclear`, telling the person that pressing Push again is safe. At start, `Pushes.Reconcile` reads the last line of each request in the audit's last 4 MiB of `audit.1.jsonl` and `audit.jsonl` (`Audit.Open`): for every push whose last line is `allowed` or `unclear`, it asks the remote recorded in that line (it must equal the project's URL) and appends pushed or refused by `engine, at start`, with the same `request` (a refused push whose commit has a saved plan in `waiting.json` says the engine decides it again and tells the agent nothing, since `Pushes.Resume` then decides it); a remote it can't reach leaves the line open for the next start. An automatic push waiting on reviews is saved in `waiting.json` on every change; at start `Pushes.Resume` keeps a doubled session's plan without deciding it (Restore above), drops a plan whose session is gone, whose branch moved or whose commit was denied, and queues the rest, one review start at a time: a role with no record or a `no-outcome` failure on its first attempt is started again (`Dispatcher.Retry`, so the subscription check applies); when every review has an outcome, the engine decides as after reviews. A full reviewer (two sessions) re-queues every 15 seconds, other passing failures (sign-in check, fetch, the plugin not installed yet) for up to 10 minutes; any other refusal decides at once, so the agent hears the held outcome. An agent's request refused because two sessions are already being reviewed joins the same queue. A review the person starts from the page arms nothing, but when a saved plan exists for that commit, its finish completes the agent's request. On a normal stop the engine first refuses new pushes, answers and handoffs ("the engine is stopping"), cancels clones, fetches and reviews (a review the engine stopped doesn't start a decision), and gives the running reviews up to 5 seconds (`reviewsGrace`, alongside the grace below) to keep each role's failed `engine-stopped` record and log its `review event=finished`, logging `review event=shutdown-timeout running=<n>` (WARN) when some are still running then, whose records the next start turns into failed; a reviewer container's start, key or sandbox check cut short this way logs `event=stopped` (INFO), not `not-started`, `key-refused` or `sandbox-failed`. It then gives decisions and approved issue or pull request calls already under way up to 25 seconds (`pushGrace`) on their own context, then 2 more seconds to write their outcome lines; Compose's `stop_grace_period` for the engine is 45 seconds to cover that and the HTTP shutdown. A project can hold the agent's own push (`/api/project` op `hold`: `afterBlock`, `maxFiles`, `maxLines`, off by default): with it on, a request by the agent (not the person's Push) gets the missing item "the person's Push: …" when a required reviewer blocked on the branch (overridden verdicts aside), or when the change from the merge base has more files or changed lines than the limit, a clipped diff, or one with a file the count couldn't read (over 1 MiB, or past the read budget below), counting as over; a binary file counts 0 lines; the engine counts, never looks at paths. The agent learns an outcome it didn't hear from a short factual note (`Registry.Note`, one per session, the latest replacing the earlier): a push after its reviews or by the person's Push or Allow ("Software Factory pushed commit 774004e to sf/… after both reviews passed."), the person's Deny, a hold or refusal after its reviews, and the end of a request answered held at 55 seconds. The engine puts the note before the person's next message to the session, or the one that wakes it (never before a command); it doesn't send a turn or wake a session for it. Several notes go in as separate paragraphs, each starting with `[Software Factory]` and a space and followed by a blank line, so one doesn't read as part of the next; the page shows each as its own line. The engine marks every frame a session's container reports (`reported`), since the container picks its text and its `from`; the page shows such a prompt's note lines as "The session reports that Software Factory told …". A prompt the engine itself made for a development ACP session isn't marked. Each line of a note after its first is indented by four spaces (`noted` in `session/notes.go`), so no note holds a blank line or a line starting with the marker, whoever wrote its text: a check note's output, which the agent controls, can't show on the page as another engine note, and the notes after it can't show as the person's words. Notes are saved in `notes.json` whenever they change, delivered once and then dropped; at start the engine loads them and drops the notes of sessions it no longer has, so a note survives a restart. A note holding a token-shaped string stays in memory only. Each issue or pull request outcome is a note of its own, so several reach the agent together. The push view carries how many required reviews passed and were overridden, so the page's Push section says how the push came about: who asked, and after which reviews or with which items missing; the commit links to the host's commit page for an `https` GitHub remote. Deliver lists the branch's audit entries under their own label, each with its time, newest first, apart from what holds the push now.

### A push's record

Code: core `session.PushRecords`, `pushrecord.go`; page `pushrecord.go`. `/api/push-record` `{sid, commit}` (40 or 64 hex digits; no other field) answers a pushed commit's record as `application/json` with `Content-Disposition: attachment; filename="software-factory-push-<12 hex>.json"`, and the push card's **Download this push's record** saves it; it is offered only on a live session's card, and the route answers 409 `not started here` for any other session and 404 `push` when the branch's audit lines hold no `pushed` line of that commit by that session, so a held, denied, refused or up-to-date commit, or one whose line rotated out of the 5,000 read, has none. The record (`format` `software-factory-push-record/1`, at most 256 KiB) is built only from engine records: the `pushed` audit line and the `allowed` line with its request id (reason, missing items, the person's reason); every `reviews.json` entry of that commit and branch (agent, role, run, provider, state, the verdict line, the override's reason, advisory, base, since, covers, the approved and team digests, pack, pack version and digest, plugin commit, Claude Code, models, run model and effort, turns, times, cost); the newest `approve-requirements` and `approve-plan` lines of the session at or before the push, with the requirements' text only when `work.json`'s current approval has the same hash (the plan's text isn't kept); the branch's `override`, `allow-file` and `allow-commit` lines at or before the push, each with its commit; the newest verification run of that commit started at or before the push, with its state, exit code, image, command hash, the command when it is still the project's, and the masked end of its output; and the agent-reported checks, frozen on the pushed card or else the session's checks from before the push, labelled as reported by the agent, or a note that none are held: the agent reported none, or the engine restarted, since it keeps them in memory only. `problems` lists what couldn't be read, such as review records the 500-record store dropped. No reviewer message or reply, prompt, page key, git host token or model credential is in it; the person's reasons, verdict lines, commands, the requirements' text and the output are masked with the engine's token detector, and the remote's URL with its password-in-URL mask. Over 256 KiB, the requirements' text goes first, then the output, the checks and the exceptions, and the reviews last. The route decides nothing and writes nothing but its log line, `push record event=built bytes=N`.

### How this change was checked

## Facts about the change

Code: core `session/uncommitted.go`, `overlap.go`, `pushextra*.go`, `testlock.go`, `specs.go`, `taskmatch.go`, `workflows.go`, `protection.go`; adapters `git/files` `worktree.go` and `workflows.go`, `git/github` `protection.go`, `install/registry`, `git/state` `lookups.go`, page `facts.go`; `web/components/session-facts.ts`, `push-facts.ts`, `project-facts.ts`.

All of it is display only. None of it reaches `gate.Push` or decides anything: holding pushes by path or file kind was rejected, so these are facts for the person and hints for the reviewers. The one exception is Proctor's specifications: by the owner's decision of 2026-11-18 (REQ-09), a change under `proctor/`, or to the root `Makefile` (REQ-13), in a project that uses Proctor holds the push as a `specification` flagged file ("Flagged files" in "Review, then push"), because those files decide what a pass means and the write-time ask doesn't see shell or ACP writes. The facts below about such a change stay display only.

- **Uncommitted edits.** An `idle` event from a session the engine admitted starts a check two seconds later, one at a time per session (`Registry.CheckWorktree`). `files.Worktrees` opens the worktree only as `<workspace>/worktrees/sf-<8 hex>` with no link on the way, reads the branch's commit tree with the hash-checked reader, and walks the worktree through an `os.Root` without following links: each tracked file is hashed as a git blob (its executable bit compared too, a link by its target), each tracked path not found counts as deleted, and an untracked path counts unless `.gitignore` files or the clone's `.git/info/exclude` ignore it (go-git's `gitignore` matcher; the user's global excludes aren't read). It doesn't read the index, so it trusts nothing the agent wrote into `.git` beyond the objects, and applies no content filter: a Git LFS file or a file with line-ending conversion can show as changed. Caps: 500,000 tracked files, 200,000 worktree entries, 2 GiB hashed, 200 paths kept; past a cap the count is "or more".
- **Parallel sessions.** The same check keeps the session's changed paths: the uncommitted ones and those the branch's commits change since it left the main branch, up to 5,000. `Info.Overlaps` compares them with every other admitted session of the same project when the page's list is built, so both sessions show the other.
- **The agent's checks.** `tool` and `tool_done` events carry the shell command the agent ran and whether it failed. The registry keeps the last test, lint, type-check and build command per session (`checkOf`), masked for secrets and cut at 300 characters, and the push card shows those reported before the card's time, copied into the card when it is made (`PushView.Checks`), so a later re-run doesn't change it, labelled as reported by the agent, and names the kinds none was reported for. A check whose exit status isn't its own (the rule in "Claims the turn doesn't back") shows its result as unknown, in the warn tone, in place of "finished without an error" or "failed or was refused", saying whether it was piped, ends in `||` and a command that isn't a check, or ran in the background (Claude Code's `run_in_background` or a Monitor call, as the plugin reports it, or a lone `&`; such a check also has `ok` false). A check is marked "the agent edited files after it ran" when a file-editing call finished without an error after the check started and before the card's time: Claude Code's `Edit`, `MultiEdit`, `Write` and `NotebookEdit`, and the development ACP agent's call of kind `edit`, `delete` or `move` (`editsFiles`). - **The push card.** `Pushes.show` attaches `PushView.Extra` for the view's commit, computed once per session and commit in the background (`computeExtra`, the last 200 kept), and shows the view again when it is ready. It reads the change since the merge base with the hash-checked reader (`ChangedFiles`, then `Blobs`, at most 3,000 files, 2 MiB a file, 16 MiB a lockfile, 96 MiB in all) and counts lines before and after in each file: test functions by name for Go, Python and JavaScript, annotated tests, skip and focus markers, assertions and negated ones, suppressions, logging and monitoring calls, `package.json` scripts, changes to files run later, and what can stop tests from running without touching them: a `_test.go` file whose `TestMain` count rises, a `conftest.py` added or changed, and a test runner's configuration added or changed (`pytest.ini`, `jest.config.*`, `vitest.config.*`, `vitest.workspace.*`, `playwright.config.*`, `cypress.config.*`, `karma.conf.*`, `.mocharc*`, `phpunit.xml`, `phpunit.xml.dist`, `.rspec`). It diffs the packages in each manifest and lockfile it knows, reads modes for symbolic links, executables and binary files (a NUL byte in the first 8,000), and lists the workflows. The review snapshot gets the test and suppression notes, the file kinds and each submodule pointer that moved, was added or was removed, with both commits, as `change-facts.md`, framed as the engine's counts and left out when it looks like it holds a secret. Each review base counts its own range, from that base to the head, so an incremental round gets the facts of the commits it reviews and a full one those since the merge base; a range with none gets no file and no line about it in the prompt.
- **Locked tests.** For a session whose tests the person locked (Work types and approvals), the hash-checked reader compares the lock's commit with the head (`ChangedFiles`, or every file of the head's tree when the lock's commit can't be read): a locked path whose blob changed, or that is gone from its path, deleted or renamed, counts; a new test file doesn't. The push card, computed again when the lock changes, shows `Locked tests changed since <short>: N` with the paths (at most 200 shown) when N isn't 0; the session's work panel shows the same from `/api/gate`, and `change-facts.md` carries the line and the paths under "Tests the person locked", so it is written for a change with no other fact too.
- **Proctor's specifications.** In a project that uses Proctor (the main branch as last fetched, or the head, holds `proctor/proctor.yaml`), the same read counts, for each path under `proctor/` the change touches since the merge base, lines in the before and after versions (`session/specs.go`; no YAML parser, so a count can be wrong): `N new waivers` (`no_state_check:` or `waive:` lines, the key quoted or not), `N fewer scenarios or table rows` (items of the top-level `scenarios:` list and of each `rows:` list), `N new declared reads or shows` (items of each `reads:` list and the paths in each `shows:`), `N new expect_logs entries`, `approved transcript or log changed` for a path under `proctor/approved/`, and `Proctor's configuration or run scripts were added`, `changed` or `removed` for `proctor.yaml`, `manifest.yaml`, `dimensions.yaml`, `mutants.yaml` and anything under `env/`, and `the root Makefile, whose proctor target runs Proctor's specifications, was …`. A file it can't read within the budgets above, a symbolic link and a submodule pointer get `couldn't read; treat as changed`. Display only, like the rest: the changes to Proctor's specifications hold the push through their flagged files, not through this section.

On the push card a file is also marked new or changed against the merge base; a file it can't parse is listed as couldn't read. The project page uses the main branch's commit with the sample branch `sf/0123abcd`.
- **Main's protection.** `/api/project-facts` (`{op: "read", repo}`, or `{op: "lookups", repo, on}`) reads the workflows on main and, through `github.API.Protection`, the rules for the main branch (`GET /repos/{owner}/{repo}/rules/branches/{branch}`, Metadata read), the branch protection rule (`/branches/{branch}/protection`, Administration read, optional) and, when that is refused, `GET /branches/{branch}` (Contents read) for whether a rule covers it and requires status checks. A part it can't read is "unknown", and "not protected" needs the rulesets read and either the protection rule or the branch. It talks only to a host that answers like GitHub's API, so the development git server shows "unknown".
- **Package lookups.** Off by default, per project, in `package-lookups.json`, and each change is audited. When on, `install/registry` asks only `registry.npmjs.org`, `pypi.org`, `proxy.golang.org` and `crates.io`, over the engine's own network with `HTTP_PROXY` honoured and redirects refused, about each package a manifest (not a lockfile) adds, at most 20 per push, after checking the name against the ecosystem's rules. Each request has 15 seconds and an answer of 16 MiB; one too large counts as found with no date. Answers are kept 6 hours. A package the registry doesn't know is marked, and so is one first published less than 30 days ago.

## Away mode

Code: core `session.Halt`, `halt.go`, `away.go`; adapter `git/state` `Halt` for `halt.json`; page route `/api/halt`. The names come from the Stop everything and Pause all switches, removed by the owner's decision of 2026-11-20; the route, file, frame and export store keep them so away mode and its saved state are unchanged.

The page's header has **Away**, which opens its menu while away mode is off; while it is on, the button reads **Away: on**, and pressing it turns away mode off (for every session and for the open session), and a banner below the header says so on every view.

**Away mode** is a toggle for every session or for one session, off by default. While it is on, the engine answers each new permission card itself with "deny" and the note "the person is away; continue without this or stop". Claude Code gets the note with the denial; ACP takes no note with an answer, so the agent gets it at the start of its next message. Question, plan, issue, pull request and push cards still wait. Turning it off brings back the usual cards. The denial happens in the engine, where every card is indexed (`Registry.Report`): an agent can't turn it into an allow, because the engine never answers allow for it, and a page answer to a card already denied is refused. The page shows "Away mode is on, so Software Factory denied …" only from the engine's own mark: `Registry.Report` drops any `away` field an agent sends before it marks the cards it denied.

`/api/halt` takes `{op: "read"}` or `{op: "away", on, sid?}` (without `sid`, for every session) and answers `{awayAll, away}`; any other `op` is 400 `op`. Turning away on for a `sid` this engine didn't start answers 409 `not started here` and saves nothing; turning it off clears the entry for any `sid`, so an entry left from before can be removed, and the page offers a session's own away item only for a session this engine started or one away is on for. A doubled session's `sid` answers 409 `branch held` either way. Every change writes an audit line (`away`), and the page's stream sends a `halt` frame (`{awayAll, away}`) on connect and after each change. `halt.json` keeps `awayAll` and `away` in `engine-state` (0600) and is read at start; the `mode` and `since` an older engine saved there are ignored, and a `halt.json` the engine can't read leaves away mode off and logs `state-not-read`.

## Caps, usage limits and loops

Code: core `session/caps.go`, `capsrun.go`, `capsdisk.go`, `capspage.go`, `usage.go`, `loops.go`, `expiry.go`, `ratewindow.go`; adapters `git/state` `Caps` for `caps.json`, `git/workspace` `Sizes.BoxSize`, `git/github/expiry.go`; page route `/api/limits`.

Every turn and tool event passes `Registry.Report`, and a message from the page passes `Registry.Message`; both call into `session.Limits`, which counts for each session:
- **turns**: each message the person sends, and each turn the agent reports starting when none is open. A message sent while a turn is open counts once, not again when the agent starts it;
- **time**: how long the session's process runs, from the engine's start or wake to its stop, by the engine's clock, so idle time in a running session counts too;
- **cost**: the agent's reported `costUsd` (Claude Code's plugin, ACP's `usage_update`), added as it grows within a run and counted again from zero after a restart of the agent. It is agent-network data: it can only reach a cap, never lower the count;
- **disk**: the size of the session's folder in the workspace volume, `s/<box>` with its clone and worktree, measured by the engine itself (`Workspace.BoxSize`, `Sizes.BoxSize`). Every running session with a disk cap is measured when it gets one and then by a round at most every 2 minutes, one folder at a time and each for at most 30 seconds, outside `Limits`' lock and under the workspace view's walk lock, so a measurement and the page's worktree sizes never walk at once; a round doesn't start while the last one runs, and saving a session's caps starts at most one measurement for it at a time, waiting or running, however often the caps are saved; a round's walk of the same session can run besides it. The round walks only running sessions with a disk cap (or at the disk cap), so a session without one is never walked by it. Raise the cap and Check again measure at once whether the session runs or not, so a stopped session at the disk cap is walked when the person presses one. The walk counts regular files' apparent size, follows no link, counts a file with several hard links at its size divided by its links (so the base copy's packs a clone links aren't charged in full to each session), and stops at 1,000,000 entries or 64 folders deep. It goes depth first and keeps open only the folders on the way down, each with at most one batch of 512 entries read and not yet counted, so its memory stays under about 12 MiB whatever the tree holds (64 folders, each with a batch of names of up to 255 bytes and its path); a tree of 200,000 folders with 240-byte names peaked at 7.5 MiB of heap, where the earlier walk, which queued every folder it saw, took 703 MiB. A folder it can't open, or a stop at a limit, makes the count "at least" (`diskMore`); each folder is opened from its parent's open handle (`openat` with `O_NOFOLLOW`), never by its path, so a folder renamed or replaced while the walk passes can't send it elsewhere, at any depth: a folder that is gone when the walk opens it, or whose own folder was removed, is skipped; one replaced by a file is counted as that file; one replaced by a link, or by anything but a file or a folder, counts nothing, as links do. Only a folder that is there and won't open, or a read that fails, makes the count "at least". So folders created and removed while the walk runs don't keep a cap from clearing. This holds on Linux and macOS builds; others have no `openat` here, so both walks open each folder by its path through the `os.Root`, as before, which follows a link that stays inside the folder, and there the disk walk marks any folder that won't open as "at least" and counts hard-linked files in full. The measurement lives in memory only and is taken again after a restart. Unlike the other counts it can go down.

A cap is set per project and may be set per session (the start form sends what was typed as the start's `caps`; the engine sets it after the start unless it equals the project's). None is set by default. At 75% and 90% of a cap the session shows a warning. At the cap the engine interrupts the turn, writes `cap-reached` to the audit (`result` is `money`, `time`, `turns` or `disk`), refuses messages with the reason, and holds the session's automatic reviews and Send findings: `Dispatcher.reviewAs` when `auto`, `Dispatcher.Retry` and `Pushes.autoFindings` ask `Limits` first, and the agent's push request hears why. **Raise the cap** must set more than the session has used, and a time cap at least a minute more, since the session's time keeps counting while it waits at the cap; **Stop** stops the session, which stays at the cap until raised, or, at the disk cap, until a measurement counts the whole folder under the cap: Check again measures a stopped session too. Each answer writes `cap-answer` (`result` the cap, `verdict` `raised` or `stopped`). A turn cap of 2 refuses the third message, and interrupts a third turn the agent starts itself. A disk cap is in GiB, from 1 to 4,096, and is reached when a measurement counts at least that much, a count that stopped early included, since it is a lower bound. At the disk cap the card also offers **Check again**, which measures the folder at once; the person frees space from outside, such as with `docker exec`, since the engine passes on no message, so the agent can't be asked to clean up. A measurement that counts the whole folder under the cap, from Check again or the 2-minute round, clears the disk cap only, never another kind, and writes `cap-answer` with `verdict` `freed` and `by` `engine`; the interrupted turn isn't sent again, so the person sends a message. A count that stopped early under the cap neither reaches nor clears it. Raise the cap measures again right after. While `caps.json` can't be read, every session counts as at its cap: messages are refused with the reason (409 `cap`, as at a reached cap), and automatic reviews and Send findings don't start, the page says the caps couldn't be read, and nothing is saved until a restart reads the file.

The usage meter keeps the windows each side reports, as `RateWindow` (the vendor's kind, utilization 0 to 1, reset time, status), and shows only those, dropping one whose reset passed:
- **agents**: the plugin sends `$.session.usage()`'s `rateLimits` from the `session.measure` hook (`five_hour`, `seven_day`, and `spend_limit` behind a gateway), taken only from a Claude Code session whose sign-in check said subscription. The plugin API has no Fable window. These windows are kept per session's container, keyed by the container the session was admitted with, since each container can be signed in to an account of its own: one session's report never changes another's, and a container's windows go when no session the engine knows uses it;
- **reviewers**: the windows a streaming review hands over (`Reviews.OnRateWindows`, connected in `cmd/server/limits.go` when the reviews have it), whose `unifiedWindows` include `seven_day_overage_included`, the weekly Fable limit;

The plan comes from the sign-in check (`planTier`, else `subscriptionType`, for claude.ai only). A side whose latest sign-in check isn't a subscription shows no meter; for Claude Code in the sessions' containers, that is the latest check of the sessions in that container. When a shown window of the session's own container or of the reviewers is at 90% or more, or `rejected`, automatic reviews and automatic Send findings of that session pause with a notice on the session until the person presses **Keep them running** (`usage-answer` in the audit, with the session for a container's window), which holds until that window resets and covers only that container's sessions. The Welcome page shows the reviewers' windows; each session's row shows one line with its own container's windows, and the session's view offers Keep them running for one near its end. The answer also starts the automatic work that window paused, through the same path as before (`LimitsConfig.Continued`, `Pushes.Continued`): for an automatic review, the reviews of the held push's commit join the review queue `Pushes.Resume` uses, and for an automatic Send findings, the engine tries it again. Nothing starts when the session's branch moved past the held commit or the commit was denied; another window near its end or a cap still holds it. **Wake at reset** shows when the session's side has a used-up window; a minute after its reset the engine wakes the session, or sends "The usage limit has reset. Continue where you stopped." if it still runs. A scheduled wake lives in memory only.

Loop detection keeps the last 8 tool calls of the turn, keyed by tool, subagent and a hash of the summary and command; 3 identical calls, or 3 failures of the same command, show "Looks stuck" until the next turn starts. It only shows.

Expiry: the sign-in check keeps Claude Code's `loginExpiresAt` for a claude.ai login; from 10 days before it, the page warns with the range from 3 days before it, since the real end can be that much earlier. The GitHub adapter reads `GitHub-Authentication-Token-Expiration` on every answer to the engine's own calls (no header clears the date), and the page warns from 7 days before. Saving or removing a host's token clears its date.

`/api/limits` takes `{op: "read"}`, `{op: "project", name, money, minutes, turns, disk}`, `{op: "session", sid, money, minutes, turns, disk}` (0 is off, and `disk`, a whole number of GiB up to 4,096, may be left out, which is off), `{op: "check", money, minutes, turns, disk}`, which saves nothing, `{op: "raise", sid, kind, value}`, `{op: "stop", sid}`, `{op: "measure", sid}` (Check again), `{op: "continue", side, kind}` (with `sid` for a window of a session's container, and without it for the reviewers') and `{op: "wake", sid, on}`, and answers the `limits` frame the stream also sends after each change. A cap outside its range (money a number of dollars from 0 to 100,000, minutes 0 to 43,200, turns 0 to 10,000 and disk 0 to 4,096 GiB, the last three whole numbers; `session.CheckCapsFault`), or one that isn't a number, is refused with 400 `{error: "fields", field, message}`, `field` the body's key (`money`, `minutes`, `turns` or `disk`, checked in that order) and `message` naming its range; a `raise` whose `value` isn't a number names `value`. The page sends what was typed, empty as 0, and marks that field with the message. It refuses what the page doesn't offer: raising a cap the session isn't at, stopping a session that isn't at one, measuring a session that isn't at its disk cap (409), continuing past a window that isn't near its end, and waking at a reset no used-up window has.

## Issues, pull requests and CI results

Code: core `session.Forges`, `forge.go`, `forgetext.go`, `forgecomment.go` (the comment after a push), `forgereview.go` (`factory_review_comments`); adapter `git/github` (GitHub's REST API, `net/http` only); page `forge.go`; component `web/components/forge-panel.ts`.

The agent's `factory_issue` and `factory_pull_request` post `{kind, title, body}` to `/forge-request` on the agent listener, `factory_checks` posts `{}` to `/checks-request` and `factory_review_comments` posts `{}` to `/comments-request`, all authenticated by the session's push token like `/push-request`, with exactly those fields and strings only (256 KiB at most). The engine takes the repository from the session's project record: the remote URL recorded at clone time names the host, owner and repository (exactly `https://HOST/OWNER/REPO`), and the token is the one saved for that host. The agent names neither. `github.com` uses `https://api.github.com`, a `*.ghe.com` host `https://api.HOST`, and any other host with a saved token is tried as GitHub Enterprise Server at `https://HOST/api/v3`; an answer without GitHub's `X-GitHub-Request-Id` header counts as not supported for that host, and known other hosts (GitLab, Bitbucket, Codeberg and the like) are refused before any call. Calls use the same HTTP client as clones and pushes (no proxy, TLS 1.2 or later, the development CA when `SF_DEV_GIT_CA` is set), never follow a redirect, read at most 4 MiB, and time out after 45 seconds (`ForgeFor`), below the MCP server's 60.

- **Requests.** The title is one line of 1 to 256 characters, the body at most 20,000; both must be UTF-8 without control or invisible characters (newlines and tabs allowed in the body). Calls are capped at 5 per 10 minutes per session for issues and pull requests together. For a pull request the head is the session's branch and the base is the project's main branch; the engine checks with the API that the branch is on the host (else "call factory_push first") and that no pull request for it is open (else it answers `exists` with the link and makes no card). For an issue it reads the repository first, which also refuses a host that isn't GitHub before anything is posted. An identical request already waiting answers held without a second card; at most 5 cards wait per session, and a card expires after 24 hours. The agent hears `held`, `exists` or `refused` with the reason.
- **The card.** The session's `forge` list reaches the page with the sessions list (the body only while the card waits) and counts toward its attention badge. The page shows the title and body as text and offers **Open issue** or **Open pull request** and **Deny**, through `/api/forge-answer` (`{sid, card, approve, draft, confirmed}`, the usual page checks; `draft` is optional and refused on an issue card, `confirmed` is optional). While a card waits, the engine runs the token detector over its title and body; on a match the card says "This looks like a secret", names the title or the line and shows that line, and Open is refused until the person ticks that they checked it (`confirmed: true`). The card shows the line as it is, so the person can judge it; the audit lines that quote the title mask the match. A pull request card has **Open as a draft**, checked by default. On Open the engine checks again for an open pull request, then posts the issue or the pull request (`maintainer_can_modify: false`, and `draft: true` when asked), and shows the number and link or the failure. When GitHub answers a draft with a 422 that names drafts, the adapter checks for an open pull request again and otherwise posts once more without `draft`, and the card and the agent's note say it opened ready for review. Every request and outcome is a line in `audit.jsonl` with `kind` `issue` or `pull-request`, the card's id as `request`, and results `held`, `sending` (written before the API call, with the SHA-256 of the title and body as `hash`; if it can't be written, nothing is sent), `opened`, `exists`, `denied`, `failed`, `unclear`, `expired` (the 24-hour limit) or `abandoned`. While the engine stops, it refuses new requests and answers. When the call's answer is lost (a transport error, a timeout, a status of 0 or 5xx, or an answer it can't read), it doesn't decide: for a pull request it asks for the open one again (opened, or failed when there's none); for an issue it reads `GET /user` and lists that login's newest 10 issues (`state=all`, pull requests dropped, or everyone's when `/user` is refused), keeps those opened since a minute before the approval, and shows them on the card, state `unclear`, marking the ones with the same title and body; with none, the card fails. Each waiting card is saved in `forge-cards.json` when it is shown, with its session, kind, title, body, branch, the commit a pull request card was written for and the time it was asked; a card whose title or body matches the token detector isn't saved. At start `Forges.Restore` shows the saved cards again whose `audit.jsonl` line is still `held` and whose session the engine still has, with their original asked time, so the 24-hour limit still counts from the request. Then `Forges.Reconcile` settles open lines, skipping requests that are cards of the running engine: `held` becomes `abandoned` and the agent is told to ask again if it still needs it; `sending` is checked the same way, and an issue with matches comes back as an `unclear` card.
- **A pull request card is bound to its commit.** On Open the engine reads the branch on the host again; when it moved since the card was written, or its answer can't be read or isn't a commit, it opens nothing. A moved branch binds the card to the new commit and shows it waiting again with "the branch has N new commits since this was written" (counted in the clone, at most 100), audited as `held`, so the person reads it again and approves once more. A branch it can't read keeps the card waiting at its commit with "the engine couldn't read the branch on the host…", also audited as `held`, and the person presses the button again. With no new commit it opens at once.
- **The outcome reaches the agent** as a note (`Registry.Note`, see Pushes): opened with the number and link, already open, denied, or failed with the reason, before the person's next message. A card shown again after a restart works the same way: its tool call ended with the restart, so the note is how the agent hears the outcome.
- **After a compaction.** When Claude Code's plugin reports that a compaction finished, the engine leaves a note for the agent's next turn built only from its own records: the requirements and plan documents with their text hashes and whether the person approved them, a held push and why, the reviewers with open blocking findings, and how many cards wait for the person. It holds no agent or reviewer text. A session gets at most 3 such notes in 10 minutes.
- **The comment after a push.** With the project setting `prComment` on (`/api/project`, `{path, op: "prComment", on}`; off by default, since it publishes under the person's account), `Forges.AfterPush` finds the branch's open pull request and posts the engine's own text (`CommentText`) as an issue comment (`POST /repos/O/R/issues/N/comments`). The text comes only from engine data: a fixed first line (`PushNoteMarker`), the full commit and branch, who caused the push, the number of items an Allow covered, each required role with its result and whether it covered the whole branch or only what changed since a commit, and the engine version, knackpack commit, Claude Code version and models where the review records hold them. It never holds the person's typed reasons, reviewer messages, missing-item text, file paths or cost. The comment is a card on the page with its whole text before and after posting, audited as `pr-comment` (`posting`, then `commented` or `failed`, the two lines sharing a `request` id; `unclear` when the call's answer is lost (a transport error, a timeout, a status of 0 or 5xx) or the engine's stop cut it off after its grace, since the host may have posted it; a 4xx is `failed`). When the token detector matches the text, the engine doesn't post it: the card waits with the same warning and line as an issue card, audited as `held`, and **Post comment** (after the person's confirmation) or **Deny** settles it through `/api/forge-answer`. A commit is commented on once per session, the engine remembers the last push per session, and when a pull request it opens has that push's commit as its head, it comments then. No open pull request means no comment; a failed comment changes nothing about the push.
- **The person's pull request comments.** `factory_review_comments` finds the branch's open pull request (none: refused, "ask with factory_pull_request"), reads the token's own login (`GET /user`) and the pull request's reviews, inline review comments and conversation comments (100 per page by page number; past 3 pages, the first page's `Link` header names the last page and the engine reads the newest 3 instead, with a note that older ones were left out; a part that can't be read becomes a note; pending reviews, which only their author sees, are dropped), and keeps only comments whose author is that login, compared without case, and that don't start with the engine's push-note line. Each body is cleaned like a log line and clipped to 4,000 characters; the newest 100 that fit in 60,000 characters are sent, oldest first, framed as the person's feedback to weigh rather than instructions that override the page or Software Factory's rules, with the warning that a repository admin can edit anyone's comment. Capped at 10 per 10 minutes per session; no card.
- **CI results.** `factory_checks` reads the branch's head on the host, then its check runs (first 100) and combined commit status, and for each failed GitHub Actions job (at most 5) the job's log: the API answers with a redirect to a short-lived download address, which the engine fetches without the token, reading at most 32 MiB and keeping the last 200 lines. Lines lose GitHub's timestamps, ANSI and other escape sequences, control and invisible characters, and are clipped to 400 characters, 16,000 characters per job and 60,000 for the whole answer, which opens by saying the rest is untrusted text from the git host. No card: it changes nothing. Capped at 10 per 10 minutes per session.
- **Token permissions** (fine-grained personal access token, the repositories you add): Contents: Read and write and Metadata: Read-only, as for pushes; Issues: Read and write for `factory_issue`; Pull requests: Read and write for `factory_pull_request`, `factory_review_comments` and the comment after a push; Actions: Read-only and Commit statuses: Read-only for `factory_checks`. A 403 or 404 from GitHub is reported with the permission that call needs. GitHub's list of fine-grained permissions doesn't name one for reading check runs; read access to the repository serves.
- **Following the pull request.** Code: core `session.Follows` (`prfollow.go`, `forgefollow.go` for the text, `forgepulls.go` for the page's pull request actions), adapter `git/github` (`pullstatus.go`, `rates.go`), store `state/prfollow.go`, page `pulls.go`, component `web/components/pull-follow.ts`. `Forges.AfterPush` marks the session's branch as pushed and `Forges.send` records a pull request the engine opened; from then on a loop that wakes every 15 seconds reads each followed session at most once a minute, one session after another: the branch's open pull request (`GET /repos/O/R/pulls?head=…`, until one is found, for up to 7 days after the last push), then `GET /repos/O/R/pulls/N` (state, `merged`, `draft`, `node_id`, `mergeable`, `mergeable_state`, the head commit), the head commit's check runs and combined status (no job logs), `GET /user` (kept for an hour) and the reviews, inline comments and conversation comments, read as `factory_review_comments` reads them. It keeps the comments whose author is the token's login or one of the project's bot logins (compared without case; at most 20, each a GitHub login), that don't start with the push-note line and that are newer than the last one sent; a comment the token detector matches is dropped and counted. Every request goes through the same client as the forge calls. The adapter records `X-RateLimit-Limit`, `-Remaining` and `-Reset` of the core resource per host, and a 403 with `Retry-After` or no remaining calls, or a 429, as limited until `Retry-After`, the reset or a minute (at most an hour); while the host is limited or under 10% of its limit, the loop skips it and the panel says until when. The session's `follow` view reaches the page with the sessions list: the pull request, the failed checks, up to 20 new comments cleaned like log lines and clipped to 4,000 characters, whether CI results are new (a SHA-256 of the head and every finished check's name and result that differs from the one last sent, and something failed), the rounds sent, why sending on its own stopped, and any problem reading. **Send to the agent** (`/api/pull-request`, `{op: "send", sid}`, 10 per 10 minutes per session) builds one message (`FollowText`, at most 19,000 UTF-16 units) that names the pull request and says everything between its two lines is untrusted git host text, with the failed checks and the comments indented, and sends it with `Registry.Message`; when the whole text matches the token detector it is withheld. Audited as `pr-follow` (`sent`, `withheld`, `not-sent`), with counts only. The same reads write the `after-review` audit lines the numbers count (see [Readiness, project numbers and the decision log](runs-and-operations.md#readiness-project-numbers-and-the-decision-log); code `afterreview.go`). `Follows.pushed` keeps, for each of the newest 20 commits pushed on the branch, which required roles passed it (an override isn't a pass) and whether all of them did. The follower writes a line for each failed check run or `failure` or `error` status on the head commit when that commit is one of them, keyed by commit, `run` or `status` and name, so a re-run that fails again isn't counted twice; and for each review asking for changes, review with comments or inline comment on one of them made after its push, from any author, unless it starts with the push-note line, keyed by its URL. It keeps each key's SHA-256 in `prfollow.json` (the newest 500 per session), so a later read or a restart doesn't write it again. Conversation comments, approvals, a commit pushed from elsewhere and a read that failed count nothing. A line carries the check's name and result cleaned like a log line, or the comment's kind and URL, never its body. The project setting **send on its own** (`{op: "set", sid, bots, auto, assign}`, saved in `prfollow.json`, off by default) sends after a read only when `Dispatcher.SessionSignIn` says subscription, the session runs, is controlled from the page and isn't in a turn, and at most 5 rounds per pull request; a waiting card (`Needs`), a held push, a stop reason or failed state, a sign-in failure report, a missing subscription or a failed send stops it and records why, until the person sends once. When the pull request is merged or closed, the record is marked done (audited `pr-follow` `done`), the agent gets a note and the page offers Delete, which posts `/api/workspace` `{op: "delete", sid}`: the workspace's own checks refuse a running session and one whose commits aren't pushed. A record is dropped when its session is deleted. Nothing in this loop writes to the git host.
- **Pull requests from the page.** `{op: "open", sid}` reads the branch on the host (refused when it isn't pushed or a pull request is open) and makes a pull request card with `from: "page"`: the title is the first heading of the approved requirements, else the only commit's subject, else "Changes from BRANCH"; the body lists up to 50 commits since the project's recorded main commit (from the clone, short SHA and subject) and says the engine wrote it. It goes through the usual card, draft checked by default. `{op: "ready", sid}` works only for a pull request the engine opened (`opened` in the record) that GitHub still shows as an open draft: it posts GraphQL `markPullRequestReadyForReview` with the pull request's node id to `https://api.github.com/graphql` (`https://api.HOST/graphql` for `*.ghe.com`, `https://HOST/api/graphql` for a server), audited as `pr-ready` (`sending`, then `ready` or `failed`, sharing a `request` id), and leaves the agent a note; 10 per 10 minutes per session. With the project setting **assign** on, after the engine opens an issue or pull request it posts `POST /repos/O/R/issues/N/assignees` with the token's login and checks that GitHub lists it, audited as `assign` (`assigned` or `failed`). The conflict status is GitHub's: `mergeable: false` or `mergeable_state: "dirty"`; the page's **Ask the agent to bring in main** posts `/api/bring-main` `{sid}`.
- **Starting from an issue.** `/api/issues` `{op: "list", path, label?, page?}` lists the project's open issues (`GET /repos/O/R/issues?state=open&sort=created&direction=desc&per_page=30`, with `labels` when given; pull requests dropped; `more` from the `Link` header; labels of at most 50 characters, pages 1 to 100), and `{op: "read", path, number}` reads one (`GET /repos/O/R/issues/N`) with its title and body as the git host has them, for the page to show escaped, why it would be refused: a token detector match in the title or any line of the body, or a closed issue, and `hash`, the SHA-256 of the framed text that would become the first message. Both take 60 reads per 10 minutes per project. `/api/dispatch` takes an optional `issue` number with that `issueHash` (one without the other, or a hash that isn't 64 lowercase hex digits, is a 400 `issue` with `field` `issue`), which `session.IssueDispatcher` (which wraps the Dispatcher) handles: it reads the issue again, refuses before anything starts, with `field` `issue`, when it would be refused or when the framed text's hash differs from `issueHash` ("Changed since you read it. Read it again."), so the agent gets only the text the person read, starts the session, saves the issue number in `prfollow.json` and sends the framed text (`IssueText`: the fixed first sentence with the number, `Title:` and the cleaned body, cut to fit 19,500 UTF-16 units) with `Registry.Message` every 3 seconds until the session takes it, for up to 10 minutes. A pull request card for that session, the agent's or the page's, gets `Closes #N` added to its body unless the body already closes that issue.
- **Issue cards from findings.** `/api/finding-issues` `{op: "read", sid}` reads the session's latest finished review: for each role that passed that commit on the session's branch without an override, the `### [Medium]` and `### [Low]` sections of the reviewer's whole reply (up to 20), each with its title, a `Location:` line or a backticked `path:line` in the title, and its text cut to 6,000 characters. When the reply carries knackpack's finding lines ("Finding lines" in [Review, then push](../../ARCHITECTURE.md#review-then-push)), a section takes its file and line from the line of the same severity and title (or naming its id, or in order when the counts match), and a line no section matches becomes a card of its own once every section has its line. `{op: "open", sid, commit}` makes one issue card (`from: "findings"`) per finding through the same path as the agent's cards (at most 5 waiting per session), skipping one the token detector matches, and only once per commit.
