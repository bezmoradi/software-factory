# Reference: work and files

This is part of the Reference section of [ARCHITECTURE.md](../../ARCHITECTURE.md#reference), which describes how Software Factory works and why.

## Start-up files

Code: core `session/startup.go`, adapters `git/files` `Startup`, `git/state` `Approvals`.

A Claude Code session on a git or uploaded pack also gets the pack's files that run or load at start in the same card, as place `pack` ("Packs", The start-up approval); knackpack's don't.

`session.StartupLists` is the one table of the files each agent loads at start that can change what it may do without asking, with a source line per entry: Claude Code 2.1.322 `.claude/settings.json`, `.claude/settings.local.json` (in the worktree, where Claude Code 2.1.322 saves "don't ask again" rules; Claude Code's documentation names the clone's own folder for a worktree, but a live run of 2.1.322 didn't apply an allow rule from the clone's file in a worktree session, so the clone's file isn't on the list), `.mcp.json`, `.claude/agents/`, `.claude/commands/`, `.claude/skills/` (also in the clone's folder, which Claude Code loads when the worktree has none at its root, and as `<subfolder>/.claude/skills/` anywhere below the worktree's root, which loads once Claude works on files there: the skills documentation's "Load skills in monorepos and subdirectories", and the 2.1.322 binary's skills "from `<folder>`/.claude/skills"), `.claude/workflows/`, `.claude/hooks/`. The development agent uses Claude Code's list.

Instruction files (`session.InstructionLists`: `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md` and `.md` files under any `.claude/rules/` for Claude Code, at any depth) change no permission, hook, server, plugin or endpoint, so they aren't part of the approval. They are an attack path all the same (planted instructions), so the card shows them as information. One walk of the worktree (`files.walkTree`, no links followed, folders sorted by name) finds them and the nested skill folders; it skips `session.WalkSkipped` (`.git`, `node_modules`, `dist`, `build`, `out`, `target`, `vendor`, `coverage`, `__pycache__`, `venv`, the page's file view's list) and the approved folders, and stops at 12 folders deep, 5,000 folders, or a folder of more than 5,000 entries. A stop is shown on the card and enters the set's hash, since a nested skill folder past it would go unapproved. The walk reads at most 100 instruction files and 2 MiB, skipping one over 1 MiB, and says on the card what it left out. For Claude Code it also checks one fixed list of folders above the worktree, from its parent up to the session's own folder (`/workspace/s/<box>/worktrees`, `/workspace/s/<box>`), which only that session's container writes; above it, the container has only the image's empty read-only folders, for `CLAUDE.md`, `CLAUDE.local.md`, `.claude/CLAUDE.md`, `AGENTS.md` and `.claude/AGENTS.md`, since Claude Code loads them from every folder above where it starts; the engine sees the same `workspace` volume at the same path. They're listed as outside the worktree (Known limits). `approvals.json` keeps, with each approval, the hash of each instruction file on the approved card (`seen`); the next card lists only those new or changed since, with a count of the rest, in a collapsed section. Instruction files never enter the set's hash, so a change to one alone asks nothing, and they're shown only when the card asks anyway. The trust card (clone folder) shows none.

Every shown file, instruction files included, is escaped the same way and carries marks (`session.Marks`), which block nothing: an `allowed-tools:` value naming `Bash` and `hooks:` in a `.md` file's front matter, inline shell (`` !`…` `` after a space or at a line's start, or a ```` ```! ```` block) in `.claude/skills/` and `.claude/commands/`, and a script bundled in a skill's folder (a shebang or a script extension, anything but `SKILL.md`). A file with any escaped character is tagged as holding hidden characters. After agent-host creates the worktree, and before each wake, `Dispatcher.admit` reads the list through an `os.Root` on the worktree and on the clone's folder, `Lstat`ing every path component. A symbolic link is shown with its target and followed only inside that folder (`os.Root` refuses one that points outside, which refuses the start): a link to a file adds the file's content to its entry, and a link to a folder lists the folder's files under the link's path, so the approval covers what the link points to and a change there asks again. Other files are opened `O_NOFOLLOW` and checking they're the file `Lstat` saw, refusing special files, files over 1 MiB, more than 400 files, more than 8 MiB or folders nested deeper than 8 (an unreadable set is refused, never approved); each file is compared with the session branch's commit with the hash-checked reader. A set's hash (`SetHash`, over the list name and each file's place, path, link target and content) is approved per repository and agent in `approvals.json` (one per pair: approving a new set replaces the old), and each approval is an `approve-startup` line in `audit.jsonl` (repository, branch, agent, the set's hash). An unapproved set refuses the start (`409 needs approval`) with the files, escaped by `session.Escape` (controls, ANSI escapes, direction and zero-width characters as `⟨U+XXXX⟩`, bytes that aren't UTF-8 as `⟨0xNN⟩`), the commit and an uncommitted note; the page sends it again with `approve: <hash>`, which counts only when it equals the set read at that moment. The refused worktree is removed (its branch stays). The engine answers Claude Code's trust question only after the person presses the page's trust button and approves any start-up files in the clone folder ("Trusting a repository in Claude Code").

## The commit name and email

Code: core `session/identity.go` (`Identities`, `CheckIdentity`); adapters `git/state` `identity.go`, `agenthost` `worktree.go`; page `identity.go`, `web/components/identity.ts`.

The session's container has no git name or email, and an agent with none may commit with the email of its sign-in, which a push makes public. The person sets one name and email for every agent on the page: **Git name and email** in the Settings menu (the gear in the activity bar), which also opens by itself each time the person goes to the Projects page until one is saved. `/api/commit-identity` takes `{op: "read"}` or `{op: "set", name, email}` and answers `{identity: {name, email}}`, or `{identity: null}` when none is set. The engine keeps it in `identity.json`. Both values are checked on the engine's side, and again by agent-host: the name has 1 to 100 characters with no control, line-break or invisible characters, no `<` or `>`, and no leading hyphen; the email has the shape `local@domain.tld`, at most 254 characters, with no spaces, no `..` and no leading hyphen. The help text suggests GitHub's noreply form, `ID+USERNAME@users.noreply.github.com`. No session of any agent starts or wakes until one is saved: the engine refuses with `409 no commit identity` and a message naming the setting, and the page's error offers **Set Git name and email**. The reason is the one above: without one, Claude Code took the account's sign-in email for its first commit.

agent-host writes it with git, not with variables, since variables likely don't reach Claude Code's `--bg` sessions. When it creates a worktree, it sets `extensions.worktreeConfig` in the clone's config, then `user.name` and `user.email` with `git config --worktree` in that worktree, so each session's worktree has its own `config.worktree` and the clone's shared config has no identity. A failure removes the new worktree, and the start fails with git's message. Every Wake writes the current name and email into the session's existing worktree first (`/v1/worktrees/identity`), and a failure refuses the Wake, so a worktree made before the setting, or a setting changed since, takes effect at the next Wake. A running session keeps what it started with. This is the same for Claude Code and the development ACP agent, since each runs `git` in its worktree. The agent can still change its worktree's config, as it can any file in the session's container, so the push's scan of commit identities (see [Pushes](reviews-and-pushes.md#pushes)) stays the check.

## Work types and approvals

Code: core `session/work.go` (`Work`), `session/testlock.go`, `internal/core/workflow`; adapters `git/state` `work.go`; page `workflow.go`; `web/components/session-work.ts`.

The step commands, the committed documents and which work types are offered come from the session's pack ("Packs", Sessions): knackpack's below, a pack's from its manifest, and none with No pack, where no Define or Plan step, so no Feature, is offered.

Each session has a work type (Feature, Fix, Incident, Docs only, Exploring, or one from the team file), picked on the page before the first message; the default comes from the new-session form, then the project, then the team file, then `fix`. A type's items are the person's approvals of requirements and plan (the SHA-256 of the text the page showed and the commit, saved in `work.json`; approving requirements again clears the plan's; for requirements the approved text is saved too, and when the reported requirements no longer match it, the gate view carries it as `previous`, so the page shows a line diff before the person approves again; a saved text whose SHA-256 isn't the approval's is dropped on load, and the oldest approvals lose their text once all of them pass 1 MiB in `work.json`), and the required roles. Every session, Claude Code's and the development ACP agent's, gets knackpack's workflow: its step commands, its documents and its gate. Approving the requirements sends the session the Plan step's command; approving the plan sends a message to implement the approved plan. **Ask for changes** on the requirements, the plan or the root cause sends `/api/message` `{sid, revise: {kind, note}}` in place of `text`, with `kind` `requirements`, `plan` or `root-cause` and the note as typed; the engine composes the message (`session.ReviseMessage`): for requirements, a request to change the agreed requirements in the session's intent record; for the plan, to change the plan in the file the gate view names; for the root cause, `/knackpack:debug-incident` asking to correct the diagnosis in that file, each followed by the note. It refuses a note that is only white space or over 2,000 characters with 400 `note` and a message the page shows under the note field, and a plan or root cause whose file the gate view doesn't name with 409 `no file`. Every other message the page sends for the person is chosen, not written: `/api/message` `{sid, ask}` names the action (`define`, `plan`, `triage`, `reproduce`, `cause`, `fix`, `commit`, `issues`, `handoff`, `incident-review` or `checkpoint`) and the engine composes its text (`session.AskMessage`, `composed.go`): the workflow's step command, `/knackpack:debug-incident`, the `/knackpack:fix-incident` request naming the approved root cause's file and SHA-256, the request to commit every uncommitted change, a knackpack Deliver command, or `/knackpack:checkpoint`. A step the session's gate view doesn't offer now (no such command, not an Incident, a root cause not approved, not knackpack) is refused with 409 `step`. `/api/gate` carries the path the page draws (`path`: each stage's state, detail, Step n of m and the actions it offers, from `session.Path`), the reviewers it requires and whether reviews are active, and the live diagram's model (`flow`); a session's listing carries its current step (`step`, from the knackpack command its prompt or Skill tool named) and whether a checkpoint was asked at the current context level (`checkpointSaved`), which the engine records when it sends `/knackpack:checkpoint`. In a Feature, before the plan is approved, the plugin's write check (`/check` → `Work.EditHold`) refuses Claude Code's file tools for paths in the worktree, other than the current step's own knackpack files; Docs only refuses paths that aren't documentation, and Code review refuses every edit. Documentation is a `.md`, `.markdown`, `.rst` or `.adoc` file, or `LICENSE`, `NOTICE`, `AUTHORS`, `CONTRIBUTORS`, `COPYING`, `README`, `CHANGELOG`, `CHANGES` or `HISTORY`, bare or with one of those extensions or `.txt` (`workflow.DocFile`). Agents' instruction files (`CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, `.github/copilot-instructions.md`, `.github/instructions/`, `.cursorrules`, `.windsurfrules`, `.claude/`, `.codex/`, `.agents/` and the like, at any depth), MDX, which runs code when a site is built, and files a built-in reviewer covers aren't documentation, so a Docs only branch that changes one needs what a Feature needs, and the work panel, the push card and `change-facts.md` list those files (Facts about the change, "The change and its work type"). This is guidance for the agent: the gate's approvals are what count, and an agent can still write files through other tools. The team file `software-factory.json` is read from the fetched main and counts only after the person approves its SHA-256 on the page (`/api/team`); it may add work types, `fileRules` and `agents` from installed plugins, never `roles`, `checks` or `"edits":"none"`. Project settings (`/api/project`): review rounds (1 to 20), the default work type, the push hold (`{path, op: "hold", hold: {afterBlock, maxFiles, maxLines}}`; see [Pushes](reviews-and-pushes.md#pushes)), `findings` (`{path, op: "findings", findings: bool}`, sending blocking findings to the agent by itself, off by default) and `prComment` (`{path, op: "prComment", on: bool}`, a comment on the pull request after each push, off by default), in `work.json`. Each approval of requirements or a plan is an `approve-requirements` or `approve-plan` line in `audit.jsonl` (session, branch, commit, the text's hash), and approving or forgetting the team file an `approve-team` or `forget-team` line (repository, SHA); a failed write is logged and the approval still counts.

**Locked tests.** Agents told to keep tests green tend to change the tests, so the person can lock them. Once the session's branch has a commit the main branch lacks, in any work type, the session's work panel offers **Lock tests** with the commit it read, and says to lock once the tests to keep are written. `/api/lock-tests` (`{sid, op: "lock", head}` or `{sid, op: "unlock"}`, the page's usual checks) is the person's press on the page only; nothing on the agent listener locks or unlocks. Lock reads the session branch's head with the hash-checked reader, refuses when it isn't the `head` the page showed, and keeps each file of the head's tree that the push card counts as a test (`isTestPath`: `_test.go`, `.test.` and `.spec.` scripts, `test_*.py`, `*Tests.java` and the like, and files under `test/`, `tests/`, `spec/` or `__tests__/`), with its blob hash: first the test files the branch adds or changes since its merge base with main, then the rest of the tree in path order, at most 2,000 files and 256 KiB of paths in all (past that the panel says only these are locked, and whether every test file the branch adds or changes is among them), as the session's `testLock` in `work.json` (`{commit, at, files, cut, branchLeft}`, `branchLeft` the number of the branch's own test files left out, omitted when 0; at most 1 MiB of locked paths across sessions, past which Lock is refused). A record without it reads as no lock. **Unlock** removes it, and approving the requirements or the plan again clears it, as approving requirements clears the plan's approval. Each is a `lock-tests` or `unlock-tests` line in `audit.jsonl` (session, branch, commit). While a lock holds, Claude Code's file tools ask the person before writing a locked path (A tool call and its card), and the push card, the gate view (`/api/gate` `testLock`) and the reviewers' `change-facts.md` show the locked tests that changed (Facts about the change). The lock is a card and a displayed fact: it never holds a push and never reaches `gate.Push`. A shell command or the development ACP agent can still change a locked test; the fact shows that it did.

**knackpack's requirements and plan from the commit.** knackpack commits both from 0.26.0, and the engine installs only 0.40.0 and later ("knackpack"), so every installed knackpack commits both when `KNACKPACK_DOCS=repo` is in Claude Code's environment: `.knackpack/<task>/REQUIREMENTS.md` and `.knackpack/<task>/PLAN.md`, each with `.knackpack/feature.json` (`{"feature_directory": ".knackpack/<task>"}`), one commit per document and a new commit per revision. The engine:
- starts Claude Code with `--settings={"env":{"KNACKPACK_DOCS":"repo"}}`. `claude --bg` carries `--settings` into the background session with `--plugin-dir`, so Wake's `claude respawn` keeps it; a session started on an engine before this mode has neither until it is started again. knackpack's `scripts/commit-docs.sh` refuses when the repository's own settings set the variable, and accepts `--settings`;
- reads `.knackpack/feature.json` from the session branch's commit with the hash-checked reader, takes `feature_directory` only when it is `.knackpack/` and a folder name matching `^[a-z0-9][a-z0-9-]{0,63}$`, and reads `REQUIREMENTS.md` and `PLAN.md` from that folder in the same commit;
- counts an approval only while that committed text's SHA-256 equals the approved one, and only that text can be approved, if the session's own commits added or changed it (below). The plugin's report is shown, marked as not committed, when nothing is committed, and neither keeps nor voids an approval;
- lets Claude Code's file tools write `.knackpack/*/REQUIREMENTS.md` and `.knackpack/feature.json` before the requirements are approved, and the approved folder's `PLAN.md` before the plan is, and approves a plan whose commits since the requirements' approval touch only those files.

**Only the session's own documents count.** For committed knackpack documents, a requirements or plan document can be approved or counted only when its path is among the files that differ between where the branch leaves the main branch and the head, as the hash-checked reader lists them (the same list the reviewers' rules use); when that list can't be read, none counts. A `feature.json` or document that is only on the base, such as one an earlier task merged, is shown as from an earlier task, already on the base branch, and isn't approvable, and that step's approval stays missing.

**Requirements that are ready.** Approving the requirements also needs the brief to be ready, which the engine works out from the text it read (`workflow.RequirementsReadiness`), never from the brief's own Readiness line, which the agent writes. A brief in the checked format has the line `knackpack-requirements/1`, and the engine reads it exactly as knackpack's `docs/requirements-format.md` says: that document is the contract, and on every text the engine gives the result knackpack's `scripts/requirements-check.sh` gives, though it words a problem its own way. A `Blocking: yes` question holds the approval, named in the refusal (at most 8, then how many more), and a brief that breaks a rule is refused with its first problem; `/api/gate`'s `holds.approveRequirements` carries the same sentence, which the page shows beside **Approve requirements** before the press. With another pack the check applies only to a brief with the marker line. In a knackpack session a brief without it is refused with "Written before the checked format; ask Claude to rewrite it.", in `holds.approveRequirements` and as 409 `held` (the owner's decision D1): `RequirementsFormatSince` (`workflow/artifacts.go`) is 0.40.0, the knackpack release that writes the format, and `Knackpack.Floor` is the same, so every installed knackpack writes it. A knackpack whose version can't be read leaves such a brief approvable as before.

**Incident.** The built-in `incident` type (Profile `incident`, matched by its built-in ID since a team file can't reuse it) has Fix's steps, roles and edits, and is offered only with a pack whose documents name a root cause file, which only knackpack's do (`Documents.RootCause`, `workflow.Offered`). Its approval follows the plan's and uses its slot: for an Incident session the engine reads `ROOT-CAUSE.md` from `feature.json`'s folder in the branch's commit instead of `PLAN.md`, `/api/approve-plan` approves it, `work.json` keeps it as the session's plan approval and `audit.jsonl` as an `approve-plan` line whose reason says root cause. It can be approved only when its Status, the first word of the first non-blank line under `## Status` as knackpack's `incident-check.sh` reads it (`workflow.RootCauseStatus`), is `CONFIRMED`, and needs no requirements. Until it's approved, a branch that changes a file that isn't documentation, `.knackpack/feature.json` aside, gets the gate item "the root cause isn't approved", and a later change to the file voids the approval the way a plan's change does. Approving it sends the session nothing. The page offers **Fix** once the gate view says the root cause is approved, sending `/knackpack:fix-incident` with the approved hash and the instruction to run knackpack's `incident-check.sh` with `KNACKPACK_INCIDENT_APPROVED_SHA256` set to it. That variable is passed in the message, not in Claude Code's environment, because `--settings` reaches a session only at its start and the approval comes later; knackpack's check is guidance for the agent, and the gate item is what holds the push. The reviewers get the approved root cause in `approved/root-cause.md` and are told the change fixes an incident, to judge its regression risk, blast radius and rollback first. The page warns on attachments in an Incident session and doesn't scan them; uploads are accepted as in any work type.

The switch is the engine's floor version, which every installed knackpack meets (`Knackpack.Floor` in `versions.go`, checked against the `plugin.json` the engine itself wrote into the agents volume, which every container mounts read-only), never a file in the repository or the session's container, since an agent could delete `feature.json` to fall back to the plugin's report; with no readable `feature.json`, nothing counts. The page shows, for a document read from a commit, the commit it was read from and the one it was approved in, and when the committed text differs from the approved one, that the approval no longer counts. In development, the development ACP agent gets the same mode, so the flow can be checked with commits made by hand in its worktree.

## Files and uploads

Code: page `files.go`, `upload.go`; core `session/uploads.go`, `session/wake.go`.

`/api/files`, `/api/file` and `/api/file-match` show the session's worktree read-only, and `/api/file` and `/api/file-check` with a `commit` show a file as a commit has it, only a commit one of the session's review records names on its branch (`Work.ReviewedFiles`, which reads the review records once per request, then each file with the hash-checked reader's `ReadFileWithin`, which refuses an object whose header gives more than 512 KiB before inflating it and stops the whole read, trees and delta bases included, at 16 MiB of work; a path that is absolute, holds `..` or a backslash, or that the secret-name rule hides is refused, as are links, submodules, binary files and files over 512 KiB), for sessions the engine started: no symbolic link is followed, a file is shown up to 512 KiB, binary files aren't shown, and `@` suggestions leave out secret-looking names. `/api/file-check` (`{sid, paths}`, 1 to 20 paths, with or without `commit`) answers `{"found": [...]}`, the asked paths that are there: in the worktree a regular file with no symbolic link at any step and no secret-looking name, looked up with `Lstat` and not read, so a file too large or binary for `/api/file` is found; at a commit, a file `/api/file` would show. It adds `unread` only when not empty: an object from each asked path that is there but that `/api/file` wouldn't show to the reason `/api/file` would give, `link` (a symbolic link at some step, not followed), `secret` (a secret-looking name, whose contents aren't read), and at a commit `large` and `binary`, so an absence check can tell such a path from a missing one, as `{"found": ["notes.md"], "unread": {"env-link": "link", "web/.env/x": "secret"}}`. A missing path, a folder, a path outside the worktree, and every path at a commit no review record of the session names, are in neither, and so is a secret-looking name at a commit, which the engine refuses without looking it up. `/api/upload` stores images (PNG, JPEG, GIF, WebP, 4 per message) and dropped files (10 MiB, refused with a message naming the file, as `/api/file-match` does before the page attaches one) in the `uploads` volume. It takes an image of up to 32 MiB (`session.MaxImageUpload`) and, for a PNG or JPEG longer than 1,568 pixels on a side or over 2.5 MiB, shrinks it to fit 1,568 pixels and re-encodes it, as PNG or JPEG at quality 90 and then JPEG at 85 if still over 2.5 MiB (`session/imagefit.go`, one at a time, at most 25 megapixels); a GIF, a WebP or an image it can't decode is kept as sent only up to 2.5 MiB, and anything else is refused with "That image is too large to send, or not one the page can read." It does this after the session checks, so an unknown session is still refused first. The hello frame of `/api/events` lists the image types in `imageTypes`, which is how the page tells an image from a file; `/api/message` refuses more than 4 images or 4 files with a message. The volume has one folder per session; files not sent within an hour are removed. Claude Code reads an image through the plugin's `pasted_image` tool, and the development ACP agent gets image blocks. Every agent can read `/uploads`, so another session's agent could read a person's upload. A message to a stopped background session wakes it (`wake.go`): up to 20 messages wait 2 minutes for the woken process.

## Screenshots

Code: core `session/screenshots.go`, page `screenshots.go`, adapter `agenthost/screenshots.go`, `cmd/server/screenshots.go`, `web/components/screenshots.ts`.

An agent saves screenshots in `/workspace/s/<box>/screenshots/<sid>/`, in its own container's folder. The plugin's start note names the folder with the session's id, and the engine passes it to its tool server as `SF_SCREENSHOTS`, whose instructions name it to the development ACP agent. `/api/screenshots` (`{sid}`) lists the regular files directly in that folder whose names end in `.png`, `.jpg`, `.jpeg` or `.gif`, newest first, at most 50, for sessions the engine started. `/api/screenshot` (`{sid, name}`) reads one with the no-follow reader the file viewer uses (`os.Root`, `O_NOFOLLOW`, no symbolic link at any step, a regular file only), refuses it over 10 MiB, sniffs PNG, JPEG or GIF from its first bytes, reads its header with that format's `DecodeConfig` and refuses more than 8,192 pixels a side or more than 256 MiB to decode (4 bytes a pixel, 8 for a 16-bit PNG, 16 for a JPEG, whose progressive decoder keeps every coefficient), then decodes it and encodes it again as a PNG of at most 24 MiB. One screenshot is decoded at a time; another request meanwhile answers 429 `busy`. The answer is JSON: `{name, type: "image/png", width, height, data}`, with `data` in base64, and the page shows it through a Blob URL, which the CSP's `img-src 'self' blob:` allows. Refusals answer 400 (`name`, `too big`, `too large`, `not image`) or 404 (`session`, `screenshot`). The folder is agent-written data: the engine shows the image it encoded, never the agent's bytes, and nothing in it decides anything. A browser check's images go through the same re-encoding ("Verification runs", Browser checks). The engine makes the folders itself, through the container's root (`files.OpenBox`): `s/<box>/screenshots` (mode 3775: setgid, so what is made in it gets the `sf` group the engine and the agents' user share, and sticky, so the agents' user can't remove or replace a session's folder there), and each session's folder when it starts the session (mode 2775), before Claude Code runs or the tool server gets `SF_SCREENSHOTS`. Where the folder's group isn't one of the engine user's, as in a native install under `/tmp`, the system refuses setgid and the engine makes the folder without it. The agents' user doesn't own them, so it can't make them unwritable to the engine, and the engine can always unlink a file in them. `Registry.Forget` deletes the folder when the session is deleted. What the engine can't remove itself (a folder an agent made inside with no group write, or a top folder an older engine left to the agent) it asks agent-host, which runs as the agents' user, to remove: `POST /v1/screenshots/remove` (`{name}`, agent mode only and, like every agent-mode route, without a key: "The image and Compose") takes one entry name, never a path, refuses one with `/`, `\`, NUL, `.` or `..`, opens `screenshots/` under its own workspace with `os.Root`, refuses it if it isn't a plain folder and refuses the entry if it's a symbolic link, removes the entry with everything in it (and if that fails, gives the agents' user write on every folder in it, at most 64 deep, and tries again), and answers whether the entry is gone. It logs `removed`, `emptied` (the folder is empty but stays) or `not-removed`, never the name. The entry the engine made stays, since the top folder is sticky and the engine owns it, so agent-host logs `emptied` for it and the engine then removes what's left itself. The engine waits at most 5 seconds for agent-host's answer and never takes it as the outcome: after its own second removal, the entry is removed only if the engine's own `Lstat` finds nothing there. A removal that still fails logs `screenshots` `not-removed` with the session's id. At each start, once its listeners serve, the engine removes in the background, for at most 30 seconds, every top-level entry in the `screenshots/` folder of each session's container it has that isn't a session it has, whatever its name and whether it's a folder, a file or a link, the same way, as it does for `keep/`. Right before each removal it checks again, under its own locks, that the entry isn't a session it has; a session it starts meanwhile is admitted before its folder is made, so that folder is never removed. Once agent-host fails or doesn't answer within 5 seconds, the sweep doesn't ask it again and logs `agent-host-skipped`, and the engine still tries its own removal; when the 30 seconds run out it logs `sweep-stopped` with the number of entries left. It logs `stray-removed` with the number removed and `strays-not-removed` with the number of entries whose names aren't session ids that it couldn't remove, never their names. A folder the engine couldn't make logs `folder-not-made`, and the agent makes it, as its instructions say.

## Claims the turn doesn't back

Code: core `session/claims.go` (the turn's record and the check), `session/claimpatterns.go` (the claim and command patterns); page `claimfiles.go`; `web/components/conversation.ts`.

When a turn ends, the engine reads the agent's last message for three kinds of claim and marks the ones nothing in the turn backs, as "Not backed by this turn's actions". A mark is a hint for the person. It holds nothing, and neither a mark nor its absence counts for the gate, a review or a push.

`Registry.Report` passes each new event of a session the engine started to `trackTurn`. A turn starts at `busy`, at the earlier of the event's time and the engine's clock, and ends at `idle`; a turn that was stopped or ended with an error isn't checked. The record keeps the turn's tool calls and the text after its last main-loop tool call, which is the last message (its last 20,000 bytes). A completed turn's last message is also kept for the review's `claims.md` ("Review, then push").

The claims, in English only, one sentence at a time:
- **tests:** "all tests pass", "the 12 unit tests passed", "the test suite passes", "Tests: passing";
- **build:** "the build succeeds", "it compiles", "builds cleanly";
- **a file changed:** "updated", "edited", "modified", "changed", "rewrote", "patched", "refactored", "fixed", "adjusted", "tweaked" or "amended" directly followed by one or more file names: a path, a name with a common extension, or a name such as `Makefile`.

Code blocks, block quotes and text in double quotes are skipped. So is a sentence with a question mark, a negation, a condition, a future or a hedge ("should", "if", "once", "probably", "let me"), a word about earlier work ("already", "previously") or about CI. The patterns are few on purpose: a false mark costs the person's trust in the marks, so most claims go unchecked.

A test or build claim is marked only when the engine knows every command the turn ran:
- **Claude Code:** the plugin's `tool` reports, for the main loop and for subagents. A Bash, PowerShell or Monitor call carries its command in the summary, cut at 300 characters; a cut command counts as unknown. A subagent's calls reported between turns count toward the next turn.
- **The development ACP agent:** the engine's own event bridge adds the command from an `execute` call's input (`command`, a string or a list) to the call's `tool` and `tool_done` events, with secrets masked. An `execute` call with no command in its input counts as unknown.

A call that may run commands the engine doesn't see makes the turn's commands unknown, and then no test or build claim is marked: `Agent` or `Task`, `Skill`, an MCP tool other than the engine's own `factory_` tools, a kind the engine doesn't know, more than 500 calls, or a gap in the session's event numbers. A test claim is backed by a command with a test word (`test`, `spec`, `pytest`, `jest`, `vitest`, `rspec`, `check`, `verify`, `e2e` and the like), or by one that runs something the engine can't judge: `make`, `just`, `task`, `nx`, `turbo`, `bazel`, `docker`, a package manager's script (`npm run lint`, `yarn build`), a script file or a program run by `python`, `node` or a shell. A build claim is backed by any of those, by a compiler or build tool (`go`, `cargo`, `tsc`, `gradle`, `mvn` and the like), or by a build, lint or vet word. The parser looks through environment assignments, `sudo`, `env`, `timeout`, `sh -c` and `bash -lc`, and `npx`.

Those test words and runners only keep "No test command ran in this turn." away. A failure is decided by the turn's last command, by the order the calls started in, that runs a test the push card calls a test (`runsTestCheck`, the same classifier as "The agent's checks"): `go test`, `cargo test`, a test runner such as `pytest`, `jest` or `gotestsum`, a package manager's `test` script (`npm test`, `yarn test:unit`), a `make`, `just` or `task` target whose name holds `test`, and a program given as a path (`./test.sh`, `scripts/run-tests.sh`, `scripts/test`) whose file name holds `test`. The shell's own `test` and `[`, also as `/usr/bin/test`, aren't tests, and `make check`, `docker compose run tests` and other runners or scripts don't decide a failure. The claim then goes by whether that call finished without an error (the `ok` of its `tool_done`):
- it failed and that test's pipeline is the command's last one (`testDecides`; a trailing `|| false`, or `|| exit N` or `|| return N` with a literal N other than 0, is skipped when finding it, since it keeps the failure): the claim is marked "The last test command in this turn failed." A refused call counts as failed too, since `ok` doesn't tell the two apart. So `go test ./... && go vet ./...` failing gives no mark, since vet may be what failed;
- no `ok` was reported for it, or it is a subagent's command reported between turns: no mark;
- its exit status isn't the check's own (`statusHiddenBy`): no mark, and it doesn't back the claim either;
- otherwise it backs the claim.

A test run in the background never backs a test claim, and is left out when finding that last command: a Claude Code Bash call with `run_in_background`, or whose result carries a `backgroundTaskId`, which the plugin reports as `background: true` on the call's `tool_done`; every Monitor call, since Claude Code's Monitor always runs its command in the background and streams its output lines back later; and a command that runs a test check in a list ending in a lone `&` (`statusHiddenBy`'s `background`, below). Its result reaches the agent later, as a task notification or through `BashOutput` or `TaskOutput`, and the engine ties none of those to the call. When no other command in the turn runs a test, the claim is marked "The test commands in this turn ran in the background, so the engine didn't see whether they passed." For Claude Code's flag and Monitor, every call the test words and runners above count is left out; for `&`, only a test check, so `npm run dev &` counts as it did before. A test run in the foreground decides as above, so a passing `go test ./...` and then a server started in the background gets no mark. An agent that leaves `background` out gets the foreground rule: the field comes from the agent's container, so it can only take trust away. A subagent's call reported between turns is counted without its flag, since the engine keeps only its command.

A command's exit status isn't the check's own when the output of a segment that runs the check is piped (`|` or `|&`) into `grep`, `egrep`, `fgrep`, `rg`, `tail`, `head`, `tee`, `less`, `more`, `sort`, `uniq`, `wc`, `awk`, `sed` or `cut` as the pipeline's last command, and the command sets no `pipefail` (`set -o pipefail`, `set -euo pipefail`, `bash -o pipefail`, zsh's `setopt pipefail`) and reads no `PIPESTATUS`; or when it ends in `||` and a command that isn't itself a check, after a check, such as `|| true`, `|| :`, `|| exit 0` or `|| echo failed`, unless that command keeps the failure (`false`, or `exit N` or `return N` with a literal N other than 0); or when the list that holds the check, from the last `;`, newline, backtick or `&` at the same depth of parentheses, ends in a lone `&`, which runs the whole list in the background: `go test ./... &`, `nohup go test ./... >log 2>&1 &`, `cd web && npm test &`, `(go test ./...; echo done) &`, and `go test ./... && npm run dev &`, but not `go test ./...; npm run dev &`. A lone `&` isn't part of `&&`, `|&`, `&>`, `>&`, `<&` or `;&`, so `2>&1` and `&>out` aren't one. The filter is found through the same prefixes as the parser above. `;`, `&&`, `||`, `&`, a newline, `$(` and a backtick end a pipeline; parentheses don't, so `(cd web && npm test) | tail` counts. The build claim's rule doesn't change.

Limits: the engine reads the command line only, so a check that reports success while tests failed inside it isn't caught: a script or `make` target that swallows the failure, `go test ./...; echo done`, a pipe into a program not in the list, or a pipe after a command substitution, as in `go test $(go list ./...) | tail`. The other way, a `&` in quotes counts as a lone one, as in `go test -run 'A&B'`, and so does `go test ./... & wait $!`, whose exit status is the test's. For Claude Code, `ok` is the plugin's reading of the call's result: false when the call was refused or Claude Code's result carries `isError`. Claude Code's documentation says a Bash command that exits non-zero is a failed call, except exit code 1 from `grep`, `rg`, `egrep`, `fgrep`, `find`, `diff`, `test`, `[`, `git diff` and `git grep`; it doesn't say in so many words that the plugin's result then has `isError`. For the development ACP agent, `ok` is whether the agent reported the call as failed.

A named file counts as touched by the turn when any of these holds:
- a Claude Code edit tool in the turn (`Edit`, `MultiEdit`, `Write`, `NotebookEdit`) named it;
- a command in the turn names its base name;
- the session branch's commits made during the turn change it: the engine reads the branch's commit with the hash-checked reader when the turn starts and again at the check, and compares the two trees;
- the worktree file's modification time is at or after the turn's start, less 2 seconds. `page.TurnFiles` reads it through an `os.Root` on the session's worktree under `/workspace/s/<box>/worktrees`, opened through `files.OpenTree`, follows no symbolic link and doesn't look at names that look like secrets. A bare name is looked up with the file list's walk of the worktree (12 folders deep, 20,000 files, 250 ms).

A file claim is shown as "Not checked" with the reason when the engine can't tell: it couldn't read the branch's commit at the turn's start, the walk was cut short, or the file isn't in the worktree, is under a hidden or skipped folder, or sits behind a symbolic link. Untracked and uncommitted files count through their modification time, since the engine reads no index.

The page gets the last 20 turns with a mark or a note in the session's `unbacked` field, and shows each under that turn's last reply. They're kept in memory: an engine restart clears them. Each quote is the claim's sentence with secrets masked as the push scan masks them, control and direction characters removed, cut at 200 characters; a quote that still looks like a secret is replaced by the mask.

Limits:
- everything here rests on the session's container's reports and files, which an agent can write. An agent can hide a mark, by reporting a test command it didn't run or by touching a file, but it can't make the engine hold anything;
- the check is per turn. A summary of earlier turns' work gets marks for files changed before this turn, and a "tests pass" about a run in an earlier turn is marked too;
- a file changed in a way that keeps its modification time (a rename, a copy with times preserved) and that no command or edit of the turn names is marked.

## The agents' user settings report

Code: core `session/homesettings.go`, `session/homewake.go`; adapters `agenthost` `home.go`, `git/state` `homesettings.go`, page `start.go`, `startup.go`; `web/components/consent.ts`.

**What is listed.** The engine asks the session's container's agent-host (`/v1/home-settings`) for a list of the agent's user-level settings in that container's home with a SHA-256 per item. agent-host reads only these paths in `$HOME`: Claude Code's `settings.json` and `CLAUDE.md` and its `agents/`, `skills/`, `commands/`, `hooks/`, `rules/`, `output-styles/`, `plugins/` and `projects/*/memory/` folders (in `CLAUDE_CONFIG_DIR` if set), `.gitconfig`, `.config/git/config` and the shell start-up files. It never opens `~/.claude.json`, which also holds account details, or a credential or sign-in file: none is on that list. It reads the single files first (`settings.json`, `CLAUDE.md`, the git files, `.npmrc` and the shell start-up files), then `hooks/`, `rules/`, `agents/`, `commands/`, `skills/`, `output-styles/`, `~/.ssh/`, each installed plugin under `plugins/cache/<marketplace>/<plugin>/` (up to 64, each starting with every version's `hooks/hooks.json`, `.mcp.json`, `.lsp.json`, `.claude-plugin/plugin.json` and `plugin.json`), the rest of `plugins/` and the memory folders. Each of those folders and plugins has its own share of the limits: whatever one reads, it leaves 80 items and 1 MiB (less when there are many, so the shares always fit in the caps) for each after it, so none can starve another, and a folder that reaches its share ends with its own `(stopped after N files, in <folder>)` item, which asks at every wake and is listed with the single files. Folders are walked without following links, at most 6 deep (`plugins/` 10, so an installed plugin's `skills/`, `agents/`, `commands/` and `hooks/` are compared by content), 2,000 entries a folder, 1,000 items, 1 MiB a file and 32 MiB in all. The walk also stops after 60 seconds, with a `(stopped after 60 seconds)` item that asks at every wake; an item of the saved list that a stopped walk didn't reach is listed as not reached, not as removed. Each item is named by its path; a name that holds a token-shaped string is masked (`[hidden: looks like a secret]`), by agent-host and again by the engine before it shows or saves a list, and every saved "changed" line is masked again when `agent-settings.json` is read and written, and a name that holds a control character or invalid UTF-8, or would be over 400 bytes with a folder's trailing `/`, is shown cleaned and cut with `…` and 128 bits of the SHA-256 of its real path, so every name agent-host sends fits the engine's 400-byte limit, so two paths never share a name, and if two ever did, the list carries an item that asks. A link is hashed by its target, which asks at every wake; a file with more than one link, over 1 MiB or past its share of the bytes is hashed by its size and time, and `~/.npmrc` and `~/.ssh/` by size and time only, since they can hold credentials; each of these asks at every wake.

A `node_modules` folder inside the listed folders is one item, read through an `os.Root` opened at that folder and hashed over every entry's path, mode and masked content. A link in it counts as compared only when Go's root resolves it, every link in the chain included, to something inside the folder; one the root refuses (an escape) or can't resolve makes the folder a link item that asks at every wake. A `.git` folder is one item hashed over everything in it but its data (`objects/`, `refs/`, `logs/`, `packed-refs`, `index`, `shallow` and the `*_HEAD` files), at its top and in every git folder below it (a folder under `modules/` at any depth, or under `worktrees/`, that holds a `HEAD` file), each data entry having to be a plain folder or file. It isn't compared, and asks at every wake, when it holds any link, a data entry that isn't a plain folder or file, a `commondir` file, or a `config` or `config.worktree` in one of those git folders that isn't plain inert text. Plain inert text is UTF-8 with no byte-order mark and no carriage return, every line blank, a comment, exactly `[section]` or `[section "sub"]`, or `key = value` with no quote, backslash, `#` or `;` in the value, and every key one that `git clone` writes and that names no program or file: `core.repositoryformatversion`, `filemode`, `bare`, `logallrefupdates`, `ignorecase`, `precomposeunicode` and `symlinks`; `remote.<name>.url` with an `https://` value, `fetch`, `promisor` and `partialclonefilter`; `branch.<name>.remote`, only naming a remote of the same file whose `url` is `https://`, and `merge`, with every `[remote]` section having such a `url`; `extensions.objectformat`; and `user.name` and `email`. Anything else (another key or section, `include`, `url`, `protocol`, `submodule`, a continuation line, a second header on a line) counts as naming a program or another file, an allow-list so that git syntax this check doesn't read, and keys git adds later, ask rather than pass. `~/.gitconfig` and `~/.config/git/config` are compared by content, so a change asks, and one that holds the word `include` anywhere (an `[include]` or `[includeIf]`, in any spelling) asks at every wake, since the file it includes isn't compared; a program such a file names, like `core.fsmonitor`, is a file the settings name outside the listed folders (below). A `.git` file (a `gitdir:` pointer) asks at every wake for the same reason. A file over 1 MiB or with more than one link, and a tree past 20,000 items in all, 24 deep or its share of the bytes make the whole folder an item that asks at every wake. Text is hashed after token-shaped strings are masked, and a file whose text masking changed is listed as `masked`. User MCP servers come from `claude mcp list`, run by agent-host with the cleared key variables in the workspace folder, each server's line hashed without its status.

**The baseline.** The engine keeps one list per container in `agent-settings.json` (`boxes`, each with its `box`; format 2), the most recently saved first, at most 256, dropping the oldest past that, so a start of one session never resets another's comparison. Past 4 MiB it drops the largest lists first and keeps a `dropped` marker for each in its place, so that container's next wake says its previous list was dropped because the record was full. A container's list goes when Delete removes the container, and each save drops the lists of containers `boxes.json` no longer holds. A format 1 file, one list with its `box`, is read as that container's list (one with no `box`, from the shared container, as none) and is copied to `backup/` before the first format 2 write. Only the engine writes this file, in `engine-state`, which no session's container mounts. A start saves the files' list after the start-up approval and before the agent's first launch, synchronously, so the agent's first seconds aren't in it; `claude mcp list` runs after the launch, in the background, and saves only the MCP servers' lines, never the files'. When the record can't be read, a save writes nothing, so the other containers' lists stay as they are.

**The wake asks.** Each wake (Wake, a message to a stopped session, and the wake at a usage reset) reads the files' list before the start-up approval of the repository's files, before the sign-in check (`claude auth status`, which loads `~/.claude/settings.json`) and before the cost question, and never runs `claude mcp list` or anything else from the home first. A wake whose container is still running but isn't waiting for an answer of this wake stops it first, so the list comes from a freshly started container with no process left from the agent. It compares the list with the container's saved one and asks (409 `needs approval`, `needs.home`: `box`, `digest`, `changed`, `more`, `first`, `problem`) when:
- an item is new, changed or removed, other than under `projects/*/memory/`, Claude Code's auto-memory, whose changes only show under Agent settings in Diagnostics;
- an item can't be compared by its content, so a change could hide behind an unchanged hash: a link, an item compared by size and time, a `masked` file, an item agent-host couldn't read, and a folder or list cut at a limit. These ask at every wake while they are there;
- there is no saved list for the container, or it was dropped;
- agent-host's list couldn't be read or broke a limit, or the record couldn't be read. Nothing is compared then, and approving wakes without a comparison.

`changed` names each item as agent-host wrote it (agent-written text, which the page shows as text only), with `(new)`, `(changed)`, `(removed)` or why it isn't compared: by risk class, which agent-host decides from each item's real path before any cleaning or masking and sends with it (`class` 1, 2 or 3; the engine takes anything else, and every item that isn't compared or is a `(stopped …)` or collision item, as 1): everything under `~/.claude/plugins/` is class 1, and so is anything under `~/.claude/hooks/`, any `.json` file, any executable file and any file `settings.json` names; outside `plugins/`, class 2, instructions, is only `CLAUDE.md` and a non-executable `.md` file whose first folder under `~/.claude/` is `rules/`, `agents/`, `commands/`, `skills/` or `output-styles/`, and class 3 is only a non-executable image, `.txt` or `.md` file outside those folders, and the memory folders. Changes under `plugins/` are never folded into a count: each plugin root (`cache/<marketplace>/<plugin>/<version>/`, or the first folder under `plugins/` for anything outside the cache, or `plugins/` itself for a loose file) gets one line of its own, first on the card, naming its changed files, changed and removed ones before new ones, up to 8 and then "and N more files in this plugin", and every plugin's line is shown however many there are. Class 1 comes first, then 2, then 3, and within each class the first item of each folder, plugin and marketplace comes before the second of any. At most 200 lines are shown. When there are more, everything else is collapsed into one line per top folder ("N other changed items in ~/.claude/plugins/ aren't listed"), so it can't hide an item of the first two classes; if those two classes alone don't fit, the card says in a line how many items that can run programs, or that give instructions, aren't listed. The hidden items are counted in `more`, which the page shows as items not shown that approving also approves. The `digest` is the SHA-256 of `software-factory home settings v1`, the container, the time of its saved list (or `none`) and each item's name, kind and hash, so an answer from an earlier question doesn't pass once the list or the saved list changed; when nothing could be compared it is a random one-time value the engine keeps in memory for 30 minutes; a use, a refusal, a wake that ends without waiting, the end of the 30 minutes' wait and every later question of that container, whether its list was read or not, each end it, so the value `/api/audit` returns with a refusal or an approval wakes nothing. `/api/wake` and `/api/message` take the answer as `home`, separate from `approve`, so a start-up approval never answers this question. The wake reads the list again and goes on only when `home` equals the new digest: it saves that list as the container's, writes a `home-settings` `approved` line in `audit.jsonl` with the digest and the count of items (never their names), which `/api/audit` returns with the entry as `hash`, as it does every entry's hash, and goes on to the start-up approval. With nothing changed it saves the list and goes on without asking.

**Answering on the page.** The page shows the list with **Approve and wake** and **Don't wake**. The engine keeps a hash of each item, not a copy, so it can't show what an item held before or restore it. Don't wake (or closing the dialog) sends `/api/wake` `{sid, refuse: true}`, which only a session whose wake is waiting on this question takes (409 `not asking` otherwise). It stops the container, writes `home-settings` `refused`, and leaves the saved list as it was, so the next wake asks about the same items; the session stays stopped and can be deleted. From the moment a wake starts until its question passes or the container stops, the engine runs nothing in that container: the wake marks the session's container before it starts it, the sign-in routes answer 409 `settings question` while the mark is set (checked once the container is known to be running), and the periodic `claude agents` and `claude daemon status` reads skip a container whose session is marked, waiting on this question or in the middle of an action, checking that under a lock per container which the wake takes to set the mark, so a read already under way ends before the wake starts the container. Delete of a Claude Code session whose list would ask doesn't run `claude rm`: the engine offers the branch's unpushed commits from its own read, as for a session whose worktree is gone, and agent-host's own git (`GIT_CONFIG_GLOBAL=/dev/null`) removes the worktree, so Claude Code never starts under settings the person didn't approve. The session list shows "settings changed: Wake to review them" (`homeHeld`) after a question nobody answered and after Don't wake. A wake at a usage reset that would ask doesn't wait: it stops the container at once, marks the session `homeHeld` and logs `wake-at-reset-held`; Wake on the page then asks. An API key pasted for the session while its wake waits after this question passed (in the sign-in panel the wake opens) saves the list again after the key step, when the list before the step matched the saved one, so the person's own key doesn't ask at the next wake; a key pasted while the agent runs, or a "don't ask again" Claude Code saves in `~/.claude/settings.json`, asks at the next wake.

**Agent settings** (in the Diagnostics dialog) shows, for each running session, "changed since the last start" with the items that are new, changed or removed in that session's container, auto-memory and MCP servers included, and says when a list couldn't be read or saved.

**What it can't see.** `~/.claude.json` (user and local MCP servers, which `claude mcp list` shows under Agent settings in Diagnostics after the wake, not before it), a file these settings name outside the listed folders, and a change from one token-shaped string to another inside a `masked` file's masked part, which asks anyway as an item that isn't compared. The list is an agent report from inside the session's container. A wake reads it from a freshly started container whose only process is agent-host, from the image, so an agent's leftover process can't answer for it; a hostile agent that found a way to change what that agent-host answers could still hide a change.

## Recap, workspace, register and notifications

Code: core `session/recap.go`, `session/workspace.go`, `session/exceptions.go`, `session/changepoints.go`, `session/viewed.go`; adapters `git/state` `auditall.go`, `recapseen.go` and `viewed.go`, `git/workspace`, page `views.go`, `pushes.go` and `viewed.go`; `web/components/recap.ts`, `workspace.ts`, `exceptions.ts`, `notify.ts`, `changes.ts`, `rules.ts`, `overview.ts`, `session-list.ts` and `palette.ts`, `web/palette-items.ts`, and `web/lib/highlight.ts`.

- **Recap.** While a session is open and the tab is visible, the page tells the engine every 30 seconds (`/api/recap`, `{op: "seen", sid}`), and the engine keeps the time in `recap-seen.json`. When the person opens the session again, `{op: "read", sid}` answers lines built from the audit file since that time: pushes and their results, review verdicts, overridden verdicts and allowed flags, permission cards answered and those away mode denied, issues and pull requests opened, comments posted, approvals, and caps reached or answered (`cap-reached`, `cap-answer`), with the number of cards waiting now. Each line is the engine's own fixed text with names, branches and short commit hashes the engine checked; none of it is agent text. At most 20 lines are shown.
- **Workspace.** `/api/workspace` (`{op: "view"}`) answers the workspace volume's free and total space from `statfs` (Linux and macOS builds; others show it as unknown), a warning below 2 GiB or 5% free, and each session's worktree size. The engine counts `worktrees/<name>` itself through an `os.Root`, depth first, reading folders in batches of 512 without following links, opening each from its parent's open handle with `O_NONBLOCK`, `O_DIRECTORY` and `O_NOFOLLOW`, at most 64 deep and 200,000 entries in 5 seconds, and says "more than" past a limit; a folder it can't open is skipped; sizes are kept for 2 minutes. The disk cap's measurement walks the same way with `Sizes.BoxSize`, the same loop with four rules apart, over the whole `s/<box>` folder and at most 1,000,000 entries ("Caps, usage limits and loops"): a folder it can't open makes the count "at least", where the page skips it; a file's stat that fails other than as gone makes it "at least", where the page skips the file; a folder replaced by a file between the listing and the open is counted as that file, where the page skips it; and a file with several hard links counts at its size divided by its links, where the page counts it in full. Both take one walk lock, so a measurement can delay the view's sizes: a session whose turn comes after the view's 30-second budget has run out shows its size as unknown, and one walked with what is left of the budget may stop early and show as "more than", kept for 2 minutes like any other size. `{op: "delete", sid}` deletes a stopped session through the same path as its own menu (`claude rm` for Claude Code, then agent-host removes the worktree; when the worktree or the session's container is gone, the engine reads the branch in the clone itself as this view does and, unless its head is on main or pushed, offers to discard it instead of running `claude rm`), and only when its branch's head is on the recorded main or is, or is under, a commit the audit file records as pushed to that branch. Otherwise it refuses, so commits that aren't pushed stay. An offer that `claude rm` or agent-host makes (`flag`, `value`) is passed back the same way, and the check runs again with it.
- **Register of exceptions.** `/api/exceptions` (`{}`) lists, read only, the audit file's pushes allowed with the person's reason (the `allowed` line with a typed reason), overridden verdicts, allowed flagged files and commits, and cap lines; the hosts added under Network access with when, their expiry and the person's reason, and the gateway; and each project's saved allow rules, which it reads the way `/api/allow-rules` does. Allow rules carry no reason, since Claude Code asks for none.
- **Notifications.** A setting in Settings (the gear in the activity bar), off by default, asks the browser's permission and keeps "on" in the tab's `sessionStorage`, as the open tabs are: the page clears the site's other storage at each load. When the tab is in the background or not focused, the page shows one notification per new card, held push, finished turn and finished review, with fixed text and the session's name as the page shows it. A finished turn and a finished review come from the engine as `notify` frames on `/api/events` (`{type: "notify", sid, what, key}`, `session/sessionnotes.go`): the engine sends one when a session reports `idle` after `busy`, and when a running review of a session ends with a commit; a session can't send that frame type itself. It keeps the keys it has seen in `sessionStorage`, so a reload doesn't repeat them, and a click focuses the tab on that session.
- **Changes view.** `/api/changes` takes `from`: `fork` (or no field) for the merge base with main, `reviewed` for the commit on the branch with the latest reviewer's pass or block (by the review's end), `turn` for the branch's head when the session last reported starting a turn (`Registry.TurnBase`, read when its `busy` frame arrives and kept in memory only, so none after an engine restart until the next turn; the frame comes from the session's container, so the agent can move this point, and the page labels it as the session's report), or `commit` with `commit`, 40 hex digits. Each of the three must be in one walk of the branch from the head back to the merge base with main (`BranchCommits`, at most 5,000 commits, stopped by the request's deadline): a reviewed or turn commit outside it isn't offered, and a chosen one answers 409, naming the 5,000-commit bound when the walk stopped there. This walk replaces the per-candidate ancestry searches. A request still makes the walks the default view always made: the merge base with main (at most 200,000 commits) and the commits from the base to the head, which first marks what the base reaches (at most 200,000 more), besides the branch walk's 5,000. Every one of these walks, and `IsAncestor` (at most 1,000,000), takes the caller's context and checks it every 256 commits, so on `/api/changes` and the benchmark's merged diff (`/api/pair`) all of them stop at the request's deadline or when the page goes away. The push decision passes its own context (bounded by `PushFor` and the shutdown grace) to the gate's facts, the work facts, the push size hold, review depth, the required-review and findings lookups and the flag scan; a review start passes its own to its plan, approved texts and team rules, and a review run passes its run context to the approval recheck after each role; the page's routes pass the request's; automatic findings sends pass the engine's run context. A cancelled read is an error, never a count: it isn't cached and the change isn't listed as uncounted. A review start whose context ends while it plans (its required roles, approved texts, team rules or incremental bases) starts no reviewer and records nothing, answering 409 `stopped`; a role's approval recheck in a run whose context ended keeps the earlier approval rather than counting none. What has no caller context and passes `context.Background()`, relying on those caps: the turn-end check of claimed files (`checkFiles`), the approved texts put in a compaction note (`ApprovedDocs`), Keep's check that it holds a commit, the push extras (`computeExtra`, `scanChange`), the worktree check after a turn (`readWorktree`), the workspace view's branch state, Forget on the team file (`ForgetTeam`) and the approval recheck it starts for the project's sessions, the approval recheck when a session reports new requirements or plan documents (`RecheckApproval`, from the registry), and the commit list written into a review's snapshot (`writeCommits`). Another value, a `commit` without `from: "commit"` or the other way round answers 400 `fields`; a point with no commit yet, or a commit not on the branch, answers 409 with the reason, and the page goes back to the merge base. The answer carries `from`, `base`, `baseRef` (the words the view shows for the base, with its commit) and `points` (`reviewed`, `reviewedAt` and `turn`, so the page offers only the points that exist). The engine computes every diff from the session's clone with its own readers, as before; the page only lays the engine's unified diff out side by side and colours it. Highlighting is `web/lib/highlight.ts`, a tokenizer of about 220 lines for the common languages (keywords, strings, comments, numbers), written for the page rather than taken from a library: the common highlighters (highlight.js, Prism) build HTML strings and set `innerHTML`, which `make files` refuses in the page; the page has no bundler, so a library would ship as extra modules or an import map, an inline script the CSP refuses; and their grammars weigh more than the whole tokenizer. It renders tokens as `span` elements with classes, never markup, and is off for a diff of more than 20,000 lines; a line over 2,000 characters, and every line past the first 400,000 characters of code, is shown as plain text, and its patterns have no overlapping quantifiers, so no line can make it backtrack; its colours are per theme (`--syn-*`, `--diff-*` in `themes.css`), each at least 4.6:1 against the page and the added and removed line tints.
- **Viewed marks.** Each file in the answer carries `blob` (the head's blob, or the old one for a deleted file), `viewed` (a mark for that path with that blob) and `stale` (a mark for that path with another blob: the file changed since the person viewed it, so it shows unviewed with "changed since viewed"). `/api/viewed` (`{sid, path, blob, viewed}`, checked like every page route; 400 `fields` for a missing or wrong-typed field, a `path` over 4,096 bytes or not UTF-8, or a `blob` that isn't 40 hex digits; 409 for a session this engine didn't start) sets or clears one mark, which `viewed.json` keeps. A mark is set only for a version the session's branch has: the path's blob at the branch's head, or a version the change from the merge base with main adds, changes or deletes (compared with the masked path the page shows); anything else answers 409 `not on branch` with the reason. Clearing a mark needs no such check. The engine prunes the marks of sessions it no longer has at each change and drops the oldest session's marks past 200 sessions or about 2 MiB; a session's 1,001st file answers 429 `viewed`. A `viewed.json` the engine can't read isn't written over: every mark answers 409 `not read`. They live with the engine, not in the browser, because the page keeps only its sign-in and open tabs in the tab's own storage, and marks meant for a review that takes days should outlive a tab and a browser.
- **What a session may do.** Its fixed refusals are only those that hold for that session's agent: the command and write checks (push-shaped commands, cloud hand-offs, protected paths) are listed for Claude Code only, with a note for other agents, and the git host line names the built-in hosts and the deny list, not every git host. `web/components/rules.ts` reads, when the person opens it, `/api/allow-rules` (`{op: "list", repo}`, the rules of this session's container and the clone folder), `/api/egress` (`{op: "read"}`), `/api/team` (`{path, op: "read"}`, the approved team file's `protect` list) and `/api/exceptions` (filtered to the session), with away mode from the page's `halt` frame. It adds no route and offers no control: each changeable item links to the control that changes it, and the fixed refusals are text.
- **The Changes tab.** The Changes view opens in an editor tab of its own (`c:<sid>`), full width in the main area, with its file list and diff expanded, and closing it returns to its session, with a one-line summary and Open Changes in the session's details. Only the main area scrolls: the root and body clip, so focusing the diff never scrolls the page.
- **What the engine decides for each session.** Each entry of a `sessions` frame carries the engine's words and allowed actions (`session/sessionstate.go`), which the page only shows: `summary` (`{word, tone}`, the status word and the dot's tone; "working" also while the session reports compacting or a running subagent), `warnings` (the sentences under the session's header), `control` (`{text, action, label, confirm, confirmText, tone, alert}`, the read-only, wake, release or control notice and its button), `actions` (for `control`, `steps`, `stop`, `wake`, `manage`, `model`, `bringMain`, `fork`, `copy`, `restore`, `checkpoint`, `review` and `rules`, an empty string when the page may offer it, else the reason it's off), `readOnly` (the note of a session whose branch another session holds) and `stalled` with `stalledSince`: a session the page controls, in its turn, with no card waiting and no subagent running, that reported nothing for 10 minutes (`StallAfter`). A `context` frame from a knackpack session carries the engine's `checkpoint` (`{level, text, said, stop}`), whatever the session sent under that key. `/api/gate` adds `started` (`true`, `false`, `"nobase"` or `null` when the branch couldn't be compared with main), `review` (`{available, reason, planned}`: the reason Review is off and the reviewers Review would run on the head) and `pushed` (the head is pushed), and each document's `note`. `/api/projects` adds `readiness` (`[{id, text, action}]`: commit name and email missing, reviewers not signed in), `hostNotes` (a sentence per git host) and, per starter, `fields` (`{model, effort, expect}`) and `command`; each work type a `startWarning` when it has one. `/api/session-work` adds each queued message's `up`, `down` and `editable`, and `canSwitchModel`. A `needs` answer adds `next` (`home`, `sign-in`, `trust`, `approve` or `cost`, the step the page asks the person for), and the page follows it until the answer has none; `/api/claude-trust` gives `tries` (approvals left) and, after the second approval of files that changed meanwhile, refuses with 409 `changing`. The page keeps only what depends on itself: its connection to the engine, a request it is waiting for, a confirm press, a dismissed stall notice, and a session the engine stopped listing while its tab is open.
- **Done.** A session whose agent finished and ended by itself (`state: "done"`) reads Done in the list (its own Done group), the title and the control line, apart from Stopped.
- **Session search and the palette.** The session list's search (name, the session's own branch, a pushed branch, project) and state filters (running, waiting for you, held push, stopped, done) are kept in the URL fragment (`#q=…&state=…`), which never reaches the engine. The palette (the header's search box, Ctrl+K, or ⌘K on a Mac) lists the page's own views and the open session's actions in a pop-up shaped after VS Code's Quick Open: an input over a listbox, each group's name at the end of its first option rather than a header row, and an option's key, only where the page has one (`?` for Keyboard shortcuts while that key is on), as key caps; each calls the function its button calls, or presses the button itself where the button asks twice (Stop and Delete), after clearing any earlier unconfirmed press, so a palette press only ever arms it and the person still presses Confirm. `?` outside a text field lists the shortcuts, and a page preference (`keys`, `on` or `off`, in `prefs.json`) turns that key off, as WCAG 2.1.4 asks of a single-character shortcut.
- **Line comments.** On the Changes view, the person picks lines in the diff (click, or the arrow keys and Enter), writes a comment for each, and Send comments sends `/api/message` `{sid, comments: [{file, line, removed, text}]}` in place of `text`, each comment as typed. The engine composes the one message the agent gets (`session.CommentsMessage`, `composed.go`): a line saying how many comments, then one line per comment with its file and line (a removed line is numbered in the old file) and its text on one line. It refuses with 400 `comments` and a message an empty list, more than 50 comments, a comment that is only white space or over 2,000 characters, and comments whose message would pass the message's limit of 20,000 characters; the page keeps the draft and shows the message beside it. A comment that isn't an object of those four fields, a `file` that is empty or over 4,096 bytes, a `line` that isn't a whole number from 0, or `comments` beside `text`, `revise`, images or files is 400 `text`.
