# Reference: the image and Compose

This is part of the Reference section of [ARCHITECTURE.md](../../ARCHITECTURE.md#reference), which describes how Software Factory works and why.

## The image and Compose

One multi-platform image (amd64, arm64) runs every role; `compose.yaml` starts three of them, and the box helper starts each session's container and each reviewer container from the image it runs itself. Build stages: Node builds the page (`npm ci --prefix web && npm --prefix web run build`), Go builds the binary with CGO off, and the runtime stage is `node:26-trixie-slim` (pinned by digest) with `git`, `ca-certificates` and `curl` added, `openssh-client`, `rsync`, `sshpass` and `netcat-openbsd` for port grants (README "Access") added with `ssh`, `scp`, `sftp`, `rsync`, `sshpass` and `nc.openbsd` group `sf` and mode 0750, so only `engine` and `agent` can run them and the reviewers (`reviewer`, not in `sf`), egress and the helper can't, and npm, corepack and yarn removed. The four packages and their libraries (`libedit2`, `libfido2-1`, `libcbor0.10`, `libpopt0`) add about 7.7 MB uncompressed (8 packages, `apt-get` on arm64, trixie 13.8). Verification runs use the project's own image, so they don't get them. The last stage, `runtime`, is the one to publish; the `dev` stage adds the marker file `/usr/share/software-factory/dev-image`, the fake ACP agent from `dev/fakeacp` and the fake reviewer from `dev/fakeclaude` (`/usr/local/bin/sf-fake-claude`), and the `gitserver` stage is a local git host (`dev/gitserver`: git http-backend over HTTPS with a self-signed CA, asking for a token, serving the seed repository at `/dev/demo.git` and the older `/demo.git`, with a small fake of GitHub's REST API under `/api/v3` in `dev/gitserver/github.go`, so the engine's GitHub adapter reaches it at `https://gitserver.test:8443/api/v3`, an untokened fake of the update check's two routes under `/release-api`, and an untokened, fetch-only stand-in for knackpack's repository at `/public/knackpack.git` ("knackpack")); both are built only by `compose.dev.yaml`, which runs the engine and the box helper on `dev` and egress on `runtime`. The API fake answers only what the engine's adapter reads (the repository, branches, open pull requests, opening issues and pull requests, issue lists, comments, reviews, `/user`, check runs and statuses), gives every answer an `X-GitHub-Request-Id`, asks for the git server's token as a Bearer token, and keeps its state in one JSON file; `sf-gitserver` subcommands add comments and reviews, switch drafts off and set delays and failures (`comment-403` refuses the next comments the engine posts), so a development run can reach the cases a real host makes rare. `sf-fake-claude` makes no model call and refuses, with an error result, a run whose flags or `--settings` aren't the engine's reviewer command line, a run a variable that looks like a credential reached, and one whose folder isn't the engine's snapshot, so a development run catches a reviewer started the wrong way; the flags and settings it checks, what it reports and the files in the snapshot's `head/` that change its reply are in [Hand checks with Compose](../../.claude/rules/compose-hand-checks.md). The fake ACP agent calls the `factory_*` tool a prompt names (`factory_review_comments` included), echoes a note the engine put before a prompt, and stays in a turn for the prompt `stall` until it is stopped. git http-backend takes pushes only from an authenticated user, so the git server sets `REMOTE_USER` after its own token check. In that overlay the gitserver is on `gitnet`, an internal network only the engine joins, as `gitserver.test:8443`; it writes its CA to the `gitserver-ca` volume, which the engine mounts read-only and trusts through `SF_DEV_GIT_CA`; and `gitserver.test` is added to the refused git hosts (`EGRESS_DENY`) of both the engine and egress, so the sandbox check covers it.

The `gitserver` stage removes `reviewer` and gives its uid to `gitsrv`, which the `gitserver-data` volume's files carry. The image contains no agent.

**Claude Code's managed settings** (`/etc/claude-code/managed-settings.json`) turn off the features of Claude Code that reach a session around the page, or reach outside the sandbox, in every session and review. Managed settings outrank user and project settings and `--settings`, and Claude Code adds their list keys, such as `permissions.deny`, to the other sources' lists. Neither the agent nor the reviewer user can change the file or add one beside it in `managed-settings.d/`: the folder is root's, on a read-only root filesystem. The file sets:
- `crossSessionInbound: "refuse"`: a message from another Claude Code session, or from any program of the same user posting to a session's inbox socket (`CLAUDE_CODE_MESSAGING_SOCKET`), is dropped;
- `permissions.deny` with `SendMessage` and `ListAgents`: a session can't list or message other sessions. `SendMessage` also continues a subagent and messages agent-team teammates, so those go too; a subagent's result comes back as the `Agent` call's result, not through `SendMessage`;
- `disableRemoteControl: true`: `claude remote-control`, `--remote-control`, `remoteControlAtStartup` and the in-session toggle are refused, so no session reaches the person's cloud sessions or Remote Control sessions on other machines. `isolatePeerMachines: true` is a second guard: a message to a session on another machine needs approval;
- `syncClaudeAiPlugins: false`, `syncClaudeAiSkills: false` and `disableClaudeAiConnectors: true`: a session signed in with claude.ai loads none of the account's synced plugins or skills and none of its connectors. Reviews need this most: `--setting-sources user` doesn't skip them, and a synced skill's text could sway a verdict;
- `autoMemoryEnabled: false`: Claude neither reads nor writes auto memory (`~/.claude/projects/<project>/memory/`), which every worktree of a repository would share in the session's writable home and a later wake of it loads without a start-up card. This is hygiene for honest sessions, not a defence against a hostile agent: `~/.claude/CLAUDE.md` in the same home is a stronger channel (Known limits). The cost: what the person types to correct Claude no longer carries over to later sessions on its own. The repository's instruction file (`CLAUDE.md`) is the place for that;
- `env` with `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE: "0"`: Claude Code's experimental Code Mode (2.1.323 and later), in which Claude writes JavaScript that makes the tool calls, stays off in every session and review. Code Mode changes how tool calls reach hooks: a shell command can reach the plugin's tool check in a compound form (a `git push` in a folder `app` as `cd 'app' && git push`), and a hook that doesn't finish in time refuses the call, where today the plugin falls back to its own check. The managed file is where it's turned off because the agent can write its own `~/.claude/settings.json` (Known limits), where a `"1"` would turn it on: by Code Mode's documentation, a `"0"` in managed settings wins over a `"1"` set anywhere else, and Claude Code ignores the variable in a project's settings files. The pinned 2.1.322 has no Code Mode, so the key does nothing yet; moving the pin past it has its own checks (`.claude/rules/moving-a-pin.md`);
- `prependPlugins: []`: keeps the plugin's `classic.*` hooks running. A managed file with any key in it (not `{}`) makes Claude Code 2.1.322 seat its built-in guard, `cc-plugin-sec-default`, ahead of every other plugin, and the guard sends every `classic.*` event past user and `--plugin-dir` plugins. Without this key the plugin's `classic.SessionStart` (the sandbox context), `classic.UserPromptSubmit` and `classic.Stop` (the permission mode the page shows), `classic.StopFailure` (a sign-in failure) and `classic.PermissionRequest` (the page's permission cards) are skipped. And with a host answering prompts (`--permission-prompt-tool`), Claude Code's own ask replaced the plugin's `tool.check` ask, so in auto mode, with no saved rule, `rm -rf ~/x` ran without a prompt. A set `prependPlugins` seats the guard only where it names it, so the empty list leaves it out; naming the plugin before the guard didn't change the order. The cost is the guard's protection of managed policy from other plugins: by Claude Code's documentation, a plugin installed in the agents' home could then approve a call a deny or ask rule stops, or change what managed hooks receive. Plugins run in the order they had with no managed file, when the guard loaded only for a Team or Enterprise `/login`; by the documentation, the empty list leaves it out for those sign-ins too.

The keys and their types come from Claude Code's settings documentation, apart from `prependPlugins`, which that page doesn't list: it comes from the 2.1.322 binary's behavior and settings schema, and Claude Code's plugin documentation (`plugins/mods/admin` and `plugins/mods/reference`) describes it. Offline checks against 2.1.322, with a stand-in model API and no sign-in, showed the deny rules, `crossSessionInbound`, `autoMemoryEnabled` and `prependPlugins` taking effect; no key's effect has been checked on a signed-in run, and the sync, connector, Remote Control and peer-machine keys need one. Two things outrank the file. A claude.ai organization that delivers server-managed settings: Claude Code then uses that policy and skips the file, apart from the two sync keys and `disableClaudeAiConnectors`, which it reads from every managed source. `prependPlugins` is lost with the file, so the guard is probably seated again and the plugin's `classic.*` hooks skipped, the page's permission cards included; this hasn't been checked. And `CLAUDE_CODE_DISABLE_AUTO_MEMORY` in a session's environment, which outranks `autoMemoryEnabled` either way; agent-host passes only its own list of variables, which leaves it out.

`compose.yaml`:

- **The page** is published only as `127.0.0.1:${SF_PORT:-7799}:8080`, written in the long syntax (`target`, `published`, `host_ip`), with `SF_PAGE_HOST=0.0.0.0` inside the container and `SF_PUBLIC_PORT` matching. Bound to every interface, it accepts a connection only when its local address is loopback (the healthcheck) or an address of `SF_PAGE_NAME` (`engine-page`, resolved on `outside`, where Docker delivers the published port), and closes the rest before they count toward its connection limit, so the agent and reviewer networks never reach it. The engine refuses to start when that name doesn't resolve to one of its own addresses, or resolves to loopback or the agent listener's address.
- **Hardening.** Every service: non-root user, `cap_drop: [ALL]`, `no-new-privileges`, read-only root filesystem, `init: true`, memory and pids limits, a healthcheck and `restart: unless-stopped`. Writable places are the volumes and tmpfs mounts only. `SF_UMASK=0002` keeps files in the shared workspace group-writable.
- **The box helper** (`helper`) runs `box-helper` as `10005:10005` with `group_add: ["${SF_DOCKER_GID:-0}"]` (the socket's group; Docker Desktop's socket is `root:root` 0660), the hardening above, 64 MiB and 64 processes, `stop_grace_period: 60s`, `helpernet` only, `helper-key` read-only, and one bind mount, `${SF_DOCKER_SOCKET:-/var/run/docker.sock}:/var/run/docker.sock`. The engine starts after it and is restarted with it (`depends_on` with `condition: service_started` and `restart: true`), since a new helper stops every session's container. It doesn't wait for the helper to be healthy, so the page stays up when the helper can't start, such as with a wrong `SF_DOCKER_GID`: the engine asks the helper's `/healthz` every 10 seconds and the Welcome page then says the helper isn't answering, while every start and wake fails with the reason. Its client speaks Docker's Engine API over the Unix socket with `net/http`, no SDK, pinned to `/v1.48/`. Its settings: `SF_BOX_MEMORY` (default `2g`, memory and memory with swap), `SF_BOX_CPUS` (default `2`), `SF_MAX_BOXES` (unset: no limit; set: the helper counts running and starting containers under one lock and refuses a start past it with 409 `limit`), `SF_BOX_RUNTIME` (unset, or `runsc`), `SF_BOX_SUBNETS` (default `10.213.0.0/20`), `SF_BOX_SWEEP_DRY` (`1` logs what the start-up sweep would remove and removes nothing) and `SF_BOX_LIVE` (development only, above). `SF_REVIEWER_MEMORY` (default `2g`) and `SF_REVIEWER_CPUS` (default `2`) cap each reviewer container the same way. The arithmetic for a machine: the engine 1 GiB, egress 256 MiB and the helper 64 MiB, 1.3 GiB of caps before any session or review, plus up to 2 GiB for each running session and each running reviewer container by default; `MaxReviewerRuns` (8 reviewer runs at once) bounds the reviewer containers. On an 8 GiB Docker VM the caps pass the memory once a session and three reviewer containers run; the out-of-memory score (500 for both kinds) then takes a session's or a reviewer container first, and a reviewer run that is killed fails as not passed.
- **A session's container** is made by the helper from its recipe, not by Compose. Docker copies the image's labels into a container, and an image Compose built carries `com.docker.compose.project` and `.service`, so the recipe sets every `com.docker.compose.*` label of the image to an empty value: Compose never counts a session's container as one of its own, so `up`, `restart` and `--remove-orphans` leave it alone. The helper owns a container only when those labels are empty, or, for a container made before this rule, equal the image's, which it only stops and removes. Name `<project>-box-<box>`; image: the helper's own image ID; user `10002:10000`; command `agent-host` (with `SF_BOX_LIVE` in a development image, entrypoint `/opt/sf-dev/bin/software-factory`); `Init`, a read-only root, `CapDrop: [ALL]`, `SecurityOpt: ["no-new-privileges:true"]`, not privileged, no devices, no published ports, no sysctls, a private cgroup namespace, a private IPC namespace with a 64 MiB `/dev/shm`, `OomScoreAdj` 500 so the VM's out-of-memory killer takes a session before the engine or egress, `PidsLimit` 2048, memory, swap and CPUs from the settings, restart `on-failure` 3 times, `json-file` logs of 10 MB × 3, and a healthcheck of agent-host's `/healthz`. Mounts, and no binds: `workspace` with subpath `s/<box>` at `/workspace/s/<box>`; `agents` read-only; its home volume at `/home/agent`; `uploads` with subpath `<box>` at `/uploads/<box>`, read-only; tmpfs `/tmp` (1g) and `/run/sf` (1m, 0700, uid 10002); and with `SF_BOX_LIVE`, `dev-bin` read-only at `/opt/sf-dev/bin`. Environment: `SF_WORKSPACE=/workspace/s/<box>`, `HOME=/home/agent`, `SF_AGENT_HOST_LISTEN=:8090`, `SF_ENGINE_AGENT_ADDRESS=engine-agents:8081`, `SF_PLUGIN_SOCKET`, `SF_UMASK=0002`, `HTTPS_PROXY`/`HTTP_PROXY` (both cases) set to `http://egress:3130`, `NO_PROXY` for loopback only, and `DISABLE_AUTOUPDATER=1`. Its network `<project>-box-<box>` is `internal`, without IPv6, with `com.docker.network.bridge.gateway_mode_ipv4=isolated` and the box's /28; `/etc/hosts` maps `engine-agents` to the `.2` and `egress` and `egress-agents` to the `.3`. Labels: `dev.software-factory.stack=<project>`, `dev.software-factory.box=<box>` and `dev.software-factory.recipe=<SHA-256 of the recipe>`, which the network and the home volume carry too (without the recipe). After create and before start the helper inspects the container and compares the network mode, the one endpoint and its address, the capabilities, privilege, devices, security options, an AppArmor profile that isn't `unconfined`, masked and read-only paths that hold at least Docker's long-standing defaults, ports, sysctls, the IPC mode and `/dev/shm` size, DNS servers, options and search domains (none), the OOM killer left on, cgroup namespace, read-only root, `OomScoreAdj`, mounts with their volume names, driver and propagation, image and user with the recipe; any difference removes it and refuses the start. The box's endpoint may carry no driver options and no aliases but the container's own ID and name. Ulimits must be empty after create, before start; the daemon adds its own default ulimits at start, so they aren't compared after that, and Docker can't change a container's ulimits later. It doesn't compare the volumes' paths on the host, which differ between Docker installs; the number of `docker exec` sessions shows as a fact, `execs`, not a refusal, since every healthcheck is one. A running container it reuses must also have exactly the engine, egress and itself on its network, which `members-only` reports. The hash it reports comes from that inspection. At its start the helper removes the stack's containers that aren't running and the stack's networks without a container, and reconnects the engine and egress to the running ones; it follows Docker's events to reconnect a recreated engine or egress; on SIGTERM it stops every container, so `docker compose down` leaves none running. `docker compose down -v` leaves the home volumes, which Compose doesn't know.
- **A reviewer container** is made by the helper from its second recipe, not by Compose, for one call of the engine's reviewer host (`cmd/server/reviewers.go`): each run of a role, the manual test list, Explain this change, Review this plan and Suggest lines gets one that mounts its snapshot, and each sign-in step, `claude --version`, sign-in check and agent-file write one with no snapshot; the page's Subscription sign-in keeps one from `start` until `code`, `cancel` or 10 minutes. Name and network `<project>-reviewer-<run>`, a /28 from `SF_BOX_SUBNETS` like a box's; image: the helper's own image ID; user `10004:10004`; command `agent-host -mode review` (with `SF_BOX_LIVE` in a development image, the live entrypoint); the session containers' hardening (`Init`, a read-only root, `CapDrop: [ALL]`, `no-new-privileges`, not privileged, no devices or ports, private cgroup and IPC namespaces, 64 MiB `/dev/shm`, `OomScoreAdj` 500, `PidsLimit` 2048, `SF_BOX_RUNTIME`), memory, swap and CPUs from `SF_REVIEWER_MEMORY` and `SF_REVIEWER_CPUS`, restart `no`, `json-file` logs of 10 MB × 3 and the same healthcheck. Mounts, and no binds: `reviews` with subpath `<snapshot>` at `/reviews/<snapshot>`, read-only, when the run has one; `agents` read-only; `<project>-reviewer-home` at `/home/reviewer`; tmpfs `/tmp` (1g); and with `SF_BOX_LIVE`, `dev-bin` read-only. Environment: `SF_WORKSPACE=/reviews`, `HOME=/home/reviewer`, `SF_AGENT_HOST_LISTEN=:8090`, the proxy variables set to `http://egress-review:3128`, `NO_PROXY` for loopback only and `DISABLE_AUTOUPDATER=1`; `/etc/hosts` maps `egress-review` to the network's `.3`. The engine reserves a random 16-digit run id before it asks, adds the container's /28 to egress's reviewer side, gives its agent-host a new random 256-bit key with `/v1/key` (agent-host takes one key once and keeps it in memory, so a second caller gets 409), runs the sandbox probe in it when it mounts a snapshot, makes the call through the gateway wrapper, and then asks the helper to remove it and drops the /28, whether the call passed, failed or timed out. At most 8 reviewer containers run at once (`MaxReviewerRuns`): every container the engine asks for takes one of 8 slots until it is removed, whatever it is for, a role's run, a role-less run, a sign-in check, a version read, an agent-file write or a sign-in or key step. A run, a version read or an agent-file write waits for a slot within its own time limit. A sign-in check and a sign-in or key step from the page wait at most 10 seconds in all, for the engine's key lock and for a slot together, and then answer 429 `reviews` with the reason, so a sign-in never makes a ninth container (only the engine's own slot refusal counts as busy: a `reviewers-busy` code an agent-host sends back is an ordinary refusal); the key removal after a Subscription code waits up to 30 seconds, and if every container stays busy the page says the sign-in finished and the old key needs **Remove key**. Before that, the engine admits work in runs against the same 8: a review holds one run per planned role run until its role runs end, when it drops to none, and the manual test list, Explain this change, Review this plan and Suggest lines one each; a start that would pass 8 with other runs going is refused with "Wait for one to finish" (an agent's push request then waits in the queue), and a single review that plans more than 8 runs alone starts, its runs past 8 waiting for a slot. A Review checks this before its sign-in check, so a refused one starts no container. The status the page shows for the reviewers' sign-in is the last check, kept up to 10 minutes and shown with the time the check started; a sign-in code, a key change, an allowlist or gateway change or a new reviewers' Claude Code version makes the next status check run again, while a step refused as busy before it started changes nothing; a check that started before such a change finished isn't kept (a generation counter, raised when the step starts and again when it ends), so it can't bring back the old status, and the check `finished()` runs after the change is kept. When the reviewers are busy, the status keeps the last check, marked as not checked again (the reviewers' expected sign-in kind is never adopted from such a status, nor from any check made before the person last set the expectation to any, so clearing it holds), or says the reviewers are busy when there is none; when a sign-in code, a key change or another of the changes above came after that check, it is also marked stale (`SignIn.Stale`, `stale` in the page's JSON, in the `reviewer` frame the change sends at once and in the status `/api/projects` carries), and the dialog says it was checked before the latest change and isn't current, marks no kind "In use" from it, and the Projects page treats the reviewers' sign-in as unknown and doesn't open the sign-in dialog by itself, and the open dialog checks again every 15 seconds; it opens showing the last status the page knows, with its time and "Checking again…", until the check answers. The check after a sign-in or key change runs on the engine's own context, carrying the request id, and in the reviews' wait group, so shutdown stops and waits for it; the page waits for it at most 10 seconds. Every review, test list, explanation and plan review still checks the sign-in first. **Reviewers' sign-in** in the command palette opens the reviewers' sign-in dialog at any time. At its start, and every 5 minutes, the engine removes every reviewer container the helper lists that no call of its own holds, so an engine restart mid-review leaves none behind. Review mode answers only `/healthz`, `/v1/key`, `/v1/run` (runs up to 25 minutes), `/v1/review-run` (the same, streamed: see [Reviews](reviews-and-pushes.md#reviews)), `/v1/sign-in`, `/v1/login`, `/v1/api-key` and `/v1/agents` (writes agent files, review mode only), and every route but `/healthz` and `/v1/key` needs the `X-SF-Host-Key` header to match the key it took. Agent-mode agent-host has no key: it runs as the agents' own user, so a key it holds the agents could reach too, and every route it answers in the session's container, `/v1/screenshots/remove` included, gives an agent nothing it can't already do as that user. Other traffic between containers, apart from the TLS control channel to egress ("Networks"), is plain HTTP on Docker's internal networks, which are the accepted transport boundary. Review mode has no worktrees, no long-lived processes, no plugin socket and no relay to the engine. The person signs Claude Code in for the reviewers once, from the page (the sign-in dialog, from **Reviewers’ sign-in** in the command palette), which runs the sign-in in a reviewer container and writes it to the shared home.
- **The allowlist** is `EGRESS_ALLOW`, given to both egress and the engine from `SF_ALLOW` (default: Anthropic's API and sign-in hosts) plus `SF_EXTRA_ALLOW`; `SF_EXTRA_DENY` adds git hosts to the built-in refused ones. Add the host of every repository you clone that isn't GitHub, GitLab or Bitbucket when an allow entry covers it (a gateway's `.corp.example`, say): the sandbox check fails until you do.
- **The allowlist on the page.** `EGRESS_ALLOW` is egress's starting list for both listeners, and the engine's list until the person saves a change under Network access. The engine then keeps the settings in `egress.json` in `engine-state` (at most 64 added hosts with their expiry and the person's optional reason, and the gateway) and sets two lists in egress over `controlnet` with the control key: for agents, Claude Code's model and sign-in hosts (`session.AgentHostTable`), the added hosts and the gateway's host; for reviewers, Claude Code's hosts and the gateway's host. egress swaps the lists at once, refuses a list that names or covers a git host, refuses an added host after its expiry, and closes open tunnels to a host that is no longer allowed within 10 seconds. The engine drops expired hosts from `egress.json` every 15 seconds and sets the lists again. Each change writes an `egress-allow` line to `audit.jsonl`. A reason is plain text on one line, at most 200 characters; the engine refuses one that holds control characters or looks like a token or a key, and a file without reasons loads as before. The page refuses a git host, a host that covers a repository's host or the sandbox check's outside host, and asks to confirm a host that also accepts uploads (`UploadHost` in `internal/core/session/egresshosts.go`).
- **The gateway.** The page's gateway is an https base URL on port 443, with no user name, query or fragment, and always covers the agents and the reviewers together: `/api/egress` op `gateway` takes only `url`, an empty one removing it, and `egress.json` holds no choice of sides (an older file's `agents` and `reviewers` are ignored, so its gateway covers both from the engine's start, and are dropped at its next save). The engine adds `ANTHROPIC_BASE_URL` and `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` to every Claude Code command it runs through agent-host (starts, wakes, reviews and sign-in checks; `cmd/server/gateway.go`). The gateway's key or token is pasted beside its address and takes the API key's path (see "Signing Claude Code in"): after the gateway is saved, the page sends it as a `key` step of `/api/claude-login` for the reviewers, and a session's is pasted in its own sign-in panel, since each session runs in its own container; that container's agent-host saves it in the same file for the same `apiKeyHelper`, which Claude Code sends in both the `Authorization` (Bearer) and `x-api-key` headers. One helper per container, so the gateway's key replaces an API key saved there. Before the engine saves a gateway whose host differs from the one saved (turning it on, changing its host or removing it), it removes the key saved in the reviewers' and the sessions' containers (agent-host step `clear`), so no key reaches an address it wasn't pasted for; if that fails, the gateway isn't changed. **Remove key** (`/api/claude-login` step `clear-key`) removes it from the gateway's containers and keeps the gateway.
  - **The address.** `CheckGatewayURL` lowercases the host, drops port 443 and every trailing `/`, so checking its own answer gives the same string, and `egress.json` is read back the same way. It refuses a host with a leading dot, which egress would read as every subdomain.
  - **No change while Claude Code runs there.** A session keeps the environment it started with, and Claude Code reads `apiKeyHelper` again on its own, so a session started before the change would send the next key to its old address. While the gateway's host would change and a Claude Code session is running, starting or busy, or a review or manual test list is running, the gateway step answers 409 `running` with "Stop these sessions first: …" naming them, before any key is removed or sent. Turning a gateway on or changing its host also needs egress's control channel to answer; otherwise it answers 409 `egress`.
  - **Where a saved key goes.** The engine records in `keyroutes.json`, before it sends a pasted key, that a key may be saved in that container and the gateway host then, or none; it records no key once the key is removed. A key isn't taken while `egress.json` can't be read. At start, before any session or review is restored, and before every Claude Code start, wake, review and manual test list, the engine compares that record with the gateway it applies now: none when `egress.json` can't be read or the control channel is off. When a key was pasted for a gateway the engine doesn't apply now, or for no gateway while one is applied, or the record is missing or unreadable while a gateway is applied or unknown, it removes the key in that container first. If that fails, Claude Code doesn't start there, and the refusal says to check that the container runs and try again. An Anthropic API key pasted with no gateway is left alone.
  - **Anthropic's hosts while a gateway is on.** While the gateway is on, both lists in egress leave out every entry `ClaudeVendorHost` names (`internal/core/session/egresshosts.go`): `anthropic.com`, `claude.ai` and `claude.com` with their subdomains, and Claude Code's telemetry hosts, Statsig (`statsig.com`, `statsigapi.net`), Sentry (`sentry.io`) and Datadog (`datadoghq.com`), whether they come from Claude Code's hosts or from added hosts. The gateway's host stays even when it is one of them. So a key pasted for the gateway can't leave for an Anthropic host on a side request, whatever Claude Code does; removing the gateway brings them back. Alongside `ANTHROPIC_BASE_URL` the engine sets `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` (the name in the 2.1.322 binary) for every Claude Code command, and egress logs the host of each tunnel it allows (`event=allowed host=…`), never a path, as it does for refusals.
  - **`ANTHROPIC_BASE_URL` and background sessions.** The engine runs `claude --bg` and `claude respawn` from the session's own worktree. Read from the 2.1.322 binary: the `--bg` client passes its shell's provider variables, `ANTHROPIC_BASE_URL` among them, to the session the supervisor opens when the session is in the folder it was started from, and withholds them only for a session opened in another folder (`CLAUDE_BG_GATEWAY_WITHHELD`, with the notice "No LLM gateway: … respawn from its own folder"). Reviews run `claude -p` directly. A live run with a gateway hasn't checked this yet.
- **Access grants** (README "Access", "Credentials" and "Presets", `internal/core/session/grants.go`, `grantcards.go`, `grantrisk.go`, `credentials.go`, `credentialpage.go`, `presets.go`, `handover.go`). A grant opens one host, named as Network access names added hosts (`HostName`, `ValidAllowEntry`; no host that covers `SF_SANDBOX_OUTSIDE`), or one port of one host over plain TCP (a port grant, below), or hands over one saved credential and opens the hosts it is bound to, to one session (`scope` `session`, the default) or every session of its project (`project`), for 1 hour (the default), 1 day, 1 week or until taken back (`expires` `hour`, `day`, `week`, `never`); with a gateway set, a grant can't name a host `ClaudeVendorHost` names, and one made before is left out of egress's lists while the gateway is on. A git host (one the deny list names or covers, or a project's host, `Allowlist.gitEntry`, or for an address, one of the current addresses of those hosts, `GitAddress`, below) can be granted, always at high risk. A grant opens a git host only when the person accepted it at its red card: each grant records the entries it was given for that were git hosts then (`GitAccepted`), and the egress lists, the handover's `ports`, the "already open" answers and the git marker open an entry that is a git host now only when it is in that list (`opens`). An entry that has become a git host since (a project added there, the deny list changed, an address that is now a git host's) is left out of that grant's lists altogether, so egress refuses it (`not_allowlisted` for a repository host, `git_host` for a denied one), the Access dialog's grant carries `closed` with the engine's words, and the host is given again at its red card; a refusal of a git host makes no card, as for any git host. Credential grants follow the same rule for each bound host, and their secret is still handed over. Each grant holds an id (32 hexadecimal digits), the host (and `port` for a port grant), or the credential's id, name and bound hosts as they were when it was made and the delivery (`handed`; `signing` for an SSH key, `copy` for AWS keys; `Credential.Delivery`), the scope, the session it was made in, the project, its expiry, a reason (the agent's or the person's, with Network access's limits: one line, at most 200 characters, refused when it holds control characters or looks like a token or key; the agent's is required, the person's optional), who asked (`agent`, `person` or `preset`, a preset applied at a start), the preset it came from, when it was made, and the git hosts accepted at its card. A grant is refused (429 `grants`) when it would give one session's container more than 256 hosts or 256 port targets (`session.MaxEgressEntries`, which egress's `MaxEntries` and the sandbox check's limit are set to, so the three can't differ): counted for the session it is made in, and for a project grant for every running session of the project and for a session started later, which gets the project's grants alone; so `PUT /boxes` is never sent a list egress refuses.
  - **Port grants** (`grantports.go`). The target is one host name or an IP literal and a port from 1 to 65535 (`host` and `port`; `[fd00::1]` is read as `fd00::1`). A name can't be a leading-dot pattern, a `.local` name (containers don't resolve mDNS; the refusal asks for the machine's address), a host `ClaudeVendorHost` names (409 `vendor`), the sandbox check's outside host, or have port 443, which is a host grant (400 `port`). An address is never one `AddressNever` refuses: the unspecified address, loopback, link-local (`169.254.0.0/16`, `fe80::/10`), the cloud metadata addresses `100.100.100.200` and `fd00:ec2::254`, multicast, and the reserved ranges egress refuses for names (`0.0.0.0/8`, `192.0.0.0/24`, `198.18.0.0/15`, `240.0.0.0/4`, `::/96`, NAT64, Teredo, 6to4, `fec0::/10`); nor an address on one of the stack's own networks: `SF_BOX_SUBNETS` and every network the engine's own interfaces are on (`controlnet`, `helpernet`, `outside`, each session's and reviewer's /28, and so their gateways), and the Docker host: every address `egress.DockerHostNames` (`host.docker.internal`, `gateway.docker.internal`, `docker.for.mac.host.internal`, `docker.for.mac.localhost`, `kubernetes.docker.internal`) resolves to, and the gateways in `/proc/net/route`, looked up by the engine and by egress each every minute (`egress.Known`). On Docker Desktop 4 (checked on macOS from a container on a user-defined network, through Docker's DNS at `127.0.0.11`) `host.docker.internal` and `docker.for.mac.localhost` are `192.168.65.254` and `fdc4:f303:9324::254`, `gateway.docker.internal` `192.168.65.1` and `fdc4:f303:9324::1`, and `kubernetes.docker.internal` `192.168.65.3`, and they reach the Mac's own loopback services, the page among them; on Linux they resolve only where a Compose file adds `host-gateway` for them, and the host answers at the gateway of every Docker network on it. Egress refuses the gateways of the networks it and the engine are on, but not those of other networks, such as `docker0`'s `172.17.0.1` or another Compose project's bridge, since the helper's Docker access lists only this stack's networks, so a LAN port grant to one of them, or to the host's address on the person's LAN, which egress can't know either, reaches the host's services that listen there; its card is red, as for any LAN address. Each is refused before a card (409 `never`, field `host`), and egress refuses it at the dial whatever the lists hold (`own_network`). A private, LAN or CGNAT address (RFC 1918, `fc00::/7`, `100.64.0.0/10`) is allowed only this way, as an address in a port grant; a name dials only public addresses. A port grant to a git host's name (port 22 of `github.com`) is a git-host grant, and so is one to an address the engine knows is a current address of a git host (`GrantsConfig.GitAddress`: the deny list's and the projects' hosts, `Allowlist.GitNames`, resolved by the engine every minute), whose card adds "`<address>` is an address of `<host>`, a git host." Both sets also hold the addresses of `session.ForgeSSHNames` (`ssh.github.com`, `altssh.gitlab.com` and `altssh.bitbucket.org`, the forges' SSH over port 443), which `egress.Known` resolves with the git names, and which are git hosts by name for the card too. Egress keeps its own set, resolving its deny list and the names the engine sends as `git` in `PUT /boxes` (at most 256, host names only) every minute and at once when that list changes, keeping a name's last addresses when a lookup fails, and refuses a port grant's dial to any of them (`git_host`) unless that /28's `git` list holds the target, as it does only for a grant given at the red card; until its first lookup ends, it refuses port grants as `resolve_failed`. What this can't catch: a git host behind an address neither looked up, such as another name of the same host that isn't one of those, a mirror, an address a name answers only sometimes, or a git host that isn't on the deny list or a project's host. A credential can be bound to `host:port` targets too, with the same rules, and its grant opens those ports.
  - **Storage.** `grants.json` in `engine-state`, format 4, `{"version":4,"grants":[{"id","host","port","credential","name","bound","delivery","scope","session","project","expires","reason","askedBy","preset","made","gitAccepted","owner"}]}` with times in Unix seconds, `expires` left out for until taken back, `port` only for a port grant, `host` or the four credential fields, and `gitAccepted` (at most 16 entries, each one of the grant's own host or bound targets) left out when no git host was accepted; formats 1 to 3 are read too, as accepting no git host, since step 2's format 3 kept no record of what the card showed: a grant made then at a git host's red card is closed until it is given again (an older engine refuses format 4, and one before 3 refuses port grants), and the first write keeps a copy of it in `backups/`. At most 64 grants (`session.MaxGrants`), and a 65th is refused with 429 `grants`. The engine reads it back as it reads `egress.json`: a file it can't read, or any grant in it it doesn't take, makes the engine take no grant, make none and take none back (409 `state`) until the file is moved away. An export carries it as dropped, so an import gives no grant (`runs-and-operations.md` "Export, import and store formats").
  - **Credentials.** `access-secrets.json` in `engine-state`, mode 0600 like `tokens.json`, format 1, `{"version":1,"credentials":[{"id","name","type","bound","tags","saved","secret":{…}}]}`, where `secret` holds the type's fields: `token` `variable`, `value`; `aws` `keyId`, `secretKey`, `role`, `region`; `ssh` `user`, `privateKey` or `password`, `hostKey`; `file` `path`, `mode`, `contents`; `vars` `vars` (`name`, `value` pairs). `bound` is a list of targets: host names as Network access takes them, and `host:port` port targets (`192.168.1.20:22`, `[fd00::1]:22`) as port grants take them; an address without a port is refused (400 `bound`). Limits (`credentials.go`): at most 32 credentials (429 `credentials`), a name of small letters, digits, `_` and `-` up to 40 characters, unique, 1 to 16 bound hosts and ports, tags `write` and `production`, a token or variable value of one line up to 4,096 characters, at most 32 variables, a variable name of capital letters, digits and `_` up to 64 that isn't `PATH`, `HOME`, a proxy variable, `SSHPASS`, `SSH_ASKPASS`, `SSH_ASKPASS_REQUIRE` or another the container uses, nor starts with `ANTHROPIC_`, `CLAUDE_`, `SF_`, `LD_`, `DYLD_` or `BASH_FUNC_`, an AWS access key id `AKIA`/`ASIA` and 16 more, a 40-character secret, an optional role ARN and a region, an SSH user up to 32 characters, an unencrypted private key up to 8 KiB that x/crypto/ssh reads (ed25519, ECDSA or RSA; 400 `privateKey`) or a password up to 512, a host key line (`ssh-ed25519 AAAA…`) up to 4,096, a file path under the home folder up to 200 characters with no `..` that isn't under `.claude`, `.config/software-factory`, `.ssh`, `.aws`, git's configuration or a shell's start-up files, mode `0600` or `0644`, and contents up to 16 KiB. A credential bound to a host `ClaudeVendorHost` names (409 `vendor`) or holding `sk-ant-` in any secret field (409 `model credential`) is refused. A file the engine can't read makes it save, delete and hand over none (409 `credentials`). It is never logged, never answered to the page (which gets `id`, `name`, `type`, `typeLabel`, `bound`, `tags`, `saved` and the live grants made with it, each with `lead`, the engine's words for how it is given (`Handed over to`, `Signs SSH logins for`, `Short-lived copies handed to`), and for AWS keys `copy`, when the latest copy the agent may have taken expires), never exported (`classOut`, like `tokens.json`) and has no format copy in `backups/`. Replacing a credential takes back its grants; deleting one takes back its grants and deletes its presets.
  - **Presets.** `presets.json`, format 3 (formats 1 and 2 are read too, as accepting no git host), `{"version":3,"presets":[{"id","name","host","port","credential","scope","expires","project","auto","made","gitAccepted","owner"}]}`, `gitAccepted` the git hosts among its targets when it was saved, at most 32 (429 `presets`), a name of one line up to 60 characters, unique without regard to case; `project` empty for every project, and required when `auto` is set. A preset whose risk has an `accept` sentence is saved only with `confirmed`. Every 15 seconds the engine applies each `auto` preset once to each running session of its project, as a grant with `askedBy` `preset`, and adds a note to the session's listing (`accessNotes`, at most 8), which the page shows as a desktop notification; it makes no card. Before **Apply** or an `auto` apply, the engine computes the preset's targets' git hosts again (`presetMaking`): one that isn't in its `gitAccepted`, since it became a git host after the preset was saved, refuses the apply (409 `git host`, "`<host>` became a git host after the preset `<name>` was saved, so applying it would let the agent push around Software Factory's gate without its red card. …"), and an `auto` apply skips the preset with that note instead, as it does for any grant it can't make, the list limit included. Removing a project drops its grants and presets. An export carries presets as dropped.
  - **Handed over.** Every 15 seconds and after each change, the engine sends each running session container's agent-host the credentials its live grants hand over (`POST /v1/handover`, `{box, items, ports}`, at most 2 MiB, `ports` the port targets its live port grants and handed-over credentials open, oldest grant first, at most 256, session containers only; a reviewer container's agent-host answers 404), when that set changed since it last took it; a credential whose variable, file or SSH host another one already uses there is left out, and a grant that would clash in the project is refused (409 `clash`). Agent-host, as the container's own user, under its home folder through `os.Root` (no link out of it is followed, and a file or link it didn't write isn't replaced, 409 `files`): first removes everything it wrote before, as `~/.config/software-factory/access/written.json` lists, then writes a token and variables, and an SSH password as `SSHPASS`, as `export` lines in `~/.config/software-factory/access/env.sh`; an AWS copy (below) as `[<name>]` with `aws_access_key_id`, `aws_secret_access_key` and `aws_session_token` in `~/.aws/credentials` and `[profile <name>]` with `region` in `~/.aws/config`; for an SSH credential (a key the engine signs with, below, or a password) a `Host` entry per bound host (`*.example.com` for `.example.com`, the host alone with `Port <n>` for a `host:port` target) in `~/.ssh/config` with `User`, and with a host key `UserKnownHostsFile ~/.ssh/software-factory_known_hosts` and `StrictHostKeyChecking yes`, without one `StrictHostKeyChecking accept-new`; an SSH password's entries have `PreferredAuthentications password,keyboard-interactive`, and `~/.config/software-factory/access/askpass` (0700), with `SSH_ASKPASS` naming it and `SSH_ASKPASS_REQUIRE=force` in `env.sh`, prints `$SSHPASS` only for ssh's own prompts for its user at its bound hosts (`<user>@<host>'s password:` and `(<user>@<host>) …`) and refuses every other prompt, so plain `ssh` signs in with it; for `ports`, one `Host` entry naming their hosts with `ProxyCommand nc -X connect -x egress:3130 %h %p` (`session.PortProxy`) and `ServerAliveInterval 30`, and a listener on `127.0.0.1:<port>` for each (the oldest grant's, when two share a port; a port something else in the container already holds is skipped, and logged as `forwards-not-open`) that opens a `CONNECT` through egress for each connection, at most 64 at once per listener; a file at its path and mode. Entries in a shared file go between the lines `# software-factory access begin` and `# software-factory access end`; removing them puts the file's modification time back, and removes a file agent-host created that holds nothing else, so the user-settings comparison at the next wake (`~/.ssh` is in it) sees no change. Agent-host does the same removal when it starts. Agent-host runs every command with `CLAUDE_ENV_FILE` naming `~/.config/software-factory/access/claude-env.sh`, which it writes at start and which sources `env.sh` when it exists: Claude Code (2.1.331 read) reads that file once and runs it before each Bash command, so a variable written or removed later reaches the next command without a restart. A process already running keeps what it had, and only Claude Code's Bash commands and their children read it, not Claude Code itself or its MCP servers. Taking back, expiry, the session stopping, the project's removal and deleting or replacing the credential remove what was written, and close the listeners and their connections, at the next send that reaches agent-host (at once for a take-back or a deletion, within 15 seconds for an expiry), or when agent-host next starts; egress closes the tunnels within its 10-second sweep either way. So the answers say the handed-over files and variables are removed "when the engine next reaches the session's container", not that they are. While the last send to a running session's container failed (no route, an error or a 409), the engine sends again every 15 seconds and the session's listing's `accessMarker` carries "Software Factory couldn't update the handed-over files in this session's container yet; it tries again every 15 seconds." (`session.HandoverPendingNote`), until a send succeeds or nothing is left to send. Replacing a credential keeps its presets when its type, bound hosts and delivery are unchanged (an SSH key replaced by a password changes the delivery from signing to handed over), and deletes them, saying "Its presets are deleted too, since what it opens changed.", when either changed, since an `auto` preset would otherwise hand the new secret to hosts nobody accepted for it.
  - **Signing without holding (SSH keys,** `grantssh.go`, `internal/adapters/access/sshsign`, `internal/adapters/agenthost/sshagent.go`). An SSH credential with a key is never handed over: its `items` entry carries only `user`, `hostKey` and `bound`, so agent-host writes the `Host` entries without `IdentityFile` or `IdentitiesOnly`. Agent-host serves an ssh-agent protocol socket at `/run/sf/ssh-agent.sock` (`session.SSHAgentSocket`, 0600 in `/run/sf`, 0700, at most 16 connections, each closed after 10 idle minutes) and the image's `/etc/ssh/ssh_config.d/software-factory.conf` sets `IdentityAgent /run/sf/ssh-agent.sock` and `ForwardAgent no` (agent-host strips `SSH_AUTH_SOCK` from what it runs, `env.go`), so plain `ssh`, `scp` and `rsync` use it. Agent-host passes on only two requests, through golang.org/x/crypto/ssh/agent: list identities (11) and sign (13); every other request, Add, Remove, Remove all, Lock, Unlock and every extension (`session-bind@openssh.com` included, so there is no host-key binding), gets `SSH_AGENT_FAILURE` and a `refused` log line with its type. It relays them to the engine's agent listener, which knows the container by the /28 address pair the connection comes from, as egress does, and needs no token: `GET /ssh-keys` answers `keys` (`key`, the public key in base64, and `comment`, the credential's name, at most 32) of the SSH key credentials the session's live grants cover, and `POST /ssh-sign` (`key`, `data` in base64, at most 8 KiB, and `flags`, which pick `rsa-sha2-256` or `-512` for an RSA key; body at most 32 KiB) signs only when that key is one of those, and only an SSH user-authentication request: `data` must be a session id of at most 64 bytes, byte 50 (`SSH_MSG_USERAUTH_REQUEST`), the credential's saved user, `ssh-connection`, the method `publickey` or `publickey-hostbound-v00@openssh.com` with its flag set, an algorithm, that same key, and for the host-bound method the server's host key, and nothing after. Anything else (`ssh-keygen -Y sign`, commit signing, another user) is refused (409 `not a login`), as is a key no live grant covers (404 `key`), a container no running session of this engine is in (409 `session`) and more than 60 signatures a minute for one container (429 `signs`). Anything in the container can call these routes or the socket, the agent included; the engine checks each request against the person's grant and decides nothing else on its word. Each signature is logged (`ssh event=signed` with the credential's name and the session, never the data or the signature), and the grant's `access` audit line when it ends or is taken back says how many SSH logins it signed since the engine started, and when the last was. Taking the grant back, its expiry, the session stopping and deleting or replacing the credential stop signing at the next request, since each is checked against the live grants; an SSH connection opened during the grant goes through egress (`ProxyCommand nc -X connect`, or agent-host's `127.0.0.1:<port>` forward), whose tunnels egress's 10-second sweep closes once the port leaves the session's list. Residual risks: during the grant, a host the agent reaches with `ssh -A` (the agent can override `ForwardAgent`) can ask for logins too, and with no host binding a signature the agent obtains is good for any server that trusts the key and that it can reach, or relay to through an upload host it holds, as the saved user.
  - **Short-lived copies (AWS keys,** `grantaws.go`, `internal/adapters/access/sts`). AWS keys are never handed over. For each running session container a live grant covers, the engine asks AWS STS for a copy with the saved keys, at `https://sts.<region>.amazonaws.com/` (`.amazonaws.com.cn` for a `cn-` region): `AssumeRole` with the saved role ARN and `RoleSessionName` `software-factory-<box>`, otherwise `GetSessionToken`, as a form `POST` with API version `2011-06-15`, signed with Signature Version 4 in the standard library (checked against AWS's published test vectors). `DurationSeconds` is the time until the grant ends, at most 3,600 and at least 900 (STS's shortest), so a role's own maximum, never under an hour, never cuts it. Its copy (an `ASIA…` key id, its secret, the session token and its expiry) is handed over as above, and asked for again when 10 minutes or less of it are left and the grant lasts past it, on the 15-second delivery loop. When STS refuses (an error answer: only its `Code`, such as `AccessDenied`, or the HTTP status is kept) or can't be reached in 5 seconds, the grant stays but nothing of that credential is handed over, the session listing's `accessMarker` says "AWS refused a short-lived copy of `<name>` (`<code>`), so this session gets none of it; Software Factory asks again every 15 seconds." (or that it couldn't reach `sts.<region>.amazonaws.com`), the Access dialog's grant says the same in `copy`, and the engine tries again at most every 10 seconds. A renewal that fails keeps the copy that still works. Taking the grant back removes the copy at the next send but can't end it: the answers, the Access dialog and the Credentials page (`copy` on each grant) name when the copy the agent may have taken expires. The engine reaches STS directly over the `outside` network, as it does for pushes (no proxy, TLS 1.2 or later, redirects refused, 15-second limit), so no setting or Compose change is needed. The engine logs `aws event=copy-made` with the credential's name, the box and the expiry, or `copy-not-made` with the error code; never a key, a token or the request.
  - **When grants end.** Every 15 seconds (`session.ExpireWatch`), and when a session's container goes down or a session is deleted, the engine drops expired grants (`expired`) and the grants of a session whose container doesn't run (`ended`), so a session's grants end when it stops, is deleted or the engine restarts, which stops every session; project grants stay until they expire or are taken back. Each per-subnet list also carries `git`, the entries of `allow` that name or cover a git host; egress refuses an `allow` entry that names or covers a denied host unless `git` lists it, and a `git` entry that `allow` lacks. A `CONNECT` refused as `git_host` is let through when its /28 has an unexpired `git` entry covering the host; the sweep closes it when that entry goes. On the agents' proxy, a `CONNECT host:port` whose target is an unexpired `ports` entry of its /28 is forwarded as plain TCP, with no TLS check, since the grant is for whatever answers there: an address only after checking it is none `AddressNever` refuses and on none of the stack's own networks (`own_network`), a name only after resolving it once and finding every address public (`private_address` otherwise) and on none of those networks, dialling only the addresses checked, so a name that changes its answer can't reach a private one. Every other port and every address egress refused before is refused as before (`port`, `ip_literal`). The tunnel keeps the idle (5 minutes) and total (1 hour) limits and the connection cap, and the 10-second sweep closes it when its /28's `ports` no longer lists the target. ports only on `127.0.0.1`; mounts only of type `volume` or `tmpfs`; top-level sections only `name`, `services`, `networks`, `volumes` and `x-` extensions; the project named `software-factory`; networks only with `name`, `internal`, an empty `ipam` and the default `bridge` driver, so no `external` or `macvlan` one; Anyone can run it on a rendered file: `sh scripts/release-check.sh <image@sha256:digest> <config.json>`. The install is `curl -fsSL https://github.com/bezmoradi/software-factory/releases/latest/download/install.sh | sh`, GitHub's link to the newest release that isn't a draft or a pre-release; the checked install downloads one version's `install.sh` from `releases/download/v<version>/`, runs `gh attestation verify install.sh -R bezmoradi/software-factory --signer-workflow bezmoradi/software-factory/.github/workflows/release.yml --source-ref refs/tags/v<version>`, then `sh install.sh`, and the release's notes and the page's update panel give those lines with the version filled in. The script runs everything from one function, so `sh` has read all of it before anything runs, and points its own input at `/dev/null`, so no command it starts reads the rest of the pipe; it uses no `eval`. It checks `docker`, `docker compose` and the daemon, Docker Engine 28 or later and Compose 2.24.4 or later, the first that reads `!override`, and refuses Compose 5.1.4, whose compose-go 2.11.0 has a bug reading `<<: *anchor` merge keys, which the Compose files use (docker/compose#13812, compose-go#878, fixed in 5.2.0); `!reset` is older, `start_interval` needs 2.24.0, `up --wait` 2.1.1, and `depends_on` with `restart: true` restarts the engine with a recreated helper on `up` from 2.35.0, which an upgrade doesn't need, since it recreates both. It keeps its files in `${SF_HOME:-$HOME/software-factory}` and refuses a folder with `.git`. It downloads each Compose file beside its final name, checks its SHA-256 with `sha256sum` or `shasum -a 256`, and moves both into place only when both match, so a failed or tampered download changes nothing. It writes the socket file only from an `SF_DOCKER_GID` of digits (default `0` on macOS, `stat -c %g` of the socket elsewhere) and an absolute `SF_DOCKER_SOCKET` of letters, digits, `.`, `_`, `/` and `-`, says so when containers of the project `software-factory` run, and runs `docker compose -p software-factory -f compose.yaml -f compose.release.yaml -f software-factory-socket.yaml up -d --wait --remove-orphans` in that folder, without `-y`: with no input, Compose's question about a volume whose configuration changed is answered no, so no data is deleted. It prints the version, the folder and the address `docker compose port engine 8080` gives. The SHA-256 sums tie the Compose files to the script, and the attestations tie all three to the release workflow's run for the tag; what the image's signature covers is the engine image: the agents come from npm and GitHub at first start ("Agent installs"). The browser image isn't published, and gVisor needs only `SF_BOX_RUNTIME=runsc` in the environment at `up`. Only the owner starts a release: a tag ruleset (`.github/rulesets/tags.json`) lets only the admin role create `v*` tags, the job runs in the `release` environment, which waits for the owner's approval, and it fails unless the run's triggering actor is the owner, the tag equals `v` plus the engine's `Version` and the tagged commit is on `main` (a guard against mistakes only, since the tagged commit's own workflow file runs it). An install from a release leaves the three files in its folder, and `docker compose -p <project>` reaches the stack for `exec`, `ps`, `logs` and `down` from any folder (checked with Compose 5.2.0), while `up` and `run` need the three `-f`. So `compose.yaml` passes the engine its project name, `SF_COMPOSE_PROJECT: ${COMPOSE_PROJECT_NAME:-}`, which Compose fills in with the name it uses (from `name:`, `-p` or the overlay's own name), and every command the engine, the page and the plugin show starts `docker compose -p <project>` (`session.Compose`). The engine takes the value only when it follows Compose's rule for project names (lowercase letters, digits, `-` and `_`, starting with a letter or digit), and shows commands without `-p` otherwise. The page reads it from the events stream's `hello` frame and the plugin from the engine's `/register` answer, each checking it against the same rule. `run` commands stay in the README only.
