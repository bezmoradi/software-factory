# Reference: the image and Compose

This is part of the Reference section of [ARCHITECTURE.md](../../ARCHITECTURE.md#reference), which describes how Software Factory works and why.

## The image and Compose

One multi-platform image (amd64, arm64) runs every role; `compose.yaml` starts three of them, and the box helper starts each session's container and each reviewer container from the image it runs itself. Build stages: Node builds the page (`npm ci --prefix web && npm --prefix web run build`), Go builds the binary with CGO off, and the runtime stage is `node:26-trixie-slim` (pinned by digest) with `git`, `ca-certificates` and `curl` added and npm, corepack and yarn removed. The last stage, `runtime`, is the one to publish; the `dev` stage adds the marker file `/usr/share/software-factory/dev-image`, the fake ACP agent from `dev/fakeacp` and the fake reviewer from `dev/fakeclaude` (`/usr/local/bin/sf-fake-claude`), and the `gitserver` stage is a local git host (`dev/gitserver`: git http-backend over HTTPS with a self-signed CA, asking for a token, serving the seed repository at `/dev/demo.git` and the older `/demo.git`, with a small fake of GitHub's REST API under `/api/v3` in `dev/gitserver/github.go`, so the engine's GitHub adapter reaches it at `https://gitserver.test:8443/api/v3`, an untokened fake of the update check's two routes under `/release-api`, and an untokened, fetch-only stand-in for knackpack's repository at `/public/knackpack.git` ("knackpack")); both are built only by `compose.dev.yaml`, which runs the engine and the box helper on `dev` and egress on `runtime`. The API fake answers only what the engine's adapter reads (the repository, branches, open pull requests, opening issues and pull requests, issue lists, comments, reviews, `/user`, check runs and statuses), gives every answer an `X-GitHub-Request-Id`, asks for the git server's token as a Bearer token, and keeps its state in one JSON file; `sf-gitserver` subcommands add comments and reviews, switch drafts off and set delays and failures (`comment-403` refuses the next comments the engine posts), so a development run can reach the cases a real host makes rare. `sf-fake-claude` makes no model call and refuses, with an error result, a run whose flags or `--settings` aren't the engine's reviewer command line, a run a variable that looks like a credential reached, and one whose folder isn't the engine's snapshot, so a development run catches a reviewer started the wrong way; the flags and settings it checks, what it reports and the files in the snapshot's `head/` that change its reply are in [Hand checks with Compose](../../.claude/rules/compose-hand-checks.md). The fake ACP agent calls the `factory_*` tool a prompt names (`factory_review_comments` included), echoes a note the engine put before a prompt, and stays in a turn for the prompt `stall` until it is stopped. git http-backend takes pushes only from an authenticated user, so the git server sets `REMOTE_USER` after its own token check. In that overlay the gitserver is on `gitnet`, an internal network only the engine joins, as `gitserver.test:8443`; it writes its CA to the `gitserver-ca` volume, which the engine mounts read-only and trusts through `SF_DEV_GIT_CA`; and `gitserver.test` is added to the refused git hosts (`EGRESS_DENY`) of both the engine and egress, so the sandbox check covers it.

Users: `engine` (10001) and `agent` (10002), both in group `sf` (10000) so each session's folder is shared between the engine and that session's agent, `helper` (10005, its own group, which owns the `helper-key` folder), `egress` (10003, its own group `egress`, 10003, which owns the `egress-key` folder) and `reviewer` (10004, its own group, not `sf`). The `gitserver` stage removes `reviewer` and gives its uid to `gitsrv`, which the `gitserver-data` volume's files carry. The image contains no agent.

**Claude Code's managed settings** (`/etc/claude-code/managed-settings.json`) turn off the features of Claude Code that reach a session around the page, or reach outside the sandbox, in every session and review. Managed settings outrank user and project settings and `--settings`, and Claude Code adds their list keys, such as `permissions.deny`, to the other sources' lists. Neither the agent nor the reviewer user can change the file or add one beside it in `managed-settings.d/`: the folder is root's, on a read-only root filesystem. The file sets:
- `crossSessionInbound: "refuse"`: a message from another Claude Code session, or from any program of the same user posting to a session's inbox socket (`CLAUDE_CODE_MESSAGING_SOCKET`), is dropped;
- `permissions.deny` with `SendMessage` and `ListAgents`: a session can't list or message other sessions. `SendMessage` also continues a subagent and messages agent-team teammates, so those go too; a subagent's result comes back as the `Agent` call's result, not through `SendMessage`;
- `disableRemoteControl: true`: `claude remote-control`, `--remote-control`, `remoteControlAtStartup` and the in-session toggle are refused, so no session reaches the person's cloud sessions or Remote Control sessions on other machines. `isolatePeerMachines: true` is a second guard: a message to a session on another machine needs approval;
- `syncClaudeAiPlugins: false`, `syncClaudeAiSkills: false` and `disableClaudeAiConnectors: true`: a session signed in with claude.ai loads none of the account's synced plugins or skills and none of its connectors. Reviews need this most: `--setting-sources user` doesn't skip them, and a synced skill's text could sway a verdict;
- `autoMemoryEnabled: false`: Claude neither reads nor writes auto memory (`~/.claude/projects/<project>/memory/`), which every worktree of a repository would share in the session's writable home and a later wake of it loads without a start-up card. This is hygiene for honest sessions, not a defence against a hostile agent: `~/.claude/CLAUDE.md` in the same home is a stronger channel (Known limits). The cost: what the person types to correct Claude no longer carries over to later sessions on its own. The repository's instruction file (`CLAUDE.md`) is the place for that;
- `env` with `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE: "0"`: Claude Code's experimental Code Mode (2.1.323 and later), in which Claude writes JavaScript that makes the tool calls, stays off in every session and review. Code Mode changes how tool calls reach hooks: a shell command can reach the plugin's tool check in a compound form (a `git push` in a folder `app` as `cd 'app' && git push`), and a hook that doesn't finish in time refuses the call, where today the plugin falls back to its own check. The managed file is where it's turned off because the agent can write its own `~/.claude/settings.json` (Known limits), where a `"1"` would turn it on: by Code Mode's documentation, a `"0"` in managed settings wins over a `"1"` set anywhere else, and Claude Code ignores the variable in a project's settings files. The pinned 2.1.322 has no Code Mode, so the key does nothing yet; moving the pin past it has its own checks (`.claude/rules/moving-a-pin.md`);
- `prependPlugins: []`: keeps the plugin's `classic.*` hooks running. A managed file with any key in it (not `{}`) makes Claude Code 2.1.322 seat its built-in guard, `cc-plugin-sec-default`, ahead of every other plugin, and the guard sends every `classic.*` event past user and `--plugin-dir` plugins. Without this key the plugin's `classic.SessionStart` (the sandbox context), `classic.UserPromptSubmit` and `classic.Stop` (the permission mode the page shows), `classic.StopFailure` (a sign-in failure) and `classic.PermissionRequest` (the page's permission cards) are skipped. And with a host answering prompts (`--permission-prompt-tool`), Claude Code's own ask replaced the plugin's `tool.check` ask, so in auto mode, with no saved rule, `rm -rf ~/x` ran without a prompt. A set `prependPlugins` seats the guard only where it names it, so the empty list leaves it out; naming the plugin before the guard didn't change the order. The cost is the guard's protection of managed policy from other plugins: by Claude Code's documentation, a plugin installed in the agents' home could then approve a call a deny or ask rule stops, or change what managed hooks receive. Plugins run in the order they had with no managed file, when the guard loaded only for a Team or Enterprise `/login`; by the documentation, the empty list leaves it out for those sign-ins too.

The keys and their types come from Claude Code's settings documentation, apart from `prependPlugins`, which that page doesn't list: it comes from the 2.1.322 binary's behavior and settings schema, and Claude Code's plugin documentation (`plugins/mods/admin` and `plugins/mods/reference`) describes it. Offline checks against 2.1.322, with a stand-in model API and no sign-in, showed the deny rules, `crossSessionInbound`, `autoMemoryEnabled` and `prependPlugins` taking effect; no key's effect has been checked on a signed-in run, and the sync, connector, Remote Control and peer-machine keys need one. Two things outrank the file. A claude.ai organization that delivers server-managed settings: Claude Code then uses that policy and skips the file, apart from the two sync keys and `disableClaudeAiConnectors`, which it reads from every managed source. `prependPlugins` is lost with the file, so the guard is probably seated again and the plugin's `classic.*` hooks skipped, the page's permission cards included; this hasn't been checked. And `CLAUDE_CODE_DISABLE_AUTO_MEMORY` in a session's environment, which outranks `autoMemoryEnabled` either way; agent-host passes only its own list of variables, which leaves it out.

`compose.yaml`:

- **The page** is published only as `127.0.0.1:${SF_PORT:-7799}:8080`, written in the long syntax (`target`, `published`, `host_ip`), with `SF_PAGE_HOST=0.0.0.0` inside the container and `SF_PUBLIC_PORT` matching. Bound to every interface, it accepts a connection only when its local address is loopback (the healthcheck) or an address of `SF_PAGE_NAME` (`engine-page`, resolved on `outside`, where Docker delivers the published port), and closes the rest before they count toward its connection limit, so the agent and reviewer networks never reach it. The engine refuses to start when that name doesn't resolve to one of its own addresses, or resolves to loopback or the agent listener's address.
- **Hardening.** Every service: non-root user, `cap_drop: [ALL]`, `no-new-privileges`, read-only root filesystem, `init: true`, memory and pids limits, a healthcheck and `restart: unless-stopped`. Writable places are the volumes and tmpfs mounts only. `SF_UMASK=0002` keeps files in the shared workspace group-writable.
- **The box helper** (`helper`) runs `box-helper` as `10005:10005` with `group_add: ["${SF_DOCKER_GID:-0}"]` (the socket's group; Docker Desktop's socket is `root:root` 0660), the hardening above, 64 MiB and 64 processes, `stop_grace_period: 60s`, `helpernet` only, `helper-key` read-only, and one bind mount, `${SF_DOCKER_SOCKET:-/var/run/docker.sock}:/var/run/docker.sock`. The engine starts after it and is restarted with it (`depends_on` with `condition: service_started` and `restart: true`), since a new helper stops every session's container. It doesn't wait for the helper to be healthy, so the page stays up when the helper can't start, such as with a wrong `SF_DOCKER_GID`: the engine asks the helper's `/healthz` every 10 seconds and the Welcome page then says the helper isn't answering, while every start and wake fails with the reason. Its client speaks Docker's Engine API over the Unix socket with `net/http`, no SDK, pinned to `/v1.48/`. Its settings: `SF_BOX_MEMORY` (default `2g`, memory and memory with swap), `SF_BOX_CPUS` (default `2`), `SF_MAX_BOXES` (unset: no limit; set: the helper counts running and starting containers under one lock and refuses a start past it with 409 `limit`), `SF_BOX_RUNTIME` (unset, or `runsc`), `SF_BOX_SUBNETS` (default `10.213.0.0/20`), `SF_BOX_SWEEP_DRY` (`1` logs what the start-up sweep would remove and removes nothing) and `SF_BOX_LIVE` (development only, above). `SF_REVIEWER_MEMORY` (default `2g`) and `SF_REVIEWER_CPUS` (default `2`) cap each reviewer container the same way. The arithmetic for a machine: the engine 1 GiB, egress 256 MiB and the helper 64 MiB, 1.3 GiB of caps before any session or review, plus up to 2 GiB for each running session and each running reviewer container by default; `MaxReviewerRuns` (8 reviewer runs at once) bounds the reviewer containers. On an 8 GiB Docker VM the caps pass the memory once a session and three reviewer containers run; the out-of-memory score (500 for both kinds) then takes a session's or a reviewer container first, and a reviewer run that is killed fails as not passed.
- **A session's container** is made by the helper from its recipe, not by Compose. Docker copies the image's labels into a container, and an image Compose built carries `com.docker.compose.project` and `.service`, so the recipe sets every `com.docker.compose.*` label of the image to an empty value: Compose never counts a session's container as one of its own, so `up`, `restart` and `--remove-orphans` leave it alone. The helper owns a container only when those labels are empty, or, for a container made before this rule, equal the image's, which it only stops and removes. Name `<project>-box-<box>`; image: the helper's own image ID; user `10002:10000`; command `agent-host` (with `SF_BOX_LIVE` in a development image, entrypoint `/opt/sf-dev/bin/software-factory`); `Init`, a read-only root, `CapDrop: [ALL]`, `SecurityOpt: ["no-new-privileges:true"]`, not privileged, no devices, no published ports, no sysctls, a private cgroup namespace, a private IPC namespace with a 64 MiB `/dev/shm`, `OomScoreAdj` 500 so the VM's out-of-memory killer takes a session before the engine or egress, `PidsLimit` 2048, memory, swap and CPUs from the settings, restart `on-failure` 3 times, `json-file` logs of 10 MB × 3, and a healthcheck of agent-host's `/healthz`. Mounts, and no binds: `workspace` with subpath `s/<box>` at `/workspace/s/<box>`; `agents` read-only; its home volume at `/home/agent`; `uploads` with subpath `<box>` at `/uploads/<box>`, read-only; tmpfs `/tmp` (1g) and `/run/sf` (1m, 0700, uid 10002); and with `SF_BOX_LIVE`, `dev-bin` read-only at `/opt/sf-dev/bin`. Environment: `SF_WORKSPACE=/workspace/s/<box>`, `HOME=/home/agent`, `SF_AGENT_HOST_LISTEN=:8090`, `SF_ENGINE_AGENT_ADDRESS=engine-agents:8081`, `SF_PLUGIN_SOCKET`, `SF_UMASK=0002`, `HTTPS_PROXY`/`HTTP_PROXY` (both cases) set to `http://egress:3130`, `NO_PROXY` for loopback only, and `DISABLE_AUTOUPDATER=1`. Its network `<project>-box-<box>` is `internal`, without IPv6, with `com.docker.network.bridge.gateway_mode_ipv4=isolated` and the box's /28; `/etc/hosts` maps `engine-agents` to the `.2` and `egress` and `egress-agents` to the `.3`. Labels: `dev.software-factory.stack=<project>`, `dev.software-factory.box=<box>` and `dev.software-factory.recipe=<SHA-256 of the recipe>`, which the network and the home volume carry too (without the recipe). After create and before start the helper inspects the container and compares the network mode, the one endpoint and its address, the capabilities, privilege, devices, security options, an AppArmor profile that isn't `unconfined`, masked and read-only paths that hold at least Docker's long-standing defaults, ports, sysctls, the IPC mode and `/dev/shm` size, DNS servers, options and search domains (none), the OOM killer left on, cgroup namespace, read-only root, `OomScoreAdj`, mounts with their volume names, driver and propagation, image and user with the recipe; any difference removes it and refuses the start. The box's endpoint may carry no driver options and no aliases but the container's own ID and name. Ulimits must be empty after create, before start; the daemon adds its own default ulimits at start, so they aren't compared after that, and Docker can't change a container's ulimits later. It doesn't compare the volumes' paths on the host, which differ between Docker installs; the number of `docker exec` sessions shows as a fact, `execs`, not a refusal, since every healthcheck is one. A running container it reuses must also have exactly the engine, egress and itself on its network, which `members-only` reports. The hash it reports comes from that inspection. At its start the helper removes the stack's containers that aren't running and the stack's networks without a container, and reconnects the engine and egress to the running ones; it follows Docker's events to reconnect a recreated engine or egress; on SIGTERM it stops every container, so `docker compose down` leaves none running. `docker compose down -v` leaves the home volumes, which Compose doesn't know.
- **A reviewer container** is made by the helper from its second recipe, not by Compose, for one call of the engine's reviewer host (`cmd/server/reviewers.go`): each run of a role, the manual test list, Explain this change, Review this plan and Suggest lines gets one that mounts its snapshot, and each sign-in step, `claude --version`, sign-in check and agent-file write one with no snapshot; the page's Subscription sign-in keeps one from `start` until `code`, `cancel` or 10 minutes. Name and network `<project>-reviewer-<run>`, a /28 from `SF_BOX_SUBNETS` like a box's; image: the helper's own image ID; user `10004:10004`; command `agent-host -mode review` (with `SF_BOX_LIVE` in a development image, the live entrypoint); the session containers' hardening (`Init`, a read-only root, `CapDrop: [ALL]`, `no-new-privileges`, not privileged, no devices or ports, private cgroup and IPC namespaces, 64 MiB `/dev/shm`, `OomScoreAdj` 500, `PidsLimit` 2048, `SF_BOX_RUNTIME`), memory, swap and CPUs from `SF_REVIEWER_MEMORY` and `SF_REVIEWER_CPUS`, restart `no`, `json-file` logs of 10 MB × 3 and the same healthcheck. Mounts, and no binds: `reviews` with subpath `<snapshot>` at `/reviews/<snapshot>`, read-only, when the run has one; `agents` read-only; `<project>-reviewer-home` at `/home/reviewer`; tmpfs `/tmp` (1g); and with `SF_BOX_LIVE`, `dev-bin` read-only. Environment: `SF_WORKSPACE=/reviews`, `HOME=/home/reviewer`, `SF_AGENT_HOST_LISTEN=:8090`, the proxy variables set to `http://egress-review:3128`, `NO_PROXY` for loopback only and `DISABLE_AUTOUPDATER=1`; `/etc/hosts` maps `egress-review` to the network's `.3`. The engine reserves a random 16-digit run id before it asks, adds the container's /28 to egress's reviewer side, gives its agent-host a new random 256-bit key with `/v1/key` (agent-host takes one key once and keeps it in memory, so a second caller gets 409), runs the sandbox probe in it when it mounts a snapshot, makes the call through the gateway wrapper, and then asks the helper to remove it and drops the /28, whether the call passed, failed or timed out. At most 8 reviewer containers run at once (`MaxReviewerRuns`): every container the engine asks for takes one of 8 slots until it is removed, whatever it is for, a role's run, a role-less run, a sign-in check, a version read, an agent-file write or a sign-in or key step. A run, a version read or an agent-file write waits for a slot within its own time limit. A sign-in check and a sign-in or key step from the page wait at most 10 seconds in all, for the engine's key lock and for a slot together, and then answer 429 `reviews` with the reason, so a sign-in never makes a ninth container (only the engine's own slot refusal counts as busy: a `reviewers-busy` code an agent-host sends back is an ordinary refusal); the key removal after a Subscription code waits up to 30 seconds, and if every container stays busy the page says the sign-in finished and the old key needs **Remove key**. Before that, the engine admits work in runs against the same 8: a review holds one run per planned role run until its role runs end, when it drops to none, and the manual test list, Explain this change, Review this plan and Suggest lines one each; a start that would pass 8 with other runs going is refused with "Wait for one to finish" (an agent's push request then waits in the queue), and a single review that plans more than 8 runs alone starts, its runs past 8 waiting for a slot. A Review checks this before its sign-in check, so a refused one starts no container. The status the page shows for the reviewers' sign-in is the last check, kept up to 10 minutes and shown with the time the check started; a sign-in code, a key change, an allowlist or gateway change or a new reviewers' Claude Code version makes the next status check run again, while a step refused as busy before it started changes nothing; a check that started before such a change finished isn't kept (a generation counter, raised when the step starts and again when it ends), so it can't bring back the old status, and the check `finished()` runs after the change is kept. When the reviewers are busy, the status keeps the last check, marked as not checked again (the reviewers' expected sign-in kind is never adopted from such a status, nor from any check made before the person last set the expectation to any, so clearing it holds), or says the reviewers are busy when there is none; when a sign-in code, a key change or another of the changes above came after that check, it is also marked stale (`SignIn.Stale`, `stale` in the page's JSON, in the `reviewer` frame the change sends at once and in the status `/api/projects` carries), and the dialog says it was checked before the latest change and isn't current, marks no kind "In use" from it, and the Projects page's sign-in notice treats the reviewers' sign-in as unknown and doesn't show, and the open dialog checks again every 15 seconds; it opens showing the last status the page knows, with its time and "Checking again…", until the check answers. The check after a sign-in or key change runs on the engine's own context, carrying the request id, and in the reviews' wait group, so shutdown stops and waits for it; the page waits for it at most 10 seconds. Every review, test list, explanation and plan review still checks the sign-in first. **Reviewers' sign-in** in the command palette opens the reviewers' sign-in dialog at any time. At its start, and every 5 minutes, the engine removes every reviewer container the helper lists that no call of its own holds, so an engine restart mid-review leaves none behind. Review mode answers only `/healthz`, `/v1/key`, `/v1/run` (runs up to 25 minutes), `/v1/review-run` (the same, streamed: see [Reviews](reviews-and-pushes.md#reviews)), `/v1/sign-in`, `/v1/login`, `/v1/api-key` and `/v1/agents` (writes agent files, review mode only), and every route but `/healthz` and `/v1/key` needs the `X-SF-Host-Key` header to match the key it took. Agent-mode agent-host has no key: it runs as the agents' own user, so a key it holds the agents could reach too, and every route it answers in the session's container, `/v1/screenshots/remove` included, gives an agent nothing it can't already do as that user. Other traffic between containers, apart from the TLS control channel to egress ("Networks"), is plain HTTP on Docker's internal networks, which are the accepted transport boundary. Review mode has no worktrees, no long-lived processes, no plugin socket and no relay to the engine. The person signs Claude Code in for the reviewers once, from the page (the **Sign Claude Code in** notice on the Projects page), which runs the sign-in in a reviewer container and writes it to the shared home.
- **The allowlist** is `EGRESS_ALLOW`, given to both egress and the engine from `SF_ALLOW` (default: Anthropic's API and sign-in hosts) plus `SF_EXTRA_ALLOW`; `SF_EXTRA_DENY` adds git hosts to the built-in refused ones. Add the host of every repository you clone that isn't GitHub, GitLab or Bitbucket when an allow entry covers it (a gateway's `.corp.example`, say): the sandbox check fails until you do.
- **The allowlist on the page.** `EGRESS_ALLOW` is egress's starting list for both listeners, and the engine's list until the person saves a change under Network access. The engine then keeps the settings in `egress.json` in `engine-state` (at most 64 added hosts with their expiry and the person's optional reason, and the gateway) and sets two lists in egress over `controlnet` with the control key: for agents, Claude Code's model and sign-in hosts (`session.AgentHostTable`), the added hosts and the gateway's host; for reviewers, Claude Code's hosts and the gateway's host. egress swaps the lists at once, refuses a list that names or covers a git host, refuses an added host after its expiry, and closes open tunnels to a host that is no longer allowed within 10 seconds. The engine drops expired hosts from `egress.json` every 15 seconds and sets the lists again. Each change writes an `egress-allow` line to `audit.jsonl`. A reason is plain text on one line, at most 200 characters; the engine refuses one that holds control characters or looks like a token or a key, and a file without reasons loads as before. The page refuses a git host, a host that covers a repository's host or the sandbox check's outside host, and asks to confirm a host that also accepts uploads (`UploadHost` in `internal/core/session/egresshosts.go`).
- **The gateway.** The page's gateway is an https base URL on port 443, with no user name, query or fragment. For the sides chosen, the engine adds `ANTHROPIC_BASE_URL` and `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` to every Claude Code command it runs through agent-host there (starts, wakes, reviews and sign-in checks; `cmd/server/gateway.go`). The gateway's key or token is pasted beside its address and takes the API key's path (see "Signing Claude Code in"): after the gateway is saved, the page sends it as a `key` step of `/api/claude-login` for each side chosen, and that container's agent-host saves it in the same file for the same `apiKeyHelper`, which Claude Code sends in both the `Authorization` (Bearer) and `x-api-key` headers. One helper per container, so the gateway's key replaces an API key saved there. Before the engine saves a gateway whose host differs for a side from the one saved (turning it on, changing its host, turning the side off or removing it), it removes the key saved in that container (agent-host step `clear`), so no key reaches an address it wasn't pasted for; if that fails, the gateway isn't changed. **Remove key** (`/api/claude-login` step `clear-key`) removes it from the gateway's containers and keeps the gateway.
  - **The address.** `CheckGatewayURL` lowercases the host, drops port 443 and every trailing `/`, so checking its own answer gives the same string, and `egress.json` is read back the same way. It refuses a host with a leading dot, which egress would read as every subdomain.
  - **No change while Claude Code runs there.** A session keeps the environment it started with, and Claude Code reads `apiKeyHelper` again on its own, so a session started before the change would send the next key to its old address. While a side whose gateway host would change has a Claude Code session running, starting or busy, or a review or manual test list running, the gateway step answers 409 `running` with "Stop these sessions first: …" naming them, before any key is removed or sent. Turning a gateway on or changing its host also needs egress's control channel to answer; otherwise it answers 409 `egress`.
  - **Where a saved key goes.** The engine records in `keyroutes.json`, before it sends a pasted key, that a key may be saved for that side and the gateway host the side had then, or none; it records no key once the key is removed. A key isn't taken while `egress.json` can't be read. At start, before any session or review is restored, and before every Claude Code start, wake, review and manual test list, the engine compares that record with the gateway it applies now: none when `egress.json` can't be read or the control channel is off. When a key was pasted for a gateway the engine doesn't apply now, or for no gateway while one is applied, or the record is missing or unreadable while a gateway is applied or unknown, it removes the key in that container first. If that fails, Claude Code doesn't start there, and the refusal says to check that the container runs and try again. An Anthropic API key pasted with no gateway is left alone.
  - **Anthropic's hosts while a gateway is on.** While the gateway is on for a side, that side's list in egress leaves out every entry `ClaudeVendorHost` names (`internal/core/session/egresshosts.go`): `anthropic.com`, `claude.ai` and `claude.com` with their subdomains, and Claude Code's telemetry hosts, Statsig (`statsig.com`, `statsigapi.net`), Sentry (`sentry.io`) and Datadog (`datadoghq.com`), whether they come from Claude Code's hosts or from added hosts. The gateway's host stays even when it is one of them. So a key pasted for the gateway can't leave for an Anthropic host on a side request, whatever Claude Code does; removing the gateway brings them back. Alongside `ANTHROPIC_BASE_URL` the engine sets `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` (the name in the 2.1.322 binary) for every Claude Code command on that side, and egress logs the host of each tunnel it allows (`event=allowed host=…`), never a path, as it does for refusals.
  - **`ANTHROPIC_BASE_URL` and background sessions.** The engine runs `claude --bg` and `claude respawn` from the session's own worktree. Read from the 2.1.322 binary: the `--bg` client passes its shell's provider variables, `ANTHROPIC_BASE_URL` among them, to the session the supervisor opens when the session is in the folder it was started from, and withholds them only for a session opened in another folder (`CLAUDE_BG_GATEWAY_WITHHELD`, with the notice "No LLM gateway: … respawn from its own folder"). Reviews run `claude -p` directly. A live run with a gateway hasn't checked this yet.

**Optional overlays.** `compose.gvisor.yaml` sets `SF_BOX_RUNTIME=runsc` on the helper, which then makes every session's container with the gVisor runtime on a Linux host where the person registered it, and refuses each start while `docker info` lists no `runsc`; the helper's reviewer containers get it too, and the engine, the helper and egress stay on runc. gVisor's network stack doesn't reach Docker's embedded DNS server, and every session's container already has fixed addresses on its own network with `engine-agents`, `egress` and `egress-agents` in its `/etc/hosts`, so the overlay sets nothing else. The sandbox check isn't changed for it: in a session's container a git host's name doesn't resolve, a direct dial finds no route, and a DNS query to `127.0.0.11` gets no answer, and the check counts each of those as passing. `compose.browser.yaml` gives the helper the `browser` stage, as its image and so every session's container's (`SF_BROWSER_STAGE` names another, such as `dev-browser`, which adds the development fakes); the engine and egress keep `runtime`, and the reviewer containers, made from the helper's image, get that stage too. That stage adds Chromium, `chromium-common` and `fonts-liberation` at pinned versions from `snapshot.debian.org` at one fixed time, with `apt` reading the snapshot through the image's own Debian keyring, and sets `--no-sandbox --disable-dev-shm-usage` for the `chromium` command in `/etc/chromium.d/software-factory`. `--no-sandbox` has to stay: Chromium's own sandbox needs user namespaces (or its setuid helper), which the session's container's `cap_drop: [ALL]`, `no-new-privileges` and Docker's default seccomp profile refuse, so the container is the sandbox. Started there without the flag (`/usr/lib/chromium/chromium --headless --screenshot=/tmp/a.png about:blank`, as the `agent` user, read-only, no network), Chromium exits 1 with "No usable sandbox!", and with it, it writes the screenshot. A page that exploits the renderer then runs as the agents' user in the session's container, which holds no git host token and reaches only what egress allows. The snapshot date fixes Chromium's version, so its security fixes arrive only when the pin moves ([Moving a pin](../../.claude/rules/moving-a-pin.md)). Both stages sit before `runtime`, which stays the last stage. `compose.live.yaml`, for `make dev` only, runs the engine and egress from the `dev-bin` volume, read-only, gives the helper the `dev` stage and `SF_BOX_LIVE=1` (so session and reviewer containers run it too; the helper itself runs its image's binary, so a change to the helper needs the image rebuilt), and declares the one-off `dev-bin` service (profile `dev-bin`: root, no network, no capabilities, a read-only root) that `make dev` runs to copy the binary from its input into the volume. It mounts no folder of the host.

**Releases.** `.github/workflows/release.yml` publishes a tagged version as the multi-platform image `ghcr.io/bezmoradi/software-factory:<version>` and a GitHub release with three files: `install.sh`, `compose.yaml` and `compose.release.yaml`. `compose.release.yaml` gives the three services the image by its index digest, written in by `scripts/release-compose.sh` in place of a placeholder, with `pull_policy: missing`, resets `engine`'s `build`, so an install pulls and never builds, and resets the helper's `group_add` and replaces its volumes with `helper-key` alone (`!override`), so the release's files mount nothing from the host; `make up` reads `compose.yaml` alone and keeps building from source. `install.sh` is `scripts/install.sh` with the version and the SHA-256 of the two Compose files written in by `scripts/release-install.sh` in place of its placeholders (and refuses to run with them unfilled), so it fetches only its own version's files, from `https://github.com/bezmoradi/software-factory/releases/download/v<version>/`. The image is pushed by digest, started on both platforms, its Compose files written and checked and `install.sh` written, then the image is signed and attested, the three files' build provenance attested with `actions/attest` (`subject-path`, stored with GitHub's attestations, each subject named by its file name), and only then is its version tag made, from the signed digest; the last job checks the three files against each other once more, and `install.sh` against the SHA-256 the Release job attested, and attaches them as it creates the release. The digest is signed with cosign keyless by the workflow's identity for that tag, and carries GitHub attestations of its SLSA build provenance and of one SPDX SBOM per platform from Syft; BuildKit's own provenance and SBOM are off, so the index has only the two platform images. Docker's socket reaches the helper only through a local file the install writes, `software-factory-socket.yaml`, holding just `services.helper.volumes` with `<SF_DOCKER_SOCKET>:/var/run/docker.sock` and `services.helper.group_add` with `SF_DOCKER_GID`, passed as the third `-f`. `scripts/release-check.sh` is what keeps a bind mount, or anything else outside an allow-list, out of the release's files: on the rendered configuration of the two files the release attaches (`docker compose config --format json`), it requires exactly the services `egress`, `engine` and `helper`, each on `$IMAGE@$IMAGE_DIGEST` with `pull_policy: missing`, and refuses anything outside an allow-list: a service may set only `cap_drop`, `command`, `depends_on` (on those four only), `entrypoint`, `environment`, `healthcheck`, `image`, `init`, `logging`, `mem_limit`, `networks`, `pids_limit`, `ports`, `pull_policy`, `read_only`, `restart`, `security_opt`, `stop_grace_period`, `tmpfs`, `user` and `volumes`, so `build`, `privileged`, `cap_add`, `devices`, `gpus`, `deploy`, `runtime`, `sysctls`, `cgroup_parent`, `pid`, `ipc`, `network_mode`, `volumes_from`, `post_start` and `pre_stop` hooks, `provider` and `models` all fail; every service needs `cap_drop: [ALL]`, `security_opt: ["no-new-privileges:true"]` exactly (so no `seccomp=` profile or `unconfined`), `read_only: true` and its own user (`engine`, `egress`, `10005:10005`); ports only on `127.0.0.1`; mounts only of type `volume` or `tmpfs`; top-level sections only `name`, `services`, `networks`, `volumes` and `x-` extensions; the project named `software-factory`; networks only with `name`, `internal`, an empty `ipam` and the default `bridge` driver, so no `external` or `macvlan` one; volumes only with `name`, the `local` driver and the existing tmpfs `driver_opts`, so no `external` volume and none that binds a host folder, and a volume that keeps data (every one but `uploads`, `egress-key` and `helper-key`) only with `name`, so no release changes its configuration and makes Compose ask to recreate it; every network and volume named `software-factory_<key>`, as Compose names them, so none names another project's; `SF_BOX_LIVE` nowhere, and no `SF_DEV_` name anywhere, in an environment key, a value or a command, since each is a development switch; and the helper on `helpernet` alone. Anyone can run it on a rendered file: `sh scripts/release-check.sh <image@sha256:digest> <config.json>`. The install is `curl -fsSL https://github.com/bezmoradi/software-factory/releases/latest/download/install.sh | sh`, GitHub's link to the newest release that isn't a draft or a pre-release; the checked install downloads one version's `install.sh` from `releases/download/v<version>/`, runs `gh attestation verify install.sh -R bezmoradi/software-factory --signer-workflow bezmoradi/software-factory/.github/workflows/release.yml --source-ref refs/tags/v<version>`, then `sh install.sh`, and the release's notes and the page's update panel give those lines with the version filled in. The script runs everything from one function, so `sh` has read all of it before anything runs, and points its own input at `/dev/null`, so no command it starts reads the rest of the pipe; it uses no `eval`. It checks `docker`, `docker compose` and the daemon, Docker Engine 28 or later and Compose 2.24.4 or later, the first that reads `!override`, and refuses Compose 5.1.4, whose compose-go 2.11.0 has a bug reading `<<: *anchor` merge keys, which the Compose files use (docker/compose#13812, compose-go#878, fixed in 5.2.0); `!reset` is older, `start_interval` needs 2.24.0, `up --wait` 2.1.1, and `depends_on` with `restart: true` restarts the engine with a recreated helper on `up` from 2.35.0, which an upgrade doesn't need, since it recreates both. It keeps its files in `${SF_HOME:-$HOME/software-factory}` and refuses a folder with `.git`. It downloads each Compose file beside its final name, checks its SHA-256 with `sha256sum` or `shasum -a 256`, and moves both into place only when both match, so a failed or tampered download changes nothing. It writes the socket file only from an `SF_DOCKER_GID` of digits (default `0` on macOS, `stat -c %g` of the socket elsewhere) and an absolute `SF_DOCKER_SOCKET` of letters, digits, `.`, `_`, `/` and `-`, says so when containers of the project `software-factory` run, and runs `docker compose -p software-factory -f compose.yaml -f compose.release.yaml -f software-factory-socket.yaml up -d --wait --remove-orphans` in that folder, without `-y`: with no input, Compose's question about a volume whose configuration changed is answered no, so no data is deleted. It prints the version, the folder and the address `docker compose port engine 8080` gives. The SHA-256 sums tie the Compose files to the script, and the attestations tie all three to the release workflow's run for the tag; what the image's signature covers is the engine image: the agents come from npm and GitHub at first start ("Agent installs"). The browser image isn't published, and gVisor needs only `SF_BOX_RUNTIME=runsc` in the environment at `up`. Only the owner starts a release: a tag ruleset (`.github/rulesets/tags.json`) lets only the admin role create `v*` tags, the job runs in the `release` environment, which waits for the owner's approval, and it fails unless the run's triggering actor is the owner, the tag equals `v` plus the engine's `Version` and the tagged commit is on `main` (a guard against mistakes only, since the tagged commit's own workflow file runs it). An install from a release leaves the three files in its folder, and `docker compose -p <project>` reaches the stack for `exec`, `ps`, `logs` and `down` from any folder (checked with Compose 5.2.0), while `up` and `run` need the three `-f`. So `compose.yaml` passes the engine its project name, `SF_COMPOSE_PROJECT: ${COMPOSE_PROJECT_NAME:-}`, which Compose fills in with the name it uses (from `name:`, `-p` or the overlay's own name), and every command the engine, the page and the plugin show starts `docker compose -p <project>` (`session.Compose`). The engine takes the value only when it follows Compose's rule for project names (lowercase letters, digits, `-` and `_`, starting with a letter or digit), and shows commands without `-p` otherwise. The page reads it from the events stream's `hello` frame and the plugin from the engine's `/register` answer, each checking it against the same rule. `run` commands stay in the README only.
