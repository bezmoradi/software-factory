# Moving a pin

`internal/adapters/install/npm/versions.go` pins Claude Code, and names the repository, branch and floor version knackpack follows (`Knackpack`): knackpack isn't pinned, and each engine start installs the head of its `main` (ARCHITECTURE.md "knackpack"). The engine relies on exact behavior of each, and no test catches a change. Read the release notes, then check each item against the new version; for knackpack, run the items below when its `main` moves, since every install takes the new head at its next start without a Software Factory release. A live run here means the real agents (`make up`), since the fakes in `dev/` copy the old behavior; change `dev/fakeclaude` with any format it copies.

- **npm integrity:** copy each package's `dist.integrity` from `npm view <name>@<version> dist.integrity` into `Pinned`. The installer refuses a tarball whose hash differs.
- **Provenance and advisories:** run `make pins` (`software-factory check-pins`). It checks each pinned npm package's SLSA build provenance from the registry's attestations endpoint against the `Source` beside the pin (repository, workflow and tag ref), and asks OSV about the pinned versions and the current head of knackpack's `main`, which it reads anonymously, following a redirect from either only to the same scheme and host, at most 10; it fails on provenance that doesn't check out, provenance missing where a source is pinned, or a known advisory. Set `Source` with the new version's tag. Claude Code 2.1.322 publishes no npm provenance, so its pins name no source and show as "no provenance"; when a release publishes some, read its repository and workflow from the attestation and pin them. `check-pins -attestations <file> <name>@<version>` checks a saved attestations file instead, to try a tampered one.
- **CI's Claude Code:** with Claude Code's pin, change `VERSION` and `SHA256` in the Plugin job of `.github/workflows/ci.yml`; the SHA-256 is in that release's `manifest.json`.
- **knackpack's floor:** `Knackpack.Floor` is the oldest knackpack the engine installs. The installer refuses a head whose manifest (`.claude-plugin/plugin.json`) doesn't name `knackpack`, gives a version not of the form `x.y.z` (a suffix after `-` or `+` is allowed), or one older than the floor, or that could start programs in the trusted reviewer container (a manifest key outside `inertKeys` in `plugins.go`, a top-level entry in `serverFiles`: `.mcp.json`, `.lsp.json`, `monitors`, `workflows`, or a top-level `settings.json`, an argument placeholder (`$ARGUMENTS`, `$` and a digit, front matter declaring `arguments` or using a YAML tag), `${CLAUDE_DEV_MODS_DIR}`, or inline shell (`!$`, `` !` `` except right after a backtick, ```` ```$ ````, ```` ```! ````, also once every innermost `${…}` and then every `$` is removed) in any file under `skills/` or `commands/` (any extension, any letter case) or in a top-level `skill.md` (see `promptProblem`), `!`, a backtick, `$` or white space in a path under `skills/`, `commands/` or `agents/`, a symbolic link there, or an agent whose front matter mentions `skills` other than as a plain list of `knackpack:<name>`, opens an explicit key (`?`), has a top-level key that isn't plain, or spells `skills` across lines (see `preloadsOthers`); the installed commit is checked again at every start, before any review; until F-22's reviewer view), and keeps the installed commit. When knackpack starts to use another manifest key, read what Claude Code does with it before adding it to `inertKeys`. Raise the floor when the engine starts to need something a newer knackpack added; installs already on an older one keep it until a head at or above the new floor is on `main`.
- **Trust screens:** `screenOf` in `internal/adapters/agenthost/trust.go` matches each start-up screen's text (text style, security notes, the fullscreen renderer offer it declines, the trust question, the prompt screen), and `internal/adapters/agenthost/trust_unix.go` presses the keys. Trust a new repository on the page.
- **Background sessions:** `internal/core/session/starter.go` reads the `backgrounded · <id>` line and "not trusted" from `claude --bg`, and `sessionId`, `id`, `kind` (`background`), `cwd` and `pid` from `claude agents --json --all`, counting a leftover stopped at start as running only when its row has a `pid`. `internal/core/session/wake.go` shows `state`, `status` and `waitingFor` as they are, counts a row without a `pid` as stopped, and reads `claude daemon status`. Start, stop and wake a session.
- **Tool names:** `internal/core/gate/tools.go` counts a name it doesn't map as unknown. Compare its map with the `tools` list in the `system` `init` message of `claude -p --output-format stream-json --verbose`, map each new name, and change the plugin's fallback list in `plugin/hooks/check.ts` with it.
- **Cloud hand-offs:** `internal/core/gate/hazard.go` lists Claude Code's cloud flags, subcommands and slash commands. Add new ones from the release notes.
- **Managed settings:** check that each key in `configs/claude-code/managed-settings.json` keeps its meaning in the new version's settings documentation. `prependPlugins` isn't documented there: check that a permission card still reaches the page, which needs the plugin's `classic.*` hooks, and reread its cost in `ARCHITECTURE.md` "The image and Compose".
- **Code Mode off:** 2.1.323 adds Code Mode, which the managed settings keep off (`ARCHITECTURE.md` "The image and Compose"). Past 2.1.322, check in its `code-mode` documentation that `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE` set to `"0"` in managed settings still blocks it whatever else sets it, and that a session with `"1"` in the agent's `~/.claude/settings.json` starts without Code Mode (`/status` gives the reason).
- **Code Mode's shell commands:** Code Mode sends hooks a shell command in a compound form: a `git push` in a folder `app` arrives as `cd 'app' && git push`. Check that the plugin's tool check (`check` and `fallback` in `plugin/hooks/check.ts`) and `shellParse` in `internal/core/gate/shell.go` still find a push, a cloud hand-off and an irreversible command in each part of it. Code Mode's own tool, `REPL`, carries JavaScript in `tool_input.code`, and `internal/core/gate/tools.go` counts it as unknown until it's mapped.
- **A slow `/check`:** `ask` in `plugin/hooks/check.ts` waits `ASK_MS` (5 s) for the engine's answer and then uses `fallback`. With Code Mode, a hook that doesn't finish in time refuses the call ("the hook did not finish"), on a call from code and on any call once code has run in the session, so a slow answer refuses rather than allows. Check Claude Code's time limit for the plugin's `tool.check` against `ASK_MS`.
- **Code Mode in an agent's home:** the agents' user settings report (`ARCHITECTURE.md` "The agents' user settings report") hashes `~/.claude/settings.json` and the shell start-up files whole, so `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE` written there shows only as that file changed, without the variable's name. Check that the documentation still ignores the variable in a project's settings files, and that agent-host still passes Claude Code only its own list of variables (`Environment` in `internal/adapters/agenthost/env.go`), which leaves it out.
- **A plugin's `engines` range:** from 2.1.323, a plugin's `.claude-plugin/plugin.json` can set a semver range under `engines` `claude-code`, and a range that leaves out the pinned version can stop the plugin loading with nothing on the page. Read the field in the head of knackpack's `main`, which the engine doesn't refuse for it (`engines` is in `inertKeys`: 2.1.322 strips it as an unknown key, and later versions read it as a version range only), and check that the plugin and knackpack still load (`claude plugin list`, and `/plugin`'s Errors tab, in a session's container).
- **Plugin API:** run `make plugin-validate`, and update `tools/plugincheck/claude-code.d.ts` from the declarations the new version writes beside the plugin.
- **Start-up and instruction files:** `StartupLists` in `internal/core/session/startup.go` and `InstructionLists` in `internal/core/session/instructions.go` name the files each agent loads at start. Check them against the new version's documentation.
- **Sign-in status:** `internal/adapters/agenthost/signin.go` reads `authMethod` and `apiProvider` from `claude auth status --json`, and for a claude.ai login `loginExpiresAt`, `planTier` and `subscriptionType`; `ARCHITECTURE.md` "Sign-in and cost" lists the values.
- **Usage limits:** the plugin reads `rateLimits` and `changed` from the `session.measure` hook (`plugin/hooks/register.ts`, declared in `tools/plugincheck/claude-code.d.ts`); `windowWords` in `internal/core/session/usage.go` names Claude Code's window kinds. Check each against the new version and see the page's usage limits on a subscription.
- **Reviewer runs:** `internal/core/session/reviewargv.go` passes the reviewers' flags and settings, `internal/adapters/agenthost/reviewrun.go` reads `--output-format stream-json --verbose` line by line: the `type` that starts each line, the `tool_use` blocks in `assistant` lines' `message.content`, the last `result` line and the last `rate_limit_event` line, whose `rate_limit_info.unifiedWindows` (`five_hour`, `seven_day`, `seven_day_overage_included`, each `utilization`, `resetsAt` and `status`) `RateWindowsOf` in `internal/core/session/reviewstream.go` reads, and isn't in Claude Code's public documentation; `internal/core/session/reviewresult.go` reads the result's `result`, `subtype`, `is_error`, `num_turns`, `permission_denials`, `modelUsage` and `total_cost_usd`, and `reviewerVersion` in `internal/core/session/reviewversions.go` reads the first word of `claude --version`. Run a review.
- **knackpack's verdicts:** `internal/core/review/verdict.go` reads the `knackpack-verdict/1:` line and each role's phrases, and `internal/core/review/severity.go` reads `### [Critical]` and `### [High]` headings, `| F1 | High |` rows and the `knackpack-findings/1:` line. Compare them with knackpack's `scripts/review-protocol.md` and its reviewers' verdict words.
- **knackpack's findings:** `internal/core/session/findingissues.go` reads each `## [Medium]` and `## [Low]` heading (two to four `#`) for the issue cards, with the finding's `Location:` line or a backticked `path:line` in its title, ending the finding at the next heading or a `knackpack-finding/`, `knackpack-findings/` or `knackpack-verdict/` line; `internal/core/session/lessons.go` reads `## [Critical]` and `## [High]` headings the same way for the lessons. `internal/core/session/findinglines.go` reads the per-finding lines, `knackpack-finding/1`, a space and one line of JSON with `id`, `severity`, `blocking`, `title` and optional `path`, `line`, `endLine`, `category` and `evidence`, and drops a line with any other value or type; `findingsShaped` in `internal/core/review/verdict.go` keeps them out of the verdict's sentences, and `keptReply` keeps them when it clips the 4,000-character message, and `keptWhole` keeps the whole reply's last 16 KiB (up to 32 KiB for them). Check each field and limit against knackpack's review protocol, and that `dev/fakeclaude/findings.go` writes them as knackpack does. Three more read lines of a reply: `internal/core/review/check.go` the slop reviewer's "simpler change available" verdict, `keptReply` in `internal/core/session/reviewrole.go` the closing `knackpack-findings/` and `knackpack-verdict/` lines it keeps when it clips a reply, and `quotedReply` in `internal/core/session/reviewprompt.go` the `knackpack-verdict/` lines it removes. Compare them with knackpack's `scripts/review-protocol.md`, then check that a passing review's Medium finding is offered as an issue card and a blocking review's High finding counts toward a lesson.
- **knackpack's agents and commands:** `internal/core/workflow/adapter.go` and `internal/core/session/review.go` name the role agents (`knackpack:adversarial-reviewer`, `knackpack:slop-reviewer`), `internal/core/workflow/files.go` the file reviewers used without a catalog, and `adapter.go` the step commands. Check each still exists.
- **knackpack's reviewer catalog:** `internal/core/workflow/catalog.go` reads `agents/catalog.json` (`ParseCatalog`): `format` `knackpack-catalog/1`, and of each agent `name`, `kind` (`reviewer` or `adjudicator`), `summary` and `appliesTo.always` and `appliesTo.paths`, ignoring every other field, and refuses a pattern that repeats more than 100 times or compiles (with `regexp/syntax`) to more than 1,000 instructions, or a catalog past 10,000 in all (the built-in patterns take at most 306 and 727 in all), and memoizes the catalog's matches per changed-file list (64 entries, dropped when the catalog changes); `Plugins.Catalog` in `internal/adapters/install/npm/catalog.go` reads the file from the installed commit. When the new commit ships a catalog, check that the engine logs it as used (`reviewer catalog`, `event=used`) and not refused, that each `paths` pattern still compiles and stays under the limits, that the review panel shows the reviewers' summaries, and that a change to a Go file still requires `knackpack:go-code-reviewer`; a new format (`knackpack-catalog/2`) is refused until `catalog.go` reads it. Keep `files.go` in step for a knackpack without one. Tool limits, the permission mode, the read limit and which roles are required never come from the catalog.
- **knackpack's committed documents:** with `KNACKPACK_DOCS=repo` (`DocsSettings` in `starter.go`), knackpack's `scripts/commit-docs.sh` commits `.knackpack/<task>/REQUIREMENTS.md` and `PLAN.md` with `.knackpack/feature.json`, which `internal/core/workflow/artifacts.go` reads. `Knackpack.Floor` in `versions.go` is the first version that does, so every installed knackpack does. Approve requirements and a plan in a Feature session.
- **knackpack's hooks:** its `hooks/hooks.json` runs in agent sessions as the agents' user, and reviews turn hooks off (`disableAllHooks` in `reviewargv.go`). Read what changed in them.
- **Running sessions:** a running `--bg` session keeps the old binary and the knackpack commit it started with until it is started again, and gets knackpack's documents mode only then. Wake shows the change (`internal/core/session/wakeversions.go`), and the old commit's folder stays while a saved session names it.
- **Minimum reviewer version:** when Claude Code's pin moves for a security reason, set `MinimumReviewerClaudeCode` beside the pins to the new version, so passes by older reviewers stop counting. knackpack has no minimum: it follows `main`.
- **A bad knackpack commit:** when a commit on knackpack's `main` turns out to have made reviewers pass what they should have blocked, add its full 40-hex SHA to `RefusedKnackpack` in `versions.go` and release. The engine then never installs it; if it is the installed one, reviews and new sessions stop using it (reviews refuse and new sessions start without knackpack until `main` has a head it doesn't refuse); a session already running it keeps it, and its wake note says "This session runs knackpack <7 hex>, which this engine refuses; start a new session."; and every pass recorded with it stops counting and runs again. Its folder stays while `current` or a saved session names it. Revert or fix `main` too, since a refused head keeps the installed commit, and check that the next head installs.
- **Plugin components that run programs:** on each Claude Code pin move, read the new version's plugin manifest schema as data (never run it): its top-level keys and the components it loads from a default location at the plugin root. Check that every component that runs programs (MCP and LSP servers, monitors, workflows, hooks, skills' and commands' inline shell and anything new) either stays refused at knackpack's install (`inertKeys` and `serverFiles` in `plugins.go`, `shellRefused` in `promptscan.go`) or stays off in the `-p` reviewer runs (`reviewargv.go`: `disableAllHooks`, `disableSkillShellExecution`, `--tools`). Recheck skills' inline shell on each pin move: that the setting keeps its name and still takes effect from `--settings`, that an agent's `skills:` preload still goes through it, and that `promptProblem` in `promptscan.go` still refuses a superset of what Claude Code runs: that inline shell still needs `` !` `` or ```` ```! ```` after filling-in, with the start of a line or white space before the `!`, and runs only from skills and commands, in every file Claude Code loads as one (compare the extensions and names its plugin loader accepts, case included). Recheck which placeholders Claude Code fills in before it looks for inline shell (2.1.322: `$ARGUMENTS`, `$ARGUMENTS[n]`, `$n`, named arguments from `arguments:` front matter, `${CLAUDE_SKILL_DIR}`, `${CLAUDE_PROJECT_DIR}`, `${CLAUDE_SESSION_ID}`, `${CLAUDE_EFFORT}`, `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}`, `${CLAUDE_DEV_MODS_DIR}`, `${user_config.…}`): every one knackpack's text can make Claude Code fill in from outside must stay refused (`argumentRef`, the `arguments` front-matter test), and every `${CLAUDE_*}` value must still hold no `!` or backtick, with `${CLAUDE_SKILL_DIR}`'s path covered by `unsafeName`. A new placeholder, or a value that can hold `!` or a backtick, breaks the superset until `promptscan.go` refuses it. Recheck how its front-matter parser opens front matter and reads `skills` (`preloadsOthers`).
- **The browser stage:** the Dockerfile's `browser` stage installs Chromium 156.0.8078.79 (`chromium` and `chromium-common` `156.0.8078.79-1~deb13u1`, with `fonts-liberation`) from Debian's snapshot of `20261103T013555Z`. Move the snapshot date and the versions with each agent pin update, and at least monthly, since Chromium's security fixes reach the image only when the pin moves. Pick a newer snapshot time, set both `sed` lines and the package versions that snapshot holds, build with `compose.browser.yaml`, and take a screenshot in a session. A project whose browser check runs in the stack's browser image gets the new Chromium too, and Playwright drives a Chromium through `executablePath` only within the range its own release supports, so run a browser check with that image after the move (ARCHITECTURE.md "Verification runs", Browser checks).
- **The release workflow's tools:** Dependabot moves the actions in `release.yml` (`sigstore/cosign-installer`, `docker/login-action`, `actions/attest`, `actions/upload-artifact`, `actions/download-artifact` and the ones `ci.yml` shares), but not what they run. `COMPOSE_VERSION` is the Compose the Release job installs to render the release's files for `scripts/release-check.sh`, and `COMPOSE_SHA256` its `docker-compose-linux-x86_64` line in that release's `checksums.txt`; move both together, and read a new Compose's release notes for changes to `config --format json` and to merging (`!reset`, `!override`, merge keys), which the check and `install.sh` rely on. `COSIGN_VERSION` is the cosign the installer fetches, and `COSIGN_SHA256` its `cosign-linux-amd64` line in that release's `cosign_checksums.txt`, which a step checks after the installer; move both together. `SYFT_IMAGE` is `docker.io/anchore/syft` by tag and index digest: read the digest with `docker buildx imagetools inspect`, and check that `ghcr.io/anchore/syft` gives the same. Read a new cosign's release notes for changes to `sign` and `verify` flags, since the job and the README's optional check use them, and a new Syft's for its SPDX output, since the job requires SPDX 2.3, the version `gh attestation verify --predicate-type https://spdx.dev/Document/v2.3` finds.
- **Version numbers in the docs:** `grep -rn` the old version in `ARCHITECTURE.md`, `CLAUDE.md`, the files in `.claude/rules/` and `README.md`, and update each statement you checked again.
