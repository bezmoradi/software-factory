# Proctor's specifications of the Go API

`proctor/` holds Proctor specifications of the page server's HTTP API: `proctor.yaml` (drivers, identities, the declared reads and what each shows, the declared destructive routes, and the largest body a step may send), `dimensions.yaml` (the routes, methods and key variants the page-security tables must cover, TBL-07), `manifest.yaml` (the suites, in run order), `specs/*.yaml`, `mutants.yaml` (the mutants, [below](#mutants)), the scripts in `env/` that run them against the development overlay, and `environments/compose.proctor.yaml`, the stack's Compose overlay, in the folder Proctor doesn't read as specifications. They are Proctor's files, not Go tests: CLAUDE.md's "No automated tests" says what its exception covers. `make proctor` runs them on your machine, and CI's Proctor workflow runs them in authoritative mode on every pull request to `main`, with the latest Proctor release ([CI](ci.md)). They cover every case the page's curl security checks did, which are gone: each POST route's refusals of no key, a key in each refused form, another Host, Origin or site, no Origin, another Content-Type, a query, another method, a body over its limit and a field it doesn't take, the security headers on those answers, loading the page, the event stream's key, and the removed routes.

A pull request that changes anything under `proctor/` fails CI's Workflow guard until the owner adds the `review-override` label after its latest push ([CI](ci.md)).

Once main holds `proctor/proctor.yaml`, Software Factory guards these files in its own sessions too: Claude Code's file tools ask the person before every write under `proctor/` and to the root `Makefile` (whose `proctor` target runs them), and every change a session's push carries to them (added, changed, deleted or renamed) is a `specification` flagged file that holds the push until the owner allows it with a reason on the page, bound to the versions the page showed; a later change to the same file holds it again. A symbolic link under `proctor/` that points outside it can't be allowed at all. A session working on the specifications therefore ends at the owner's Allow, never at an agent's own push.

## Running

- `make proctor` (or `sh proctor/env/run.sh`): checks the route tables (`env/routes.sh`), validates, starts the stack, runs every suite, checks the report for the run's credentials, prints the count of `level=ERROR` lines in the engine's log and tears the stack down. `--keep` leaves the stack up; `sh proctor/env/down.sh` stops it, and `down.sh --purge` also removes the agents' cache volume. Other arguments go to `proctor run`. `run.sh` passes no `--call-timeout`, so every call waits Proctor's default 10 s except a step with its own `timeout`.
- Proctor: `PROCTOR=<path to proctor>` names the binary, or `proctor` on `PATH`. Before anything else `run.sh` reads the build's features with `proctor version --features` and refuses a build that lacks one of these, naming each it lacks: `http.reads` and `http.shows` (the http driver's `reads` list and what each shows, HTTP-11), `policy_from` (INT-18), `http.destructive` (the `destructive` list), `exe09.related_guard` (EXE-09's guards, which REP-003, FLD-001 and the tables' later rows on one route rely on), `waive.rows` (named-row table waivers), `docker` (the read-only docker driver, `proctor-driver-docker` beside `proctor`), `exe11.fact_paths` (EXE-11, so a Docker absence check can't pass on a path the fact never holds), `app_logs` and `app_logs.logfmt` (EXE-10 reading the engine's logfmt lines), `cleanup` (a scenario's cleanup acts, which run whatever happened in its steps, EXE-14, as SES-007's do), `report.always` (a report on every exit, so the scrub check reads one), `exe09.waivers_guard_nothing` (a waived act guards no later act on its target, so every such row is named in its waiver), `matchers.matches`, `matchers.excludes` and `matchers.differs` (EXE-12, the request id's format and change and the diagnostics text's absences), `matchers.matches_numbers` (`matches` on a JSON number, such as a pack's `addedAt` in epoch milliseconds), `step.timeout` (a step's own `timeout`, bounded by `time_limits.max_call`), `relations` (the `relations` that let a Docker read count after an act, INT-20), `tables.covers` (TBL-07, the tables checked against `dimensions.yaml`), `http.body_base64` and `http.body_fill` (bodies that aren't JSON or text, HTTP-14), `http.stream`, `matchers.overflow` and `time14.accumulates` (the event stream read with `http.open` and `http.frames`, HTTP-15, whose claims fail past the kept frames, and whose `eventually` can't pass before a frame arrives, TIME-14), and `transcripts` and `approved_logs` (the approved transcripts and log, TRN-01 and ALG-01). `run.sh` doesn't run `proctor approve`, so it doesn't require `approve`; updating the approved files needs a build that has it. A build without `version --features` is refused too, with a message to use a newer build. Add a feature to `needed` in `run.sh`, and here, when the configuration or a specification starts to use it.
- CI's path: with `PROCTOR_SF_AUTHORITATIVE=1`, `run.sh` runs `proctor run --authoritative` (pass `--pr-head` or `--base` and the other flags as arguments; `--authoritative` itself is refused as an argument, so `up.sh` always agrees), and `up.sh` builds nothing: it needs `software-factory-proctor:{dev,local,gitserver}` already loaded and each one's image ID from the build in `PROCTOR_SF_BUILT_DEV_DIGEST`, `PROCTOR_SF_BUILT_LOCAL_DIGEST` and `PROCTOR_SF_BUILT_GITSERVER_DIGEST`, fails unless each tag is its built image and each service's container runs its loaded image (the engine and the helper dev, egress local, the gitserver its own), and writes `environment: github-actions`, `disposable: true` and `images` into the binding, with `dev`, `local` and `gitserver` each giving its built ID and the image ID of the container that runs it (the engine's for dev), as Proctor's REP-11 needs. It writes no `image`, which would repeat `images.dev`. `PROCTOR_SF_CHECKOUT` names the folder whose code and specifications `routes.sh`, `proctor validate` and `proctor run` read, by default the one holding the scripts; CI runs the base commit's scripts from outside the checkout with it set to the tested checkout, and the state folder must be outside both.
- The stack: Compose project `sf-proctor`, `compose.yaml` and `compose.dev.yaml` with `environments/compose.proctor.yaml`, published on `127.0.0.1:17799` (`PROCTOR_SF_PORT`) with the preview on `127.0.0.1:17800` (`PROCTOR_SF_PREVIEW_PORT`), images `software-factory-proctor:{dev,local,gitserver}` so your `software-factory:*` images aren't retagged. `down.sh` keeps the volume `sf-proctor_agents`, so later runs don't install the agents again, and removes every other object labelled with the project. State, the key, the binding and the report are in `/tmp/sf-proctor` (`PROCTOR_SF_STATE`, which must be outside the repository).
- `up.sh` refuses to start while `software-factory` or `software-factory-dev` runs, as live checks run with your own stack stopped ([Hand checks with Compose](compose-hand-checks.md)), while `sf-proctor` has containers, or while either port is taken. It signs in twice, so the first key is one a newer sign-in replaced (the `replaced` variant), saves the dev git host's token, adds `https://gitserver.test:8443/dev/demo.git` and waits for its clone, then writes the binding.
- The binding's `docker.socket` is the Unix socket `DOCKER_HOST` names, or else the current Docker context's, the one the `docker` CLI and Compose use; `up.sh` fails when it isn't a `unix://` path to a socket. It isn't `SF_DOCKER_SOCKET`, which is the socket's path on the Docker host for the helper's bind mount. The identity value `page.port` is the published port, so a specification writes `${page.port}`, and `page.preview_port` the preview's, which NAV-T01's `frame-src`, STK-001's engine ports and EVS-090's `tab` name.
- `up.sh` gives the engine, the helper and egress `SF_BOX_SUBNETS=10.213.15.240/28,10.213.15.224/28`, a pool of two /28s. The helper takes the first free /28 in that order, so while one session's container runs its network is `10.213.15.240/28`, with the engine at `.242`, egress at `.243` and the session's container at `.244`, and the specifications assert those addresses (SES-001). The second /28 is for GATE-014, where a goal session's card starts a task session on another project while the goal still runs, and the goal's delete wakes its container while the task's runs; no other scenario runs two session containers at once, and none asserts a pool refusal. A leftover network of another stack on either /28 makes the helper refuse to start until that stack's `down.sh` removes it.
- The app-log check (Proctor's EXE-10) is on: `up.sh` follows the engine's output into `$state/engine.log` and names it in the binding, and `proctor.yaml`'s `app_logs` reads it as logfmt, the engine's `slog.TextHandler` lines. A line at ERROR, or a `panic:` or `fatal error:` line, written while a scenario runs fails that scenario; for a table, every case of it. A line that isn't logfmt, other than a panic's stack trace, makes the scenario ERROR `app_logs_unparsed`, not a pass; `app_logs.unparsed` stays strict, so find what wrote such a line rather than setting `allow`. An ERROR line a scenario causes by design goes in its `expect_logs` (level, the exact `msg`, optional `count`) with the reason in the scenario's name or a step's, never to quiet a line that shows a bug. A scenario whose requests the engine doesn't log has an empty window and passes: HLT's `/healthz`, which is served outside the request logger, and STK's Docker reads. `run.sh` still prints the run's count of `level=ERROR` lines beside it.

## Changing the API

CLAUDE.md's rule that every change keeps these specifications passing says when `make proctor` must pass and that a specification changes only on purpose. This is what such a change touches.

- **A route.** Adding or removing a page route updates its rows in the page-security tables and its entry in `dimensions.yaml` in the same change; otherwise TBL-07 fails the run, naming each missing or doubled row ([Tables](#writing-specifications)).
- **An approved file.** An intended change to a file under `proctor/approved/` is re-approved with `proctor approve`, and the owner reviews it as its code owner (`.github/CODEOWNERS`; [Updating them](#transcripts-and-approved-logs)).
- **The plugin's path checks.** A change to them in `plugin/hooks/register.ts` or `check.ts` is ported to `dev/fakeacp/gate.go` in the same change, since the gate specifications run the fake, not the plugin ([The gate](#the-gate) names what to port).

## The page key

- The run's sign-ins are the two in `up.sh`; the second key is the run's. No specification may send a request that succeeds at `/api/session`: it ends the run's key, and every later step fails as 401. Refusals there are safe only because the check under test refuses before a key is issued; a reviewer of a change under `proctor/` checks every step on that route for that. SEC-006 sends `/api/disconnect`, the route Disconnect used before it was removed, with only an unknown field, so a Disconnect that came back would refuse it with 400 `fields` before ending the key.
- No browser on port 17799 during a run, and no engine restart.
- The key, the variants and the git token are only in 0600 files in the state folder, never on a command line or in the repository. `run.sh` fails the run if any of them is in the report or the engine's log.
- The refused variants: `unknown` is a key the page never issued, `replaced` the key of `up.sh`'s first sign-in, which its second replaced, `no_scheme` the page's key with no scheme, and `basic_scheme` and `token_scheme` the page's own key under `Basic` and `Token`, so CRD-T01 fails if the scheme isn't checked; a random value there would be refused by the key check alone.

## Writing specifications

- **Declared reads.** `proctor.yaml` declares, on the `http` driver, the POST routes whose handler changes nothing for any body it accepts; `http_misdirected` takes the same policy with `policy_from: http`, so the two can't drift apart. A declared read is an observe step: it can be the later state check an act needs (EXE-07), `eventually` can poll it, and it can't carry `no_state_check`. Declare a route only after reading its handler and what it calls; a route whose body decides read or write (`/api/keep` with `op: read` or `restore`, the `op` routes) or that fills a cache later answers come from (`/api/files`) isn't declared. `env/routes.sh` fails on a declared path, a path a read shows, or a destructive path, that the page doesn't serve.
- **What a read shows.** Proctor counts a later read as an act's state check only when it reads the act's own path (every route here is its own path, `/api/<name>`), expects a status that describes the state (2xx, 3xx, 404, 409, 410, 412 or 423; a 400, 401, 403, 405, 415, 422 or 429 doesn't count) and, for a read of another route, the read's `reads` entry lists the act's path under `shows`. Add a path to `shows` only after reading both handlers and the core code they call and finding the read's answer built from the state the act writes (`/api/projects` lists the records `/api/add-repo` and `/api/remove-repo` change and the hosts `/api/save-token` saves, and answers only for the key `/api/session` would replace; `/api/backup`'s `canImport` and `why` come from `Backups.staged`, which a successful `/api/import` sets; `/api/audit` lists the entries `Limits` and `Verifier` write for `/api/limits` and `/api/verify`, and `/api/gate`'s `approved` comes from the approval `Work.Approve` keeps); `proctor diff` reports each added path as a `state_check_declared` weakening. Never add a read, or a `shows` path, only to satisfy EXE-07. A read on the docker driver counts only through a relation ([Docker reads](#docker-reads)), and Proctor refuses a `no_state_check` on an act a later read already checks.
- **Waivers.** Follow an act with the read that shows its effect, and assert the effect there; then it needs no waiver. A `no_state_check` is for an act no read can show: a refusal table on routes that act gets one at table level, saying why; a row on a declared read gets none, so each refusal table comes in two, `<id>` for routes that act and `<id>R` for declared reads.
- **Destructive routes.** `proctor.yaml`'s `destructive` list holds `/api/remove-repo` and `/api/remove-session`, so Proctor's EXE-09 treats them like a DELETE: the target is the path and the body, and it is fixed unless the body refers to `${run.id}` or a value saved earlier in the scenario. Before a remove step with a literal name or id, read the target with a request whose `shows` names the remove route (`/api/projects` for remove-repo; `/api/gate` or `/api/audit` for remove-session) and expect what the scenario relies on, as REP-003's `cloned` and FLD-001's `unknown-before` do. Waive EXE-09 only when the request can't remove anything, and say why. In a refusal table the waiver sits on the table's step and names the rows it covers, `waive: { EXE-09: { rows: [<case ids>], reason: <text> } }`, and its reason says why each of those rows removes nothing; Proctor refuses a named row the rule doesn't apply to and a remove row the list leaves out, so a new remove route's rows go on the list deliberately, and `proctor diff` reports each as a `rule_waived` weakening. Never add a read only to satisfy EXE-09. A new route that deletes or overwrites what its body names goes on the `destructive` list, after reading its handler; `proctor diff` reports dropping one as `destructive_removed`.
- **Tables.** Case IDs are unique across a file (prefix them with the table, `t03_add_repo`). The page-security tables must list every route, and Proctor checks that (TBL-07): `dimensions.yaml` names the dimensions `post_routes` (every POST route), `body_limited_routes` (the 1 MiB routes), `other_methods` (PUT, DELETE, PATCH), `refused_key_variants` (`unknown`, `basic_scheme`, `token_scheme`, `no_scheme`) and `replaced_key_variants` (`replaced`), and one set per table and its `R` twin, which the table names with `covers`; across a set's tables every combination, less its `except` entries, must have exactly one row, and `proctor validate` names each one missing or doubled, as `no row for (route="/api/wake")`. An exception is for a route that can't take the table's row, with the true reason: `no_key` leaves out `/api/session`, the sign-in route, which takes no key, and `json_over_64k` the routes with their own limit (`/api/upload` and `/api/import`, which take no JSON, and the 1 MiB routes, which `json_over_1m` covers); `proctor diff` reports a new exception as `coverage_exception_added` and a value taken out of a dimension as `dimension_value_removed`. `env/routes.sh` reads the routes from `pageRoutes`, `workflowRoutes` and the `*Route` constants in `internal/adapters/http/page` and fails naming each POST route but `/api/events` that `post_routes` lacks, and each it lists that the page doesn't serve, so a new route fails `make proctor` until it is in the dimension, and then until every table has its row; `body_limited_routes` is kept by hand, from `approveRoutes` and `reviewerAgentsRoute`. `SEC-T11` (with the page's Origin) and `SEC-T12` (with none) send PUT, DELETE and PATCH, a method in each row's third cell, and cover `post_routes` × `other_methods`; they come without an `R` table, since only POST is declared a read, so PUT, DELETE and PATCH act on every route and every row takes the table's `no_state_check`. PUT, DELETE and PATCH are destructive to Proctor whatever the route, and a waived row guards no later row on the same target (Proctor's P-48), so their EXE-09 waiver names every row, PUT, DELETE and PATCH alike, and SEC-T14's names both remove-repo rows. `SEC-T14` (an Origin that only starts with the page's) lists a few routes, not all, and covers no set. The refusal tables added after `SEC-T10` send `{ proctorUnknownField: true }` rather than `{}`, so a defect that lets a row through reaches a handler that refuses an unknown field: `/api/session` doesn't sign in. `SEC-T15` sends each of `refused_key_variants` to every POST route but `/api/session` (set `other_key`, whose route and variant columns each exception names), `SEC-T16` the `replaced` key (set `replaced_key`), and `SEC-T17` the page's key with that unknown field (set `unknown_field`), which every handler refuses with 400 before it acts, so its rows assert the status, a reason code and words rather than each handler's own reason; `/api/upload` and `/api/import` are left out, as they take no JSON, and `/api/session`, since each request there counts toward the sign-in rate. A variant row takes `variant: "${row.variant}"`, and its EXE-09 waiver names every packs, remove-repo and remove-session row, one per variant. These three tables also assert the page's `Content-Security-Policy` and the absence of each CORS response header the Fetch standard names (`access-control-allow-origin`, `-allow-credentials`, `-allow-methods`, `-allow-headers`, `-allow-private-network`, `-expose-headers`, `-max-age`): Proctor matches a header by its name, not by a prefix, so a new `Access-Control-*` header is caught only once it is listed.
- **Bodies.** `specs/bodies.yaml` sends real bodies to `/api/upload` and `/api/import`: `body_base64` for a few bytes of an image or a gzip header, `body_text: ""` with the step's own `Content-Type` for an empty file, and `body_fill` for a body at a limit and one byte over it (32 MiB for an image, 10 MiB for a file, 256 MiB for an import; `session.MaxImageUpload`, `MaxDrop` and `MaxImport`). The http driver's `max_body_bytes` is 268435457, the 256 MiB import plus one byte; Proctor's client sets `Content-Length` to the body's length, which both handlers refuse before reading, and `proctor diff` reports a raised value as `max_body_bytes_higher`. The upload refusals name a session the engine didn't start, so a body that passes every other check is refused with 404, and each takes a `no_state_check`: no page read lists uploads. Every import is refused with 409 `not empty` before its archive is read, since the engine holds the project `up.sh` adds, and IMP-001's `/api/backup` reads show nothing was staged. A successful upload is in EVS-011, with a session of its own.
- **Streams.** `specs/events-stream.yaml` opens `/api/events` with `http.open` and reads its NDJSON lines with `http.frames`. The first frames are the `hello` (`stream`, `sessions`, `supervisor`, `compose`) and the `halt` frame of away mode (`Registry.Attach`); a session's listing, prompts, the agent's text and turns follow as they happen. The page holds two streams at once (`session.MaxStreams`), and Proctor closes a scenario's streams when it ends, so a scenario holds at most two open, as EVS-010, whose third is refused with 429 `streams`, checks. Wait for a frame with `eventually` and a claim that only a frame can meet; a `none` goes in a `consistently` step (TIME-14), and every `none` key must be in some frame (EXE-11), so `json.sid` there needs a frame that has one. An `http.frames` step reports no targets, so it isn't an http request's state check: EVS-011's upload and the message carrying it, whose effect only the stream shows, take a `no_state_check` that names the frames step asserting it; as in GATE, every frames read but `turns-ended`, which waits for both turns before the stop, EVS-014's `background-ended`, which waits after both turns until the background subagent the fake agent starts (its `agent-bg:` line, 3 seconds) has finished, so its next message goes while that subagent still runs, EVS-015's `watch-stopped`, which waits until the fake agent's Monitor watch (its `watch:` line) has stopped while its longer `bg:` command still runs, before the next message, whose five `read:` lines keep its turn going until that command has ended, and the task cards' reads in GATE-014 and GATE-015 (`carded`, which saves a card's id from the hello frame, since only the stream carries a goal session's cards, and GATE-014's `task-live`, which waits until a second session is listed and live, since the session the engine starts after the clone answers no request), comes after the session is removed, so a failed read leaves no session behind. The hello frame lists sessions by id, so a scenario reads `sessions[0]` only while it holds one session: GATE-014 removes the goal session before it opens the stream that saves the task session's id. A frame's text holds the ports note on a session's first message (`portNote`), whose ports depend on what else ran, so assert it on later messages only.
- **Values.** `${run.id}` in every value a scenario writes and later matches. A value fixed by the engine (a work type, a pack id, an op name) instead takes an earlier observe step of the later step's request that expects something else there, or a `FIX-05` waiver saying why it can't vary (Proctor's FIX-05). A table case's run id holds `_`, which a session id can't, so use the fixed unknown id `00000000-0000-4000-8000-000000000000` there. Expected values come from the handlers; when an answer differs from what the code says, find out why before changing the expectation.
- **Formats, absences and change.** Assert a value's format with `matches` (an RE2 pattern Proctor anchors at both ends), what text must not hold with `excludes`, and that a value changed with `differs` against one saved earlier, never with `present` alone. Assert only what the code promises: every answer that asserts `X-SF-Request` matches `[0-9a-f]{16}` on `[0]` and has no `[1]` (`shared.NewRequest` hex-encodes 8 random bytes and `requestLogger` sets the header once; Proctor's HTTP-09 refuses a `length` on it), SEC-005 checks two answers' ids differ, and DGN-001 checks that `/api/diagnostics` text starts with `software-factory-diagnostics/1` and holds none of `demo`, `proctor`, `gitserver`, `/workspace`, `/var/lib`, `/tmp`, `https://`, `http://` and `@` (`session/diagnostics.go`'s field patterns and URL check). The `diagnostics` suite runs last, so its text holds the events of every other suite. `/api/diagnostics` isn't a declared read, since it refreshes the box helper's cached Docker facts (`boxes.Client.keepAbout`), so DGN-001's step carries a `no_state_check`.
- **Timeouts.** A call waits 10 s unless its step sets `timeout`. Only `/api/dispatch` gets one, `110s`: the engine gives a start up to 105 s (`dispatchFor` in `start.go`), and its own answer at that limit should reach the report rather than Proctor's timeout. `proctor.yaml`'s `time_limits.max_call` is `110s`, the longest step timeout; raise both together only after reading the route's limit in the code, since `proctor diff` reports either as a weakening (`max_call_longer`, `step_timeout_longer`). The other routes the specifications reach answer well inside 10 s: on 2026-11-18 a dispatch took about 5 s, and the slowest other request, `/api/remove-session` waking and stopping its container, about 2 s; give a step its own `timeout` when a run shows it nearing 10 s.
- No comments, as everywhere (CLAUDE.md); quote a value that holds a space followed by `#`.

## Docker reads

- The `docker` driver reads containers, networks and volumes and changes nothing: it sends only GET requests, to a fixed list of Docker API paths, never reads a container's environment, command, entrypoint, healthcheck command or log options, and returns no host path. Docker's socket can't be made read-only, so the report says `proof read_only: unproven`.
- Its scope in `proctor.yaml` is two labels, either of which makes an object visible: `com.docker.compose.project=sf-proctor` (Compose's containers, networks and volumes) and `dev.software-factory.stack=sf-proctor` (what the box helper makes, whose copied `com.docker.compose.*` labels it empties). Anything else reads as not found, and a visible object's reference to one outside the scope is shown without its name. Narrowing the scope makes absence checks pass without looking, so treat a change to it like a change to an assertion.
- SES-004 reads a verification run's container, `sf-proctor-verify-${run}`, with `${run}` from `/api/verify`'s start answer (`runs[0].id`), while its check command still sleeps; the run's end is waited for on `/api/audit`'s `verify` `ended` line, which the engine writes after it records the result. Its browser check runs in that same image, which has no browser in Proctor's stack, so it pins the `no-browser` refusal and that neither the container nor its `/out` volume is left; a browser check that passes and keeps files needs the browser image and stays a hand check (gate-hand-checks.md).
- `stack.yaml` (STK) runs right after `health`, before any session, since the engine and egress join each session's network while it runs. SES-001 reads its session's container, network and home volume: `${box}` comes from the audit entry of its start (`/api/audit`'s newest entry, `entries[0].box`), and the names are `sf-proctor-box-${box}` and `sf-proctor-home-${box}`.
- A Docker read is an observe step, so `eventually` can poll it (use `every: 1s`, since a read makes several requests), but it is an act's state check only through a `relations` entry in `proctor.yaml` naming the act's path and the read's target: `/api/wake` shows `container/sf-proctor-box-{}` (`Dispatcher.wakeFor` and `RefuseWake` start and stop it through `boxes.Helper.Start` and `Stop`) and `/api/verify` shows `container/sf-proctor-verify-{}` (`Verifier.execute` through `StartVerifier` and `RemoveVerifier`). Declare one only after reading the act's handler and the code it calls and finding that it creates, starts, stops or removes exactly that object; `proctor diff` reports each as `state_check_declared`. Never add a relation or a Docker read only to satisfy EXE-07. Docker reads aren't allowed in `setup` (FIX-03), and every path an expectation or `save` names must be one the fact can hold: Proctor checks that for every driver (EXE-11), against the driver's `fact_schema`, and a `none` claim or a `count` with `is: 0` fails when one of its keys is in no element of a non-empty list. Labels and options are lists of `{ key, value }`, since a path can't name a key with a dot; check them with `any`, `none` or `count`.
- Assert what the code or a Compose file sets, not what a Docker install chooses: not the runtime, the AppArmor profile, the socket's group, or a log driver the service doesn't set (the gitserver's).

## The gate

`specs/gate.yaml` (GATE) tests `/check` through the real route, from inside a session's container. The engine gives each development ACP session a check-only key. A specification sends the fake agent script lines with `/api/message`, as SES-001 does, and the fake asks `/check` over agent-host's socket with Claude Code's plugin's body (`tool`, `input`, `top` and each path's plain and real forms). It writes the engine's answer byte for byte to `gate-answers/<id>.json` in the worktree, and what it did to `gate-answers/<id>.txt`. It then obeys the answer as the plugin does: it writes nothing on a refusal or an ask, and writes inside the worktree when allowed. With no usable answer it uses the plugin's fallback, which allows a write, so a broken `/check` changes both files and fails the scenario rather than passing it.

- **Lines.** `try: <id> <path>` sends `Write`. `try-run: <id> <command>` sends `Bash`. `try-tool: <id> <Tool> <JSON input>` sends any tool. `key-at: <id> conn|push <METHOD> <path> [JSON body]` sends the key as `X-SF-Conn` or `X-SF-Push` to another route and records the answer, and records `no key` and sends nothing when the engine gave none. `ask-tool: <id> <tool> <JSON arguments>` calls one of the factory tools through agent-host's MCP server, with the session's push token as a real agent's call has it, and writes the tool's whole MCP result to `gate-answers/<id>.json` and `mcp: called <tool>` to `<id>.txt` (GATE-009's `factory_work_type`, GATE-012's `factory_request_access`). `mkdir:` and `link: <path> -> <target>` make a folder or a symbolic link unasked, like `write:`, which still doesn't ask, and `commit: <path>` writes `ok` and a newline to that file and commits it alone as `Add <path>`, unasked too, so a scenario can have work committed on an approval (GATE-019), or commit a workflow document such as `.knackpack/t/REQUIREMENTS.md` on purpose to reach the push's refusal (GATE-018). `remove: <path>` deletes that file or folder in the worktree and commits the deletion alone as `Remove <path>`, unasked, so a scenario can take `.knackpack/` off a branch, which still leaves the earlier commits carrying it (GATE-018); it refuses an empty path and anything under `.git`. The fake also answers knackpack's step commands, writing each document in `$SF_DOCS` and committing none: Define's `/knackpack:challenge-requirements` by writing `REQUIREMENTS.md` from the lines after the command's, Plan's `/knackpack:plan-implementation` by writing a fixed `PLAN.md` (GATE-060), `/knackpack:debug-incident` by writing the next step's `ROOT-CAUSE.md`, and `/knackpack:fix-incident` by checking the message's `KNACKPACK_INCIDENT_APPROVED_SHA256` against that file and committing the fix (GATE-006). With `SF_DOCS` unset or relative it writes no document and says so. `grow-for: <seconds> <MiB> <path>` makes a sparse file of that apparent size unasked and removes it after that many seconds, which SES-003 uses to reach a disk cap and free it, since a message can't reach the fake while the session is at the cap. An `<id>` is `a-z`, `0-9`, `_` and `-`. A Code change or Incident session, and a session nobody picks a work type for, whose effective type is the built-in default, Code change (GATE-009, GATE-016), sends each plain typed message, attached files included, to the agent as Define's (Triage's) command with the engine's notes and the text, until the step's document is in `$SF_DOCS` (the requirements brief; Incident: `ROOT-CAUSE.md` with a Status). The fake runs a message with a `say:` line as a script even when it comes as that command, and answers a command message without one by writing the brief, so a plain message with an attached file and no `say:` line is what shows whether a message went as the command (GATE-004 pins the wrapping, GATE-009 that with no type picked a write under `.knackpack/` is denied with the sentence naming the session's documents folder, which raises no work type card, and the untyped hold holds any other write, GATE-016 a message too long for the command, a question, attached files and the end after a written brief, GATE-017 the notice while files change before the requirements are approved). The write-check and command scenarios use Explore, which wraps no message and holds no write. The fake's port of the plugin is `dev/fakeacp/gate.go`. Change it with `plugin/hooks/check.ts` (`fallback`, `checkedOf`, `ASK_MS`, the 10-second fallback after a failed ask) and `register.ts` (`worktreeTop`, `placed` with `linkOf`, which the fake reads with `os.Readlink` where the plugin runs `/usr/bin/readlink`, `placeOf`, `refusalOf`, and which answers ask). One difference is deliberate: the fake doesn't keep answers for 10 seconds, so it asks again for the same call.
- **What each scenario reads.** Assert the whole answer and the whole outcome, both from `/api/file`, a declared read that shows `/api/message`. A message's turn runs after its `202`, so wait with `eventually` until `/api/file-check` finds the last line's outcome file, whatever it holds. The engine's own record of a refusal is `/api/audit`'s `refusals`. Its counts are per project and held in memory, so GATE's scenarios run in order after `sessions`, each expects the running totals once its own calls are in, and no earlier suite may call `/check`; a scenario that changes a count changes every later scenario's totals too. Whether a file landed is `/api/file-check`: `found` lists the asked paths that are regular files there, and `unread`, present only when not empty, maps each asked path that is there but that `/api/file` hides to its reason, `link` for a symbolic link at any step (not followed) and `secret` for a name `/api/file` hides as secret-looking (a dot folder, `.env`-like names, keys and the rest of `files.go`'s `hiddenPath`), `secret` first when both apply; its contents aren't read. So an absence check asserts the whole answer, `unread` included: a path in neither is missing (GATE-002's `pinned-unread`). For `.agents`, `.codex`, `.git` and environment files the proof is the refusal count and the answer, until the fake can commit and `/api/changes` lists what landed.
- **Pinned answers.** Today's answers stay pinned as they are, and each is named in its scenario's name, so a later decision can find it. The write check allows `.claude/settings.json` and `CLAUDE.md`, which the start-up approval covers, and a folder named `.env`. It refuses a `.git` part anywhere in the absolute path (the worktree's `.git` file and the session clone's `.git/` included) and a file named `.env`, `.envrc` or `.env.<anything>` at any depth of the worktree, through symbolic links too: the plugin sends the path folded, and the path as written and the folded path each walked through their links, dangling or not, a `..` after a missing folder resuming the walk, a leading `~/` placed under the home folder as Claude Code places it, and a path with white space around it placed both as written and trimmed (GATE-002, the owner's decisions of 2026-11-19, REQ-32 and REQ-33, and review finding F2). A link loop is refused by the plugin itself, without asking, so it isn't counted.
- **Proctor's rules.** Every act is followed by its read: `/api/dispatch` by `/api/audit`, `/api/message` by `/api/file`, or by `/api/changes`' commits for a turn whose effect `/api/file` can't read, since it writes only in the session's documents folder or commits a dot-folder file `/api/file` hides (GATE-004, GATE-006, GATE-007, GATE-008, GATE-018, GATE-060); the brief, plan and root cause the fake writes there are read through `/api/gate`, whose `requirements` and `planDoc` carry the folder's path, `/workspace/s/${box}/docs/${sid}/` (the session's box and id, which `docsFolder` names too), the approvals by `/api/gate`, `/api/stop-session` by `/api/audit`, `/api/wake` by the docker read of the session's container (GATE-019), and `/api/remove-session` by `/api/gate` and `/api/audit`. `/api/remove-session` names the saved `${sid}`, so EXE-09 is met without a waiver; GATE-006's start waives FIX-05 for its fixed work type. Each scenario starts its own session and removes it, since the pool holds one session's container. Proctor has no clean-up step and skips a scenario's later acts once a step fails, so each scenario stops its session as soon as the last outcome file exists and makes every other read, the exact answers included, after the stop: a failed read then leaves a stopped session behind, never one holding the pool's only container, which would fail every later session's start. EXE-10 is strict there: an ERROR line fails it.

## Transcripts and approved logs

- **What they are.** A scenario with `transcript: true` (REP-001 to REP-004, HLT-001) has its whole story, each step's request and the answer that came back, compared byte for byte with `proctor/approved/<spec id>/<scenario id>.transcript.yaml`. REP-001 also has `approved_log: true`: the engine's log lines written while it ran, cut to `app_logs.approved.fields` and scrubbed, are compared with `proctor/approved/repositories/REP-001.log`. Both add a check and replace none: the scenario's own assertions stay the contract, and a transcript or log that changed fails a scenario that passed (`transcript_changed`, `log_changed`). An approved log never allows an ERROR line: EXE-10 fails the scenario whatever the approved log holds, so never approve one to accept an error, and never take an ERROR line into a log by widening `levels`.
- **What's scrubbed.** Proctor scrubs the run's credentials, `${run.id}`, saved values and identity values itself. `proctor.yaml`'s `transcripts.scrub` names only what differs between runs: `X-SF-Request` and `Date` (in both `headers` and `header_lists`, since the http driver holds each header twice), the epoch-millisecond `savedAt` and `addedAt` in `/api/save-token` and `/api/projects` answers (by index, since a path has no wildcard and a pattern doesn't reach numbers), and RFC 3339 times, a starting rule that matches nothing in today's transcripts or log. `app_logs.approved` keeps `side`, `method`, `route`, `status`, `event`, `why` and `req`, and scrubs `req`: never list `time` or `duration`, which differ each run, or a field that can hold a token, a host secret or a path with a person's folder. Add a rule only after two runs show a real difference, since each rule hides what it matches; `proctor diff` reports a new or changed rule as `scrub_widened`.
- **Size.** `transcripts.max_bytes` and `app_logs.approved.max_bytes` are 524288, so an approved file passes `make files`' 512 KiB limit.
- **Updating them.** When a change makes a transcript or the log differ, the scenario fails with a diff and the run writes what it saw to a private folder outside the repository (`Received:` in the output; `sh proctor/env/run.sh --received <new folder>` picks it). Run twice into two folders and `diff -r` them: a difference between the two runs needs a scrub rule, not an approval. Read each received file: it must hold no token, page key, host secret or path into a person's folder (`run.sh`'s scrub check reads only the report and the engine's log, not the received folder). Then `proctor approve <ids>` (or `--all`) shows each diff, asks, and writes it under `proctor/approved/`; without a terminal it needs `--yes`, and it refuses in CI, after a change to the specifications or `proctor.yaml` since the run, and for a scenario that failed on its own. `proctor approve` approves nothing: the approval that counts is the owner's code-owner review of the change that carries the files, so the change's description says why each one changed.
- **Timing.** The engine's log reaches `engine.log` through `docker compose logs -f`, and Proctor waits 300 ms after a scenario's last step before it closes the scenario's log window. REP-001's log ends with `sandbox check event=check-passed`, from the recheck the engine starts in the background when a host's token is saved (`repos.OnHosts` in `cmd/server/server.go`), about 20 ms after the save and the scenario's last request; on 2026-11-19 it fell inside REP-001's window in every run. If `log_changed` shows only that line or another moving between REP-001 and REP-002, the window raced: that is a finding to fix in the scenario or the log follower, not a change to approve.

## Mutants

- **What they are.** `mutants.yaml` lists mutants, each an exact edit of the engine's code that a specification should catch (Proctor's mutation testing). `proctor.yaml`'s `mutation:` declares it, with `up: env/mutant-up.sh`, `down: env/mutant-down.sh` and `binding: /tmp/sf-proctor/binding.yaml`, so Proctor reads it as a protected input rather than an unlisted specification (INT-05, which fails an authoritative run), `proctor validate` checks each edit's file (tracked, and not a protected input) and each `line` an edit gives, and `proctor diff` reports a removed or changed mutant, or a changed `mutation:`, as a weakening.
- **Keeping them applying.** `validate` doesn't check a `find` that comes without a `line`, and none here has one: after a change to a file a mutant edits, check that its `find` still appears exactly once (or `count` times), since one that no longer matches is an ERROR when it runs, never a kill. Update a `find` that drifted to the new text and keep what the mutant breaks; never delete a mutant or change what it breaks to make it apply.
- **Running them.** `proctor mutate` can't run them yet: Proctor reads the identities' keys from its own environment, set before its first `up`, while each start of this stack signs in anew with new keys. So `env/mutant-up.sh` refuses with that reason and `env/mutant-down.sh` has nothing to stop. Run a mutant by hand: apply its edit to your working tree, run `make proctor`, check that a scenario fails (one its `killed_by` names, when it names any), and undo the edit.

## What the specifications can't check

These stay hand checks, with curl or in [Hand checks for the gate and reviews](gate-hand-checks.md):

- The 15-minute and 24-hour expiry, so the 401's `why: ended`: they would end the run's key. The specifications pin the other two answers: `why: replaced` for the `replaced` variant (SEC-T16, SEC-T16R, EVS-012, CRD-003), and `{"error":"token","message":"The page's key is missing or isn't one the engine issued. Reload the page to sign in."}` with no `why` for no key, a key the engine never issued and a key under another scheme (SEC-T01, SEC-T01R, SEC-T15, SEC-T15R, CRD-T01, EVS-T01, EVS-001, EVS-002).
- Two `Origin`, `Authorization`, `Content-Type`, `X-SF-Session` or `X-SF-Name` headers, a bare `?` with no query, and a `Content-Length` other than the body's own, so a chunked body over a limit that only `http.MaxBytesReader` refuses: Proctor sends one value per header and the body's true length.
- `/api/import`'s archive checks and a successful import: the engine refuses every import with 409 `not empty` before reading its archive while it holds a project, which `up.sh` adds before any suite and every later suite needs, and a successful import restarts the engine.
- The `/api/screenshot` rows that need a file in the session's screenshots folder.
- Anything that needs a commit in a session: `/api/file` and `/api/file-check` with a `commit` (whose `unread` adds `large` and `binary`, and never holds a secret-looking name, which isn't looked up at a commit), a held push and its decision, locking tests at a head and `changed`, `viewed` then stale, Restore branch, reviews and their verdicts, such as a reviewer's read outside its review folder, which loses only a pass (mutants SESS-930 to SESS-934, checked by hand in [Hand checks for the gate and reviews](gate-hand-checks.md)). The fake ACP agent commits only a `commit:` or `remove:` line's change and the Incident fix, never a workflow document of its own, and no scenario goes on from them to a test lock or a review; GATE-060 and GATE-018 push only to pin a hold before the reviews and the refusal of workflow documents. So `/check`'s `guarded` answer is specified only as `""`: the `protect` list, locked tests and Proctor's own files under `proctor/` and the root `Makefile` are guarded only once main or the session's branch holds what they need (`gate.yaml`'s GATE-002 pins the last while this project doesn't use Proctor).
- Parts of the workflow documents rule (the owner's decisions REQ-49 and REQ-51): a push that only deletes workflow documents, which is allowed, since it needs main to hold `.knackpack/` and the dev git host's `demo` doesn't; a pack's own documents folder, which needs a session on a pack that writes documents; a push of more than 1,000 commits, which the engine refuses since it reads only the first 1,000 (mutant SESS-768); an approved document that's then missing or unreadable, which keeps its approval on the engine's copy (D1, mutant SESS-769), since the fake can't delete or corrupt a file in `$SF_DOCS`; an approval kept across an engine restart, since a run can't restart the engine (GATE-019 checks a Stop and a Wake); and that reviews, compaction and the pull request read the engine's copy, since no specification reaches a review ([Hand checks for the gate and reviews](gate-hand-checks.md)).
- The Execution path while the agent works on a later step than the first one not done (Plan started by a typed command before Define's brief is approved, or reviews running before Implement is done): the earlier step's `waiting` state and its **Waiting for your approval** or **Not done** status, and the step card on the later step. The fake agent ends each scripted turn at once and sets no step while it stalls, so no read sees it busy on Plan.
- The rest of the Execution path while the agent works (the owner's decision REQ-60). EVS-026 pins it on Define only, with a background subagent that outlives the turn: the path's `busy`, no Continue defining and no press hint until the subagent ends. It reads the path within the fake's 3 seconds (`backgroundAgent` in `dev/fakeacp`), so a slow stack fails it rather than passing it. Not pinned: busy from a compaction, which the fake can't start; Plan's Start, the Incident steps, Fix and Write the incident review held back while the agent works, and their press hints, since no scenario reaches those steps with a subagent running; and the page showing the documents as drafts with no Approve while `busy` holds, which is the page's own drawing.
- The first message's label (the owner's decision REQ-55) on a prompt the agent reports as its own: the engine labels only prompts from the page or the history (`stepShown` in `internal/core/session/firststep.go`), but the development agent's bridge reports every prompt as from the page and Proctor can't reach the agent listener, so EVS-019 and EVS-020 can't catch SESS-792; it is read from the code.
- A diagnostics text that leaks a token, a prompt, log text, or a name, host or path DGN-001's `excludes` doesn't list: only reading the file the page shows finds those.
- A reviewer container's recipe (its user, its own internal network, its snapshot mounted read-only): no specification reaches a review, so `stack.yaml` asserts only that none is left over.
- Verification runs, beyond SES-004 and the refusals: SES-004 sets a check command and the helper's own image, pinned by its image ID (`proctor@${helper_image}`, read from the helper's container, since no image on the Proctor host has a repository digest a specification knows), runs a pass and a failure on the session's start commit, reads the run's container with the docker driver while it runs (no network, read-only root, user `10006:10006`, only `/in` mounted, read-only) and its result, and clears the commands again. These stay hand checks ([Hand checks for the gate and reviews](gate-hand-checks.md)): a push held for a run, since the team file's `verify` must be committed to the dev git host's main, which no specification can write; a timeout, which takes `SF_VERIFY_MINUTES` (at least a minute, and 15 on this stack); out of memory, which needs a smaller `SF_VERIFY_MEMORY` than the stack sets; an engine restart mid-run, which would end the run's key; the isolation from inside the container (`docker exec` and a commit, which the fake can't make); and a refused tree, which needs a commit.

Gate hand checks' first block covers the listener.
- The check-only key across containers, and after its session: `FromBox` refusing it from another container needs a second container on the pool of one, and nothing outside the fake holds the key, so neither a specification nor a hand check can send an old or another container's key; these are read from `registry.go` only.
- That Claude Code's own `Skill` call of Define doesn't count as Define having run, and that the plugin passes a wrapped Define command's attached files on: the development agent's tool calls can't name `Skill`, and Proctor's stack runs the fake, not the plugin ([Hand checks with Compose](compose-hand-checks.md)).
- A card that asks (`waits`, `irreversible`, `guarded`): the fake reports it as asked and writes nothing, and no specification answers a card. Its id is only in the event stream's frames, which a specification can now read; none reads a card yet.
- A grant whose host becomes a git host after it was given, which the engine takes back within 15 seconds, and the saved credentials, presets, actions and grants it drops at a start for opening a git host: the first needs a git host token saved for another host, or a project added, while a session runs, which changes `/api/projects` for every later suite and starts a sandbox recheck, and the second an engine restart. - A session whose container ran out of memory (the owner's decision REQ-78): the engine reads the container's out-of-memory kills from agent-host's `/v1/memory` only when a Claude Code background session's listing shows it gone, which the development agent, an ACP session, never reaches, and the fake can't run out of memory.
