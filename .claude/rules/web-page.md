# Page modules and stylesheets

- The page's modules live only in `web/`, `web/components/` and `web/lib/`, are named like `^[a-z][a-z0-9-]*\.ts$`, and import each other by exact relative path with the `.ts` extension. `internal/adapters/http/page/assets.go` serves only those folders and `web/styles/`, and only names like `^[a-z][a-z0-9-]*\.(js|css|svg)$`, so a module anywhere else, named otherwise or imported without its extension 404s in the browser and blanks the page while `tsc` still passes; `make web-arch` catches it.
- The stylesheets' layout is read by code, so keep it: each theme in `web/styles/themes.css` starts on a line of its own as `[data-theme="<id>"] {` (one selector, not indented) and sets `--label` and `--default`; each text size starts a line as `:root[data-scale="<percent>"]`. The engine finds themes and sizes with those patterns (`internal/adapters/http/page/assets.go`, `themeRule` and `scaleRule`) and refuses to save any other, and `web/lib/prefs.ts` matches the same selectors exactly. A theme written another way, such as in a selector list, silently drops out of the picker.
- The page meets WCAG 2.2 Level AA: every Level A and AA success criterion holds for each part of the page, in every theme and text size, such as Reflow (1.4.10) at 320 CSS pixels wide, Focus Order (2.4.3) and Status Messages (4.1.3), and a review grades the page's accessibility findings against it. Reason: the owner's decision of 2026-11-17, so the page has one stated target that a change is checked against and every reviewer grades by, instead of each choosing its own.
- **The page is only a presentation layer; the engine's API holds every rule.** Another UI could replace the page without losing any behavior. The page lays out and renders what the engine sends, manages focus, keyboard and ARIA, formats numbers and dates for display, keeps view state (open panels, drafts, scroll, theme, text size) and sends what the person typed as typed. It doesn't decide what's allowed or what happens next, compute values the engine could give it, compose messages to agents, or word a decision; a new rule goes in the engine and reaches the page through the API. Reason: the owner's decision of 2026-11-20.
- **All validation of what a person enters is the engine's.** The page checks nothing before sending: every form has `novalidate` and no `required`, `pattern`, `minlength`, `maxlength`, `min`, `max` or `checkValidity`/`reportValidity`/`setCustomValidity`, and no TypeScript check of empty, length, format or size; it sends the request and shows the engine's answer as text. An answer about one field goes in red beside that field's visible label with `labelError` in `web/lib/dom.ts`, which marks the field `aria-invalid` and describes it by the error, so every form looks the same (the owner's decision of 2026-11-20); a field with no visible label gets one. Any other answer goes in the line under the form. A required field carries `aria-required="true"` instead of `required`, so assistive technology still announces it. A new limit or format goes in the engine (core, or the page adapter for wire format) with its Proctor rows, never only in the page. Page code that isn't validating input stays: a button disabled while its request runs, a confirm step, parsing the engine's answers. Reason: the owner's decision of 2026-11-20, so there is one set of rules, the engine's, which the page can't drift from and other clients can't skip.
