# Page modules and stylesheets

- The page's modules live only in `web/`, `web/components/` and `web/lib/`, are named like `^[a-z][a-z0-9-]*\.ts$`, and import each other by exact relative path with the `.ts` extension. `internal/adapters/http/page/assets.go` serves only those folders and `web/styles/`, and only names like `^[a-z][a-z0-9-]*\.(js|css|svg)$`, so a module anywhere else, named otherwise or imported without its extension 404s in the browser and blanks the page while `tsc` still passes; `make web-arch` catches it.
- The stylesheets' layout is read by code, so keep it: each theme in `web/styles/themes.css` starts on a line of its own as `[data-theme="<id>"] {` (one selector, not indented) and sets `--label` and `--default`; each text size starts a line as `:root[data-scale="<percent>"]`. The engine finds themes and sizes with those patterns (`internal/adapters/http/page/assets.go`, `themeRule` and `scaleRule`) and refuses to save any other, and `web/lib/prefs.ts` matches the same selectors exactly. A theme written another way, such as in a selector list, silently drops out of the picker.
- The page meets WCAG 2.2 Level AA: every Level A and AA success criterion holds for each part of the page, in every theme and text size, such as Reflow (1.4.10) at 320 CSS pixels wide, Focus Order (2.4.3) and Status Messages (4.1.3), and a review grades the page's accessibility findings against it. Reason: the owner's decision of 2026-11-17, so the page has one stated target that a change is checked against and every reviewer grades by, instead of each choosing its own.
- **The page is only a presentation layer; the engine's API holds every rule.** Another UI could replace the page without losing any behavior. The page lays out and renders what the engine sends, manages focus, keyboard and ARIA, formats numbers and dates for display, keeps view state (open panels, drafts, scroll, theme, text size) and sends what the person typed as typed. It doesn't decide what's allowed or what happens next, compute values the engine could give it, compose messages to agents, or word a decision; a new rule goes in the engine and reaches the page through the API. A Save the engine finds changes nothing gets its "No change" warning (`message` with `tone` `warn`, still 200), never the page's own "Saved": a component shows a successful save's `message` with `savedTone()` from `web/api.ts` (the owner's decisions REQ-41 and REQ-45), in a toast with `toast()` from `web/components/toasts.ts`, as it does the outcome of any action that went through, with one `id` per form or panel so a repeated save replaces its toast; a refusal stays at the form, by the field's label or in the line under the form (the owner's decision REQ-132). A modal dialog keeps its outcomes in its own line, since `showModal()` leaves the toasts behind its backdrop and inert. Reason: the owner's decision of 2026-11-20.
- **Every form and dialog is built by one wrapper, so they all look and space the same, and a change to their spacing is made once.** A form is built with `web/lib/form.ts`: `form()` makes the `<form>` (with `noValidate` and its submit handler), `field()` each labelled control, a checkbox or radio included, `fieldRow(…, 'halves')` two fields side by side at half the width each, wrapping under each other when the dialog is too narrow (the owner's decision REQ-69), and `actions()` the row of buttons, the submit button last and filled (`primary`), whatever the form or dialog (the owner's decision REQ-131), except a decision for the person to weigh (Allow it, Override, a lesson's Approve), which stays plain so the page doesn't push one answer, which starts further below the last field (1.25rem) than one field sits below the next (.5rem), so the buttons read as their own group (the owner's decision REQ-61). Their spacing (between fields, label to control, before the actions) lives only in the form rules of `web/styles/app.css`. A component never creates a `<form>` or a control's `<label>` itself, or adds spacing of its own to a form, field or actions row; `make web-check` fails if it does. Every control comes from one helper per kind in `web/lib/controls.ts`: `textbox()` (text, url, email, search, password, number), `textarea()`, `dropdown()` with `option()` and `optionGroup()`, `checkbox()`, `radio()` and `filePicker()`. Every text box and drop-down has one size, the compact one, set only in `web/styles/app.css` (`--compact-*`: 28px tall, .8125rem text, 4px corners), stacked, side by side or in a toolbar, and every small button and every button in a form's or dialog's button row (`actions()`) is as tall, with the same text size and corners, from the same `--compact-*` values (the owner's decisions REQ-52 and REQ-74: "Everything needs to be in compact no matter what"); a component never sizes a control itself, except the composer's message box, which keeps its own look. A field's border stays 1px in every state: focus turns it the accent color and an error red, with no thicker ring (the owner's decision REQ-55); the transparent focus outline stays for forced-colors mode. `make web-check` fails on an `input`, `select`, `textarea`, `option` or `optgroup` created anywhere else. Every control whose value is sent sits in a form, so Enter submits it. A dialog is built with `modal()` in `web/lib/dialog.ts`, which places its title, its **View in docs** link and its buttons, with the same space between the title and the first paragraph in every dialog. Any heading with a paragraph right below it (a dialog's title row, a page's heading row, a section heading; a list, or a block that starts with a paragraph, counts as one) sits `--heading-gap` (.25rem, about 8px text to text, still more than the paragraph's own lines; the owner's REQ-64 and REQ-65 took 4px off) above the paragraph's first line, clearly more than the paragraph's own lines are apart (about 7px), so the heading stands apart: the shared rules at the end of `web/styles/app.css` drop the heading's margin and the row's 24px minimum there and add that gap, and let the **View in docs** link and a dialog's close button keep their click area without pushing the paragraph further (the owner's decision REQ-60); a list right under a heading or a `pageHead()` intro line drops its first row's top padding, so the intro sits as far above the first row's text (.75rem) as above a form's first label (REQ-155); a bordered button, in a heading row or at the end of a `.text-row`, keeps its full height so nothing touches it (REQ-109). A button in a heading row (Reviews, the gateway's Remove gateway, any `pageHead()` action) stays in the row at its full height, and the first line sits `--heading-gap` below the row's lowest edge, the button's border when it is taller than the heading, so nothing touches; a row whose buttons wrap keeps .5rem between button lines; the borderless **View in docs** link takes no extra height and, beside an action, sits just before it at the row's end (REQ-109). A section heading (`h2.label`, `h3`, `h4`, a row holding one, a block whose first child is one or a `summary.label` (the Welcome page's session groups), or whose first child's first child is an `h3` or `h4`, unless the block is a bordered box such as a card, a dialog or popover, or a side-panel section) that follows anything but hidden elements sits `--section-gap` (1.375rem, about 23px from the content above to the heading's text; REQ-66 took 2px off), less .1875rem after text (a paragraph, a list without buttons, a closed disclosure, or a block that ends in one; an empty status line in between is skipped; a list in a bordered box, such as a session table, is a box, not text), whose own line spacing adds that much below its text, so the space looks the same after text as after a field or a button (REQ-67), and less .05rem right after another heading, whose text sits that much high in its line (REQ-109), clearly more than the gap under it, so it belongs to the text it heads. Inside a form's grid the heading takes the grid's gap off; the side panel's sections sit `--section-gap` apart from the bottom. A component sets no margin on its headings, on the block that starts with one, or below a block a heading follows: only the shared rules do (REQ-104). A component doesn't centre or right-align its own pieces either: a line of text with its button at the right end is a `.text-row` (`.row.text-row`: the text, a `.spacer`, the button), a row of form or dialog buttons is `actions()`, and anything else stacks to the left; only what is centred by design stays centred (the Projects first-run panel, the page-gone card, keys, badges, counters, diff signs, Markdown table cells marked center) (REQ-109). Rendered Markdown keeps its own heading spacing (the owner's decision REQ-62). Every dialog, a confirmation included, links to the docs section that explains it: `modal()`'s `docs` and `confirmDialog()`'s second argument are a required section id (the slug of a README heading between "What you need" and "Development"), so `tsc` fails on a dialog without one; the link closes the dialog and `app.ts` opens that section. A dialog or page heading links to the section titled exactly like it, a varying title to the section titled with its fixed part ("Sign Claude Code in for this session"), and a confirmation, whose title is a question or sentence, to the section about its topic (the owner's decisions REQ-79 and REQ-82). Each section a dialog's link, or a link beside a heading inside the dialog, opens shows **Open** and the dialog's title beside its heading, which opens that dialog (REQ-81): `web/lib/dialog-docs.ts` lists those dialogs, each with its title and the headings inside it that link to the docs; the dialog takes its title and docs id from there with `dialogDocs()`, so the two can't drift; `docs.ts` adds the button with `dialogLink()` to the sections they name; and `palette-items.ts` holds one opener per dialog in a `Record<DialogName, …>`, so `tsc` fails on a listed dialog without one, which `app.ts` runs on the button's click. A dialog whose title varies, or that needs a session or a release to show, isn't listed and gets no button, and neither do confirmations. The one exception is the command palette, which passes `docs: false` and shows no link (the owner's decision REQ-48: it's a search box, not something to read about). Reason: the owner's decision of 2026-11-21 ("consistency matter"), and for controls REQ-49, after the arcauthic client's `Input` and `Form*` components.
- **Repeated pieces come from one helper each, never built by hand.** A page's or panel's heading row (title, an optional one-line intro, an optional **View in docs** link or action) comes from `pageHead()` in `web/lib/page.ts` (on the project settings page every heading, a part's `h3` sub-heading too, has its intro, its **View in docs** link and a README section of its own, the owner's decision REQ-149; the page has no group headings, so each part's heading is an `h2` and its sub-headings `h3`, and its Contents list is flat, one entry per part, REQ-161), an empty list's message from `emptyState()` there, one plain muted line with no box, right under the sentence before it (only the Projects page's first-run panel, with a title, an icon and an action, keeps a box; the owner's decisions REQ-83, REQ-84 and REQ-87), and a checklist row (a status mark that isn't colour alone, a short label, a muted value, an optional action at its end) from `checkRow()` there, a set of numbers as label/value pairs from `factGrid()` there, a value whose detail belongs in the shared tooltip from `tipText()` in `web/lib/tooltip.ts` (REQ-159), a usage figure such as the workspace volume from `usageMeter()` there, a card with a label, the percent used, a bar that turns the warning color when the engine says it is low, and the amounts below (REQ-88). A short description that belongs to a label or tag shows in the shared tooltip, `tooltip()` or `tipTag()` in `web/lib/tooltip.ts`, which opens on hover, keyboard focus and tap, never as a `title` attribute or a line of text under it (the owner's decision REQ-98). A progress figure, such as a clone's, is the `sf-progress` element of `web/components/progress.ts`, on the native `<progress>`: fed a percent (none draws a moving bar, which stands still under reduced motion) and the engine's words, which are also its `aria-valuetext`, it draws only those and announces nothing as they change (REQ-119). A required field carries no mark; an optional one gets a muted "(optional)" from `field()`'s `optional` option, never typed into its label. Every dialog closes on a click outside it unless a control in it has been changed, which `modal()` decides for all dialogs; typing in a dialog that only searches, such as the command palette (`searchOnly`), isn't a change. A docs section's **Open** button comes from `dialogLink()` there. `make web-check` fails if `page-head`, `page-intro`, `docs-link`, `docs-open`, `empty-state` or "View in docs" appears in a page module or `index.html` other than `web/lib/page.ts`. Reason: the owner's decision of 2026-11-21, taken from the arcauthic client's `PageHeader`, `EmptyState`, forms and dialog rules, so each piece looks and behaves the same everywhere and changes in one place.
- **No refresh buttons: every view loads when it opens and refreshes by itself, by cost, through `whileOpen()` in `web/lib/refresh.ts`**: engine reads every 5 seconds while open (`CHEAP_EVERY_MS`), file walks and disk measurements every 30 (`WALK_EVERY_MS`), git host reads once each time the view opens, and Diagnostics built once per opening; it redraws only when the answer changed, keeps focus and scroll, skips a view whose form holds unsaved input, and never polls a route that writes (the owner's decision REQ-86).
- **Every request to the engine goes through `web/api.ts`, with the browser's own `fetch`; no HTTP library such as axios.** `request()` there sends it with the page key and `no-store` and reads the answer once into `{ok, status, error, field, message, body}`, with one wording when the engine doesn't answer and one when a refusal isn't a JSON object with a `message` (a proxy's error, a cut-off body); the form wrapper shows `field` beside its label and any other `message` under the form. Every refusal the engine sends carries `message` in words, so a component shows it as it is and never falls back to words of its own (`a.message || '…'`, a `fallback` to `showAnswer`); `make web-check` fails on the forms it can match, `message`, `said` or `Message` followed by `||` or `??` and a value, a ternary on one, and a `fallback:` option (the owner's decision REQ-40). A component never calls `fetch` or reads an engine answer's JSON itself; `make web-check` fails if it does. The one other `fetch` is `stream.ts` loading its own module to notice an engine restart. Reason: the page has no runtime dependencies and no bundler (`tsc` output is served as is, and `assets.go` serves only `web/`'s own modules), so a library would need a bundler or a vendored copy; the live event stream reads `fetch`'s streamed body; a refusal is data the form shows, not an exception; and each npm package is supply-chain risk in the code that holds the page key (axios 1.14.1 and 0.30.4 shipped a remote access trojan on 2026-03-31). The owner left the choice to Claude on 2026-11-21.
- **All validation of what a person enters is the engine's.** The page checks nothing before sending: every form has `novalidate` and no `required`, `pattern`, `minlength`, `maxlength`, `min`, `max` or `checkValidity`/`reportValidity`/`setCustomValidity`, and no TypeScript check of empty, length, format or size; it sends the request and shows the engine's answer as text. An answer about one field goes in red, in brackets, after that field's visible label with `labelError` in `web/lib/dom.ts` ("Host (Needs a host like …)"), in every form, a side-by-side row included, so every form looks the same; it takes the place of a muted "(optional)" while it shows, clears as soon as the person types in or changes that field, marks the field `aria-invalid` and describes it by the error (the owner's decision REQ-56, after the arcauthic client's labels, which keep the form from reflowing on submit); a field with no visible label gets one. Any other answer goes in the line under the form. Every engine answer about one field carries `field`, and its `message` doesn't start with the field's name, since the page shows it in brackets after the label: "Name (Needs 1 to 100 characters)", not "Name (The name agents commit with needs 1 to 100 characters)". Its `message` is one short clause of at most 60 characters saying what the field needs (`Email (Needs an address like you@example.com)`), with no list of examples and no reason: those go in the form's own text (the owner's decision REQ-46). `make files` fails on a longer literal ([Page server](page-server.md)). A required field carries `aria-required="true"` instead of `required`, so assistive technology still announces it. A new limit or format goes in the engine (core, or the page adapter for wire format) with its Proctor rows, never only in the page. Page code that isn't validating input stays: a button disabled while its request runs, a confirm step, parsing the engine's answers. Reason: the owner's decision of 2026-11-20, so there is one set of rules, the engine's, which the page can't drift from and other clients can't skip.
