# Page modules and stylesheets

- The page's modules live only in `web/`, `web/components/` and `web/lib/`, are named like `^[a-z][a-z0-9-]*\.ts$`, and import each other by exact relative path with the `.ts` extension. `internal/adapters/http/page/assets.go` serves only those folders and `web/styles/`, and only names like `^[a-z][a-z0-9-]*\.(js|css|svg)$`, so a module anywhere else, named otherwise or imported without its extension 404s in the browser and blanks the page while `tsc` still passes; `make web-arch` catches it.
- The stylesheets' layout is read by code, so keep it: each theme in `web/styles/themes.css` starts on a line of its own as `[data-theme="<id>"] {` (one selector, not indented) and sets `--label` and `--default`; each text size starts a line as `:root[data-scale="<percent>"]`. The engine finds themes and sizes with those patterns (`internal/adapters/http/page/assets.go`, `themeRule` and `scaleRule`) and refuses to save any other, and `web/lib/prefs.ts` matches the same selectors exactly. A theme written another way, such as in a selector list, silently drops out of the picker.
- The page meets WCAG 2.2 Level AA: every Level A and AA success criterion holds for each part of the page, in every theme and text size, such as Reflow (1.4.10) at 320 CSS pixels wide, Focus Order (2.4.3) and Status Messages (4.1.3), and a review grades the page's accessibility findings against it. Reason: the owner's decision of 2026-11-17, so the page has one stated target that a change is checked against and every reviewer grades by, instead of each choosing its own.
- **The page is only a presentation layer; the engine's API holds every rule.** Another UI could replace the page without losing any behavior. The page lays out and renders what the engine sends, manages focus, keyboard and ARIA, formats numbers and dates for display, keeps view state (open panels, drafts, scroll, theme, text size) and sends what the person typed as typed. It doesn't decide what's allowed or what happens next, compute values the engine could give it, compose messages to agents, or word a decision; a new rule goes in the engine and reaches the page through the API. A Save the engine finds changes nothing gets its "No change" warning (`message` with `tone` `warn`, still 200), never the page's own "Saved": a component shows a successful save's `message` with `savedTone()` from `web/api.ts` (the owner's decisions REQ-41 and REQ-45). Reason: the owner's decision of 2026-11-20.
- **Every form and dialog is built by one wrapper, so they all look and space the same, and a change to their spacing is made once.** A form is built with `web/lib/form.ts`: `form()` makes the `<form>` (with `noValidate` and its submit handler), `field()` each labelled control, a checkbox or radio included, and `actions()` the row of buttons, the submit button last. Their spacing (between fields, label to control, before the actions) lives only in the form rules of `web/styles/app.css`. A component never creates a `<form>` or a control's `<label>` itself, or adds spacing of its own to a form, field or actions row; `make web-check` fails if it does. Every control whose value is sent sits in a form, so Enter submits it. A dialog is built with `modal()` in `web/lib/dialog.ts`, which places its title, its **View in docs** link and its buttons, with the same space between the title and the first paragraph in every dialog. Every dialog, a confirmation included, links to the docs section that explains it: `modal()`'s `docs` and `confirmDialog()`'s second argument are a required section id (the slug of a README heading between "What you need" and "Development"), so `tsc` fails on a dialog without one; the link closes the dialog and `app.ts` opens that section. Reason: the owner's decision of 2026-11-21 ("consistency matter").
- **Repeated pieces come from one helper each, never built by hand.** A page's or panel's heading row (title, an optional one-line intro, an optional **View in docs** link or action) comes from `pageHead()` in `web/lib/page.ts`, and an empty list's message from `emptyState()` there. A required field carries no mark; an optional one gets a muted "(optional)" from `field()`'s `optional` option, never typed into its label. Every dialog closes on a click outside it unless a control in it has been changed, which `modal()` decides for all dialogs; typing in a dialog that only searches, such as the command palette (`searchOnly`), isn't a change. `make web-check` fails if `page-head`, `page-intro`, `docs-link`, `empty-state` or "View in docs" appears in a page module or `index.html` other than `web/lib/page.ts`. Reason: the owner's decision of 2026-11-21, taken from the arcauthic client's `PageHeader`, `EmptyState`, forms and dialog rules, so each piece looks and behaves the same everywhere and changes in one place.
- **Every request to the engine goes through `web/api.ts`, with the browser's own `fetch`; no HTTP library such as axios.** `request()` there sends it with the page key and `no-store` and reads the answer once into `{ok, status, error, field, message, body}`, with one wording when the engine doesn't answer and one when a refusal isn't a JSON object with a `message` (a proxy's error, a cut-off body); the form wrapper shows `field` beside its label and any other `message` under the form. Every refusal the engine sends carries `message` in words, so a component shows it as it is and never falls back to words of its own (`a.message || '…'`, a `fallback` to `showAnswer`); `make web-check` fails on the forms it can match, `message`, `said` or `Message` followed by `||` or `??` and a value, a ternary on one, and a `fallback:` option (the owner's decision REQ-40). A component never calls `fetch` or reads an engine answer's JSON itself; `make web-check` fails if it does. The one other `fetch` is `stream.ts` loading its own module to notice an engine restart. Reason: the page has no runtime dependencies and no bundler (`tsc` output is served as is, and `assets.go` serves only `web/`'s own modules), so a library would need a bundler or a vendored copy; the live event stream reads `fetch`'s streamed body; a refusal is data the form shows, not an exception; and each npm package is supply-chain risk in the code that holds the page key (axios 1.14.1 and 0.30.4 shipped a remote access trojan on 2026-03-31). The owner left the choice to Claude on 2026-11-21.
- **All validation of what a person enters is the engine's.** The page checks nothing before sending: every form has `novalidate` and no `required`, `pattern`, `minlength`, `maxlength`, `min`, `max` or `checkValidity`/`reportValidity`/`setCustomValidity`, and no TypeScript check of empty, length, format or size; it sends the request and shows the engine's answer as text. An answer about one field goes in red beside that field's visible label with `labelError` in `web/lib/dom.ts`, which marks the field `aria-invalid` and describes it by the error, so every form looks the same (the owner's decision of 2026-11-20); in a side-by-side row (`fieldRow()` or `form({inline: true})`) the error goes instead on a line of its own under the row, the row's full width, after the label's text ("Host (…)"), so a long error doesn't squeeze the label into a narrow column; a field with no visible label gets one. Any other answer goes in the line under the form. Every engine answer about one field carries `field`, and its `message` doesn't start with the field's name, since the page shows it in brackets after the label: "Name (needs 1 to 100 characters)", not "Name (The name agents commit with needs 1 to 100 characters)". Its `message` is one short clause of at most 60 characters saying what the field needs (`Email (Needs an address like you@example.com)`), with no list of examples and no reason: those go in the form's own text (the owner's decision REQ-46). `make files` fails on a longer literal ([Page server](page-server.md)). A required field carries `aria-required="true"` instead of `required`, so assistive technology still announces it. A new limit or format goes in the engine (core, or the page adapter for wire format) with its Proctor rows, never only in the page. Page code that isn't validating input stays: a button disabled while its request runs, a confirm step, parsing the engine's answers. Reason: the owner's decision of 2026-11-20, so there is one set of rules, the engine's, which the page can't drift from and other clients can't skip.
