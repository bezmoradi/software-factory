The page is published on 127.0.0.1:7799 (SF_PORT changes it):

```bash
docker compose up -d --build --remove-orphans && docker compose ps   # all healthy
docker ps --filter label=dev.software-factory.stack=software-factory   # one container per running session, <project>-box-<box>
docker exec software-factory-box-<box> curl -sS https://github.com         # refused by the proxy (403)
docker exec software-factory-box-<box> curl -sS -o /dev/null -w '%{http_code}\n' https://api.anthropic.com   # any HTTP status

docker inspect software-factory-box-<box>                    # the recipe: read-only root, CapDrop ALL, no ports, no binds, its own network only
docker network inspect software-factory-box-<box>            # internal, no IPv6, gateway_mode_ipv4=isolated, engine .2, egress .3, box .4
docker exec software-factory-box-<box> curl -sS --noproxy '*' -m 3 https://helper:8099/healthz   # doesn't resolve: the helper shares no network with a session
docker compose stop helper && docker ps --filter label=dev.software-factory.stack=software-factory   # no session container left
docker compose logs helper | grep -E 'action=(create|start|stop|remove)'   # each operation with box, recipe hash and outcome, never a key

docker compose logs helper | grep verifier                   # each start, kill_overdue and remove with run, digest, recipe hash and outcome, never the command
```

`make proctor` checks the `docker inspect` and `docker network inspect` lines for a session's container and the Compose services with Proctor's docker driver (`proctor/specs/stack.yaml`, SES-001; [Proctor's specifications](proctor.md)); the `docker exec` lines, reviewer containers and verification containers stay by hand; STK-004 checks that none of the last is left over.

**Run the live checks on your own Docker, with your Software Factory stopped.** The owner chose this over Docker-in-Docker on 2026-11-17 and accepted the risk. The helper creates and removes containers, networks and volumes, and acts only on those carrying its stack's label, so a defect in it, or in a check, could still reach your other projects on that Docker. Stop your own stack first (`docker compose -p software-factory down`; its volumes stay), then start the development overlay as CLAUDE.md says, with `SF_DOCKER_GID` set as `make up` sets it, on the `127.0.0.1` port it publishes. Make the first start after a change to the helper a dry run, `SF_BOX_SWEEP_DRY=1`, and read what its start-up sweep would remove before you start without it. Docker Desktop can't add a runtime, so gVisor checks need a Linux host with `runsc` installed and registered. To set it up, extract `runsc` from the release's `gvisor.tar.bz2` after `sha512sum -c` of the `.sha512` beside it, run `runsc install`, then send `dockerd` a SIGHUP (`kill -HUP`), which loads the new runtime without a restart (checked with Engine 29.9.3). The release's Compose files can be tried the same way. Push the image to a `registry:2` container on `127.0.0.1:5000`; Docker talks plain HTTP to a registry on `127.0.0.1` by itself. For benchmarks the dev git host fakes merged pull requests: the pull request list with `state=closed` and `GET /repos/dev/demo/pulls/<n>` carry `merged_at`, `merge_commit_sha` and the base's `sha`. `merged <title> <body>` commits a file on a new branch from main, merges it into main with a merge commit, and records it as a merged pull request, printing its number. It keeps the ref `refs/sf-bench/<number>/base` at the pull request's base, because the dev git server serves commits only by ref, not by hash as GitHub does; `merged-token <title>` does the same with a description that holds a fake token, built when it runs, so a benchmark from it is refused. `merge <pr>` marks an open pull request merged without changing main, which a benchmark can start from too.
