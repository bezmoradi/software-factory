# CI

The workflows in `.github/workflows/` never push, publish an image or log in to a registry, with one named exception: `release.yml` may log in to GHCR and push the image `ghcr.io/bezmoradi/software-factory`, with its signature and attestations, attest the release's three files, and create the GitHub release with those files, and nothing else. Each sets `permissions: {}` and gives each job only what it needs, checks out with `persist-credentials: false` and has a `timeout-minutes`. Every action is pinned to a commit with its version beside it, every container to a digest, and every download to a version and a SHA-256, except Proctor's in `proctor.yml`, which is the latest release at run time, checked by its signed provenance.

- **`ci.yml`** (CI), on pull requests, pushes to `main`, Mondays at 06:17 UTC (advisories for pinned modules and actions appear without a change here) and by hand. A new push to a pull request cancels its older run. Its jobs, each a required check by its name:
  - **Go**: `go build`, `go vet`, `make lint`, `make arch-check`, `make fix-check`, `make vuln`.
  - **Cross-builds**: `make cross-build`, so files built only on another platform keep compiling. windows/amd64 is left out until `internal/adapters/git/files` and `git/state` build there (they use `syscall.O_NOFOLLOW` and `O_DIRECTORY`); add it to `CROSS_TARGETS` in the `Makefile` then, and the `!unix` files are compiled too.
  - **TypeScript**: `make web-check` and `make plugin-check`, with the Node the Dockerfile's page stage uses.
  - **Plugin**: `claude plugin validate plugin` with Claude Code 2.1.322, the version `internal/adapters/install/npm/versions.go` pins; the job fails when that file pins another. The binary comes from the release the official installer downloads (`downloads.claude.ai/claude-code-releases/<version>/linux-x64/claude`), checked against the SHA-256 in that release's `manifest.json`. The installer itself isn't used, since it first downloads and runs the latest release. No sign-in is needed.
  - **Image**: the `runtime` target for linux/amd64 and linux/arm64 with Buildx, kept in the builder's cache and never pushed. QEMU (`tonistiigi/binfmt`) and BuildKit are pinned by digest; Buildx is the runner's own. It also builds the `dev` and `gitserver` targets for linux/amd64, then loads the `runtime` image and starts `compose.yaml` as the project `sf-ci`, with `SF_DOCKER_GID` set to the group of the runner's Docker socket so the box helper can use it, and waits until every container is healthy.
  - **No comments**: `make no-comments` (`scripts/nocomments`, a Go program in its own module so the layer rules and `./...` don't include it). It reads Go with `go/parser` and the other kinds with small scanners that skip strings, template literals, regular expressions, heredocs and YAML block scalars (it scans the shell in `run:` blocks, Dockerfile `RUN` instructions and Makefile recipes). It allows only the exceptions in `CLAUDE.md`: `//go:`, `//nolint`, `//line` and `// Code generated … DO NOT EDIT.`; `/// <reference>` and `// @ts-…`; a shebang on the first line; `# syntax=`, `# escape=` and `# check=` at the top of a Dockerfile; `# zizmor: ignore[…]` and `# shellcheck` directives; and a `# v…` version comment on a line with a 40-character commit SHA or an `@sha256:` digest.
  - **No tests**: `make no-tests` (`scripts/check-no-tests.sh`) fails on `*_test.go`, `testdata/` and `__tests__/` folders, `*.test.*` and `*.spec.*` scripts, imports of Go's `testing` packages, `httptest` or testify and of `node:test`, and test frameworks in a `package.json`.
  - **Files**: `make files`: nothing over 512 KiB, no CRLF line endings, no conflict markers, no paths that differ only by case, no inline script, style or event handler in `web/index.html`, no Go or TypeScript outside `dev/` that names a credential store, reads a model key variable or runs `git` through `exec.Command`, and no `innerHTML`, `eval` or the like in the page or the plugin; then `scripts/check-refusals.sh`: no refusal the page listener sends without a message in words ([Page server](page-server.md)). Then `make instructions` (`scripts/check-instructions.sh`): each rule file in `.claude/rules/` starts with a `paths:` list of double-quoted globs, each matching a file in the repository, and isn't ignored by git; `CLAUDE.md` links every rule file and no missing one, and stays within `INSTRUCTIONS_MAX_BYTES` in the `Makefile`; and there's no `AGENTS.md` at the root.
  - **Shell**: `make shell`: shellcheck at warning level, POSIX `sh`.
  - **Markdown**: `make markdown`: markdownlint-cli2 with every rule on except line length (MD013, one paragraph per line), `$` prompts (MD014), blank lines around headings and lists (MD022, MD032; GitHub renders them the same), fence languages (MD040, for prompts and plain text), table pipe alignment (MD060), and inline HTML other than the centered banner at the top of `README.md` and `web/docs.md` (MD033).
  - **Spelling**: typos 1.52.0 with `.typos.toml`, whose three words are correct where used: `ue`, a variable in `internal/adapters/git/github/github.go` and `internal/adapters/git/remote/remote.go`, `iy`, a regular expression's flags in `web/components/markdown.ts`, and `assum`, a regular expression's word stem in `internal/core/session/claimpatterns.go`. Its one ignore rule skips PEM blocks, whose base64 in `internal/adapters/install/npm/sigstore.go` reads as words.
  - **Workflows**: `make workflows`: `scripts/check-review-workflow.sh`, actionlint (with ShellCheck on every `run:` step) and zizmor with its default persona, given the job's read-only token so it runs its online audits too, such as known-vulnerable actions and commits no tag holds. The pedantic persona isn't used: it requires a comment on each permission, which `CLAUDE.md` forbids. `.github/zizmor.yml` allows `dangerous-triggers` for `claude.yml` and `workflow-guard.yml`, for the reasons below.
  - **Links**: lychee, offline, over the Markdown files.
  - **Secrets**: gitleaks 8.30.1 over every commit, so a secret removed later still fails. `.gitleaks.toml` adds a rule for the token `claude setup-token` prints, which the default rules miss, and allows two things: the line `GITSERVER_TOKEN: sf-dev-gitserver-token` in `compose.dev.yaml`, the development git server's documented value, and the refused-pack table rows in `proctor/specs/packs.yaml`, each a `pck_` case name, then the 40-character git commit of the development git server's fixture pack, then the message `The engine refused this pack:`. Another value or shape there, or those lines in another file, is still reported. The allowlist names the `generic-api-key` rule because gitleaks skips every file that an allowlist without `targetRules` names in `paths`, whatever its `condition`.
- **`claude-code-review.yml`** (Claude review, then Claude approval). Claude reviews every push to a pull request against `CLAUDE.md` and the rule files in `.claude/rules/`, which the action restores from the base branch before Claude starts (the pull request's own copies go to `.claude-pr/`). Every problem it confirms blocks, however minor: it comments on the lines and returns a verdict, and the job posts one summary comment, edited on each review. The review only reviews: its job has only `contents: read` and `pull-requests: write`, passes `github_token: ${{ github.token }}` (the Claude app's token could push), allows only `gh pr diff`, `gh pr diff --name-only`, `gh pr view` and the inline-comment tool, and denies Edit, Write, MultiEdit and NotebookEdit; `scripts/check-review-workflow.sh` fails if any of that changes or if an option that could commit, push or widen its permissions appears. **Claude approval** fails closed: drafts, forks (which get none of the repository's secrets; push a copy of the branch here instead), and a review that fails, times out or returns no verdict all fail it, and GitHub would count a skipped required check as passing, so it always runs.
- **`claude.yml`** (Claude) answers `@claude` in issues, pull requests and reviews. The action starts Claude only for people with write access, only the owner's comments (`include_comments_by_actor: bezmoradi`) reach its prompt, and on a pull request it restores `CLAUDE.md` and Claude Code's start-up files from the base branch first. It uses the Claude GitHub app's token, which can push branches; the ruleset keeps it off `main`. It passes `--permission-mode acceptEdits`, because claude-code-action v1.0.273 and later start sessions in auto mode, where a safety review can let a tool call run that no allow rule covers; acceptEdits is the earlier mode, the opt-out the action's release notes give for `@claude` mentions. Its comment triggers run with the repository's secrets, which is acceptable because nothing runs the pull request's code.
- **`pull-requests.yml`** (Linked issue) fails a pull request whose description doesn't close an issue (`Closes #12`); editing the description runs it again. Dependabot's pull requests pass: GitHub sets the author's login, so nobody else can claim `dependabot[bot]`.
- **`workflow-guard.yml`** (Workflow guard) fails a pull request that changes `.github/`, `scripts/`, `proctor/`, the `Makefile`, `.golangci.yml`, `.go-arch-lint.yml`, `.gitleaks.toml`, `.typos.toml` or `.markdownlint-cli2.jsonc` until the owner (`bezmoradi`; nobody else's labeling counts) adds the `review-override` label after its latest push. A `pull_request` run uses the pull request's own copy of those files, so such a change could make its own checks pass. The guard runs on `pull_request_target`, the base branch's copy, and only reads the pull request's files, labels, events and runs through the API; it checks out and runs nothing from it. A later push needs the label added again. `proctor/` is guarded because its specifications are the API's checks, and a change could weaken them.
- **`proctor.yml`** (Proctor), on pull requests to `main` when opened, pushed, reopened, labeled or unlabeled (any label, `review-override` included, starts it again); a newer run for the same pull request cancels the older one. It runs Proctor's specifications ([Proctor's specifications](proctor.md)) in authoritative mode on the stack, adapted from Proctor's `examples/github/`, and takes about 40 minutes. Its jobs:
  - **Proctor change kind** (no permissions) maps the pull request's one `proctor:` label (`proctor:refactor`, `proctor:docs`, `proctor:fix` or `proctor:feature`) to Proctor's change kind, which Proctor then checks the protected changes against. No such label passes no kind; two, or one naming no kind, fail the job.
  - **Proctor release** (no permissions) reads the tag of Proctor's latest release once, checks that it is `v<major>.<minor>.<patch>`, and passes it to the later jobs, so a re-run of failed jobs uses the same version; Re-run all jobs reads the latest again. No Proctor version or checksum is written in the workflow (the owner's decision of 2026-11-26, since Proctor releases often), so a new Proctor release can fail a pull request that changed nothing. Then read the failure and Proctor's release notes: fix the specifications, `proctor.yaml` or the scripts in a pull request of their own, never by loosening a check, or report the regression to Proctor; until then every pull request fails.
  - **Proctor build** (`contents: read`) builds the `dev`, `runtime` and `gitserver` targets of the tested commit, GitHub's test merge, as `software-factory-proctor:{dev,local,gitserver}`, outputs each image's ID and uploads them as the artifact `proctor-images`, kept a day.
  - **Proctor run** (`contents: read` for the checkout and Proctor's CODEOWNERS check, `id-token: write` for Proctor's check of the workflow's identity; 75 minutes). It checks that the runner is amd64 with Docker Engine 28 or later, Compose 2.24.4 or later, 7 GiB of memory (GATE-014 runs two 2 GiB session containers beside the stack) and the tools `up.sh` uses; ubuntu-24.04 for a public repository has 4 CPUs and 16 GB, and image 20261116 has Engine 28.0.4 and Compose 2.38.2. It finds the base as the test merge's first parent, after checking that its second is the pull request's head, and takes `proctor/env/`, `proctor/environments/`, `compose.yaml` and `compose.dev.yaml` from the base commit into a folder outside the checkout, refusing anything there that isn't a regular file, a base whose scripts have no authoritative path, and a base whose `up.sh` doesn't take each image's ID (`PROCTOR_SF_BUILT_DEV_DIGEST`, `PROCTOR_SF_BUILT_LOCAL_DIGEST` and `PROCTOR_SF_BUILT_GITSERVER_DIGEST`). It loads the images and checks each ID against the build's. It downloads that tag's archive and `SHA256SUMS`, checks both with `gh attestation verify` against Proctor's `release.yml`, the tag's ref and GitHub-hosted runners, the archive against its line in `SHA256SUMS`, then the archive's own `SHA256SUMS` and `proctor version`, and logs the version and the SHA-256 of the `proctor` it runs. Then it runs the base's `run.sh` with `PROCTOR_SF_AUTHORITATIVE=1`, the three image IDs, `PROCTOR_SF_CHECKOUT` set to the checkout and its state in the runner's temporary folder, passing `--pr-head`, the earlier attempts' reports and the change kind, uploads the report as `proctor-report-<attempt>`, also after a failure, and tears the stack down. So the specifications, `proctor.yaml`, the `Dockerfile` and the code come from the tested commit, and what defines and starts the environment from the base: a change to `proctor/env/`, `proctor/environments/` or the Compose files takes effect here once merged, so merge it first in a pull request of its own that works with the code already on `main`.
  - **Proctor verdict** (no permissions) always runs and fails unless every job above succeeded and this attempt's report is one passing authoritative report for this commit, run, attempt and Proctor version, whose workflow identity Proctor verified with the job's OIDC token. A pull request from a fork gets no OIDC token (GitHub makes its write permissions read-only, and `id-token` has only `write`), so its report says `workflow_identity: unverified` and the verdict fails: push a copy of its branch here instead, as for Claude approval.
  - **What it can't prove.** The box helper mounts the runner's Docker socket, and the pull request's code builds it, so during Proctor run that code is root on the runner (whose user also has passwordless `sudo`). It could read the job's read-only token and its OIDC request token, mint OIDC tokens for this workflow at the pull request's merge ref, and rewrite Proctor, its report or the stack's answers, so a hostile pull request can make the verdict pass. The verdict shows that an honest change keeps the specifications passing; a hostile one is stopped only by the owner's reading of the change. Taking the environment from the base keeps an honest change from weakening how the stack starts and signs in, not a hostile one. The Image job of `ci.yml` already gives a pull request's code the runner's Docker the same way, without an OIDC token. Nothing outside GitHub trusts this workflow's OIDC tokens; keep it so (no cloud role or registry may trust `proctor.yml`). Running the stack in a virtual machine on the runner, with Proctor outside it reaching the page and the machine's Docker socket through forwarded ports, would keep the pull request's code off the runner, at the cost of a pinned machine image, Docker installed inside it, KVM on the runner, and several more minutes a run; it isn't built.
- **`release.yml`** (Release) runs on a pushed tag `vMAJOR.MINOR.PATCH`, in the GitHub environment `release`, which waits for the owner's approval. Its **Release** job (`contents: read`, `packages: write`, `id-token: write`, `attestations: write`) fails unless `github.triggering_actor` is `bezmoradi`, the tagged commit is on `main` (checked out with full history; `git merge-base --is-ancestor`) and the tag is `v` plus `Version` in `cmd/server/server.go`. It installs Compose 5.7.1 by version and SHA-256 as the user's CLI plugin, so the files are rendered by a known Compose rather than whichever the runner has. It refuses a version whose image tag GHCR already holds, and goes on only when the lookup answers `<ref>: not found`: any other error stops it. It builds the `runtime` target for linux/amd64 and linux/arm64 with no cache and without BuildKit's own provenance and SBOM, and pushes it by digest only, with no tag (`push-by-digest=true`), with the `org.opencontainers.image.source`, `.version` and `.revision` labels. It starts that digest on linux/amd64 and on linux/arm64 (under QEMU): `git --version`, `uname -m` matching the platform, and `software-factory` with an unknown role, which must fail with `unknown role`. It then writes the release's files into a folder of their own: `compose.yaml` as committed, `compose.release.yaml` from `scripts/release-compose.sh` with the index digest in place of its placeholder (and fails unless it replaced it), checks the two files' merged configuration with `scripts/release-check.sh` (an allow-list: exactly `egress`, `engine` and `helper`, every one on that digest with only the keys, user and hardening the release allows, only volume and tmpfs mounts, ports on `127.0.0.1` only, default networks and volumes, no `SF_BOX_LIVE` and no `SF_DEV_` setting, the helper on `helpernet` alone; `compose.release.yaml` drops the helper's socket mount and group, which the install's local `software-factory-socket.yaml` adds), and writes `install.sh` with `scripts/release-install.sh`, which fills `scripts/install.sh` with the version and both files' SHA-256. Then it signs the image's digest with cosign keyless (no `--recursive`), verifies it with the identity the optional check in `web/docs.md` uses, attests SLSA provenance on the index digest with `actions/attest`, attests SLSA provenance of `install.sh`, `compose.yaml` and `compose.release.yaml` with the same action and `subject-path` (stored with GitHub's attestations, not in the registry; each subject is the file's name), and last, `docker buildx imagetools create` tags the signed index `ghcr.io/bezmoradi/software-factory:<version>`, and the job fails unless the tag reads back as that digest; it uploads the three files as the artifact `release-files`, kept a day, and passes on `install.sh`'s SHA-256. So a run that fails before the end leaves no image version tag, only an unsigned digest, and no release. The **SBOMs** job (`packages: read` only, so Syft's image never holds a credential that can push) writes an SPDX 2.3 SBOM per platform with Syft's image and uploads them as an artifact; the **Attest the SBOMs** job (`packages: write`, `id-token: write`, `attestations: write`, running only GitHub's actions and `docker/login-action`) attests each on the index digest. The image's attestations are pushed to the registry, with no storage record. The **Release notes** job (`contents: write`, the only job that can write to the repository) runs after the SBOMs are attested, downloads `release-files`, fails unless `install.sh` has the SHA-256 the Release job attested and carries the version and the SHA-256 of both Compose files and `compose.release.yaml` names the image digest, and creates the GitHub release with `gh release create`, attaching the three files; its notes give the install command; the checked install, which downloads this version's `install.sh`, runs `gh attestation verify install.sh -R bezmoradi/software-factory --signer-workflow bezmoradi/software-factory/.github/workflows/release.yml --source-ref refs/tags/v<version>`, then `sh install.sh`; the optional `cosign verify` and `gh attestation verify` checks on the image digest; and the digest. There are no `latest` or other floating image tags, and no build cache in any job; the install command's `releases/latest/download/` is GitHub's link to the newest published release, which `install.sh` then pins to its own version's files.
- **`.github/dependabot.yml`**: weekly, for updates out at least 7 days, one grouped pull request each for the actions, the Go modules, the page's npm packages and the Dockerfile's base images. Not covered, so update them by hand: the agent versions, integrity hashes and knackpack's commit in `versions.go` ([Moving a pin](moving-a-pin.md) lists what to check; with Claude Code's, update `VERSION` and `SHA256` in the Plugin job; when a pin moves for a security reason, set `MinimumReviewerClaudeCode` or `MinimumReviewerKnackpack` there to the new version or commit, so passes by the older reviewer stop counting); `third_party/node/LICENSE` and setup-node's `node-version`, which must match the Node in the Dockerfile's base image; the gitleaks and typos downloads and the QEMU and BuildKit images in `ci.yml`; `COMPOSE_VERSION`, `COMPOSE_SHA256`, `COSIGN_VERSION`, `COSIGN_SHA256`, `SYFT_IMAGE` and the QEMU and BuildKit images in `release.yml`; and the images and versions in the `Makefile` (actionlint, zizmor, lychee, gitleaks, typos, golangci-lint, go-arch-lint, govulncheck). Proctor in `proctor.yml` isn't pinned at all: each run takes the latest release.
- **Vulnerable dependencies** are fixed by how much they put at risk: an advisory `make vuln` reports as reached in our code, or any Critical or High one in an image or the page's packages, within 7 days of it being published, with a release if one is out; any other advisory, including ones govulncheck lists as not reached, within 30 days, usually through the weekly Dependabot pull request. When no fixed version exists yet, record the advisory and what limits it in the pull request that next touches the dependency.
- **`.github/rulesets/main.json`**: no deletion or force push of `main`, changes only through pull requests merged by squash, and the checks above plus Claude review, Claude approval and Proctor verdict required, with no bypass actors, so it binds admins too. It's only a file until applied.
- **`.github/CODEOWNERS`** names the owner for `proctor/` and for itself, so GitHub shows the owner as their code owner and requests the owner's review when someone else's pull request changes them. It enforces nothing: `require_code_owner_review` stays off in `main.json`, since pull requests here are the owner's own and GitHub doesn't count an author's approval, so it would block every one. The Workflow guard's `review-override` label is the owner-only gate for these files. Keep it the only CODEOWNERS file (none at the root or in a top-level `docs` folder), since GitHub reads only the first it finds.
- **`.github/rulesets/tags.json`**: only the repository's admin role (its one bypass actor, `RepositoryRole` 5) creates, moves or deletes a `refs/tags/v*` tag, so neither the Claude GitHub app's token nor anyone with write access can start a release. Also only a file until applied.

What the owner sets on GitHub:

1. The `CLAUDE_CODE_OAUTH_TOKEN` secret, from `claude setup-token`, as an Actions secret and again as a Dependabot secret (runs Dependabot starts get only Dependabot secrets).
2. The Claude GitHub app on the repository, for `claude.yml`.
3. The label: `gh label create review-override --repo bezmoradi/software-factory --description "The owner has read this change to the checks"`.
4. Squash merging allowed in the repository's settings, then the ruleset: `gh api --method POST repos/bezmoradi/software-factory/rulesets --input .github/rulesets/main.json`. To apply a later change to the file, find its id with `gh api repos/bezmoradi/software-factory/rulesets --jq '.[] | select(.name == "main") | .id'` and run `gh api --method PUT repos/bezmoradi/software-factory/rulesets/<id> --input .github/rulesets/main.json`, which also removes any bypass added on GitHub.
5. The labels for Proctor's change kinds, which a pull request may carry one of: `for k in refactor docs fix feature; do gh label create "proctor:$k" --repo bezmoradi/software-factory --description "Proctor checks this pull request's protected changes as a $k"; done`.
6. Apply the ruleset change that requires Proctor verdict only after the pull request that adds `proctor.yml` and the scripts' authoritative path is merged: until then a pull request's base has no such path, its Proctor run fails, and a required verdict would block it.
7. The tag ruleset: `gh api --method POST repos/bezmoradi/software-factory/rulesets --input .github/rulesets/tags.json`, and a later change with `PUT` as above, its id from `--jq '.[] | select(.name == "release-tags") | .id'`.
8. The environment `release` (Settings, Environments): the owner as its required reviewer, and deployments limited to selected tags, the pattern `v*`.
9. After the first release: make the package `software-factory` public in its package settings. GHCR makes a new package private, and an install pulls anonymously.
10. Immutable releases, in the repository's settings (General, Releases), so a published release's three files and its tag can't be changed or replaced: the attestations prove what the release workflow built, and this keeps the files GitHub serves at a release's links the ones it attested. It applies to releases published after it is turned on.

To release: set `Version` in `cmd/server/server.go`, merge it, tag that commit on `main` with `v` and the version (the job fails for a commit that isn't on `main`, a guard against mistakes only, since the check is in the tagged commit's own `release.yml`), push the tag, and approve the Release job's deployment. Tag only a commit whose `web/docs.md` describes what ships, since the image builds it into the page as its Docs view, and whose `README.md` still gives a working install.
